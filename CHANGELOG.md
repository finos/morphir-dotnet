## [Unreleased]

### Added
- `morphir extension install nuget:<package-id>[@<version>] --home <abs-home> --no-probe` installs an extension from a NuGet feed: nuget.org, a private V3 feed such as Azure Artifacts, or a folder feed. It reads the sources, package source mapping, credentials (`packageSourceCredentials` and credential provider plugins) and signature policy of `nuget.config`, as `dotnet tool install` does, through the Microsoft NuGet client packages. `--source` names one source (a configured name, a V3 `index.json` URL or a folder), `--configfile` names the `nuget.config`, and `--interactive` lets a credential provider prompt; the three options apply only to a `nuget:` source. No version selects the highest stable listed version. The main package carries `morphir/release.json`; a process artifact is the subtree under its `root` of the main package (one package) or of a package whose id extends the main id (one package per platform, such as the RID packages of a self-contained .NET tool), pinned by its tree digest. A framework-dependent .NET tool is refused. Signatures are checked as the dotnet CLI checks them on each operating system. The command writes only to the Home: no NuGet HTTP cache, global packages folder or NuGet temporary folder. New codes: `extension.nuget_not_found`, `extension.nuget_unreachable`, `extension.nuget_unauthorized`, `extension.nuget_signature_invalid`. See [Publish an extension as a NuGet package](docs/content/docs/guides/publish-extension-nuget.md).
- `NuGetPackageProvider` in `Morphir.Extensions.Installation`, and `ExtensionSourceRequest.WithNuGetOptions`. `ExtensionSources.ProviderFor(request, http, home)` takes the Home for a NuGet source. The package ships `buildTransitive/Morphir.Extensions.Installation.props`, which sets the `NuGet.UseSystemTextJsonDeserialization` feature switch in each application that references it.
- `morphir extension install github:<owner>/<repo>[@<version-or-tag>] --home <abs-home> --no-probe` installs an extension package from a GitHub release ([#493](https://github.com/finos/morphir-dotnet/issues/493)). The release carries the extensions-family `release.json` as an asset; the command picks the artifact for this platform, streams the asset into a private stage and checks its SHA-256 against the descriptor before the installer reads it. `@<version>` selects the tag `v<version>`, else `<version>`; no `@` selects the latest release. It uses the anonymous GitHub API, or `GITHUB_TOKEN` or `GH_TOKEN` when set, and reports a rate limit as `extension.github_rate_limited`. `--local-developer` does not apply to a named release; `--no-probe` is still required. The installed extension then runs with `--extension-id`, with no network.
- Source providers in `Morphir.Extensions.Installation`: `IExtensionSourceProvider` (`Scheme`, `ResolveAsync`, `FetchAsync`), with `GitHubReleaseProvider` and `LocalRepositoryProvider`. A provider only resolves and fetches; validation, the package tree, and the catalog, lock and journal writes stay in one installer. A new source (a plain HTTPS URL, OCI, a registry index) is one more provider.

### Changed
- The extension installer writes and reads the extension family `0.1.0-preview.3` ([finos/morphir#1176](https://github.com/finos/morphir/pull/1176), merged as `65bbbc96`): the package format `nupkg` (a NuGet package, pinned by its tree digest only), the provenance `nuget-package` and the source `nuget-package-entry`. Catalogs, locks, journals, repositories and release descriptors of `0.1.0-preview.2` are refused and not converted: install again into a new Home, and publish `release.json` with the preview.3 `$schema`. A release descriptor may now offer `process` and `wasm` artifacts; the installer selects the `process` artifact for the platform, else a `wasm` artifact, and the lock records the selection. Installing a WASM artifact is not supported yet and fails with `extension.unsupported_package`.
- Build: the Native AOT publish of `morphir` fails on any trim or AOT warning from `NuGet.*` or `Newtonsoft.Json`. `morphir` and `dotnet-morphir` set `NuGet.UseSystemTextJsonDeserialization`, with which NuGet.Protocol has no such warning.
- The extension installer writes and reads the extension family `0.1.0-preview.2` ([finos/morphir#1173](https://github.com/finos/morphir/pull/1173)), where an artifact `source` and an `index` provenance are provider-tagged unions (`local-file` or `github-release-asset`, `local-directory` or `github-release`). Catalogs, locks, journals, repositories and release descriptors of `0.1.0-preview.1` are refused and not converted: install again into a new Home, and publish `release.json` with the preview.2 `$schema`. The package tree manifest format is unchanged.
- The install scripts `scripts/install-morphirup.sh` and `scripts/install-morphirup.ps1` install `morphirup` from the [finos/morphir releases](https://github.com/finos/morphir/releases): they download `morphirup` and `morphirup-v<version>.sha256` from `https://github.com/finos/morphir/releases/download/v<version>/`; the scripts stay hosted here. `morphirup` is on finos/morphir from `0.5.0-alpha.2` on; earlier `morphirup` releases stay on the [finos/morphir-dotnet releases](https://github.com/finos/morphir-dotnet/releases). With no version, the scripts take the newest finos/morphir release that has `morphirup` for the machine and skip the others, such as `v0.5.0-alpha.1` (the CLI only) and the releases of the earlier Rust CLI (`v0.4.0-beta.*` and older), in the release list (up to 100 releases from the GitHub API) and in the release feed `https://github.com/finos/morphir/releases.atom`. A given version whose release has no `morphirup` for the machine is refused with "finos/morphir release v<version> has no morphirup-<rid>; morphirup releases before 0.5.0-alpha.2 are on finos/morphir-dotnet": the `sh` script reads the HTTP status of the download instead of letting `curl -f` report a 404 as a network error, and the PowerShell script reads the status of the failed request. The line `downloading <file> <version> from <url>` names the download, and `MORPHIRUP_DOWNLOAD_URL` mirrors `https://github.com/finos/morphir/releases/download`. Two testing hooks, `MORPHIRUP_RELEASES_FILE` and `MORPHIRUP_FEED_FILE`, read the release list and the release feed from local files; the end-to-end scenarios of `InstallScripts.feature` use them with a local release mirror to check, with no network, that the script of the machine skips the releases without `morphirup` in both and refuses a Rust release given by version.
- mise installs `morphirup` with `mise use -g 'github:finos/morphir[matching=morphirup,version_prefix=v,prerelease=true]'`. mise also lists the releases without `morphirup`; with one of those it stops with "No matching asset found" and installs nothing, so name a release that has `morphirup`, such as `@0.5.0-alpha.2`.
- The proto plugin downloads the `morphir` CLI from `https://github.com/finos/morphir/releases/download/v<version>/`. The plugin itself is still released here.
- The manual workflows `install-scripts.yml` and `morphirup-release-journey.yml` use the finos/morphir releases. The pinned version of `install-scripts.yml` is `0.5.0-alpha.2`, each of its runs checks that the download comes from finos/morphir, and a run of the Rust release `0.4.0-beta.12` must be refused by name.

## [0.5.0-alpha.2] - 2026-11-13

### Fixed
- `morphirup setup --yes` and extension package installation work on macOS 15. Before, they failed with `extension.io_error: Cannot access '…/store/extensions/packages/sha256': native error 13.` macOS 15 refuses to rename a directory that is not writable, even when the directory stays in the same parent, and the installer sealed a package (mode 0555) before it published it with a rename. macOS 26 allows that rename, so the macos-latest jobs passed. The installer now seals the package's contents before publication and the package root after it, while it still holds the state lock. An installation of a package that is already in the store seals the root if a publication was interrupted before it did.
- Build: the release and its dry run also run the osx-arm64 setup journey on macOS 15 (`build-morphirup`, `os: macos-15`), beside macos-latest (macOS 26). That leg uploads nothing: the new `morphirup-build.yml` input `upload` (default `true`) is `false` for it, and the macos-latest leg still produces the osx-arm64 assets. Pull requests do not run it.

### Changed
- `morphirup setup` sets up from the [finos/morphir releases](https://github.com/finos/morphir/releases), the official place for Morphir releases, from the next release, `0.5.0-alpha.2`, on. It downloads from `https://github.com/finos/morphir/releases/download/v<version>/`, with the same `v<version>` tag and the same three redirect hosts (`github.com`, `release-assets.githubusercontent.com`, `objects.githubusercontent.com`, at most three redirects), and keeps its `release-checksum` assurance. There is no fallback to the finos/morphir-dotnet releases: a bundle whose asset URLs name finos/morphir-dotnet is refused. A release generation records `https://github.com/finos/morphir` as its repository; the candidate's `sourceRepository` still names finos/morphir-dotnet, where the code is built from.
- The composed local-toolchains family moves from `0.1.0-preview.4` to `0.1.0-preview.5` ([finos/morphir#1171](https://github.com/finos/morphir/pull/1171), merged as `00a48d4a`), which differs from preview.4 only in the release repository of the bundle's asset URLs and of the generation's `acquisition.repository`. The producer writes preview.5, and `morphirup` reads preview.5 only: candidates, bundles, receipts, selections and generations of preview.4 (written by 0.5.0-alpha.1) are not read and are not converted. `select`, `show` and `run` read only the preview.5 selection pointer: in a Home set up with preview.2, preview.3 or preview.4 they refuse with `local.setup_required`, which says to run `morphirup setup --yes` again (and then `select`, for a local candidate). Setup in that Home installs preview.5 beside the earlier generations without reading them, and replaces the selection pointer. A refused `setup`, `select` or `show` writes a preview.5 result. The historical preview.1 local route is unchanged.
- Build: finos/morphir can call `morphirup-build.yml` at a pinned commit of this repository, as it calls `cli-offering.yml`. The new inputs `repository` and `ref` (a full commit SHA) choose what the job checks out and builds, and the Windows source check compares the checkout with `ref`. With the new input `upload-host-offering: true`, a job that packs a toolchain (win-x64, win-arm64, or osx-arm64 with `toolchain: true`) also uploads its self-contained host as the artifact `morphir-dotnet-self-contained-<rid>`: the archive with its `.build-launch.json`, `.build-contents.json` and `.sha256`, the files `cli-offering.yml` uploads for that offering. The inputs default to empty and `false`, so `morphirup.yml` and `deployment.yml` work as before. The checkout no longer keeps the workflow token in the Git configuration.

## [0.5.0-alpha.1] - 2026-11-13

### Added
- Documentation: a getting-started walkthrough, [Your first model with morphirup](docs/content/docs/getting-started/first-model.md), and a [troubleshooting](docs/content/docs/getting-started/troubleshooting.md) page. The walkthrough installs `morphirup`, sets up the toolchain, compiles the `examples/morphirup-fsharp` model, generates F#, changes a rule and compares the output, then compiles and generates again offline. The getting-started pages now cover tasks only: the local candidate journey moves to the contributing section, implementation detail moves to the reference pages, and troubleshooting moves to the new page. The [morphirup](docs/content/docs/cli/morphirup.md) reference opens with a task section for `setup`, `show`, `select` and `run`, and `examples/morphirup-fsharp/README.md` repeats the walkthrough's commands.
- Install `morphirup` with one command. `scripts/install-morphirup.sh` (POSIX `sh`, Linux x64 and ARM64, macOS on Apple silicon) and `scripts/install-morphirup.ps1` (Windows x64 and ARM64, Windows PowerShell 5.1 and PowerShell 7) install the newest `finos/morphir-dotnet` release that has `morphirup` for the machine, prereleases included, or the release given with `--version` / `-Version`. Each script checks the file against the release's `morphirup-v<version>.sha256` and installs nothing on a mismatch or a missing line. The `sh` script installs to `~/.local/bin` and prints the `PATH` line to add; the PowerShell script installs to `%LOCALAPPDATA%\Programs\morphirup` and adds it to the user `PATH`. Intel macOS and musl Linux are refused. On restricted networks, both scripts use `HTTPS_PROXY` and `NO_PROXY` (the PowerShell script also uses the Windows proxy settings and the current user's proxy credentials, and passes `HTTPS_PROXY` itself on Windows PowerShell 5.1), accept an HTTPS mirror in `MORPHIRUP_DOWNLOAD_URL`, fall back to the release feed on github.com when api.github.com cannot be reached, and stop connecting after 30 seconds. The manually triggered workflow `install-scripts.yml` (inputs `version` and `platforms`) runs both scripts and the mise command `mise use -g 'github:finos/morphir-dotnet[matching=morphirup,version_prefix=v,prerelease=true]'` (also with `@<version>`) on Linux, macOS and Windows.
- Release setup on macOS ARM64: the release attaches the `osx-arm64` toolchain (the self-contained host archive, the F# frontend and backend archives with their release and manifest files, `morphir-host-candidate-osx-arm64.json`, `morphir-extensions-osx-arm64.json` and the bundle `morphir-toolchain-osx-arm64.json`), and its one `SHA256SUMS` covers win-x64, win-arm64 and osx-arm64. On Apple silicon, `morphirup setup --yes`, then `run -- compile` and `run -- generate --target fsharp`, work from the published release. The release job packs the toolchain on the native macOS ARM64 runner of `build-morphirup` and runs the acquired setup journey there; the pull request workflow does not, so its macOS job is unchanged. `WindowsToolchainChecksums` takes `--toolchain-platforms` for a run that packs only some toolchains.
- Experimental `morphirup` setup on macOS ARM64 (`osx-arm64`). `morphirup setup --local-developer` with a local candidate, host archive and bundle, then `select`, then `run -- compile` and `run -- generate --target fsharp`, works on Apple silicon with no .NET on `PATH` and no network. Release setup (`setup --yes`) accepts an `osx-arm64` manager and bundle too. Intel macOS stays unsupported.
- Build: `PackWindowsToolchain --rid osx-arm64` packs the macOS ARM64 setup inputs: tar.gz archives, the entry points `morphir`, `morphir-fsharp-frontend` and `morphir-fsharp-backend`, and the candidate, selection, release descriptors, manifests, bundle and `SHA256SUMS`. The target keeps its name, and the Windows outputs are unchanged.
- `Morphir.Extensions.Installation` installs tar.gz extension packages by the package policy of ZIP packages: at most 4096 entries (for tar, PAX/GNU metadata headers count too), only regular files and directories, the same package path rules (a `./` prefix, as `tar -C dir -czf package.tar.gz .` writes, is removed), the same size bounds, no inspection of a resource as a nested archive, and the canonical modes 0555 and 0444. Before, it refused them with `package.format_not_implemented`. A package format other than `zip` or `tar.gz` is refused with `package.archive_format` before staging.

### Changed
- The README and the installation guide start with `morphirup`: the install scripts, mise, manual download with checksum verification, and what works on each platform: macOS on Apple silicon and Windows set up, compile and generate; on Linux `morphirup` installs, but `morphirup setup` does not support Linux yet. Troubleshooting moves to its own page. The proto, `install-*.sh` and `dotnet tool install` routes to the standalone `morphir` CLI follow under "Other ways to install the standalone morphir CLI". The duplicate page `docs/content/getting-started/installation.md` is gone; its address redirects to the installation guide.
- The composed local-toolchains family moves from `0.1.0-preview.3` to `0.1.0-preview.4` ([finos/morphir#1164](https://github.com/finos/morphir/pull/1164), merged as `648ae374`; [spec](https://github.com/finos/morphir/blob/main/docs/spec/toolchain/local-platforms-and-release-bundle.md)), for every platform. Preview.4 adds `osx-arm64` with the archive format `tar-gzip`. The producer writes preview.4, and `morphirup` reads preview.4 only: candidates, bundles, receipts, selections and generations of preview.3 (written by 0.4.0-alpha.5 and earlier) are not read and are not converted. `select`, `show` and `run` read only the preview.4 selection pointer: in a Home set up with preview.2 or preview.3 they refuse with `local.setup_required`, which says to run `morphirup setup --yes` again (and then `select`, for a local candidate). Setup in that Home installs preview.4 beside the earlier generations without reading them, and replaces the selection pointer. The historical preview.1 local route is unchanged. The candidate reader refuses an `osx-arm64` candidate that does not declare `tar-gzip`, and a Windows candidate that does not declare `zip`. Setup and run refuse an `osx-arm64` entry point that is not `morphir` with `local.launch_structure` when they check the archive or the installed folder.
- `morphirup` off Windows uses the physical path of the parent folders of `--home`, with each link resolved (at most 40). The installed host refuses a source file below a link, and on macOS `$TMPDIR` is below the link `/var`. The last part is not followed, so a Home that is itself a link is still refused.
- `morphirup run` and the setup probes also remove `DOTNET_ROOT_ARM64` from the host's environment.
- A refused `morphirup setup`, `select` or `show` writes a local-toolchains `0.1.0-preview.4` result, on the preview.1 local route too. Before, every refusal except the composed local setup's wrote the preview.1 result with `origin: local-developer`. The `origin` is now the origin of the preview.4 generation that `select` names or of the selection that `show` reads, and `local-developer` when there is none. A completed preview.1 step still writes the preview.1 result.

### Fixed
- `morphir ir verify` no longer runs without end on a typical IR file. Each union branch of the schema checked its whole subtree even when the tag was another branch's, so the time grew exponentially with nesting. The `greeting-example.json` IR v3 example of finos/morphir (29 KB) ran for more than ten minutes and now takes under a second. The 3.5 MB LCR example takes about 20 seconds. A value with an unknown tag still lists the tags that were expected. For a value with a known tag, the deep errors of the other branches are gone: each other branch reports only that its tag does not match.
- `morphir ir verify` accepts IR v3 whose values carry their inferred types as attributes, as morphir-elm writes them, and names with a word that is a number. Both come from the current finos/morphir v3 schema. Before, the greeting example was not valid.
- `morphir ir verify` reads IR nested up to 512 levels. Before, a file deeper than 64 levels, such as the LCR example of finos/morphir, was reported as malformed JSON.
- `morphir` (and so `morphirup run -- compile` and `run -- generate`) no longer writes `[INF] Foundatio.Mediator registered 3 handler(s) and 0 middleware.` to stderr. The CLI logger caps the `Foundatio.Mediator` category at Warning, so the mediator's warnings and errors are still shown. Stdout is unchanged.
- Build: restoring the solution no longer rewrites the committed `packages.lock.json` of the `Morphir.Configuration.IO.Smoke` and `Morphir.Configuration.Microsoft.Smoke` hosts with the host's RID, so release artifacts built on Linux or Windows no longer record a dirty origin. A trimmed publish of these hosts passes `-p:PublishTrimmed=true`, and CI fails when restore changes the working tree.
- On Linux and macOS, an extension installation lock is free as soon as its owner releases it. Before, the lock stayed held while another thread of the same process was starting a child process, because that child shared the lock's file until it ran its program. A second extension operation in that window could fail with "Lease is busy".
- Extension installation works on Linux ARM64. Before, every operation on the extension Home there failed with `Cannot access '…/.morphir': native error 22.`: installing and registering extensions, reading the installed state, and `morphirup` downloads. The safe file layer passed the Linux x64 values of `O_DIRECTORY` and `O_NOFOLLOW`, which on ARM64 mean `O_DIRECT` and `O_LARGEFILE`, so it also did not refuse a symbolic link there. It now takes its open flags from a table for Linux x64, Linux ARM64 and macOS.

## [0.4.0-alpha.5] - 2026-11-12

### Added
- Releases attach the Windows toolchain for `win-arm64` as well as `win-x64`: the self-contained host, the F# frontend and backend archives, the candidate, the extension selection and the bundle, with one `SHA256SUMS` over both platforms' files, so `morphirup-win-arm64.exe setup` installs from the release. Each Windows toolchain is built once, by the same job as its manager, after `CheckBuildMachine`; the separate win-x64 toolchain job is gone. Pull requests build and check the `win-arm64` toolchain in `morphirup.yml` and keep it downloadable for seven days.
- `deployment.yml` has a `dry-run` input for a manual run: it builds every platform, assembles the release assets and checksum files, uploads them as the `dry-run-release-assets` artifact, and publishes nothing to NuGet or GitHub releases.
- Windows ARM64 (`win-arm64`) is a released platform. The release workflow builds `morphir-win-arm64.exe`, `morphir-win-arm64-v<version>.tar.gz`, `morphirup-win-arm64.exe` and `morphirup-win-arm64-v<version>.tar.gz` on the hosted `windows-11-arm` runner, natively, and the morphirup checksum file lists the morphirup ones; the pull request workflow `morphirup.yml` builds and checks `morphirup` there too. The names, contents and checks of the other platforms' assets are unchanged. Earlier releases have none of these files ([#611](https://github.com/finos/morphir-dotnet/pull/611)).
- Experimental Windows release setup with `morphirup`: in a project, `morphirup setup --yes` downloads the runtime-bundled Morphir host and the independent F# frontend and backend from the exact `finos/morphir-dotnet` release of the manager's own version (or the exact version `.morphir/toolchain.toml` requests), checks each file's byte count and SHA-256 against the release's `SHA256SUMS`, installs the complete folders into the content-addressed store, runs the fixed readiness workflow and selects the completed generation last. `morphirup run -- compile` and `morphirup run -- generate` then use the installed folders with no network access. `setup --dry-run` creates nothing. This is release-checksum delivery, not publisher-authenticated: HTTPS and a matching checksum do not authenticate the publisher, and trust commands are not included. The release transport starts at the exact repository and version tag and follows at most three HTTPS redirects to `github.com`, `release-assets.githubusercontent.com` or `objects.githubusercontent.com`. The release attaches the setup bundle for Windows x64 and Windows ARM64. `Morphir.Extensions.Installation` is a new library package ([#608](https://github.com/finos/morphir-dotnet/pull/608)).
- Build: `CheckBuildMachine --rid <rid>` fails unless the machine's operating system and architecture are the RID's and the .NET SDK runs natively (not x64 under emulation on ARM64), and logs the machine. The CLI release jobs and `cli-offering.yml` run it before they build.
- Build: `FlattenReleaseAssets` copies each downloaded platform output into the release assets once, accepting byte-identical duplicates and failing on two different files under one name instead of overwriting; the morphirup checksum jobs use it. `WindowsToolchainChecksums` writes one `SHA256SUMS` over both Windows toolchain outputs, and writes nothing when a Windows RID's bundle or manager is missing, or an asset its bundle names is missing or differs.
- `scripts/install-windows.ps1` and the proto plugin choose `win-arm64` on Windows ARM64, where they refused before. The Windows installer now reads the machine's architecture, so an x64 PowerShell under emulation on ARM64 also chooses `win-arm64`. Releases before this one have no `win-arm64` file, so asking either for an earlier version fails on Windows ARM64.
- Experimental configured Python WASM commands: `morphir compile --language python` and `morphir generate --target python` use `extensions.python.path` through the existing MEP model adapters and owned WASM sessions. Includes a pinned Python 0.6.0 walkthrough; Windows x64 retains its named runtime refusal ([#610](https://github.com/finos/morphir-dotnet/pull/610)).
- Experimental WASM host-kit reports adopt the pinned parent report schema, computed ordered verdict reasons, per-profile guest-kit citations and eight named refusals. All 22 fixed policy controls are checked independently; the runner retains observation recomputation and exact report rebuilding. Citation-bearing runs fail closed with an explicit unavailable-checker result until the actual generic-kit report checker is integrated. This does not qualify a host, guest, artifact or platform ([#564](https://github.com/finos/morphir-dotnet/issues/564)).
- Internal current-family standalone and embedded claim reader, retaining supplied JSON beside existing MEP values and an understood-member projection, with recursive metadata checks, critical paths and host comparators reused from Toolchain. Claims 27/27 and affected SharedReaders 19/19 pass on Windows, repeated after pinned formatting. Public codecs, full corpus conformance, probes and installation lifecycle remain unfinished ([#558](https://github.com/finos/morphir-dotnet/issues/558)).
- Internal extension-family reader increment with pinned, offline hash-checked schemas and case data from parent `0439c4c0`. The focused Windows SharedReaders suite passes 19/19, including six parent release/schema cases and two I-JSON refusal cases with valid parse controls. Full claim/package semantics, state codecs, inventory, probes and command lifecycle remain unfinished; the 137 identity and 66 package cases have not all been executed ([#558](https://github.com/finos/morphir-dotnet/issues/558)).
- Extension installer security corrections: descriptor-bound single-file publication, interprocess run-directory ownership coordination, directory/owner identity checks, and gzip metadata/padding budgets with cancellation below the tar reader. Windows regression evidence is 131 passed with three Unix-only cases ignored. Independent security/interop re-review of `b6936ba5` found no concrete remaining finding under the approved cooperating Home boundary; Unix runs and AOT remain pending. Recorded the approved selection, command, provenance and explicit developer-consent decisions; inherited default staged `auto` grants no automatic install consent. Shared readers use parent source `0439c4c0`; portable pin/overlay formats remain parent toolchain work ([#558](https://github.com/finos/morphir-dotnet/issues/558)).
- Extension installation library foundations: portable distribution identifiers over the existing domain types, RID/descriptor/index mappings and exact implemented MEP eligibility within the supported 0.2 line. Includes an Expecto suite and C# probe; CLI installation and Native AOT qualification remain unfinished ([#558](https://github.com/finos/morphir-dotnet/issues/558)).
- Extension installation I/O: a single-file content-addressed store that hashes while copying, rehashes reuse and refuses corrupt objects without replacement; ZIP and tar-gzip inspection with the recorded path, type and resource limits; and exclusive ownership and stale cleanup of .NET run directories. Windows tests and the C# JIT probe cover these APIs. Package formats, extraction, inventory, activation and CLI installation are unfinished; Unix filesystem runs and Native AOT qualification remain pending ([#558](https://github.com/finos/morphir-dotnet/issues/558)).
- `morphir mck <args>` runs the separately installed Morphir Compatibility Kit, `morphir-mck <args>`, a development tool from finos/morphir, in every entry point (`morphir`, the managed `morphir`, `dotnet-morphir`). The arguments, working directory, environment and standard streams are passed on unchanged, and the exit code is the tool's. `MORPHIR_MCK` names the tool's absolute path; otherwise only absolute `PATH` folders are searched, never the current directory, and on Windows only `morphir-mck.exe` is a candidate. Setup resolves a `.morphir/toolchain.toml` request against a recipe file for every platform the lock would record and prints the plan with its `planSha256`.
