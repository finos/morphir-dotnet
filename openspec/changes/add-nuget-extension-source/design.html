Context

See proposal.md for the motivation. The requirements are in extension-source-providers and nuget-extension-source.

Observed state on main (53c645fe):

  • src/Morphir.Extensions.Installation/Providers.fs has IExtensionSourceProvider (Scheme, ResolveAsync, FetchAsync), LocalRepositoryProvider, GitHubReleaseProvider and ExtensionSources. ProviderFor is a closed match over the internal SourceRequestKind.
  • Sources.fs has the closed unions ArtifactSource and IndexProvenance and their JSON, at extension family 0.1.0-preview.2. The pinned schemas (tests/Fixtures/ExtensionAcquisition/parent-1f22f491/) are closed: they know only the local and GitHub kinds.
  • PackageInstaller.InstallFromAsync (Packages.fs) hashes the whole archive, matches on plan.Format (zip or tar.gz) and calls PackageTreeIO.extractZip or extractTarGz, which write into the stage themselves.
  • PackagePlan.Read accepts only a process artifact with a package member ("Packages require process runtime"). No provider can install a WASM artifact, although SingleFileStore exists. That is open task 5.4 of add-extension-installation.
  • src/Morphir/Morphir.csproj treats IL3050 as an error in its Native AOT publish. IL2xxx warnings are not errors there.

The spike spikes/nuget-extension-source/ (osx-arm64, SDK 11.0.100, NuGet client 7.9.0) gives the facts the decisions below use. Its results are in spikes/nuget-extension-source/results/osx-arm64.md.

Goals and non-goals

Goals:

  • Behave as NuGet behaves: the same sources, mapping, credentials, signature policy and version rules as dotnet tool install, through Microsoft's own client packages.
  • No compromise on Native AOT: zero trim and AOT warnings from the NuGet packages.
  • Each provider owns the layouts it supports; one installer core keeps every check and every write.
  • WASM and process artifacts from every provider.

Non-goals:

  • Publisher tooling, such as an MSBuild target that writes release.json. This change documents the publish steps (DOC-1).
  • NuGet V2 feeds beyond what NuGet.Protocol gives without extra code, package search, and extension update from a feed.
  • Framework-dependent .NET tools, which need an installed .NET runtime to start. A RID payload must be self-contained or Native AOT; the provider refuses an entryPoint ending in .dll or a <entry point>.runtimeconfig.json that names a shared framework, with extension.unsupported_package. (The spike fixture is framework-dependent; the change's fixture is self-contained.)
  • A provider registry for third-party providers. ProviderFor stays a closed match.

Decisions

The decisions follow one journey. On a Mac (osx-arm64), a user runs:

$ morphir extension install nuget:Acme.Morphir.Python@1.2.3 --home ~/.morphir --no-probe

Their nuget.config lists nuget.org and a private Azure Artifacts feed acme, maps Acme.* to acme, and the Azure Artifacts Credential Provider is installed. The feed holds the three packages of the running example in the nuget-extension-source spec.

UP-1 The schema lands in finos/morphir first

The lock and catalog this change writes need three things that the pinned family schema does not have: the package format nupkg (with no file sha256), the provenance kind nuget-package and the source kind nuget-package-entry. The project rule is that morphir-dotnet invents no member. So the order is the one #654 used with finos/morphir#1173: the finos/morphir coordinator lands the schema, the member tables, the identity and package cases and a "NuGet package convention" section in distribution-and-acquisition.md; this repository then pins that commit as a new tests/Fixtures/ExtensionAcquisition/parent-<sha>/ folder and moves every family URL it reads and writes.

The request went to the coordinator on 14 November 2026, who opened finos/morphir#1176 (head b777e212f4): the family moves to 0.1.0-preview.3 with these members. Rules in that PR that this change follows: for nupkg, root and treeSha256 are required and the artifact sha256 and the catalog and lock digest are forbidden; root is a relative POSIX path with no . or .. segment; the feed is an https URL ending in /index.json with no userinfo, query or fragment, or an absolute folder path (http is refused); the recorded id is lower case and the version normalized with no build metadata; a lock pairs a source only with the provenance of the same provider; an artifact package id is the main id or starts with <id>. (a host rule).

"package":    { "format": "nupkg", "root": "tools/net11.0/osx-arm64", "entryPoint": "acme-python", "treeSha256": "…" }
"source":     { "kind": "nuget-package-entry", "feed": "https://pkgs.dev.azure.com/acme/_packaging/tools/nuget/v3/index.json",
                "id": "acme.morphir.python.osx-arm64", "version": "1.2.3", "path": "tools/net11.0/osx-arm64" }
"provenance": { "kind": "nuget-package", "feed": "…", "id": "acme.morphir.python", "version": "1.2.3",
                "revision": "<sha256 of release.json>" }

Implementation may start in a branch against the proposed shapes; the PR merges only after the pin. If upstream changes a name, only Sources.fs, the descriptor reader and the fixtures move.

SRC-1 The request and its options

ExtensionSourceRequest.Parse gains the scheme nuget and the case SourceRequestKind.NuGet of NuGetPackageRequest. The id is parsed with NuGet's rules (NuGet.Packaging.PackageIdValidator) and the version with NuGetVersion.TryParse; an absent version is NuGetVersionSelector.LatestStable. The CLI adds options that only a nuget: source takes:

morphir extension install nuget:<id>[@<version>] [--source <url|folder|name>] [--configfile <path>] [--interactive]
                          --home <absolute-home> --no-probe [--dry-run]

The option names are those of dotnet tool install, so a .NET user can guess them. The parsed request carries the options, so the provider never reads raw CLI text. Alternatives: a source URL in the positional argument (nuget:https://…#Acme.Morphir.Python) was rejected as hard to read and to quote.

NUG-1 The Microsoft NuGet client packages, with the System.Text.Json switch

The provider uses NuGet.Versioning, NuGet.Packaging, NuGet.Configuration, NuGet.Protocol and NuGet.Credentials at the version Directory.Packages.props pins (7.9.0 today; NuGet.Packaging is pinned there already). The user prefers NuGet's own code to a re-implementation that could drift from NuGet's behavior, and the spike shows it is AOT-safe with one setting:

NuGet.Protocol 7.9.0 has a System.Text.Json path behind the AppContext switch NuGet.UseSystemTextJsonDeserialization, declared with FeatureSwitchDefinitionAttribute. Set as a trimmed runtime option, the trimmer removes the Newtonsoft path. The AOT-compiled part of the .NET SDK CLI (sdk/11.0.100/libdotnet-aot.dylib) carries the same switch name and no Newtonsoft.Json. Alternatives: our own V3 HTTP code with System.Text.Json (works, but diverges from NuGet and re-implements credentials and plugins); NuGet.Protocol without the switch (fails at run time); rooting assemblies for the trimmer (still fails, and keeps the warnings).

SRC-2 Sources and version selection

Settings.LoadDefaultSettings(currentDirectory) reads the nuget.config hierarchy, or Settings.LoadSpecificSettings the file --configfile names. PackageSourceProvider.LoadPackageSources() gives the enabled sources, and PackageSourceMapping.GetPackageSourceMapping(settings) narrows them for the package id when a mapping exists. --source replaces that list with one source: a configured name, or a URL or folder that becomes a PackageSource; the credentials of a configured source with the same URL still apply.

  • Exact version (@1.2.3): the provider asks each applicable source in configuration order through FindPackageByIdResource.DoesPackageExistAsync and takes the first that has it. Prereleases and unlisted versions can be named.
  • No version: the provider reads PackageMetadataResource.GetMetadataAsync(id, includePrerelease: false, includeUnlisted: false) from every applicable source and takes the highest version, as dotnet tool install without --version does. A folder feed has no listing, so all its versions count. The version and the source that has it are then fixed for the rest of the install.

In the journey, mapping leaves only acme, and the exact version 1.2.3 is found there. The feed recorded in provenance is that source's URL as nuget.config spells it.

NUG-4 Credentials

The provider sets HttpHandlerResourceV3.CredentialService to a CredentialService built from SecurePluginCredentialProviderBuilder(PluginManager.Instance, canShowDialog: false, logger). The service is non-interactive unless --interactive is given; then a plugin can use its device flow, writing its prompts to stderr. packageSourceCredentials come from nuget.config through PackageSource.Credentials. NuGet's own HTTP handler sends a credential only to the source it belongs to.

The spike proved both ways NuGet finds plugins: a .dll in NUGET_PLUGIN_PATHS (started with dotnet) and a nuget-plugin-* executable on PATH (started directly). A native executable in NUGET_PLUGIN_PATHS exits with code 1, because NuGet starts it with dotnet; the installer documentation says so. A 401 or 403 after the credential service has answered maps to extension.nuget_unauthorized, naming the source and --interactive. The NuGet logger adapter writes to stderr only (the CLI logging rule) and never writes a credential.

NUG-2 The package convention

Every NuGet call uses a SourceCacheContext with NoCache and DirectDownload set, so the provider writes nothing to NuGet's HTTP cache or global packages folder; only credential provider plugins keep their own caches. The provider downloads the main package (FindPackageByIdResource.CopyNupkgToStreamAsync) into a bounded private stage under the Home and opens it with PackageArchiveReader. It checks the .nuspec id and version against the request, reads morphir/release.json, and runs PackagePlan.Read for the host platform. Then it locates the selected artifact:

ArtifactWhere the provider looksPayload
runtime wasmentry morphir/<filename> of the main packageWASM module, pinned by sha256
runtime process, format nupkg, filename = the main package's file namethe main package (layout A)subtree under root, pinned by treeSha256
runtime process, format nupkg, another filenamepackage <id> at the same version, from the same source (layout B, .NET tools)subtree under root
runtime process, format zip or tar.gzrefused with extension.invalid_descriptor: a NuGet package is already the archivenone

The file name is parsed as <id>.<version>.nupkg by splitting off the known version (NuGet ids can contain dots and digits, so the version is matched as the suffix .<normalized main version>.nupkg, compared case-insensitively). The id must be the main id or start with <main id>.. This keeps a descriptor from pulling a package of another publisher, and on nuget.org it lines up with ID prefix reservation. In the journey, the process artifact names acme.morphir.python.osx-arm64.1.2.3.nupkg, so the provider fetches Acme.Morphir.Python.osx-arm64 1.2.3 from acme.

The provider never reads DotnetToolSettings.xml: the descriptor's root already says where the payload is. That keeps .NET tools a special case of layout B, not a third code path. Alternatives considered: a RID-to-package-id convention (needs a RID table and breaks for custom ids), parsing <RuntimeIdentifierPackages> (works only for tools), and inner .tar.gz files (rejected: the package is already the archive, and it would double every RID package).

NUG-3 Integrity and signatures

The pins never cover .nupkg bytes: nuget.org adds a repository signature to every package, which changes the bytes after the author packs it, and a release.json inside a package cannot hold its own package's hash. So:

  • the descriptor is pinned in provenance by the SHA-256 of the release.json bytes, as for GitHub;
  • a nupkg payload is pinned by treeSha256, computed by the installer core from what the sink wrote;
  • a WASM entry is pinned by its sha256; entry bytes do not change when a package is signed;
  • signatures are verified when the dotnet CLI verifies them on the same OS (decided by the user: match dotnet per OS): by default on Windows and Linux, not on macOS, and as DOTNET_NUGET_SIGNATURE_VERIFICATION overrides. NuGet.Packaging reads that variable itself, and X509TrustStore.InitializeForDotNetSdk sets up the trust store as the SDK does: the OS store on Windows and macOS, and on Linux the fallback bundle trustedroots/codesignctl.pem and timestampctl.pem, which morphir ships beside its binary (copied from the pinned NuGet client release and updated with it). Every package the provider reads, main and artifact packages, then goes through ClientPolicyContext.GetClientPolicy(settings, logger) and PackageSignatureVerifier with the policy's settings and trustedSigners: in accept mode an unsigned package passes and a signed one must pass integrity and trust checks; in require mode unsigned or untrusted packages are refused. Refusal is extension.nuget_signature_invalid.

Security. With a tree pin, the zip reader parses package bytes before any digest has been checked; for a zip or tar.gz archive the file digest comes first. The protection rests on: the bounded package download, NuGet's signature check before the payload is read, the ZIP layout and header rules applied to the whole package and the entry rules to every entry under root (entries outside root are neither refused nor extracted nor hashed, as #1176's packages.md requires), writes that can only reach the private stage, and the treeSha256 check before publication. The upstream convention states this order.

SEL-1 A process artifact before a WASM artifact

Decided upstream after this design was approved: finos/morphir#1176 (docs/spec/extensions/packages.md, the requirements "A descriptor may offer more than one runtime" and "A host selects a matching process artifact before a WASM artifact") allows a release to list process and wasm artifacts. So:

  • the descriptor reader does not refuse a descriptor that mixes the runtimes (Descriptors.fs drops the refusal; add-extension-installation drops its "Mixed runtimes" scenario);
  • PackagePlan.Select selects, for every provider, the one process artifact whose platform matches the host, else the first wasm artifact, else extension.no_matching_artifact; two matching process artifacts are refused;
  • the lock records the selected artifact with its runtime; activation follows the lock and never selects again.

A --runtime option to let the user choose is a follow-up issue, not part of this change. A NuGet release can therefore carry a WASM module and process subtrees in one main package (the nuget-layout-a case of #1176).

PKG-1 Providers, payload readers and one installer core

The installer core stops matching on archive formats. A provider returns a payload, and the core gives the payload a sink:

/// Where a payload reader puts package files. The sink owns every path rule, limit, mode and write.
type internal PackageTreeSink =
    member AddDirectory: path: string -> unit
    member AddFile: path: string * length: int64 * content: Stream -> unit   // mode from the plan

/// Fetched bytes of one shape. It reads entries into the sink; it never touches the store.
type internal IPackagePayload =
    abstract Integrity: PayloadIntegrity
    abstract ReadAsync: sink: PackageTreeSink * ct: CancellationToken -> Task<unit>

and PayloadIntegrity =
    | FileThenTree of file: Sha256Digest * tree: Sha256Digest   // zip, tar.gz
    | TreeOnly of tree: Sha256Digest                             // nupkg subtree
    | ModuleFile of sha256: Sha256Digest                         // WASM, single-file store
  • PackageTreeIO.extractZip and extractTarGz become ZipArchivePayload and TarGzArchivePayload. Their checks move into the sink unchanged; the existing package tests must stay green without edits (a pure refactor step, first in the task list).
  • NuGetPackagePayload reads a PackageArchiveReader, runs ArchiveChecks on every entry, and reports only the entries under root, with the root/ prefix removed.
  • FetchedExtensionArtifact carries an IPackagePayload in place of openArchive; InstalledExtensions.InstallPreparedAsync takes it.
  • PackagePlan.ArchiveDigest becomes the PayloadIntegrity union. PackagePlan.FromState, which reads the artifact file name back from the lock source (Packages.fs), reads it from the new source kind too.

Alternative: a match on a new "nupkg" format inside InstallFromAsync. Rejected: every new layout would grow the core, and the core is the one place every provider must trust.

WASM-1 WASM installation in the core

PackagePlan.Read accepts a selected WASM artifact (no package, no platform, as the descriptor schema already requires). The core publishes it with SingleFileStore.PublishAsync after the ModuleFile check and writes a lock with runtime wasm, claimCheck unchecked, no args and executable false. It does not run the guest. Local declarations, GitHub releases and NuGet packages all reach this path; the providers only differ in where the module bytes come from (a file, a release asset, a package entry). This takes over the WASM part of add-extension-installation task 5.4; that task is updated to point here, and its requirement "A WASM package installs without running the guest" is the behavior this implements.

WASM-2 Running an installed WASM extension

Decided by the user: this change also runs installed WASM extensions. Today InstalledExtensionConnector (src/Morphir.Tooling/Infrastructure/) captures an installed record and starts captured.Activation.EntryPointPath as a process. A configured WASM module already has a complete path: ConfiguredWasmModule.TryOpen gives a WasmModuleSource to IWasmModuleLoader.Load, which checks the runtime, the digest and the profile, and MepFrontend.ConnectChannelCheckedAsync (or the backend equivalent) runs the session over the returned channel. The installed path reuses it:

  • InstalledActivation gets a runtime union: Process of entryPointPath or Wasm of modulePath * Sha256Digest. InstalledExtensions.CaptureAsync verifies the stored module against the lock offline, as it verifies a process tree, and holds the same leases while the guest runs.
  • InstalledExtensionConnector.FrontendAsync and BackendAsync take the connector's IWasmModuleLoader. For Wasm they build a WasmModuleSource from the module path and lock digest and open it with the same helper that configured modules use, then connect over the channel and run the existing CheckSession claim check.
  • A host whose loader reports no WASM runtime fails with the loader's extension.runtime_unavailable. extension list already reports such an entry as unavailable (add-extension-installation).

Alternative: a separate WASM connector for installed extensions. Rejected: two WASM paths could drift in their digest and profile checks.

CODE-1 One project, a folder per provider

All of it stays in src/Morphir.Extensions.Installation (decided by the user: no project per provider). Folders group each provider's code; F# compile order is explicit in the .fsproj, so identity types that the closed unions in Sources.fs need compile before it, and provider logic after Providers.fs:

Core/       Identifiers, Platforms, SharedJson, FileSafety, PrivateStaging, Store, StateDocuments, InstalledState
Install/    PackageTree.fs (sink, IPackagePayload, PayloadIntegrity), Packages.fs, ActivationRecords.fs
Formats/    Archives.fs, ArchivePayload.fs          (zip, tar.gz: shared by local and GitHub)
Sources/    GitHub/GitHubRepository.fs, NuGet/NuGetPackageRequest.fs   (identity types first)
            Sources.fs, Providers.fs
            Local/LocalRepositoryProvider.fs
            GitHub/GitHubReleaseProvider.fs
            NuGet/NuGetSettings.fs     sources, mapping, policy, credentials
                  NuGetFeed.fs         version selection, download into staging
                  NuGetPayload.fs      package subtree and WASM entry readers
                  NuGetPackageProvider.fs
            ExtensionSources.fs        ProviderFor, InstallAsync

The types C# calls (ExtensionSourceRequest, the providers, ExtensionSources) stay in the namespace Morphir.Extensions.Installation; provider internals are internal. The F#/C# rules of the fsharp-csharp-interop skill apply to every new public member.

AOT-1 The feature switch in every host

The switch is a runtime host option, so the application sets it, not the library. Three places:

  • src/Morphir/Morphir.csproj and the dotnet-morphir tool project src/Morphir.Tool/Morphir.Tool.csproj get <RuntimeHostConfigurationOption Include="NuGet.UseSystemTextJsonDeserialization" Value="true" Trim="true" />.
  • The Morphir.Extensions.Installation package ships buildTransitive/Morphir.Extensions.Installation.props with the same item, so an outside consumer gets it.
  • A guard: the Native AOT publish of morphir fails on any IL2xxx or IL3xxx warning from an assembly named NuGet.* or Newtonsoft.Json (TrimmerSingleWarn false, and the warnings for those assemblies as errors). IL3050 is an error there already, which catches a missing switch today; the guard also catches IL2xxx.

DOC-1 Publishing guidance

A page for extension authors describes layouts A and B and RID-specific .NET tools, the package type MorphirExtension, and the two-pass publish the spike found: dotnet pack packs the main and every RID package in one run and copies Pack="true" items into all of them, and a RID package's treeSha256 exists only after it is packed. So: pack the RID packages, compute each tree digest with the package contract’s tree digest rule, then pack the main package with the finished release.json. Duplicate morphir/ entries in RID packages are harmless: they are outside root. The repository has no command that computes a tree digest for an author today (PackageManifest.FromFiles computes it internally); such a command is a follow-up issue, not part of this change.

Migration plan

  1. Pin the upstream schema; the family URLs move to the new version. Following DOC-1 of the family, documents of the old version are refused with no conversion, as #654 did for preview.1.
  2. Land the payload seam as a pure refactor inside the same PR, with the existing tests unchanged and green.
  3. Land WASM installation, then the NuGet provider, its CLI options and the docs.

Rollback: the change is additive for users; reverting the PR removes nuget: and WASM installs. A Home written at the new family version is not readable by an older CLI, as with every family version move.
