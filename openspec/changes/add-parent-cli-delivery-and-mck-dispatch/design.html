Context

See proposal.md for why. The requirements are in specs/cli-tool-dispatch and specs/cli-build-interface.

  • One command layer. All three entry points (the Native AOT morphir in src/Morphir, the managed morphir in src/Morphir.Managed and dotnet-morphir in src/Morphir.Tool) call MorphirApplication.Run in src/Morphir.Tooling. It handles --version before System.CommandLine is built, and the rest goes through MorphirCliBuilder, which redirects Console.Out to standard error so that only command output reaches standard output.
  • No MCK in the CLI today. src/Morphir.Conformance is a library: the case reader, the comparisons, the runner, FrontendAdapter (in-process frontends through Morphir.Compilation) and CliAdapter (runs a CLI executable). No entry point references it; only test projects do. The parent's morphir-mck, extracted under modified Decision 16A, is the only MCK executable for now.
  • Process code already exists. Morphir.Tooling/Infrastructure/BoundedProcess.cs runs a child with captured pipes, a deadline and a byte budget, and stops its tree, with kill on a process group on Unix. Routing needs the opposite: inherited streams and no budget.
  • Publication today. .github/workflows/deployment.yml builds the legacy morphir-<rid> single-file executables and morphirup on four runners. Its release job pushes every library package and Morphir.Tool with PublishAll, and create-github-release attaches morphir-* and morphirup-*. The named release profiles (PublishRelease, PackRelease) exist but no workflow publishes them.

Goals and non-goals

Goals.

  • A routing of mck that behaves like running the standalone tool, in every entry point.
  • One switch that stops CLI publication here without touching library publication.
  • A build interface that finos/morphir can call at a pinned commit and that starts the executables it produces.

Non-goals.

  • A general plugin mechanism (morphir <name> running morphir-<name>).
  • Implementing or porting MCK commands, or moving Morphir.Conformance into a tool.
  • The parent's workflows, its .gitmodules, its docs and the removal of the Rust CLI, which the parent worker owns.
  • A production release, CET mitigation or WASM engine changes.

Decisions

MCK-1. Route before System.CommandLine parses

MorphirApplication.Run checks whether the first argument is exactly mck, before it builds the command tree, and routes the rest of the arguments unparsed.

  • Why before the parser. Pass-through must be exact. System.CommandLine applies its recursive --help and its response-file (@file) expansion before any action runs.
  • Why it is still a command. The tree also gets an mck command that takes the remaining tokens and routes them the same way, so that morphir --help lists it and a host built with CreateApp (as tests do) behaves the same.
  • Alternative. Only a command with TreatUnmatchedTokensAsErrors = false. Rejected, because help and response files would still be interpreted.

MCK-2. Inherit the streams, the working directory and the environment

The tool starts with UseShellExecute = false and no redirection, so it inherits the CLI's operating-system standard handles. Pipes, redirection, terminal detection and colours then behave as for the standalone tool, and nothing is copied or buffered. The working directory is the CLI's current directory and the environment is the CLI's. The routing runs before the CLI builder, so the CLI writes nothing to standard output and no logging is set up.

Alternative. Redirecting and pumping the streams. Rejected: it breaks TTY detection and adds a buffer that can reorder standard output and standard error.

MCK-3. Resolve through MORPHIR_MCK or absolute PATH folders only

A pure resolver takes MORPHIR_MCK, PATH, the platform and a file probe, and returns either an absolute path or a refusal.

  • MORPHIR_MCK, when set, must be an absolute path to an existing file. A relative path is refused, not resolved against the current directory.
  • Otherwise, the PATH entries are taken in order. Empty and relative entries, . included, are skipped.
  • The candidate is morphir-mck.exe on Windows: .cmd and .bat would need cmd.exe. Elsewhere it is morphir-mck, a regular file with an execute bit.
  • The resolved absolute path is what starts. So the Windows search order of CreateProcess, which includes the application folder and the current directory, never applies.

The resolver is the unit-tested core. The process start is tested end to end (see MCK-6).

MCK-4. Interrupts reach the tool; termination stops its tree

  • Ctrl+C reaches every process of the console (Windows) or of the foreground process group (Unix), so the tool gets it directly. The CLI cancels its own default handling (Console.CancelKeyPress, SIGINT), waits, and exits with the tool's code, as dotnet run does.
  • SIGTERM or SIGHUP on Linux and macOS stops the tool's process tree, and the CLI exits with 143. A forwarded SIGTERM would reach only the tool, and its children would be orphaned once it exited, so the tree is stopped while the CLI can still find it. A graceful stop is what Ctrl+C is for.
  • Windows. Before the tool starts, the CLI puts itself into a job object with JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE. The tool and everything it starts inherit the job, so there is no window between start and assignment. When the CLI process ends, even by TerminateProcess, its handle closes and Windows ends every process in the job. If the job cannot be created (an old system that refuses nested jobs), routing goes on without it and says so on standard error.
  • A cancellation token (the command-tree path) kills the tool's tree.

Alternative. Assigning the child to a job after Process.Start. Rejected: the child can start processes before it is assigned.

MCK-5. Exit code 127 for a missing tool

127 is the shell's "command not found". It does not collide with the codes a gate tool uses for its own results (0, 1, 2), so a CI job can tell "no tool" from "gate failed". A refused MORPHIR_MCK also exits with 127, and a resolved file that cannot be started exits with 126, the shell's "not executable". The diagnostic names morphir-mck, where it looked (MORPHIR_MCK and the absolute folders on PATH, not the current directory), and that the tool is a separately installed, development-only tool from finos/morphir.

MCK-6. Test with a stub tool and the produced apphosts

  • The stub. tests/Morphir.Mck.Stub builds an apphost named morphir-mck. It writes its arguments, working directory and standard input as JSON, writes a line to standard error, exits with a requested code, and can start a grandchild and wait.
  • What runs. The tests start the produced apphosts (morphir, dotnet-morphir, the managed morphir), not dotnet exec, with PATH set to the stub's folder.
  • What they compare. Arguments, working directory, standard input, the separation of standard output and standard error, the exit code, routed against standalone output, the missing-tool diagnostic, and that killing the CLI stops the stub and its grandchild.

DLV-1. Stop CLI publication behind one repository variable

In deployment.yml:

  • build-executables, build-morphirup and the CLI parts of create-github-release run only when vars.MORPHIR_DOTNET_CLI_PUBLICATION == 'enabled'.
  • The release job runs PublishLibs, plus PublishTool only under the same condition.
  • The GitHub release of this repository is still created, for the library release notes, with no CLI assets unless enabled.

Unset, the default stops competing publication at once. Setting the variable is the rollback, with no code change.

Alternative. Deleting the jobs. Rejected for now: the parent's channel is not yet live, and the jobs are the rollback.

DLV-2. A reusable workflow at a pinned commit

.github/workflows/cli-offering.yml is a workflow_call. It takes these inputs:

  • repository, default finos/morphir-dotnet;
  • ref, a commit SHA, required;
  • deployment: native-aot, self-contained, framework-dependent or dotnet-tool;
  • rid, empty for dotnet-tool;
  • os;
  • configuration.

It checks out that repository at that ref with full history, because the version comes from the CHANGELOG and the commit. It sets up the SDK from the checkout's global.json and runs ./build.sh --target PackRelease. It qualifies the result:

  • an archive is extracted and its morphir apphost or Native AOT executable is started with --version;
  • the tool package is installed into a tool path and dotnet-morphir --version is started.

It uploads the artifact morphir-dotnet-<deployment>-<rid|any>, with the archive or package, its .build-launch.json and a .sha256 file. Its outputs are the artifact name, the file name and the SHA-256.

  • Why the caller's ref is checked out. In a reusable workflow, actions/checkout checks out the caller's repository by default.
  • Why it is a workflow. The parent can call it at the same commit it pins as ecosystem/morphir-dotnet, without copying the build logic.
  • Alternative. The parent runs the Nuke targets in its submodule directly. That stays possible, and the targets are part of the documented interface.

Risks and trade-offs

RiskMitigation
Between this change and the parent's first release, no CLI is published anywhere.No production release is planned. MORPHIR_DOTNET_CLI_PUBLICATION=enabled restores publication here if one is needed.
The job object also ends a process that the tool meant to leave running after it exits.A gate tool has no reason to leave daemons; this is stated in the docs. The job applies only to mck.
On Linux and macOS a SIGKILL of the CLI cannot be forwarded, so the tool keeps running.Stated as a limit. SIGTERM, SIGINT and cancellation are covered and tested.
Ctrl+C sent to the CLI's process id alone (kill -INT), not to its group, does not reach the tool.The tool still stops on SIGTERM or when the CLI's tree is stopped. Interactive Ctrl+C reaches the whole group.
The reusable workflow builds what the profiles define. A qualification gap in a profile (the macOS packaged input path under /var, which resolves to /private/var) carries into the parent.It is recorded as unqualified evidence, and no link check is weakened.
Tests that start apphosts depend on the runtime being found.The tests pass DOTNET_ROOT from the test's own runtime.

Migration plan

  1. This change lands. A release tag here then publishes libraries only.
  2. finos/morphir pins this repository as ecosystem/morphir-dotnet and calls cli-offering.yml at the pinned commit for each offering and platform. It qualifies the artifacts and publishes them, Morphir.Tool included, under its release tags.
  3. The parent provides morphir-mck (modified Decision 16A). Its development gates run through it, standalone or as morphir mck.
  4. Rollback: set MORPHIR_DOTNET_CLI_PUBLICATION=enabled in this repository. Routing mck needs no rollback: without a tool it is a diagnostic.

Open questions

  • When the job definitions are deleted. The variable-gated jobs can be removed once the parent has published a release. That is a follow-up change, not part of this one.
