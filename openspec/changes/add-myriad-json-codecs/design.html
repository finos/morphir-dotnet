Context

See proposal.md for the motivation and the spec for the requirements.

  • Morphir.Myriad already ships a Myriad 0.85.0 plugin as a NuGet package. Its package has a private Myriad host that runs with FSharp.Core 11 and .NET major-version roll forward, and an MSBuild coordinator (Morphir.Myriad.Build) that runs the host and orders the generated files before handwritten files. The car rental example uses it through a local feed (artifacts/myriad-feed).
  • src/Morphir.Internal.CodeGeneration has a json-codec generator that returns empty output, a GenerateJsonCodec attribute and a JsonCodecConfig record. No project uses them. Its IMPLEMENTATION_STATUS.md lists the JSON codec phase as not started.
  • Myriad gives a generator the untyped syntax tree of its input file (Fantomas/FCS AST), not type-checked symbols.
  • System.Text.Json source generation reads C# syntax only. In reflection mode, System.Text.Json has some F# support, but not for unions, and reflection mode is not trim-safe.
  • FSharp.SystemTextJson (reflection-based) defines the union encoding vocabulary that F# users know (JsonUnionEncoding, JsonFSharpOptions, JsonName).

Goals and non-goals

Goals: generated code that a trimmed or Native AOT application can use with the normal JsonSerializer calls; the same JSON as FSharp.SystemTextJson for the shared options, so users can move with no wire change; the extra shapes that Morphir needs (MEP, IR V4 and classic, configuration); a public package that other F# projects can use.

Non-goals:

  • Generic user types (type Page<'T> = …). They need a type info for each closed type; the first release reports a build error. Generic F# collections and options are supported.
  • Classes and C#-style objects with constructors. System.Text.Json source generation already serves them from a C# project.
  • Reflection fallback. A shape that is not supported fails the build.
  • Other JSON libraries (Newtonsoft.Json, Thoth). The presets copy their JSON shape, not their API.
  • A new Myriad host. The plugin uses the host that Morphir.Myriad already packages.

Decisions

GEN-1. Generate System.Text.Json converters and a context

For each type, the plugin generates a sealed JsonConverter<T> that reads and writes with Utf8JsonReader and Utf8JsonWriter. For each context, it generates:

type AppJson(options: JsonSerializerOptions | null) =
    inherit JsonSerializerContext(options)
    static member val Default = AppJson(JsonSerializerOptions(...defaults...))
    member this.Person : JsonTypeInfo<Person> = // cached, from JsonMetadataServices.CreateValueInfo
    override this.GetTypeInfo(t: Type) : JsonTypeInfo | null = // a match on typeof for each type
    override _.GeneratedSerializerOptions = ...
  • A member whose type is in the same context calls that generated converter directly. A member whose type is elsewhere asks options.GetTypeInfo(typeof<T>), which is trim-safe when the options' resolver covers T. Primitive types use the public built-in converters of JsonMetadataServices.
  • Callers use the normal API: JsonSerializer.Serialize(value, AppJson.Default.Person), JsonTypeInfoResolver.Combine, and JsonSerializerOptions.TypeInfoResolverChain. The Default instance is also an IJsonTypeInfoResolver.
  • Generated code depends only on System.Text.Json and FSharp.Core. The annotations package is needed only at compile time for the attributes; nothing in it runs.

Alternatives considered:

  • Plain encode and decode functions (the stub's plan). Rejected: callers could not use JsonSerializer, ASP.NET Core or other libraries that take JsonTypeInfo, and the result would not be "the F# equivalent" of the C# generator.
  • Annotate F# types in a C# project with [JsonSerializable]. Rejected: the C# generator cannot represent F# unions, and has no union encodings.
  • Emit C# and run the C# generator. Rejected: same limits, plus a second language in every F# consumer.

GEN-2. The FSharp.SystemTextJson vocabulary, checked by output

The options use the FSharp.SystemTextJson names and meanings, so a user can read their documentation and move a type with no wire change:

GroupValues
Base union encodingAdjacentTag (default), ExternalTag, InternalTag, Untagged
Union flagsNamedFields, UnwrapFieldlessTags, UnwrapSingleFieldCases, UnwrapSingleCaseUnions, UnwrapRecordCases, UnwrapOption, FieldNamesFromTypes, AllowUnorderedTag, TagCaseInsensitive
PresetsDefault, NewtonsoftLike, ThothLike, FSharpLuLike
Namesunion tag name (Case), fields name (Fields), tag and field naming policies, JsonName on cases and fields, JsonPropertyName on fields
Otherskippable option fields, allow null fields, map format (Object, ArrayOfPairs, ObjectOrArrayOfPairs), include record properties

The compatibility tests serialize a corpus of shapes with every encoding, flag and preset through both the generated context and FSharp.SystemTextJson (a test-only dependency, JIT only), and compare the JSON. They also have expected JSON written by hand for each base encoding, so the corpus does not depend only on the other library. Where FSharp.SystemTextJson has a defect, the test records the deviation and follows the documented meaning.

AllowUnorderedTag needs a look-ahead: the converter copies the Utf8JsonReader struct, scans the object for the tag member, and then reads from the original position, as System.Text.Json polymorphism does. Without the flag, the tag must come first, and there is no copy.

GEN-3. What the untyped syntax tree can and cannot tell

Myriad gives the plugin syntax, not types. The rules that follow from this:

  • Built-in names are known by spelling: string, the numeric types, bool, option, voption, list, array and [], Set, Map, ResizeArray, IReadOnlyList, IReadOnlyCollection, IReadOnlyDictionary, DateTimeOffset, Guid, JsonElement and tuples. A user type with one of these names in an opened namespace is a build error, not a silent guess.
  • Types declared in the input file get generated converters. Any other named type is resolved at run time through the options (GEN-1). A test-time check (AppJson.Verify(options)) asks the options for each such type, so a missing context fails in a unit test, not in production.
  • Type abbreviations in the input file are expanded. Abbreviations in other files are not visible; they must be declared in the context's input files or used through their target type.
  • Attributes are matched by their name (with or without the Attribute suffix, short or qualified). The annotations package defines them, so the compiler checks their arguments.
  • The generated file opens the same namespaces as the input file, and is compiled right after it.

GEN-4. Configuration: project item, then attributes

<ItemGroup>
  <Compile Include="Mep/Types.fs" />
  <FSharpJsonContext Include="Mep/Types.fs" Name="MepJson" Namespace="Morphir.Mep"
                     Preset="Default" UnionEncoding="ExternalTag, UnwrapFieldlessTags"
                     NamingPolicy="CamelCase" SkippableOptionFields="true"
                     UnknownMembers="Ignore" />
</ItemGroup>
[<JsonUnion(BaseEncoding = JsonUnionEncoding.InternalTag ||| JsonUnionEncoding.NamedFields, TagName = "kind")>]
type Shape =
    | [<JsonName "circle">] Circle of radius: float
    | [<JsonName "square">] Square of side: float

[<JsonParsedValue(ParseMember = "Parse", TextMember = "Value")>]
type ExtensionId = private ExtensionId of string ...
  • The project item sets the context defaults. An attribute on a type, case or field overrides them for that item only. There is no global mutable configuration.
  • Every type in the input files that has a JSON attribute, or that a context member reaches, is in the context. [<JsonIgnoreType>] leaves a type out.
  • The option enums and attributes live in the annotations package, which has no dependency, so a domain project can reference it without a JSON dependency at run time.

GEN-6. Errors

  • Run time: every failure is a JsonException with a message that names the type and member. System.Text.Json adds the JSON path and position when a converter throws. A parse failure keeps the parser's text.
  • Build time: an unsupported shape, an unknown attribute argument, contradictory options or an ambiguous untagged union fails generation with an error that names the file, type and member. Morphir.Myriad's coordinator turns it into an MSBuild error and blocks compilation.

GEN-7. Build integration and packaging

  • Names (decided 2026-11-07): the plugin package Morphir.Myriad.SystemTextJson (plugin, build props and targets, the shared Myriad host), the attributes package Morphir.Myriad.SystemTextJson.Annotations (attributes and option enums, netstandard2.0, no dependency), and the Myriad generator morphir-system-text-json (class MorphirSystemTextJsonGenerator). The names keep the Morphir prefix, as Morphir.Myriad and its generator morphir-fsharp do. They do not use the FSharp.SystemTextJson or Myriad prefixes, which belong to other projects. The generator name has the morphir- prefix because one Myriad run can load generators from more than one plugin, and Myriad 0.85.0 filters them by name.
  • The private Myriad host and the coordinator from Morphir.Myriad become a shared build component. Both packages carry it. The coordinator gains a mode for .fs inputs with one output file per context; the morphir-fsharp path does not change.
  • Projects in this repository: a ProjectReference to the plugin with ReferenceOutputAssembly="false" orders the build, and a repository props file points the targets at the plugin's build output. The targets are the same as in the package. No package feed is needed.
  • Generated files go under obj/<configuration>/<tfm>/system-text-json/. Snapshot tests keep a copy of the generated code for a sample context, so reviewers see changes to the generated code in diffs.

Publishing. The two new packages and Morphir.Myriad are published to NuGet.org with every morphir-dotnet release (decided 2026-11-07), through the existing path: PackLibs packs them, and deployment.yml pushes them with NuGet trusted publishing. Today Morphir.Myriad is packed only into the local feed artifacts/myriad-feed, and it is not in the LibraryPackages list, so no Myriad plugin is published yet. This change adds:

  • the three packages to LibraryPackages: Morphir.Myriad after its backend, and the annotations package before the plugin, so that publishing keeps dependency order;
  • for Morphir.Myriad: the release version replaces the fixed local version 0.1.0-local.5 in the getting-started article, the car rental example and its README, which then restore from NuGet.org; the local feed stays for the package tests;
  • a plugin-package check in PackageValidator: the plugin and its dependencies under tools/, the Myriad host, the build props and targets, the README, the license and ThirdPartyNotices.txt; the existing library check applies to the annotations package;
  • a smoke test after packing: a clean project restores the packages from the packed output only, and builds a context and a Morphir model;
  • the release notes entry and the package README, which is also the NuGet.org page.

The first push of a new package id needs a NuGet.org account that may create ids with the chosen prefix. The release manager checks this before the first release that has the packages.

Alternative considered: commit the generated files and check them for drift in CI. Rejected for this repository: it does not exercise the package path that users take, and it adds a manual step to each type change.

GEN-8. Replace the internal stub

The stub json-codec generator, GenerateJsonCodecAttribute and JsonCodecConfig are removed, with their tests. IMPLEMENTATION_STATUS.md and the README of Morphir.Internal.CodeGeneration point to the new plugin. The other internal generators do not change. The elm-to-fsharp-guru skill template that calls json-codec moves to the new generator.

Risks and trade-offs

RiskMitigation
The untyped AST cannot see types in other files, so a missing context shows only at run time.The generated Verify(options) member and a unit test for each context; the build error for a reserved name used by a user type.
Myriad 0.85.0 needs the FSharp.Core host alignment; a Myriad update can break both plugins.One shared host component with its own package test; a Myriad update is its own change.
The FSharp.SystemTextJson output changes in a new version.The test reference is pinned. The hand-written expected JSON is the reference for this package; a difference becomes a recorded deviation.
Generated converters are large for big unions.Shared helpers in generated code for each context, not for each type; a size check in the AOT probe.
Scope is large for one change.Tasks deliver records and string enums first (enough for most MEP types), then each union encoding, then the additions. Each group lands with its tests.

Migration plan

Additive, except for the removal of the unused stub (GEN-8). Existing hand-written codecs in Morphir.Models and Morphir.Extensions do not change in this change. A later change can move them, one area at a time, with the existing JSON tests as the reference.

Open questions

  • Whether to offer the package to the Myriad maintainers as a listed plugin after the first release.
