route-configured-wasm-extensions

12 November 2026. Product scope explicitly authorized for alpha.5; tests are authored before implementation. No qualification work is included.

Context · Selection · An owned session · Failures and cleanup · Landing

Context

The proposal closes the gap between the runtime foundation in #570 and normal compile/generate commands. The Python 0.6.0 module is already pinned and exercised by runtime tests. Product commands currently select only built-ins or external process guests. Implementing another model decoder or generator would duplicate checks; these commands should reuse their existing adapters and publication rules.

Selection

CLI extension selection wins, followed by the existing frontend/codegen extension setting. If neither exists, a selected language/target with an extensions table containing path selects that named module. A selection with a matching module path uses the WASM connector; otherwise the current process connector remains. Path, ABI and digest come from the same effective configuration snapshot as the selection. Relative paths use the source configuration directory, with the project root as fallback. Explicit project/config selection must not be lost by reloading from the invocation directory inside the connector.

effective configuration → selected module → existing module loader
                                                   ↓
normal publisher ← existing MEP model adapter ← owned WASM channel

The module loader still decides runtime availability, digest, classification and ABI refusal in its established order. Production does not discover or download a bundle.

An owned session

The existing frontend and backend adapters negotiate model tuples, bound payloads and validate replies/artifacts. Their dependency on an owned process session becomes a small typed owned-session contract, implemented by the existing process owner and a single-message channel owner. The latter drives ordinary HostSession over WasmChannel. It does not alter MEP admission, conformance controls, notification advertisement or request allocation. Each adapter uses its existing private validation path for either transport and reports wasm for the new transport.

Disposal ownership transfers only on successful connection. Failed initialization or adapter admission closes the channel. Request cancellation waits for the bounded runtime call to settle, then closes the owned session; no task is abandoned. Shutdown/exit and disposal retain the current lifecycle rules. Bounded guest output goes to stderr, never result stdout.

A self-worker process was considered but would add executable-location and module re-read identity problems. Duplicating the frontend/backend model logic was rejected. Both commands are attempted through this shared session boundary; generate is the first landing cut if compile would miss the five-hour target.

Failures and cleanup

Windows x64 fails before reading a selected module, with extension.runtime_unavailable and win_x64_trap_unsupported. Commands selecting no WASM module do not probe its engine. Existing typed command failures, artifact path checks, compile records and owned generation publication remain. No protection setting, raw arbitrary send, conformance checker or second launcher is added.

Landing

Requirements and tasks bind the tests to the behavior. First run the new tests RED under a coordinator slot, then implement and verify the affected paths including a real digest-pinned bundle CLI run. Existing process and built-in controls prevent selection regressions. Add the experimental guide with exact commands in the implementation commit. The initial draft is a test-first checkpoint, not a test-pass claim. After #570 lands, merge main normally, obtain scoped F#/C# review and satisfy exact-head CI. Kit/report/notification/qualification/packaging work stays deferred.
