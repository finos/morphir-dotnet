Context

See proposal.md, section Why. These facts about the current state constrain the approach:

  • Generation pipeline. morphir generate already has the pipeline this change must reuse:
    • GenerateHandler runs settings, then load, then backend resolution, then generation, then publication, all through injected interfaces (src/Morphir.Tooling/Features/Generate/).
    • Backends are added through static TryAddEnumerable registration. The C# backend was added without editing the command, the handler or the resolver.
    • VersionedModel wraps a classic or v4 distribution and keeps the exact declared version as a SourceFormatVersion.
  • Format versions. Versioning.FormatVersion = Classic of int | SemVer of SemanticVersion already models integer classic versions and full SemVer, with pre-release and build parts (src/Morphir.Models/IR/Versioning.fs). The upstream writer rule is to write 3/4 for .0.0 releases and the exact string otherwise.
  • No complete IR writer exists. Readers cover classic JSON v1/v2/v3, v4 JSON and Ion. The partial TypeCodec/LiteralCodec encoders produce the wrong v1/v2 tags and a record-field shape that the reader rejects.
  • No production conversion between families. There is no classic-to-v4 or v4-to-classic conversion outside tests. Repository policy forbids silent migration of supplied v4 input to classic.
  • AOT. morphir is published with PublishAot and PublishTrimmed. dotnet-morphir is a JIT dotnet tool that delegates to Morphir.Program.Main. FSharp.Compiler.Service (FCS) is already pinned, but it is not trim-safe or AOT-safe.
  • Configuration. Project discovery and the canonical schema already exist. They have project.*, ir.format_version (default 4), frontend.language, the per-language [frontend.elm] table and workspace.out_dir.
  • Project files (checked on .NET SDK 10.0.403). dotnet msbuild X.fsproj -getItem:Compile evaluates the project without building it. It returns Compile items in declared order as JSON, in about 0.25 s, with no restore and no obj/ output. It also reports Link items whose path is outside the project directory.
  • Ecosystem (upstream finos/morphir@cde7722eb).
    • The Rust CLI implements morphir compile and the out directory with task records, tombstones and locks.
    • The latest MEP contract is 0.2.0-draft.1. It adds compileModel/generateModel with exact five-part transport tuples, bilateral limits and the MorphirModel envelope 0.1.0-draft.1. A session picks exactly one protocol version.
    • The MEP guest kit (generic-json-library-v1) still requires a legacy 0.1 stage for every guest, and a guest that is both frontend and backend. It is behind the current contract, so this design does not take it as an input (MEP-3).
    • Upstream workspace discovery is a portable search over a supplied file tree. It never runs build tools.
    • No F# frontend exists in the ecosystem.

Goals and non-goals

Goals.

  • Each future frontend, IR version (including pre-releases), project-file tool and transport is added as a new module plus a registration. Nothing already written needs editing.
  • Every stage between the effect edges (file capture, the build tool, FCS, the MEP process, publication) is a pure function from immutable input to Checked, which carries diagnostics on success and on failure (DIAG-1).
  • The F# frontend is complete and solid through the in-process dotnet-tool path before the MEP path depends on it.
  • The MEP path implements the latest upstream contract exactly. It adds no member and does not fall back to legacy.

Non-goals.

  • A Morphir type checker. Types come from FCS inference.
  • Changes to the readers or the public IR types.
  • Fixing the legacy partial encoders.
  • Resolving build-tool references.
  • Legacy MEP 0.1.
  • The Ion morphir-model profile.
  • Evidence and guarantee checking.
  • Running the generated code.

Architecture

One pipeline has four independent extension axes:

  • project-file providers, chosen by the tool's file pattern;
  • frontends, chosen by language and transport;
  • IR builders, one per IR family, which every frontend's single lowering uses (MID-1);
  • writers, chosen by exact format version.

Each axis grows by adding modules (sums), never by multiplying combinations. Generation is reached through the existing backend contracts.

Decisions

ARCH-1. Open/closed through registries of pure stages

Each axis is a small capability descriptor plus a function. A registry selects implementations by descriptor only, using the same rules as RegisteredBackendResolver: exact match, no fallback by registration order, and ambiguity is an error. In C# the same contract is an interface.

  • Adding an IR version, including a pre-release, adds a writer declaration. Adding an IR family adds a builder.
  • Adding a build tool adds a project-file provider.
  • Adding a language or transport adds a frontend registration.
  • The handler, the command and the existing stages are not edited.
// Morphir.Compilation (AOT-safe, no FCS reference). Sketch.
open Morphir.IR                        // Versioning.FormatVersion = Classic of int | SemVer of SemanticVersion

type IrTarget = { Family: ModelFamily; Version: Versioning.FormatVersion }   // never an int

// IIrBuilder<'Type, 'Pattern, 'Value, 'Package>: one native implementation per family (MID-1)
type FamilyModel =                                      // what builders produce and writers write
  | Classic of Classic.Distribution<unit, Classic.Type<unit>>
  | V4 of V4.Distribution

type IrWriter =                                         // one per writer; declares exact versions
  { Family: ModelFamily
    Versions: Versioning.FormatVersion list             // e.g. [Classic 3] or [SemVer 4.1.0-draft.1]
    Write: WriteOptions -> FamilyModel -> Checked<byte[]> }

type ProjectFileProvider =                              // one per build tool
  { Identity: string; Patterns: string list             // e.g. "*.*proj"
    Expand: ProjectFile -> CancellationToken -> Task<Checked<SourceSelection>> }

Alternative considered: each frontend lowers to every family and reads every tool's project files itself. The work multiplies, and every frontend changes when a version or tool is added.

DIAG-1. Diagnostics travel on both success and failure

Every stage between the effect edges returns Checked<'T>, never Result<'T, Diagnostic>. A Result has nowhere to put a warning, an info or a hint on success, so those diagnostics would be lost.

// Morphir.Compilation. Invariants are enforced by smart constructors.
type Checked<'T> =
    private
    | Passed of value: 'T * diagnostics: Diagnostic list   // no error-severity diagnostic
    | Failed of diagnostics: Diagnostic list               // at least one error, plus any warnings gathered before it

module Checked =
    val pass   : 'T -> Checked<'T>
    val note   : Diagnostic -> Checked<unit>              // an error fails; warning, info or hint passes
    val bind   : ('T -> Checked<'U>) -> Checked<'T> -> Checked<'U>   // keeps diagnostics in order, stops at Failed
    val zip    : Checked<'T> -> Checked<'U> -> Checked<'T * 'U>      // applicative: runs both, collects all
    val traverse : ('T -> Checked<'U>) -> 'T list -> Checked<'U list>  // applicative over siblings
// check { let! a = x and! b = y; do! Checked.note w; return f a b }

The builder is named check, because checked is a reserved F# keyword.

  • Severity alone decides failure. One error makes the result Failed. warning, info and hint never change the outcome or the exit code.
  • Nothing is lost when a stage fails. A Failed result keeps the warnings gathered before the first error, and FrontendFailure keeps them for operational failures.
  • Accumulation. Dependent steps use let!, which stops at the first failure. Independent steps (admission rules, sibling declarations, cases and arguments) use and!/traverse, which collect every diagnostic. One run therefore reports all independent problems.
  • Order. Diagnostics are kept in the order they were emitted. The report orders them by stage, in the STRM-2 stage order (settings, sources, capture, frontend, write, publish, generate, generatePublish), then by document and position, as the frontend spec requires.
  • Edges. Checked maps one to one onto MEP CompileModelResult: Passed becomes success: true with its diagnostics, and Failed becomes success: false. At the Tooling boundary, Passed becomes a successful Outcome whose success record carries the diagnostics, as GenerationSuccess already does. Failed becomes a semantic failure.

Alternatives considered:

  • Result<'T * Diagnostic list, Diagnostic list> does not enforce the severity invariants, and every caller must remember to concatenate the lists.
  • A mutable diagnostics sink is an effect inside pure stages, and it makes ordering depend on evaluation order.

STRM-1. Stream events at the pipeline edge; the report is their fold

Pure stages keep returning Checked values (DIAG-1). Streaming is added only at the orchestration edge. The compile runner in Tooling is C#, so it uses native async iterators and needs no new F# dependency:

public abstract record CompileEvent
{
    public sealed record StageStarted(CompileStage Stage) : CompileEvent;
    public sealed record DiagnosticsReported(CompileStage Stage, string? DocumentUri,
        ImmutableArray<Diagnostic> Diagnostics) : CompileEvent;
    public sealed record StageCompleted(CompileStage Stage, bool Passed) : CompileEvent;
    public sealed record Completed(Outcome<CompileSuccess> Outcome) : CompileEvent;   // always last
}
public interface ICompileRunner
{
    IAsyncEnumerable<CompileEvent> RunAsync(CompileSettings settings, CancellationToken ct);
}
  • Granularity. Each stage emits its diagnostics when it completes. Stages that work per document (source capture, admission, writing) emit per document. In this change, the F# compiler checks the whole project at once, so its diagnostics arrive together. Finer streaming comes with incremental checking.
  • The report is a fold. CompileHandler consumes the stream and folds it into the existing single report and Outcome. One property test over the corpus checks that the fold equals the batch path. The terminal Completed event carries the outcome, because the result is only known after the last diagnostic (an error anywhere fails it).
  • Consumers in this change.
    • Human mode writes each DiagnosticsReported event to stderr as it arrives.
    • --json writes only the folded report.
    • --json-lines writes each event as one JSON line on stdout as it occurs (STRM-2).
    • MEP is unchanged.
  • Later consumers use the same stream with no stage changes: watch mode, a daemon, LSP-style per-document publishing, and progress.
  • Cancellation flows through WithCancellation. Cancelling before publication gives exit code 130. IAsyncEnumerable is trim-safe and AOT-safe.
  • Upstream.
    • The Rust CLI writes one compact report line for --json-lines (crates/morphir/src/output.rs). That seems to be an incorrect implementation of the flag's intended meaning: one JSON record per line, written as events occur. This change implements the intended meaning now (STRM-2), and an upstream issue proposes the same record format so that the Rust CLI can align.
    • MEP 0.2.0-draft.1 has no diagnostics notification. This is raised upstream; no local member is invented.

Alternatives considered:

  • IAsyncEnumerable inside the pure stages. The pass/fail invariant would need a terminal state anyway, applicative collection and determinism would get harder, and effects would enter the middle-end.
  • A callback sink. This is an effect inside the stages, cannot be composed, and gives no back-pressure.

STRM-2. --json-lines is the event stream as newline-delimited JSON

--json-lines writes the STRM-1 events to stdout, one compact UTF-8 JSON object per line, ending each line with \n. Each line is flushed when its event occurs. Logs stay on stderr. Each record has an event member; the other members are camelCase, like the report.

{"event":"stageStarted","stage":"sources"}
{"event":"diagnostics","stage":"sources","document":"src/Acme.CarRental.fsproj","diagnostics":[{"severity":"warning","code":"msbuild.ignored_package_reference","message":"PackageReference Newtonsoft.Json is ignored."}]}
{"event":"stageCompleted","stage":"sources","passed":true}
{"event":"stageStarted","stage":"frontend"}
{"event":"diagnostics","stage":"frontend","document":"Pricing.fs","diagnostics":[{"severity":"warning","code":"fsharp.compiler","message":"Incomplete pattern matches on this expression.","location":{"uri":"Pricing.fs","range":{"start":{"line":11,"character":4},"end":{"line":11,"character":9}}},"data":{"errorNumber":25}}]}
{"event":"stageCompleted","stage":"frontend","passed":true}
{"event":"stageStarted","stage":"write"}
{"event":"stageCompleted","stage":"write","passed":true}
{"event":"stageStarted","stage":"publish"}
{"event":"stageCompleted","stage":"publish","passed":true}
{"event":"completed","report":{"success":true,"exitCode":0,"irVersion":"4","diagnostics":["... the same two diagnostics ..."]}}
  • Stages: settings, sources, capture, frontend (which includes building the requested family), write, publish, and, with --target, generate and generatePublish. A stage that does not run has no records.
  • Exactly one completed record, always last. It holds the same report object that --json writes, so a consumer that wants only the result reads the last line. Parse errors, the --json plus --json-lines conflict, and cancellation also end with one completed record when output can still be written.
  • The stream holds no less than the report. All diagnostics records together equal the report's diagnostics. Record order is emission order; the report keeps its stage, document and position order.
  • Compatibility. Consumers ignore unknown event types and members, so new stages, events and members can be added without a new format version. Removing or renaming a member is a breaking change.
  • Serialization uses one source-generated JsonSerializerContext for the event records and the report, so trimming and AOT work.

Alternatives considered:

  • Copying the Rust CLI's one-line report. That is not what the flag is for, and it adds nothing over --json.
  • A new flag such as --json-stream. It would leave --json-lines with the wrong meaning in the ecosystem, and it would split the tools.
  • JSON-RPC notifications on stdout. That needs a protocol for a command-line output format, and MEP has none for diagnostics.

VER-1. Format versions are always Versioning.FormatVersion

No contract, registry key, setting or report field holds a format version as an int. These all carry Versioning.FormatVersion, and SourceFormatVersion where the declared spelling matters:

  • --ir-version
  • ir.format_version
  • IrTarget
  • writer declarations
  • MEP tuples
  • records

The equivalence rule:

  • Classic n equals SemVer n.0.0.
  • Any other SemVer matches only itself, and a pre-release never matches its release.
  • Build metadata is kept in the spelling but has no effect on matching, as SemVer requires.

One pure function, FormatVersion.sameVersion, owns this rule, and property tests cover it. Writers write integer n for Classic n and n.0.0, and the exact string otherwise.

A future 4.1.0-draft.1 writer is therefore one declaration. Today's IR v4 writer declares Classic 4, which also matches 4.0.0.

Alternative considered: an int major version. It cannot represent pre-releases, and it would merge distinct draft formats.

MID-1. Lower once against an IR builder interface; each family builds natively

The middle-end is an object algebra, also called tagless-final style: an interface with one constructor for each IR node of the supported subset. A frontend writes its lowering once, generic over that interface. Each IR family implements the interface natively. Lowering and building are one pass, and there is no intermediate tree.

// Morphir.Compilation. One member per node of the supported subset; sketch.
type IIrBuilder<'Type, 'Pattern, 'Value, 'Package> =
    abstract Family  : ModelFamily
    abstract TypeRef : Span * FQName * args: 'Type list -> Checked<'Type>
    abstract Integer : Span * inferred: 'Type * BigInteger -> Checked<'Value>
    abstract Apply   : Span * inferred: 'Type * fn: 'Value * arg: 'Value -> Checked<'Value>
    abstract Match   : Span * inferred: 'Type * subject: 'Value * cases: ('Pattern * 'Value) list -> Checked<'Value>
    // ... literals, constructors, lambdas, let/let rec, records, patterns, definitions, modules
    abstract Package : PackagePlan * modules: ModulePlan<'Type, 'Value> list -> Checked<'Package>

// Native builders:
// ClassicBuilder : IIrBuilder<Classic.Type<unit>, Classic.Pattern<Classic.Type<unit>>,
//                             Classic.Value<unit, Classic.Type<unit>>, Classic.Distribution<unit, Classic.Type<unit>>>
// V4Builder      : IIrBuilder<V4.Type, V4.Pattern, V4.Value, V4.Distribution>
// F# frontend, written once:  lower : IIrBuilder<'T,'P,'V,'K> -> CheckedProject -> Checked<'K>
  • Native families. ClassicBuilder builds typed classic nodes, with the inferred type as the value attribute, and has no slot for a Span. V4Builder builds v4 nodes with InferredType and Source. Neither builder reads or creates the other family's model.
  • Refusal belongs to each family. Each family's builder refuses content it cannot hold with morphir.unrepresentable, at the node's span. Examples are an integer outside int64 or a non-BMP Char in ClassicBuilder. The frontend does not know which limits any family has.
  • Whole-program work stays outside the builders. Name collisions, dependency order, module access and the exposed-module set are computed once by the frontend, on its own symbol tables, before building. That result is the PackagePlan/ModulePlan, so it is the same for every family.
  • Classic v1, v2 and v3 share ClassicBuilder. They differ only in the writer profile (IRW-1).
  • Typed output. Builders produce typed family models. VersionedModel, whose classic attributes are wire-specific JSON, is produced only by reading written bytes back (CLI-2).
  • Open/closed. A new family is one new builder. A new version within a family, including a pre-release, is one new writer declaration (VER-1). Neither change edits a frontend. The compiler enforces completeness, because every builder must implement every interface member.
  • Classic still goes directly to the backends. The model a backend receives is the requested family's own model. A v3 compile reaches the backend's native classic path, and generate with classic input is unchanged.

Alternatives considered (N frontends, M families):

OptionCode to maintainPassesWhy not chosen
A. Lower to v4, then a checked v4→classic projection (the upstream Gleam frontend's approach)N + (M−1)2 for classicClassic is derived, not native, and depends on the draft v4 model. It needs a conversion step between families.
B. A neutral Core data model, with Core→classic and Core→v4 loweringsN + M + the Core types2Core mirrors the v4 subset almost one to one, which is repetition, and it adds a pass.
C. Each frontend lowers to each familyN × M1Repetition grows with every frontend.
D. Everything normalized to v4, and backends read only v4N + 2, with backends B × 12Breaks the direct classic-to-backend connection, and migrates supplied input.
E. Lower to classic, then promote to v4N + 12v4 output loses source spans.

Evidence for these choices: in this repository, v4 holds every classic v3 node and literal (it adds Hole, wider literals, and native, external and incomplete bodies). So option A was possible, and was rejected on design grounds, not on capability. The C# generator already lowers classic and v4 natively and separately.

Follow-up (separate change): backends still repeat a classic and a v4 lowering each. The same idea in reverse removes that repetition without migration: a read-only view interface that both families implement, so each backend is written once and classic input still reaches it directly.

IRW-1. Writers are profile-driven, and the readers are their oracle

One classic writer takes a ClassicWireProfile, a record of data and no behavior, and declares the versions that its profiles cover. Each of v1, v2 and v3 is one value of that record. The profile holds:

  • the tag spelling per node family;
  • the access wrapper (array or object);
  • the module list shape;
  • the distribution tag casing;
  • how a module without documentation is written: left out in v1 and v2, "doc": null in v3, as the upstream kit, writer and v3 schema have it. The bundled v3 schema is aligned with upstream to allow null.

The v4 writer writes the canonical compact v4 spellings with the existing CanonicalNames writers. Both writers stream to Utf8JsonWriter in a fixed member order, and take number lexemes from the model, never from a double.

Correctness is checked from outside the writers:

  • round trip through the existing readers over every fixture;
  • the bundled v1/v2/v3 JSON schemas;
  • the upstream JSON IR examples already pinned in tests/Fixtures/MorphirIon, with their provenance: each is read, written in its own version, and compared structurally.

The existing partial encoders are not reused or changed. A follow-up issue records their bugs.

SRC-1. Project files are expanded on the host, through language-neutral providers

Source selection produces one SourceSelection { Root; Documents (ordered, root-relative); Inputs; Diagnostics }, from one of three inputs:

  • --project-file, or the [frontend.<language>].project_file key with the same name;
  • --input files, in the given order;
  • an --input directory, or else project.source_directory, in lexical order.

The project file has its own flag and does not go through --input. --input keeps its ecosystem meaning (files or a directory), nothing has to guess from a file name whether an input is a project file, and the flag and the config key share one name, so the CLI overrides config in the usual way. --project-file with --input fails (sources.conflicting_source_options). An --input file that a provider recognizes as a project file fails with a hint to use --project-file (sources.project_file_as_input), and is never compiled as a source.

A project file is passed to the one provider whose pattern matches it. The selection becomes the MEP SourceSet (root plus ordered documents). Neither the frontends nor MEP know that a project file existed, and no provider value travels to a frontend.

This fits MEP's model, in which the host sends source text and the frontend needs no workspace access. It is also why expansion is not a morphir.workspace.discover concern: upstream discovery is a portable file-tree search that never runs build tools.

The first provider is MSBuild evaluation. It runs this command as a child process, which is AOT-safe:

dotnet msbuild <file> -getItem:Compile -getItem:ProjectReference -getItem:PackageReference -nologo
  env: MSBUILDDISABLENODEREUSE=1  DOTNET_CLI_TELEMETRY_OPTOUT=1  DOTNET_NOLOGO=1  DOTNET_SKIP_FIRST_TIME_EXPERIENCE=1
  • It is evaluation only: no targets, no restore, no output. Order is the declared item order.
  • It works for any MSBuild project, so a .csproj expands the same way. Whether its language is supported is the frontend registry's decision.
  • Item rules:
    • Link items outside the root get sources.outside_root.
    • ProjectReference is refused (msbuild.unsupported_project_reference).
    • PackageReference gives a warning (msbuild.ignored_package_reference).
  • The output is bounded, with a deadline. A missing SDK gives msbuild.unavailable.

Evaluation can run project logic: imports and property functions. That is why a provider runs only on a file the user named, and never on a file the command found by itself.

Alternatives considered:

  • Ionide.ProjInfo or Buildalyzer in process. Both are JIT-only and heavier, and they target F# or design-time builds.
  • Fable's FscCommandLineArgs design-time build. It is F#-specific and needs a restore.
  • A hand-written XML reader. It cannot evaluate conditions, imports or SDK defaults.

SRC-2. The configuration key is [frontend.<language>].project_file

Every language table accepts the same key, project_file, and the command reads it from the selected language's table. A project file belongs to a language's toolchain (MSBuild, Gleam, Python packaging), so the per-language tables that upstream already uses ([frontend.elm] extension) are the right place. One key name and one provider registry keep the mechanism neutral.

The schema defines project_file once, as a per-language table member. It is not repeated for each language. The upstream request is a shared key convention for [frontend.<language>] tables, not a change to project identity.

Alternatives considered (evaluated during planning):

  • [project] source_manifest needs a canonical project-identity change upstream, including in discovery snapshots.
  • A language-specific key name such as [frontend.fsharp] project needs resolver code for each language and breaks neutrality.

FE-1. The in-process compile contract has the semantics of MEP 0.2 compileModel

The in-process contract is a typed F# model of the latest MEP compile concepts: source set, package, options, context digest, output target, the success/failure result sum, frontend capability and diagnostics. It adds no concept that MEP lacks. Because of this, the MEP adapter is a pure codec, and diagnostics are in the MEP shape (zero-based UTF-16 ranges) in every path.

type SourceDocument = { Uri: string; LanguageId: string; Version: uint64; Text: string }
type CompileRequest =
  { LanguageId: string; Root: string option; Documents: SourceDocument list
    Package: PackageName; ExposedModules: string list option    // None = all public, [] = none
    Output: IrTarget; ContextDigest: Sha256 }
type FrontendCapability =
  { Languages: (string * string list) list; Outputs: IrTarget list
    Incremental: bool; MultiDocument: bool }
type CompiledPackage = { Model: FamilyModel; Modules: string list }   // the requested family
// Checked<CompiledPackage> mirrors CompileModelResult (DIAG-1):
//   Passed (package, diagnostics) = success: true, model, diagnostics of any non-error severity
//   Failed diagnostics             = success: false, no model, at least one error
type Frontend =
  { Identity: string; Transport: FrontendTransport            // InProcess | Mep of extensionId
    Capability: FrontendCapability
    Compile: CompileRequest -> CancellationToken -> Task<Result<Checked<CompiledPackage>, FrontendFailure>> }

FrontendFailure covers operational and protocol failures (exit code 2). It also carries the diagnostics gathered before the failure, so that none are lost. Source problems are always Failed (exit code 1). Warnings, info and hints travel with Passed and never change the exit code.

The in-process frontend advertises Outputs as every target for which a builder and a writer are registered. It runs its single lowering with the builder of the requested family (MID-1).

Implementation note (task 3.8): the contract is in Morphir.Compilation. CompileRequest has a private representation: only Parse, TryParse and Create build one, and they refuse a missing language, a missing package name, an empty document list, a missing document, a document without a URI or text, a document in another language and a repeated URI before analysis. A language id is a parsed LanguageId (a lowercase token, compared ordinally), never raw text. For C#, the frontend is the IFrontend interface, and the result is FrontendOutcome: Completed holds the Checked<CompiledPackage> and Failed holds the operational FrontendFailure, with a Match member. FrontendTransport has only InProcess; group 8 adds the MEP case. FSharpFrontend.registration reads fsharp with the extensions .fs and .fsi (a signature file reaches admission, which refuses it with its catalog code), and FSharpFrontend.create builds the same frontend over other builder and writer registries. A request for another language, or for a target that the frontend does not advertise, is an operational failure; cancellation ends the task with OperationCanceledException. In v4, a type node takes the location of its nearest declaration: the type name for a type definition's body, the field or union case for its field types, the parameter for an input type, the binding head for the output type, and the value or pattern node for an inferred type.

The MEP adapter decodes the guest's verified payload with the existing readers into the requested family's typed model. Classic value attributes are read as types of that wire version. Because of the writer round-trip rule, writing that model again in the same version gives the guest's payload bytes, and the parity tests check this.

FE-2. Frontend selection reads advertised capabilities on every run

FrontendResolver.resolve filters the registered frontends:

  1. by language, or by the extensions of every document;
  2. then by output target;
  3. then by multi-document support.

For a MEP frontend, "output target" means one of these:

  • a session-admitted tuple with exactly that version;
  • for classic versions 1 and 2, an admitted 3.0.0 tuple, because the host writes the same classic model with a different wire profile (MEP-3).

An explicit --extension or [frontend.<language>].extension creates and selects a MEP registration. With no extension configured, the in-process registration wins when it exists. Every refusal names the frontend and the capability.

FSF-1. The F# frontend is an effect edge followed by pure stages

documents ─▶ FcsCheck (effect: FCS, isolated)          ─▶ CheckedProject | fsharp.compiler errors
         ─▶ Admission (pure, syntax tree + rule catalog) ─▶ unit           | fsharp.unsupported_* errors (all of them)
         ─▶ TypeEvidence (effect: analysis-only FCS check) ─▶ CheckedEvidence | fsharp.unsupported_match_shape
         ─▶ Planning (pure: naming, SDK mapping, access, order) ─▶ PackagePlan | collisions, unmapped references
         ─▶ Lowering (pure: original syntax + checked evidence, generic over IIrBuilder) ─▶ requested family | morphir.unrepresentable

Admission collects every refusal before lowering. Planning does the whole-program work once, independent of the family. Lowering is total over admitted input with verified type evidence. Evidence failures stop before lowering; family representation failures come from the requested family's builder (MID-1). The stages compose with the check { } computation expression (DIAG-1). Admission and sibling nodes use the applicative and! form, so that independent problems are all reported. Every stage can add warnings and info diagnostics to a passing result. An example is an F# compiler warning such as FS0025 (incomplete match), which is kept as an fsharp.compiler warning beside the model.

Implementation note (task 3.4): planning reads the original syntax for structure and order, and the checked symbols (through the evidence project) for access and identity. Every F# module, including a nested module, is one Morphir module; namespace-level types and values of one namespace in several documents form one module. Module paths are the namespace and module names with the package path removed; an empty or foreign path gives fsharp.module_outside_package. Collision scopes are the package (module paths), each module's types, values and constructors, each record's fields, and the generic parameters of each type and value ('a and 'A would become one Morphir variable). A module-level binding must name one value; a tuple binding gives the catalog code fsharp.unsupported_declaration. A declaration with [<Morphir.MorphirName(name)>] (values, types, union cases, record fields and module segments) takes that name in canonical Morphir syntax; an invalid name gives fsharp.invalid_morphir_name. The attribute is in the new dependency-free Morphir.FSharp.Annotations package (netstandard2.0, C#); the compiler edge adds that assembly to its fixed references and records its version in the frontend identity, because user code must compile against it and a project cannot declare its own copy (a class, which admission refuses). Admission accepts MorphirName and CompiledName; CompiledName changes only the .NET name and never a Morphir name. An identifier with no Morphir words, such as a custom operator, and no MorphirName gives fsharp.unsupported_name, and an exposed module that matches no module gives compile.unknown_exposed_module. The plan holds a table from the package's own type, value and union-case symbols to FQNames for lowering. The caller parses the package name, for example with the canonical path parser (acme/car-rental is [["acme"], ["car", "rental"]]).

Implementation note (task 3.5): types are lowered from the checked FSharpType, never from syntax, and every type node takes the location of its nearest declaration (field, union case or abbreviation right-hand side). A type of the package, including an abbreviation, is lowered as a reference before any other check, because FCS answers IsTupleType and IsFunctionType through abbreviations. Other abbreviations are expanded. Records are type aliases of record types; unions are custom types whose constructor access follows the union representation's F# access; generated field names become arg-1, arg-2, and so on. A small table maps int, int64, bool, float, decimal, char, string, option, list and Result (error type first) to the Morphir SDK; task 3.7 folded it into the SDK mapping table. Any other type gives fsharp.unsupported_reference naming the F# type.

Implementation note (task 3.6): values are lowered from the original syntax by ValueLowering, generic over the builder. Types come only from the compiler, in this order: the typed expression at the same (mapped) range (TypedIndex over the evidence project's typed tree); for the head of an application, the compiler's argument and result types of the enclosing Call, Application or NewUnionCase (FCS reports the result type as the function type of an application of a generic value); the match evidence; the checked type of a non-generic value; and the checked type that the enclosing declaration expects (binding type, function parameter, branch). The type of a constructor used as a function is kept as checked parts, because FCS cannot create an FSharpType. An expression with no compiler type is refused with fsharp.unsupported_expression. Leading named parameters become value inputs; other parameter patterns (tuples, unit, constructors, as) become lambdas around the body, with types from the checked function type. A match-lambda becomes a lambda over a fresh subject-N variable and a pattern match. Task 3.7 adds operators and library functions through the SDK mapping table.

FSF-2. Original match syntax determines structure; FCS supplies checked evidence

The original range-join spike disproved the planned join. Ten of eleven probes fail because typed matches disappear, decision trees use subject ranges, or nested clause targets lose their full source range. Neither matching a larger enclosing range nor choosing a nearby target repairs this. The replacement proof reconstructs all eleven cases from original syntax with compiler-supplied types.

  1. Parse and type-check the original ordered documents with the hermetic FCS edge. Keep their syntax, symbols, diagnostics and source-node identities. Run admission on this original syntax. Original compiler errors stop the run; original warnings are published once.
  2. Enumerate original SynExpr.Match and SynExpr.MatchLambda nodes. Their subjects, clauses, patterns and bodies determine the emitted structure. Keep clauses in source order and recurse into original nested matches. Do not traverse DecisionTree targets to decide which clauses exist.
  3. Build an analysis-only copy to expose types that FCS reductions hide. Add a fresh as binding to each clause pattern for its subject type. Bind each clause result with match (originalBody) with | freshResult -> freshResult. This result witness preserves nonexpansive generalization, unlike an identity-function application. Check the copy with exactly the same references, language settings and ordered documents. It is never evaluated or emitted.
  4. Resolve generated witnesses by unique generated identity. Resolve original names and constructors through checked symbols at mapped original token locations. Instantiate generic union fields using the checked subject arguments and FSharpType.Instantiate. Checked constructor arity distinguishes separate fields from a single tuple-valued field. Tuple and list component types come from checked type arguments, never from a handwritten F# type solver.
  5. Verify that the analysis copy preserves original declaration signatures, generalization, constraints and resolved source references. Normalize generic identities across checks before comparison; never mix symbols from different checked projects. Every required type must be available and unambiguous. A generated-source error, changed original binding or missing/ambiguous evidence gives fsharp.unsupported_match_shape at the original match, with an explanation. No flattened, reordered or partially typed model is returned.
  6. Pass immutable evidence indexed by original document URI and syntax-node identity to the single lowering over IIrBuilder. Lower original patterns and bodies, with their original ranges. Other expressions use checked symbol/expression evidence; if reduction removed required expression types, expose them through the same checked-witness mechanism and verify them before lowering. Every value and pattern retains an inferred type. Builders receive no generated witnesses or analysis-copy locations. The subject is emitted once; the original evaluation structure and lexical scopes remain intact.

The supported patterns stay wildcard, variable, literal, tuple, constructor, empty-list, cons, as and unit, including function and let parameters. Guards, OR patterns and the other excluded patterns remain admission refusals. Source match-lambdas retain their implicit argument without inventing source clauses. Native classic and v4 builders and all IR writer registrations are unchanged (MID-1).

Generated identifiers are fresh across all supplied documents. An insertion map counts UTF-16 code units and maps symbol queries into the analysis copy; output ranges always come from original syntax. Nested edits must have deterministic nesting order. Production uses explicit syntax visitors, not the reflection walker in the spike. Generated diagnostics are internal evidence failures, never duplicate source warnings or exposed temporary paths.

Validation boundary. Task 3.1 proves match discovery, source order, pattern structure, subject/pattern/result types and original body spans. It also tests shadowing, generic field instantiation, computed and reduced-away subjects, generalization, constructor arity, fresh names, CRLF, UTF-16 mapping and evidence refusal. It does not qualify production expression lowering, native builders, diagnostics or MCK behavior. Tasks 3.2 and 3.6 must test those through the production API and both builders. Compiler upgrades rerun the proof.

Alternatives considered: typed decision-tree flattening duplicates or hides source structure; approximate range matching is ambiguous and misses erased matches; syntax-only lowering loses inferred types and symbol identity; identity-call witnesses change value generalization. The checked analysis copy costs a second compiler pass, but keeps FCS as the type oracle without requiring a compiler fork.

FSF-3. The unsupported-construct catalog is data

Each rule is a record: { Code; Construct; Message; Suggestion; Example; Detect }. Detect is an active pattern over syntax nodes, or a check of the document kind for .fsi files. The catalog is the single source for three things:

  • admission;
  • the generated coverage reference;
  • a corpus completeness test.

Codes use the ecosystem form <language>.<snake_case> and are stable once released.

#if directives are refused (fsharp.unsupported_conditional_compilation). This delivery does not take defines from project files, so the frontend must not pick a branch silently.

Implementation note (task 3.3): a rule also holds Flagged (the source text at the range of its example's diagnostic) and IsFallback. A detector returns findings with a Report range (the diagnostic) and a Scope range (the refused construct). A finding inside the scope of another finding is not reported, so one refused construct gives one diagnostic; for example, members inside a refused class are not reported again. Modifier rules (mutable, inline, attributes) report the keyword or the attribute. Four fallback rules (fsharp.unsupported_expression, _pattern, _type, _declaration) refuse any node outside the supported subset that no specific rule refused, so lowering only receives admitted syntax. A detector can read the original checked symbols at a range; active-pattern uses and measure annotations need them. Each diagnostic's data names the construct. Evidence keeps its own refusal for an unsupported pattern as a second line of defense. A follow-up change, add-fsharp-morphir-analyzers, reuses this catalog in an FSharp.Analyzers.SDK analyzer and an MSBuild target.

FSF-4. SDK mapping is a reversible table, checked against the generators

One table maps F# symbols, by their full compiled name, to Morphir SDK FQNames and arity. Pipes and composition are lowered structurally. A property test checks each entry against tests/Fixtures/MorphirSDK/inventory.json, and checks that the existing F# generator's forward table (TargetSyntax.sdkValue) maps it back to the same operation. Overloaded numeric operators are resolved by the inferred operand type. This is the same pattern as Fable's Replacements table, scoped to the Morphir SDK.

Implementation note (task 3.7): the table keys a function or operator by its declaring entity and compiled name (Microsoft.FSharp.Core.Operators.op_Addition), a union case by its union type and name, and a type by its full name. An overloaded operator selects its entry by the compiler's type of its first operand: + is Basics.add on int and float, Decimal.add on decimal and String.append on string; / is Basics.integerDivide on int; comparisons need an operand of the SDK comparable profile, so decimal comparison is refused. Each entry has a tier. A contract entry is an operation of the reviewed .NET SDK inventory with the same arity. An entry outside that contract names its reason; these are Basics.not and identity, String.append and length, and the Int64 and Char types. A table test also checks that the F# type of every entry lowers to Morphir; String.concat takes a sequence, so it is not mapped. The generator round trip compiles each spelling that TargetSyntax writes and checks that the frontend maps it back to the same SDK name, so the F# generator gained the forward entries it lacked. Some, None, Ok and Error are SDK constructors in values and patterns; :: in a value is List.cons. x |> f and f <| x become f x, and f >> g and g << f become a lambda over a fresh variable, with the types of the compiler's operator call. a && b becomes if a then b else false and a || b becomes if a then true else b: the SDK Basics.and and or evaluate both operands, which would lose F# short-circuit evaluation. The F# generator writes Basics.negate as checked negation, as the SDK contract requires. An unmapped function, operator, union case or .NET member gives fsharp.unsupported_reference naming the F# symbol, at the whole call when it is applied.

FSF-5. Hermetic, deterministic FCS configuration

  • The project options are made in memory, from the ordered source selection. The frontend never reads the project file.
  • The references are the hosting runtime's trusted platform assemblies plus the bundled FSharp.Core. Implementation note (task 3.2): only the trusted platform assemblies in the shared-framework directory are used (task 3.4 adds the Morphir.FSharp.Annotations assembly), so host assemblies such as the compiler service or Morphir libraries are never visible to user code.
  • Sources are given to FCS through an in-memory file system under a virtual root, so absolute host paths never reach a range or a model. Implementation note (task 3.2): the checker reads sources through DocumentSource.Custom, which FCS marks experimental (FS0057). It does not replace the process-wide file system. Each request has its own virtual folder, removes its sources and clears its project caches when it ends, and replaces virtual paths in compiler messages with document URIs.
  • The language version and warning options are fixed.
  • One FCS checker is used per process. Original and analysis-copy checks use separate project identities over the same captured document set, with the same options and no evaluation.
  • Use a supported exact FCS/FSharp.Core package pair. The spike locally uses 43.12.403/10.1.403. The repository currently pins 34.1.1/11.0.100; production integration must resolve that incompatibility explicitly and rerun the compatibility and host tests. Do not suppress NU1608 or silently alter the central Core pin. Resolution (task 3.2): the central pins are now FSharp.Compiler.Service 43.12.403 and FSharp.Core 10.1.403. FSharp.Core 11.0.100 is unlisted on NuGet, and no stable compiler service depends on an 11.x Core (43.13.101 is a release candidate that needs 11.0.101-rc3). No project used the 34.1.1 compiler API. The whole solution builds with the new pair, and Renovate updates the two packages as one group (fsharp-compiler).
  • Frontend identity records compiler service, Core, runtime and evidence-transform revisions. Analysis-copy source and maps are request-local, bounded and cancellation-aware. Compiler diagnostics from original documents remain authoritative.

CLI-1. One mediator handler owns compile orchestration

CompileCommand only captures the overrides, calls the mediator and renders the result. CompileHandler.Handle runs these stages, each returning Outcome<T>:

  1. settings
  2. source selection (SRC-1)
  3. source capture
  4. frontend resolution
  5. frontend compile, which builds the requested family
  6. writer
  7. record and publication
  8. optional generation

Pure stages return Checked (DIAG-1). The compile runner emits each stage's result as events (STRM-1), and the handler folds them into the Tooling Outcome<T>. It adds the warnings, info and hints of every stage that passed to the success record and to any later failure, so the report holds every diagnostic of the run.

Settings. ProjectCompileSettingsResolver uses the existing ProjectSystem.Discover/LoadDetailed and the CLI overrides, and it records where each setting came from. It parses --ir-version and ir.format_version with SourceFormatVersion.parse. The schema keeps ir.format_version as an integer or a SemVer string; the current "1–10" integer range in the schema is widened for SemVer.

Source capture reuses the bounded capture core from BoundedModelCapture, extracted into a shared helper.

Reporting follows GenerationReport. GenerationDiagnostic gets an optional, additive Range.

CLI-2. --target composes compile with the unchanged generation stages

After a successful compile and publication, the handler gives the exact bytes that were written to the same IModelLoader that generate --input uses. That loader produces the LoadedModel: the VersionedModel, its descriptor, representation Json, and RetainedInput.File. Classic bytes give a classic model, which reaches the backend's native classic path.

It then calls the shared tail of the generation pipeline, which moves out of GenerateHandler into GenerationStages.runFrom. The backend therefore sees exactly what generate --input would see.

The flag is --generate-output, because -o already means IR installation in the ecosystem compile command. Multi-target runs are deferred to morphir build.

MEP-2. One session core, verified envelopes, a deterministic context

Session core. The guest loop and the host client share a pure state machine, step : State -> Message -> State * Reply list. The process edge has these parts:

  • the host starts the guest with ArgumentList, with no shell;
  • bounded frame reads and a stderr pump;
  • a deadline per request;
  • termination of the process tree on timeout.

The guest redirects Console.Out before FCS starts.

Envelopes. Admission of a MorphirModel is one pure function, run in the upstream order:

  1. the outer frame limit;
  2. base64 bounds and canonical form;
  3. decoded length, then SHA-256;
  4. JSON decode under depth and node limits;
  5. profile, envelope version, IR version and critical paths.

Only after all of these does the existing reader decode the IR.

Context and identity.

  • The host computes contextDigest as the SHA-256 of an RFC 8785 canonical JSON object. That object holds the language id, the source root, each document's URI and text SHA-256 in order, the package, the exposed modules, the options and the output tuple. The construction is documented and tested so that peers agree on it.
  • The guest sets modelId to the package name.
  • The guest sets revision to the SHA-256 of the context digest plus the frontend identity and version. It is deterministic, and it is not the payload digest, as upstream requires.

MEP-3. Versions without a tuple; conformance comes from the contract, not the guest kit

The F# guest claims JSON compileModel tuples for 3.0.0 and 4.0.0. Classic format versions 1 and 2 have no defined tuple spelling, and no upstream host requests them. For those, the host compiles at 3.0.0, decodes the classic model, and writes it with the requested version's wire profile. This is exact re-encoding within one family, which upstream allows, not a conversion between families. A guest that admits only 4.0.0 cannot serve a classic request, and the host refuses before dispatch. The parity tests compare every result with the in-process path.

Conformance comes from the contract, through the MCK. The guest and the host are checked by MCK cases written here against the pinned 0.2.0-draft.1 contract (the mep.ir.json types). The Smithy session transcripts and model-transport.cases.json are imported as reviewed inputs (MCK-1).

The upstream MEP guest kit (generic-json-library-v1, run by morphir mck mep guest-run) is behind that contract:

  • It requires a legacy 0.1 stage.
  • It requires the guest to be both a frontend and a backend for its language.
  • It covers only a two-constant Bool library.

So the kit does not shape this design. The guest stays frontend-only and speaks only 0.2.0-draft.1. No backend is added and no kit language is patched locally to pass it, and the kit's expected IR is not a writer oracle. The upstream request is to update the kit to the current contract. Kit qualification follows after that update, and it does not block this change.

MCK-1. The corpus is the first Morphir Compatibility Kit suite, and the case data is the oracle

morphir-dotnet is to become the home of the Morphir Compatibility Kit (MCK) and of the conformance oracle. The full kit is planned in the separate change establish-morphir-compatibility-kit. This change seeds its first suite, F# compilation, with the minimum case format and runner that the suite needs, and does not wait for the kit change. The rule is the same as in the existing dotnet-sdk-conformance spec: the oracle is independently written case data, never an implementation, including this one.

Location and format. The suite lives in conformance/suites/frontend-fsharp/, a versioned product directory, not test fixtures. The normative case format is Gherkin, the format of the upstream IR v4 kit already pinned in tests/Fixtures/MorphirIon/kit. The decision MCK-FMT and its generalization belong to establish-morphir-compatibility-kit.

  • Cases. Each scenario name starts with a stable id, frontend-fsharp-NNNN. Tags carry the kind of case (for example @semantic, @refusal).
  • Steps. Steps come only from a closed, versioned MCK step vocabulary (conformance/steps/steps-1.md). A linter rejects any other step, and every runner implements the vocabulary. This change adds only the steps that the F# suite needs.
  • Artifacts. Small artifacts, such as F# sources and short expected IR, are docstrings with a content type ("""fsharp, """json). Large expected IR documents are sidecar files (expected/<id>/ir-<version>.json) that a step references. An optional .fsproj is a sidecar file too.
  • Matrices. Scenario Outline with Examples expresses IR version and input kind. Combinations that are excluded go in an @excluded Examples block with a reason column.
  • No adapters in features. A feature never names an adapter. The implementation under test is chosen when the runner starts.
  • Expectations. All expectations are written by hand, never produced by any writer:
    • IR, per format version;
    • diagnostics, compared by severity, code and range, but not by message text;
    • call results, as JSON values in steps.

Refusal scenarios come from the rule catalog (FSF-3). A completeness check fails on a missing row (catalog code × IR version × input kind) that has no stated reason. The MCK change generates literate Markdown pages for the docs site from these features. They are never edited by hand.

Runner and adapters. Morphir.Conformance is AOT-compatible. It loads cases, drives an implementation under test, and compares results with the expectations. It has three adapters:

  • library: the .NET frontend, in process;
  • cli: any morphir executable, through compile --json-lines (STRM-2), the compile record and the written IR;
  • mep-guest: any stdio guest that speaks MEP 0.2.0-draft.1.

The same cases can therefore qualify the Rust CLI or another guest, not only morphir-dotnet. The repository's own tests call the same runner, so there is no second harness.

Kit verdicts are portable, and any implementation can be checked against them:

  1. Structural: the result matches the expected IR under the kit's comparison rules. Object member order is ignored, and classic name-keyed lists are compared without order. Where a case has no hand-written IR for a version, it falls back to a round trip through that version's reader plus schema validation, which is .NET only. The upstream IR examples pinned in tests/Fixtures/MorphirIon are also checked.
  2. Diagnostics: the expected severities, codes and ranges are present, and no unexpected error appears.
  3. Behavioral: the case's call observations hold. The .NET runner checks them by generating F# from the compiled IR and running it. The expected values are data, written to equal the results of the original F# source.

morphir-dotnet checks apply only to this implementation and are not kit verdicts:

  • the round trip IR → F# (through the Fantomas-based backend) → IR;
  • parity: the in-process and MEP outputs are byte-equal, the compile --target and two-command outputs are byte-equal, and project-file and explicit-file inputs give the same IR.

Reports. Each run writes a deterministic verdict report. It records the kit format version, the SHA-256 of the case set, the identity of the implementation (the executable path, its SHA-256 and its reported version, or the library assembly and version), and one verdict per case, adapter and IR version. The PRD records these reports as viability evidence (see docs/adr/ and the default-CLI PRD).

Upstream inputs. Upstream transcripts, model-transport cases and IR examples are imported as reviewed inputs with provenance. They never override case expectations. When an upstream implementation or kit disagrees with the contract or with intended behavior, the disagreement is recorded with evidence in conformance/deviations.md, and the kit here is the reference. Examples: the Rust CLI's --json-lines, and the guest kit's mandatory legacy stage.

Delivery order

The order follows the maintainer priority: the F# frontend is solid in the dotnet tool before MEP depends on it.

  1. Versions, builders and writers. FormatVersion rules, the IR builder interface with the native classic and v4 builders, and the IR writers. These are independent of F#.
  2. Frontend core. The F# frontend through the library API, with the corpus, the catalog, the coverage documentation and the round-trip oracle.
  3. Tool path. dotnet-morphir compile with project-file sources, configuration, the report, records and -o. Then generate from the record, then compile --target. This completes the steel thread without MEP.
  4. MEP 0.2.0-draft.1. The codec, envelope and session core, then the guest, then the AOT host client, then parity, contract conformance and the AOT publish check.

Risks and trade-offs

RiskMitigation
Analysis witnesses could alter inference, generalization or name resolution; nested edits could corrupt locations.The replacement spike covers the original eleven cases and targeted counterexamples. Production checks original bindings and symbol identity, uses deterministic fresh names and UTF-16 maps, and rejects invalid evidence with fsharp.unsupported_match_shape. The normal corpus still has to pass through both native builders. Guards and OR patterns stay refused.
A second FCS pass adds memory and latency.Capture documents once, reuse the process checker, bound generated-source growth and honor cancellation. Measure original checking and evidence checking separately on the frontend corpus before release.
Lowering code that is generic over the builder interface is harder to read and debug than code that builds a tree, and there is no intermediate tree to inspect.Keep the interface at one member per node of the supported subset. Use the v4 builder's output, which keeps source spans, as the debugging view. Builder unit tests check each member natively. The frontend lowering is tested through both builders with the same corpus. The compiler enforces that every builder implements every member.
Until upstream aligns, --json-lines gives different output in the .NET CLI and the Rust CLI.The completed record holds the full report, so a consumer that reads only the last line still works. The CLI reference documents the difference. An upstream issue proposes the STRM-2 format as the shared meaning, and the .NET CLI aligns with any refinement upstream agrees.
The streamed diagnostics and the folded report could drift apart.The report is computed only as the fold of the stream (STRM-1), never by a second path. A corpus-wide property test checks the fold against the batch path.
MSBuild evaluation runs project logic, and the SDK version can change evaluation.The provider runs only on a project file the user named, never on a discovered one. It uses evaluation only (no targets, no restore, no node reuse), with a deadline and bounded output. The SDK version is recorded in the report. A missing SDK gives a clear error.
0.2.0-draft.1 is a draft and matches only itself. Upstream can refine it in place.Pinned fixtures with provenance. The DTOs are checked against the pinned mep.ir.json. A scheduled check compares the pin with upstream and opens an issue when it changes. All protocol code is in Morphir.Mep, behind the stable in-process contract.
No upstream kit qualification yet, because the MEP guest kit is behind the contract.Conformance is checked against the pinned contract (types, transcripts, model-transport cases). The design is not bent to fit the kit. An upstream request asks to update the kit (MEP-3).
Pre-release format versions might be compared loosely somewhere.One equivalence function (VER-1) with property tests, and no int version in any contract. Exact declarations are required for selection.
FCS reference resolution can differ between runtime versions.Hermetic references. The FSharp.Core and runtime versions are part of the frontend identity and the MEP revision.
FCS writes to the console, which corrupts MEP framing.The guest redirects the console before FCS starts. A misbehaving-guest host test covers this.
The JIT tool installs a large dependency (FCS).Only Morphir.Tool and the guest carry it. A CI closure check keeps the AOT executable free of it.
Records shared with the Rust CLI could conflict.Same lock files and modes, unknown members preserved, and interop tests against the pinned upstream examples.

Migration plan

  • All changes add something new. Existing generate --input runs behave exactly as before.
  • Only a generate without --input changes: today it fails with the missing-input error, and after this change it reads the compile record.
  • ir.format_version accepts SemVer strings as well as the current integers. Existing integer values keep their meaning.
  • Rollback: remove the scenario registrations. No IR, configuration or wire format changes.
