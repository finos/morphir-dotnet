Context

See proposal.md for the motivation. This change builds only on what add-diagram-canvas-export provides:

  • the drawable layout, with distances in quarter EMU and ToEmu(), normalised PathData with WithoutArcs, and DiagramLayout.Svg
  • RenderPlan with EnsureFor, DiagramRenderer with its two modes, and the public Diagnostic.Error and Diagnostic.Warning factories, which this package uses for slides/raster-failed
  • lowering, the three policies, and LayoutFeatures

DiagramRaster turns SVG into PNG. It is synchronous, refuses renders over its pixel and work limits, and caps scale at 16. Its pixels are deterministic, but its PNG bytes are compressed with the runtime's zlib (Encoders.fs), so they can change between .NET versions.

BPMN layouts take their coordinates from the DI, which can be negative, while the SVG's view box starts at zero.

Each SVG's ID prefix includes a fingerprint of its content, so the same diagram twice gives the same IDs.

Goals and non-goals

Goals:

  • Native, editable shapes in every slide format that allows them.
  • One placement model, with exact containment.
  • No third-party dependency and no network access in the library.
  • Failures reported before any output is written.

Non-goals:

  • Inserting into an existing .pptx or .odp.
  • Slide animations from playback steps.
  • reveal.js fragments.
  • Speaker notes.
  • Laying diagrams out again at a larger base size.

Decisions

The worked example is the flowchart from the canvas design, laid out at 420 by 120 px and placed on a 16:9 slide.

PLC-1. Placement is an exact rational fit on the target's grid

The content area of a 16:9 slide is 10,160,000 by 5,715,000 EMU. The example measures 4,000,500 by 1,143,000 EMU, so the width decides the fit.

Placement works in four steps:

  1. It takes the fitted extent: the union of the layout's bounds and the geometry of every drawable. A BPMN task at x = -40 widens the extent to the left. Stroke widths and heads are left out, because they don't scale.
  2. It rounds the area inwards onto the renderer's grid: whole EMU for PowerPoint and Google Slides, and 36 EMU (0.001 mm) for OpenDocument, whose lengths are written in millimetres with three decimals. An area that is empty after rounding is refused.
  3. It takes the fit factor as the exact ratio areaWidth / extentWidth or areaHeight / extentHeight, whichever is smaller, as a numerator and denominator. A smaller maximum scale replaces it. The centring offset is half the spare space, rounded down onto the grid.
  4. It maps each absolute coordinate x to areaLeft + offset + round((x − extentLeft) × numerator / denominator), rounding once onto the grid, half to even, with 128-bit intermediates. A size is the difference of its two mapped edges, never rounded separately.

The mapping is monotonic, and it maps the extent's far edge exactly onto the area's far edge when that side decides the fit. So every mapped edge lies within the rounded area, at the output's own precision. Only strokes, joins and heads can reach past it, by at most half a stroke width times the miter limit plus a head's length, which the spec states.

Positions, sizes, waypoints, path points, radii and font sizes scale. Stroke widths, dash lengths and arrowhead sizes don't.

This trades exact equivalence with laying the diagram out again for simplicity. The writers use fixed paddings and an integer text-width estimate, so a real re-layout at a larger size would differ slightly. Scaling keeps the diagram exactly as drawn, only larger, with strokes kept light.

PKG-1. Hand-written packages, no SDKs

All four renderers live in Morphir.Diagrams.Slides.

  • ZIP formats: OOXML and ODF packages are built in a MemoryStream, with ZipArchive, a fixed entry order and the timestamp 1980-01-01. They are then copied to the output, so the bytes don't depend on whether the output can seek.
  • Determinism: whole bytes are equal within one .NET runtime on one operating system. The bundled zlib can change between runtime versions, and ZipArchive records the platform in each entry's version-made-by field. That affects the ZIP and the PNG images inside it. Across operating systems, the tests compare entry names, the uncompressed contents of every entry other than a PNG, and the decoded pixels of each PNG.
  • Images first: every PNG fallback is drawn before the first byte is written, so a raster failure writes nothing.
  • Test-only SDK: the tests use the Open XML SDK's OpenXmlValidator, as a test-only dependency.

OrderShapes are written in paint order. Layout elements and groups are flattened, so PowerPoint declares interleaved painting.

PNG fidelity: the PNG comes from Morphir.Diagrams.Raster, which knows seven colour names and paints a gradient as its first stop. Before rasterising, the renderer checks the image's SVG with the painter's own supported-paint check, made visible to Morphir.Diagrams.Slides through InternalsVisibleTo, and warns slides/png-approximated for each image that it approximates. The raster painter's output does not change.

PNG size: the PNG is drawn at two pixels per placed CSS pixel. If that exceeds the raster limits, it is drawn at one. If that fails too, the render returns slides/raster-failed and writes nothing. The spec states the same rule. A test covers the pixel limit and the work limit separately. The token is checked before each image.

Validation: each package is validated as Microsoft 365 and as Office 2010. Extension lists are the ignorable part of DrawingML, so the Office 2010 validator and readers skip the SVG blip. If task 2.1 finds the validator rejects it, the package declares the SVG namespace in mc:Ignorable, and the spec changes with it. Task 2.3 also opens the package in a reader that shows only the PNG.

ODP-1. The OpenDocument mapping

  • Shapes: each is a draw:custom-shape whose draw:enhanced-geometry carries a svg:viewBox and a draw:enhanced-path.
    • A shape kind gets a path we write ourselves: the cylinder from two half-ellipses and two lines, the hexagon from six points, and so on. It also gets draw:type (can, hexagon and so on) as a hint to Impress.
    • A path converts its normalised data after WithoutArcs: M, L, C, Q and Z keep their letters, an open subpath ends with N, and an unfilled path adds F. The view box is the path's box in thousandths of a millimetre.
  • Connectors: draw:connector with the start and end shape and the nearest glue point, and the exact path as svg:d.
  • Markers: each arrowhead is a draw:marker in the styles. Markers belong to the connector, so every head follows it, and ODP declares both head features. ODF fills markers and never strokes them, so filled heads keep the SVG marker's outline, and stroked heads (the open arrow, the cross, the async and open half heads) become the closed outline of their stroke at the marker's 1.4 px width. ODF draws a marker with its view box's top centre at the line's end, pointing along the line, so each outline is rotated and offset from the SVG marker's frame. Task 3.3 confirms the placement in Impress.
  • Opacity: draw:opacity for fills. Text has no standard opacity, so ODP doesn't declare stroke and text opacity.
  • Package: mimetype first and stored uncompressed. A test reads the raw local header to confirm the extra-field length is zero. If ZipArchive ever writes one, the renderer writes that one header itself.

GSL-1. Google Slides as a request body

The body starts like this (the numbers are illustrative):

{ "requests": [
  { "createSlide": { "objectId": "flow_0_s0", "slideLayoutReference": { "predefinedLayout": "BLANK" } } },
  { "createShape": { "objectId": "flow_0_d1", "shapeType": "ROUND_RECTANGLE",
      "elementProperties": { "pageObjectId": "flow_0_s0",
        "size": { "width": { "magnitude": 2209800, "unit": "EMU" }, "height": { "magnitude": 1066800, "unit": "EMU" } },
        "transform": { "scaleX": 1, "scaleY": 1, "translateX": 1016000, "translateY": 2324100, "unit": "EMU" } } } },
  { "insertText": { "objectId": "flow_0_d1", "text": "Start" } }
] }
  • IDs are {namespace}_{page}_{kind}{index}, where the kind is s for a slide or d for a drawable. A namespace of 2 to 30 ASCII characters, up to 9,999 pages and up to 9,999,999 objects per page keeps every ID between 7 and 44 characters. The renderer checks both limits before writing and refuses a plan over them.
  • Options types: SlideObjectNamespace and SlideObjectId are parsed values with Parse, TryParse and Create, taking string | null. An existing slide ID can be as short as one character, since Google's own first slide is often p.
  • No groups: the renderer writes no groupObjects, so paint order stays page-wide and the renderer declares interleaved painting.
  • Page size: the caller supplies it, because a presentation has one page size and createSlide cannot set it.
  • Uniqueness: the caller chooses a namespace that the presentation doesn't use yet, which repeat submissions need too. The renderer can't check that.
  • Order: the body creates every slide and object first, in paint order, then inserts text and sets styles, and sets line connections last. Google runs the requests in order, and the flowchart paints links before nodes, so a connection set straight after its line would name shapes that don't exist yet.
  • Lines: createLine with the STRAIGHT category, then updateLineProperties connections at the nearest site and the FILL_ARROW, OPEN_ARROW or FILL_CIRCLE arrow styles. Google has no cross or half heads, so message heads arrive as arrows. Task 4.2 checks the site order through the API.
  • Text: Roboto Mono as the monospace font, sized in points.
  • Images: none, because createImage needs a public URL.

REV-1. reveal.js shows the original SVG, with section-scoped IDs

For section n, the renderer copies the layout's SvgDocument and replaces the document's ID prefix (kind-fingerprint) with sn-kind-fingerprint. The prefix appears in every element ID, every href and url(#…) reference, and every ID selector of the style sheet. Because it is one distinct token, a single substitution in attribute values and style text makes every ID unique in the deck.

Each SVG has the r-stretch class, so reveal.js fits it to the slide.

The renderer uses the contract's original-SVG mode. It receives each page unlowered, declares no features, and its assessment is native for any diagram, without claiming editable connectors or links that the deck doesn't have. A newer Morphir.Diagrams with new features is still native, because the mode doesn't depend on the feature set. The default base address is https://cdn.jsdelivr.net/npm/reveal.js@5.1.0/. Task 5.1 confirms the release and its template.

Risks and trade-offs

RiskMitigation
A hand-written .pptx triggers a repair prompt.The validator runs on every corpus package, and the files are opened by hand in PowerPoint and LibreOffice.
ZIP and PNG bytes change with the .NET runtime.Byte equality is scoped to one runtime. Across runtimes, the tests compare entry contents other than PNG, and PNG pixels.
Raster limits refuse a large PNG.Density is reduced first. Failure is reported before any output.
Connection site and glue point indices differ from the design's assumptions.Tasks 2.4, 3.3 and 4.2 check them before goldens are recorded.
Impress drops svg:d or re-routes glued connectors when it opens or edits a file. This is unverified.Task 3.3 checks both. If either happens, the renderer stops declaring polylines and exact routes, and the spec changes with it.
Office and Google fonts measure text differently.Text wraps within its box, the typeface is an option, and the README notes the difference.
A CDN outage blocks reveal.js.The base address is an option, and the README shows a local copy.

Migration plan

  • The change only adds API and one package. It lands after add-diagram-canvas-export has merged.
  • The package joins LibraryPackages after Morphir.Diagrams.Raster.
  • To roll back, revert the change.

Open questions

  • The default PowerPoint typeface (Consolas or another font that Office ships). It is an option either way.
