Context

See proposal.md for the reason. The requirements are in specs/extension-registry/spec.md. The current state:

  • One composition, two hosts. src/Morphir/Program.cs builds the CLI with MorphirCli.CreateBuilder(...).AddScenario<...>(). dotnet-morphir (src/Morphir.Tool/Program.cs) calls Morphir.Program.Main(args), so the two hosts cannot tell themselves apart today. VersionInfo is internal to each entry assembly, so Morphir.Tooling cannot read the host version.
  • Backends are already static. GenerationScenario registers FSharpGenerationBackend and CSharpGenerationBackend as IGenerationBackend through TryAddEnumerable. Each has a BackendDescriptor with Identity (morphir.csharp, morphir.fsharp), Target and per-family BackendCapability version sets. RegisteredBackendResolver selects from the same set.
  • The extension command is static. ManagementScenario.CreateExtensionCommand() builds it with no service provider. HandleExtensionList prints two fixed lines. The records in Features/Management/ExtensionCommands.cs and ExtensionHandlers.HandleList have no callers.
  • Hosted commands exist. MorphirCliBuilder.AddCommand(Func<IServiceProvider, Command>) builds a command after the container is built. GenerateCommand uses it.
  • MEP shape. The MEP contract (spec/mep/contract/src/mep.gleam in finos/morphir, 0.2.0-draft.1) defines ExtensionInfo { id, name, version, description?, types, author?, homepage?, license?, min_sdk_version? }, ExtensionType with the wire values frontend, backend, transform, validator, workspace, and BackendCapability { targets, ir_versions, generate }.
  • Constraints. The morphir executable is Native AOT and trimmed. No reflection-based discovery, no assembly loading. JSON uses source-generated contexts. Stdout carries command output only.

Goals and non-goals

Goals: one registry type that the later PRD steps extend (configured extensions in step 2, installed extensions in step 3) without a change to its shape; one source of truth for generator identity, shared with generate; a host identity that both hosts set explicitly.

Non-goals: the selection rule; changes to RegisteredBackendResolver; MEP wire types or JSON-RPC; any external runtime; registration of the pipeline plugins (PLG-1).

Decisions

REG-1. Own registry types in the shape of MEP, mapped to Morphir.Mep later

Add types in src/Morphir.Tooling/Features/Extensions/:

public enum ExtensionType { Frontend, Backend, Transform, Validator, Workspace }   // MEP wire values, lower case
public enum ExtensionDelivery { BuiltIn }                                          // more values in later steps
public enum MorphirHostKind { Native, DotnetTool }                                 // "morphir", "dotnet-morphir"

public sealed record ExtensionIdentity(string Id, string Name, string Version, string? Description,
    ImmutableArray<ExtensionType> Types);                                         // MEP ExtensionInfo subset

public sealed record BackendClaim(ImmutableArray<string> Targets, ImmutableArray<string> IrVersions, bool Generate);
public sealed record ExtensionClaims(BackendClaim? Backend);                       // other claims in later steps

public sealed record ExtensionEntry(ExtensionIdentity Identity, ExtensionDelivery Delivery,
    ImmutableHashSet<MorphirHostKind> Hosts, ExtensionClaims Claims);

The identity holds only the MEP members that a built-in fills now. author, homepage, license and min_sdk_version come when a step needs them. Delivery, hosts and availability are morphir-dotnet additions. They are not MEP members and never go on the MEP wire.

When Morphir.Mep lands (PR #495), add one mapping function from ExtensionIdentity and ExtensionClaims to the MEP ExtensionInfo and ExtensionCapabilities. Do not replace the registry types: they carry the additions.

Alternatives: wait for Morphir.Mep (blocks step 0 on PR #495, which the PRD rules out); use the MEP types directly when they land (they cannot carry delivery and hosts); reuse Features/Management.ExtensionInfo (it models installed versions per platform, not identity).

REG-2. Static registration through IExtensionSource

Each source gives entries. The container holds them through TryAddEnumerable:

public interface IExtensionSource { IEnumerable<ExtensionEntry> Entries { get; } }

public sealed class ExtensionRegistry(IEnumerable<IExtensionSource> sources, MorphirHost host)
{
    public Outcome<ExtensionCatalog> Read();   // all entries, ordinal sort by id, unique ids
}
public sealed record ExtensionCatalog(MorphirHost Host, ImmutableArray<ExtensionEntry> Entries);

Read returns a failure with code extension.duplicate_id that names each duplicate id. The command maps that failure to exit code 2. available in the report is entry.Hosts.Contains(host.Kind).

Alternatives: assembly scanning or MEF (not AOT-safe, and the PRD forbids it); attributes plus a source generator (more machinery than two built-ins need; can come later without a change to IExtensionSource); a static list in Program.cs (drifts from the backend registrations).

REG-3. Backend entries come from the registered backends

BackendExtensionSource takes IEnumerable<IGenerationBackend> and makes one entry for each backend: id from Descriptor.Identity, type backend, delivery built-in, both hosts, version from MorphirHost.Version, and BackendClaim([Target], versions, true). The IR versions are the union of the version strings of the descriptor's capabilities, in ordinal order, exactly as the backend declares them (for example 3 and 3.0.0 both appear). They are not normalized.

Add two optional init properties to BackendDescriptor: Name (default: the identity) and Description (default: none). The two backends set "C# generator" and "F# generator". This keeps one source of truth, so the spec requirement "the list agrees with generation" holds by construction, and a test checks it.

Alternative: a separate built-in table with names and ids (two lists to keep in step).

HOST-1. Each entry point states its host

public sealed record MorphirHost(MorphirHostKind Kind, string Version)
{
    public string CommandName => Kind switch { MorphirHostKind.Native => "morphir", MorphirHostKind.DotnetTool => "dotnet-morphir",
        _ => throw new ArgumentOutOfRangeException(nameof(Kind)) };
}

// src/Morphir/Program.cs
public static int Main(string[] args) => Run(args, new MorphirHost(MorphirHostKind.Native, VersionInfo.Version));
public static int Run(string[] args, MorphirHost host) { /* existing body; registers host as a singleton */ }

// src/Morphir.Tool/Program.cs
private static int Main(string[] args) => Morphir.Program.Run(args, new(MorphirHostKind.DotnetTool, VersionInfo.Version));

If PR #495 has landed when this change is applied, add the host to its CreateApp(string[] args, Action<MorphirCliBuilder> extend) seam instead of adding Run. The behavior is the same. --version stays as it is.

Alternatives: read RuntimeFeature.IsDynamicCodeSupported (true for a JIT test run of the morphir project, so it reports the wrong host); read the process name (it is dotnet when the tool runs as dotnet dotnet-morphir.dll).

HOST-2. Entries declare their hosts; availability is computed

An entry lists the hosts it runs in. A host lists every entry it knows, including entries for the other host only, and marks those as not available. This is what the PRD selection rule needs later: the AOT host can then say "not available in this build" and name the alternative. In this change all real entries have both hosts. A test source registers an entry with only DotnetTool to cover the requirement.

Rule for later steps: an entry for one host only is declared in shared code (Morphir.Tooling), and only its implementation is bound in that host's composition.

CLI-1. extension list becomes a hosted command

ManagementScenario keeps the static extension command for install, use, remove and which, and adds list to it as a subcommand built from the service provider. If the builder cannot add a hosted subcommand to a static parent, the scenario builds the whole extension command through AddCommand(Func<IServiceProvider, Command>); the four other subcommands do not change.

ExtensionListCommand keeps --platform and --local (they apply to installed extensions, and none exist before PRD step 3) and adds --json. The handler reads the registry and renders:

$ morphir extension list
ID              NAME           VERSION   TYPES     DELIVERY   HOSTS
morphir.csharp  C# generator   0.4.0     backend   built-in   morphir, dotnet-morphir
morphir.fsharp  F# generator   0.4.0     backend   built-in   morphir, dotnet-morphir
{
  "host": "morphir",
  "extensions": [
    {
      "id": "morphir.csharp",
      "name": "C# generator",
      "version": "0.4.0",
      "types": ["backend"],
      "delivery": "built-in",
      "hosts": ["morphir", "dotnet-morphir"],
      "available": true,
      "capabilities": {
        "backend": { "targets": ["csharp"], "irVersions": ["1", "2", "3", "3.0.0", "3.1.0", "4", "4.0.0"], "generate": true }
      }
    }
  ]
}

The report record and a source-generated ExtensionListJsonContext (camelCase, indented, description left out when null) live beside the command. Enum values are written through explicit string mapping functions, not a reflection-based converter. The member names inside capabilities.backend are the MEP wire names. A failure writes {"host", "extensions": [], "diagnostics": [{"code", "message"}]} with --json, or one line on stderr without it, and exits 2.

Alternative: a new morphir extension info command (the PRD names list; one command is enough).

PLG-1. The pipeline plugins are not registered in this change

The PRD lists the plugins in src/Morphir.IR.Pipeline.Plugins as first built-ins. They are not registered here, because no CLI command runs them: Morphir.Tooling does not reference that project, and the plugins are a library API (Plugin<'T>) used inside the F# generator. An entry with a validator or transform type that no command can run would be a false capability claim. PRD step 1 registers TypeValidator as a validator entry when the in-process validator contract and its command exist. The PRD is updated with this decision when this change is approved.

CLN-1. Remove the unused list records

Remove ExtensionList, ExtensionListResult, ExtensionInfo and ExtensionHandlers.HandleList from Features/Management/. They have no callers, and ExtensionInfo would be confused with the MEP record. The install, use, remove and which records stay until PRD step 3.

TST-1. Tests in both hosts

  • Unit tests (tests/Morphir.Tooling.Tests/Features/Extensions/): backend adapter mapping, sort order, duplicate ids, availability for a one-host entry, report JSON round trip, text rows.
  • Agreement test: every backend target in the registry resolves through RegisteredBackendResolver for at least one declared model, and every registered backend has an entry.
  • Executable tests (tests/Morphir.E2E.Tests): a feature that runs extension list --json and parses stdout. Today the locator finds only the morphir executable. Add a tool executable type that runs the built dotnet-morphir, and run the feature for both. Compare the shared entries of the two results.
  • The AOT publish keeps zero new trim and AOT warnings.

Risks and trade-offs

RiskMitigation
PR #495 changes Morphir.Program at the same time (CreateApp).HOST-1 names both paths. The change is a few lines in each entry point, and the rebase is small.
The registry types drift from MEP when Morphir.Mep lands.The types copy MEP names and wire values. One mapping function and a test that maps every ExtensionType value come with Morphir.Mep.
Scripts that read the old stub text ("No extensions installed.") break.The stub never listed anything. Record the output change in the release notes and the CLI documentation.
The IR version list shows both 3 and 3.0.0.This is what the backends declare, and the spec says "as declared". Normalizing belongs to the version work (Versioning.FormatVersion), not to this change.
The E2E run of dotnet-morphir needs the tool build in CI.Use the build output of Morphir.Tool (dotnet dotnet-morphir.dll), not a packed tool install.

Migration plan

No data migration. The change is additive apart from the extension list output, which was a stub. Rollback: revert the change.
