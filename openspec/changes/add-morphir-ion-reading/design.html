Context

See proposal.md for motivation. These facts shape the approach:

  • Morphir.Models models classic IR only. Its Distribution has one case, Library. Literals are int64, decimal and char.
  • The only complete classic JSON decoder is Decode.fs in Morphir.CodeGeneration.FSharp. It is internal, raises GenerationFailure, and checks the shape of dependencies without decoding them. The public codecs in Morphir.Models/Json/Codecs stop at types and literals.
  • Morphir.IR.Pipeline already has what a tree reader needs: VFileTree, lazy re-openable VFileContent, ParseError and Parser<'T>.
  • The Ion IR format is a draft. 0.1.0-draft.1 matches only that exact string, and the spelling can change.

Goals and non-goals

Goals: one lossless Ion layer under every Morphir format, with no Eleven19.IonDotnet type in a public signature. Exact-draft behavior, tested against output from the reference CLI, not against our own reading of the draft.

Non-goals: the scope limits in the proposal, plus:

  • A typed form of enrichments. They stay Ion values.
  • The workbench morphir_pipeline profile and the linked-metadata draft. A linked-metadata file carries a different ionVersion and is refused.
  • Migrating between v3 and v4.
  • Classic literal widening. Out-of-range values are refused until a separate change widens them.

The formats

Morphir has two Ion formats that look alike and are unrelated in structure. The MEP corpus says so: the morphir_model body is "not a redefinition of the separate Ion IR spelling". This is why they get separate decoders.

Decisions

ION-1. A new Morphir.Ion project owns everything Ion

Morphir.Ion references Morphir.Models, Morphir.IR.Pipeline and Eleven19.IonDotnet. Morphir.Models stays free of Ion, because many callers want the model without a parser. Adding Ion to Morphir.Models would be less to build, but would make every model consumer restore an Ion library.

ION-2. Our own IonValue, built with the streaming reader

Read with IIonReader into an immutable F# union. Every case carries its annotations. Struct fields are an ordered list, so repeats survive.

type IonValue = { Annotations: string list; Value: IonData }
and IonData =
    | Null of IonType
    | Bool of bool
    | Int of BigInteger
    | Float of double
    | Decimal of IonDecimal      // coefficient, exponent, negative zero
    | Timestamp of IonTimestamp  // keeps declared precision
    | Symbol of string
    | String of string
    | Clob of byte[]
    | Blob of byte[]
    | List of IonValue list
    | Sexp of IonValue list
    | Struct of (string * IonValue) list

The library's mutable IIonValue tree was the alternative. It has no limits on the way in, its equivalence on datagrams is broken, and exposing it would tie our public API to a package we may have to change. Our type also gives structural equality for tests.

ION-3. Limits are checked by our reader, with depth checked before each step

IonReadLimits holds MaxDecodedBytes, MaxDepth and MaxNodes, using MEP's counting rules so one type serves both formats. Bytes are checked before the reader is built, which also bounds symbol tables, as MEP requires. The defaults for local files are 256 MiB, depth 512 and 50 million nodes. MEP callers pass negotiated limits. These defaults are starting figures. Our decoders recurse, so a test decodes a document at exactly the depth limit to prove 512 fits on a default .NET stack. Every library exception is caught at this one boundary and turned into malformed_ion with the exception's message, so nothing above this layer sees an exception. Fatal errors such as OutOfMemoryException are not caught.

ION-4. Fix the package first, and consume it only from NuGet

Fix the defects in Eleven19/ion-dotnet and publish through its trusted-publishing workflow before this change's reader lands. Morphir pins that version in Directory.Packages.props. A project reference or local feed would break locked restore in CI and hide release problems.

IRF-1. Normalize layouts first, then decode one document shape

All layouts reduce to one internal NormalizedDocument: header, merged dependencies, and modules with members inline. A record expands to it. A datagram groups into it. A tree builds the datagram its files stand for and then does the same, as the draft describes, so version decoders never see a layout. Merge and duplicate rules live in that one step.

IRF-2. Decode Ion directly into typed IR, with separate v3 and v4 decoders

The v3 and v4 decoders share annotation parsing and name handling, and nothing else. Their value spellings overlap, but the attribute rules, literals and node sets differ enough that one decoder would need a version check in most branches. Transcoding Ion to JSON and using the JSON reader was the alternative. It would save writing the decoders, but the JSON would need canonical v4 spellings the reader then has to undo, and errors could not name the Ion node. Reference pairs (TST-1) hold the two paths together.

Classic attributes decode to JsonElement, matching the attribute type the transpiler already uses. Classic generic parameters stay untouched.

IRF-3. Accept collapsed records for v3 and v4, and binary Ion

A record holds the header members plus optional dependencies and modules lists, whose items are the elements a datagram writes at the top level. The draft requires readers to accept one but does not spell out those members. The knowledge base says the Rust v4 reader refuses records (morphir-vvgi.8), but that note is out of date: morphir v0.4.0-beta.12 read a v4 record with a dependency, a module, a type and a value, and produced JSON byte-identical to the equivalent datagram. The CLI's writer does not emit records, so these test vectors are hand-written, and each is checked by reading it with that CLI. We also accept binary Ion for this format, because binary and text share one data model and the reader handles both. Writers still emit text.

SPEC-1. Spec issues are discussed, then corrected here and upstream

When implementation or testing finds an issue in the Morphir Ion spec, it stops at a discussion with the maintainer, with the evidence and a recommendation. Once agreed, the correction goes into both this repository (specs, code, fixtures) and finos/morphir. Neither side changes alone, so the .NET reader and the contract stay in agreement. PROVENANCE.md records each issue and links its upstream change. A local workaround with no upstream correction was rejected, because it would let the two drift apart unnoticed.

Two issues are already agreed. The draft's match row writes [pattern body], which is not legal Ion: the package rejects [_ ()], and the reference writer emits [_, 1,]. The reader takes the comma form. The draft also needs to define the collapsed record's members (IRF-3), and the knowledge base note on v4 records needs correcting.

IRF-4. Result type and error codes

type IrDocument =
    | ClassicIr of FormatVersion * Distribution<JsonElement, JsonElement>
    | V4Ir of FormatVersion * V4.Distribution

type IonIrError =
    { Code: string; Message: string; Path: string option; Location: string option }

Codes the draft or MCK names keep those names: specs_before_3_1, definition_in_specs, duplicate_name, unsupported_node, invalid_name, unknown_member. Codes the upstream documents leave unnamed, such as unsupported_ion_version, are ours, and the README lists them as draft. Parser<'T> integration maps Code to RuleId and Path to InvalidInput.Path. Non-Ion input returns UnsupportedInput, so the next parser in a pipeline gets its turn.

TREE-1. Trees read from VFileTree, with one shared budget

Taking a VFileTree keeps file access outside the reader, and lazy sources open one file at a time. A budget object carries the limits across all files in a tree, so many small files cannot bypass them. Stem handling follows decisions 0001, 0012 and 0015 in the finos/morphir knowledge base: escape handling, the __ plus eight hex digest of a cut stem, and the @ version segment. Reading does not stream a module at a time. That matches the Rust sink and is acceptable for a first reader.

The reader looks for JSON and YAML manifests only to report ambiguous_manifest. It does not read those trees.

MEP-1. Retain bytes, decode the IR on request

type ModelDocument =
    { Bytes: ReadOnlyMemory<byte>
      Ir: IonValue
      Enrichments: Enrichment list
      Provenance: IonValue list }

module ModelDocument =
    val readPayload : IonReadLimits -> ReadOnlyMemory<byte> -> Result<ModelDocument, ModelReadError>
    val readFile    : IonReadLimits -> ReadOnlyMemory<byte> -> Result<ModelDocument, ModelReadError>
    val decodeIr    : FormatVersion -> ModelDocument -> Result<IrDocument, IonIrError>

The IR view is a separate call because MEP separates retention from admission, and an extension can forward a model whose IR it cannot read. decodeIr projects the ir member to JSON with Utf8JsonWriter and hands it to the JSON reader. The projection writes integers and decimals as raw lexemes, and refuses anything JSON has no form for: Ion-only types, annotations and repeated fields. "Namespaced" for an enrichment owner means the string contains :, which the corpus's urn: owner meets. Base64, length and digest checks belong to later MEP work, and the byte input here is what those checks would produce.

V4-1. V4 model in Morphir.IR.V4, non-generic, sharing name types

The model reuses Name, Path, PackageName, ModulePath and FQName. Attributes are the concrete TypeAttributes and ValueAttributes that v4 defines, so the generic parameters classic carries are not needed. Modeling attributes as JSON was rejected because it would tie the model to one format. Instead, constraints, extensions and document literals use a small DocumentValue union whose numbers hold lexemes.

type Literal =
    | BoolLiteral of bool
    | CharLiteral of string          // one Unicode scalar, may be astral
    | StringLiteral of string
    | IntegerLiteral of BigInteger
    | FloatLiteral of FloatValue     // finite value, optional lexeme
    | DecimalLiteral of DecimalLexeme
    | DocumentLiteral of DocumentValue

type ValueBody =
    | ExpressionBody of outputType: Type * body: Value
    | NativeBody of outputType: Type * info: NativeInfo
    | ExternalBody of outputType: Type * info: ExternalInfo
    | IncompleteBody of outputType: Type option * incompleteness: Incompleteness * partialBody: Value option

V4-2. An insertion-ordered map with two equalities

Parameter maps, record fields and entry points use an ordered list of pairs, so order counts in equality. Modules, types, values and dependencies use OrderedMap, which rejects duplicate keys, keeps insertion order and compares without regard to order. The v4 semantic model says map key order is not meaningful, while a future canonical writer must emit document order, and this type satisfies both. Using Map as classic does would lose the order. A plain list would make two equal distributions compare as different.

V4-3. Hand-written JSON readers over JsonElement

Readers walk JsonElement by hand, as Decode.fs does, and collect a JSON location. JsonDocumentOptions does not reject duplicates, so the reader checks them per object. FSharp.SystemTextJson was rejected because EnableTrimAnalyzer is on for this project and the spelling variety needs custom code anyway. Canonical strings get strict parsers: Name following decision 0001, and FQName built on the existing fromStringStrict.

CLS-1. Add Specs to the classic Distribution and move the JSON decoder

Adding a case makes illegal states unrepresentable and matches IR 3.1.0. A second wrapper type was the alternative, but every caller would then hold two distribution types. packageDefinition becomes an option. Only the classic DSL builds Distribution today, and it builds Library, so the break is small. No tag contains the type.

The decoder moves to Morphir.Models and returns Result. Decode.fs becomes an adapter that turns those errors into GenerationFailure with the same category and location, then applies the transpiler's own rules. The move is a refactor first, with existing transpiler tests passing before dependency decoding is added.

TST-1. Test against reference output, vendored with provenance

The reader's expected values must not come from the reader. Three vendored sources in tests/Fixtures/MorphirIon, each with its commit and SHA-256 in PROVENANCE.md, and a test that fails if a file's hash changes:

  • The MEP corpus and fixtures from spec/mep/mck.
  • JSON and Ion pairs, and trees, from the pinned morphir CLI, run over website/static/ir/examples and daily-rate-v3.json.
  • Ion and JSON spellings from spec/ir/mck/values.feature, extracted to a data file by a checked-in script.

Tests are Expecto, like the other F# projects, and each spec scenario names a test.

Risks and trade-offs

RiskMitigation
The change is large: a v4 model, two JSON readers, two decoders, a tree reader and package fixesTask groups land separately and in dependency order. The MEP reader needs groups 1 to 4, and can ship before the Ion spelling decoders if they run long.
The draft changes after this landsThe exact ionVersion match refuses any new draft. Spelling code is isolated in the two decoders, and new fixtures show what moved.
The CLI installed on this machine refused --output-format ion with "no codec is registered"Task 6.1 pins the v0.4.0-beta.12 release, which reads and writes Ion, and checks its published SHA-256.
Reference CLI bugs become our expected valuesDisagreements with the draft follow SPEC-1 and are not copied silently.
Morphir depends on a fork whose README still says "Deprecated" and whose text-error messages lack positionsThe maintainer owns the package. The README gets corrected. All library use sits behind Morphir.Ion, so a later switch stays internal.
Native AOT was not run. The package is netstandard2.0 with AllowUnsafeBlocksTask 2.4 publishes a small consumer with PublishAot and fails on IL warnings. No reflection use was found in package source.

Reading loads whole documents into memoryLimits bound the cost. Streaming can come later without changing results.

Migration plan

Publish the package fix first. Everything else is additive except Distribution.packageDefinition, whose callers in this repository change in the same commit. Note the break in CHANGELOG.md. To roll back, revert the merge. No data or wire format changes.

Open questions

  • Whether the planned F# frontend for Morphir can help settle remaining Ion or v4 questions, for example as a second producer of v4 IR for these tests. Nothing here depends on it.
  • Whether upstream names a code for an unknown ionVersion. If it does, rename ours.
