Context

See proposal.md for the motivation. This section describes how the code works today.

  • Writers: each family has an internal writer (FlowchartSvg, SequenceSvg, RailroadSvg, DataTreeSvg, BpmnSvg). State, swimlane and architecture diagrams use the flowchart writer through their internal Projection. Together the writers are about 4,800 lines.
    • Each writer computes positions and writes SVG in the same pass through SvgWriting.SceneBuilder.
    • SvgWriting.document runs the drawing callback twice. The first pass works out a fingerprint, and the second writes with the final ID prefix.
    • The writers emit in phases rather than by containment. Flowcharts emit container backgrounds, then edges, then nodes. BPMN emits pools and lanes, then flows, then nodes.
  • Coordinates and paths: flowchart, sequence, railroad and data-tree coordinates are whole pixels. BPMN coordinates come from the DI as floats and are written with 0.##. BPMN icon paths use relative commands, including a, c and s. BPMN lane headers are rotated text. Flowchart icons are <use> of symbols.
  • Identity in the SVG: drawn elements carry data-ref, often on a group that holds several primitives. Railroad tracks and the trace overlays have no reference. Colours are CSS variables, except colours the author set, such as a sequence box Aqua.
  • Links: these come from the metadata projection in Carriage.project, which can give several links for one reference, marks which are web links, and sorts its items by kind and identity. The layout keeps that order and takes only link items.
  • Colours: Color.Parse reads hex and rgb functions only. Authored colours such as Aqua reach the SVG as written. Some primitives also carry fill-opacity, and BPMN and railroad paths set stroke-linecap and stroke-linejoin.
  • Diagnostics: Diagnostic has an internal constructor, so another assembly cannot create one today.
  • Reusable public types: Color, ColorFamily, ThemePalette, ThemeMode, EdgeHead (none, arrow, open arrow, circle, cross, async, and the four half heads), SvgRenderOptions and DiagramElementRef.
  • Downstream outputs: Morphir.Diagrams.Raster paints the public SvgDocument. The player and the animated GIF also read DiagramScene.Connectors and the playback structure.
  • Tests: tests/Morphir.Diagrams.Tests (TUnit) reads the pinned corpora through PinnedCorpus and FixtureCatalog. tests/Morphir.Diagrams.FSharp.Tests (Expecto) has no FsCheck yet. The black-box smoke scenarios in LibraryHosts.feature and NativeAot.feature run the diagrams-smoke program.

Goals and non-goals

Goals:

  • A public layout that covers every primitive the SVG draws and agrees with it at the SVG's precision.
  • A renderer contract that an external assembly can implement against Morphir.Diagrams alone, and that stays compatible as the vocabulary grows.
  • Fallbacks applied centrally, in a defined order.
  • Two editable targets that open correctly in their applications.

Non-goals:

  • Producing SVG from the layout, or painting rasters from it (DRAW-1).
  • Letting callers build or edit layouts.
  • Reading draw.io or Excalidraw files back.
  • Animation in layouts.

DRAW-1. Record the layout in the final pass, by owner

The writers keep their layout code and their SVG output. SceneBuilder gains a layout sink, which is active only in the second, final run of SvgWriting.document. Every primitive a writer emits records a drawable, with these parts:

  • its kind and geometry
  • its paint
  • the element reference it draws, if any
  • its owner: the identifier of the container or composite element that contains it, or none

The writers already know each owner from the model. The node A belongs to the subgraph books, and a participant's lifeline belongs to the participant, although the SVG draws it outside the participant's group. So containment doesn't depend on the order in which phases emit.

The agreement test has two parts. First, it lists every primitive the SVG paints, in document order, and compares that list with the primitives the layout's drawables stand for, in paint order, one entry each. This catches primitives with no reference and anything painted out of order. Second, it checks references and owners: each data-ref names one drawable, and each primitive belongs to its innermost referenced group, except for the documented owners such as lifelines.

The sink numbers drawables in the order they are recorded, which is SVG paint order. When the pass ends, it builds the containment tree from the owners. In the example, the line from A to B is recorded before both nodes, so its paint index is lower, but the nodes are still children of the books container.

The writers' raw elements move behind helpers that write exactly the same SVG nodes and also record the drawable. For example, the diamond polygon in FlowchartSvg.shape becomes a helper that writes the identical <polygon> and records ShapeKind.Diamond. A kind drawn with several primitives records one shape that stands for all of them: the cylinder's rounded rectangle and top ellipse are one cylinder, so a renderer with native cylinders draws no extra ellipse. Primitives that no kind covers, such as a subroutine's side bars, are drawables of their own in the node's element. Symbol uses record image drawables. Their SVG is a standalone document: an svg root with the symbol's view box (0 0 24 24 for icons) and the image box's width and height, so it scales as the <use> does. The root carries the paint the symbol sets for its children (fill="none", the stroke, its width, caps and joins), with currentColor replaced by the ink at the point of use, followed by a copy of the symbol's content and its definitions.

Alternatives considered:

  • Produce SVG from the layout. This rewrites every writer, and the layout would have to carry SVG-only details to keep the bytes identical.
  • Read our own SVG back. That means guessing kinds from polygons and paths.
  • Containment by call nesting. This fails because the writers emit by phase.

DRAW-2. Digest baselines before any refactor

The first implementation task records three sets of digests before any writer changes:

  • SHA-256 digests of the SVG of every pinned corpus diagram, for each built-in theme, mode, connector style and bridge setting
  • digests of the player HTML, PNG, JPEG and GIF output for one diagram of each family, covering playback order, metadata, a railroad trace and highlights. PNG bytes come from the runtime's zlib, so images are digested as decoded pixels (and GIF frame delays), and the player HTML is digested with each embedded image replaced by its pixel digest. This keeps the baselines the same on every CI platform.
  • digests of the connector bindings and playback structure that the player and GIF read

The digests are committed as fixtures, each with its catalog entry and provenance row. Every later task must keep them unchanged. A digest that changes is a defect to fix. It is not re-approved.

UNIT-1. Quarter EMU, captured from the SVG's own numbers

Distance is a struct over an int64 count of quarter EMU. A struct is safe because default is zero, which is valid. Quarter EMU makes every hundredth of a CSS pixel exact (381 units), as well as points (50,800 units), centimetres, millimetres, inches and whole EMU.

The sink captures each coordinate from the number the writer formats. For BPMN, it parses the same 0.## text the SVG gets, so the layout agrees with the SVG by construction. For example, 100.02 px becomes 3,810,762 units.

  • Arithmetic is checked: overflow throws.
  • Multiplying by a number rounds half to even. Dividing one distance by another gives a float.
  • Renderers that need whole EMU (OOXML and Google Slides) round half to even with ToEmu(), which can differ by up to half an EMU.
  • Fraction and Scale are classes with Parse, TryParse and Create.

Alternatives considered:

  • Whole EMU cannot hold 0.01 px.
  • Hundredths of a pixel cannot hold a point exactly.
  • A rational type is exact for everything but costs a GCD on every operation.

LAY-1. A layout keeps the SVG of its own pass

DiagramExport.Layout(diagram, options) works in four steps:

  1. It resolves auto to light, because draw.io and Excalidraw open on a white canvas.
  2. It runs the SVG pipeline once.
  3. It returns the layout with that pass's SvgDocument as DiagramLayout.Svg.
  4. It reports the same diagnostics as SvgRenderer.Render.

Layout equality compares the bounds, the background, the drawables and Svg.Render() text, because SvgDocument has reference equality.

LAY-2. The drawable model

                     Cap: LineCap; Join: LineJoin }                 // advisory

    member Drawables: ImmutableArray<Drawable>     // roots, by containment
    member Features: LayoutFeatures; member Svg: SvgDocument
  • Every layout type has internal construction, so a renderer can read layouts but never build one, as interop rule 2 requires.
  • C# reads optional values as T | null, branches through Match members or the visitor, and compares values with Equals.
  • The record sketches above stand for sealed classes whose properties are read-only.
  • Authored colours go through a new internal reader that adds the 148 CSS named colours to what Color.Parse reads. A value it cannot read gets the writer's default colour and a layout/unresolved-colour warning. Color.Parse itself does not change.
  • A creation message binds the created participant's head shape, because the SVG ends it on the side of that box. Other messages bind lifelines along their length.

In the example:

  • the source end of B --> C binds to B's shape at anchor (1, 0.5), and its target end binds to C's cylinder
  • the label yes is the line's label
  • a link to the subgraph would bind the books container's identifier instead

PATH-1. One path normaliser

PathData parses SVG path grammar and normalises it to absolute M, L, C, Q, A and Z:

  • relative commands become absolute
  • H and V become L
  • S and T become C and Q, with their control points reflected

PathData.WithoutArcs(tolerance) turns arcs into cubic curves for targets without arcs, such as DrawingML. The agreement test formats both sides with the SVG's number formatting before comparing them.

CAP-1. Features, the baseline and the order of lowering

The features and their meanings are in the diagram-renderers spec. The baseline is rectangles, straight segments with no head or a filled arrow, upright text, elements and groups painted together, opaque colours, and solid or default-dashed strokes.

Lowering is a pure function of the pages and the declared features. It returns the lowered pages and the degradations. It runs in these passes, and the spec lists the same order:

  1. Containers become groups with a header text.
  2. Family roles are removed.
  3. Shape kinds and paths fall back. A kind becomes a path, or a rectangle without paths, and never an image, so its text stays editable. A path from the layout becomes an image, or a rectangle without images.
  4. Images are removed when SVG images are not declared.
  5. Bindings are resolved over the whole page, now that every replacement is known. A binding survives only with attached connectors and an eligible target: a shape or image, a container if containers are declared, or a line if line targets are declared and the route table keeps that line as one line, judged without its own bindings so no cycle arises. Otherwise the end keeps its point and loses the binding.
  6. Routes follow the route table below.
  7. Arrowheads fall back: message heads to open or filled arrows, then open and circle heads to filled arrows.
  8. Text loses its rotation, then its wrapping.
  9. Opacity is composited over the background, first for fills, then for strokes and ink.
  10. Dash patterns become the default dash.
  11. Links are removed.
  12. Paint order is only checked. Each unit whose drawables are not consecutive in paint order is reported: an element or group without interleaved painting, and a native container without interleaved containers.

Bindings come before routes because the route depends on them. Bindings come after every replacement so that no binding can name a drawable that was removed or turned into a group.

Each line gets the first route that applies:

Renderer declaresThe line receivesDegraded when
Exact routesIts exact path, waypoints and route styleNever
Smooth curves, for a curved lineIts waypoints and the curved styleNever, by the meaning of smooth curves
PolylinesA polyline through its waypointsThe exact path has rounded corners, curves or bridges
None of these, with a bound end or two waypointsOne straight segment between its endsThe line has bends, or as for polylines
None of these, no bound endA group of straight segments, heads on the first and lastAs for polylines

A test runs every combination of the four line features against a curved, an orthogonal, a bridged and a straight line, and checks the received route and the degradation for each.

Several fallbacks on one drawable are recorded as one degradation. For example, a cylinder for a renderer without cylinders or paths becomes a rectangle in pass 3, whether or not the renderer declares images, and is recorded once: cylinders become rectangles.

API-1. Render plans, the renderer and the visitor

namespace Morphir.Diagrams.Export

[<Sealed>]
type RenderPlan internal (pages, assessment, mode: RenderMode, features: LayoutFeatures) =
    member Pages: ImmutableArray<DiagramLayout>     // lowered, or unlowered for OriginalSvg
    member Assessment: Assessment
    member Mode = mode
    member Features = features                         // what the pages were lowered to
    member EnsureFor(renderer: DiagramRenderer) : unit // ArgumentException unless mode matches
                                                       // and Features ⊆ renderer.NativeFeatures

[<RequireQualifiedAccess>]
type RenderMode = Drawables | OriginalSvg

[<AbstractClass>]
type DiagramRenderer() =
    abstract MediaType: string
    abstract FileExtension: string
    abstract NativeFeatures: LayoutFeatures
    abstract Mode: RenderMode
    default _.Mode = RenderMode.Drawables
    abstract RenderAsync: plan: RenderPlan * output: Stream * cancellationToken: CancellationToken
                          -> Task<ImmutableArray<Diagnostic>>

type Diagnostic with      // new public factories on the existing type
    static member Error(code: string | null, message: string | null) : Diagnostic
    static member Warning(code: string | null, message: string | null) : Diagnostic

[<AbstractClass>]
type LayoutVisitor() =      // one virtual method per DrawableKind case;
    ...                     // Element, Container and Group default to visiting their children
  • Why abstract classes: F# cannot write default interface methods, and an abstract class can gain virtual members later.
  • No bypass: a caller cannot build a RenderPlan, so a renderer can't be driven past the assessment. A plan can still be kept and handed to another renderer directly, so it records its mode and features, and EnsureFor refuses a plan that uses a feature the renderer doesn't declare. Every renderer in the library's packages calls it first, and the README tells external renderers to do the same.
  • Diagnostics: the factories are members of the existing Diagnostic type, so renderers and the library return one type. A code is prefix/name in lowercase letters, digits and hyphens. The README asks external renderers to use their own prefix. A test assembly with its own renderer returns an error and a warning through the facade.
  • Original SVG: a renderer in this mode, such as reveal.js in the slide change, receives the pages unlowered and draws only DiagramLayout.Svg. It declares no features, so the assessment is native without claiming editable connectors or links that it doesn't write.
  • Stream rules:
    • Renderers must not seek. A renderer that writes a ZIP builds it in a MemoryStream and copies it, so the bytes are the same for any stream.
    • The facade flushes after the renderer returns and never disposes the stream.
    • A token that is already cancelled ends the call before the renderer is invoked.
    • A renderer's exceptions pass through unchanged.

API-2. The facade, the registry and compatibility

var result = DiagramExport.Layout(diagram, SvgRenderOptions.Default);      // LayoutResult: Layout | null, Diagnostics
DiagramLayout[] pages = [result.Layout!];
var assessment = DiagramExport.Assess(pages, renderer);                    // Match(native, degraded, unsupported)
var outcome = await DiagramExport.RenderAsync(pages, renderer, stream, DegradationPolicy.AllowDegraded, ct);

var renderers = DiagramRenderers.Empty.Add(new DrawIoRenderer()).Add(new ExcalidrawRenderer());
if (renderers.TryFind("flow.excalidraw.md", out var found)) { /* found is not null here */ }
  • TryFind uses a non-nullable out with [MaybeNullWhen(false)], and TryParse members follow the same pattern.
  • A C# test project with nullable analysis enabled and warnings treated as errors compiles these calls.
  • The compatibility policy from the spec is enforced in three ways:
    • a feature added later is the only way a new DrawableKind, ShapeKind or path command appears
    • Match overloads are only ever added, never changed. An older overload that meets a newer case throws InvalidOperationException, which a plan can't cause, because the case arrives only with a feature the older renderer doesn't declare.
    • EdgeHead follows the same rule: a new head arrives only with a new head feature, and falls back to an existing head.
    • a test compares the public API of Morphir.Diagrams with an approved listing in the fixture catalog, so an accidental breaking change fails the build
  • Once a release ships this API, package validation against that release replaces the listing.

PKG-1. The contract in Morphir.Diagrams, the renderers in Morphir.Diagrams.Canvas

The layout, features, lowering and contract live in Morphir.Diagrams, where the drawing pass is, so an external renderer depends only on Morphir.Diagrams.

Morphir.Diagrams.Canvas holds the three canvas renderers. It references Morphir.Diagrams only, and writes with XmlWriter and Utf8JsonWriter.

Roledraw.io's UML and BPMN library styles. Task 5.2 checks their names in draw.io.

draw.io declares interleaved painting, because elements and groups have no cells. It does not declare interleaved containers, because a container cell paints its whole subtree together. A line that leaves a container is a cell of the layer, so it paints above the container's nodes. The assessment reports this for each such container.

Cell IDs are 0 and 1 (the root and the layer), then the drawable IDs. Cells are written parents first, then siblings in paint order. The file has no modified, etag, agent or version attributes.

EXC-1. The Excalidraw mapping

  • Elements: rectangle (with roundness type 3 for rounded rectangles), ellipse, diamond, arrow, text, and image, whose SVG goes in files as a data URL. Elements are written in paint order, which is also Excalidraw's painting order, so Excalidraw declares interleaved painting.
  • Arrows: every line is an arrow, because Excalidraw binds only arrows. A line with no heads has null startArrowhead and endArrowhead. Each arrow has startBinding and endBinding, mirrored in the bound element's boundElements. Its points are relative to the first point, and a curved line gets roundness type 2. Heads map to triangle, arrow and dot.
  • Curves: Excalidraw draws a rounded arrow as a curve through its points, which meets the meaning of smooth curves. Task 6.1 checks this in the pinned release by sampling the rendered curve at each waypoint.
  • Text: Excalidraw only lets rectangles, ellipses, diamonds and arrows contain text. So a label of an image or of a group becomes a free text element that shares a group identifier with its drawable.
  • Opacity: element opacity fades the fill, stroke and text together, so Excalidraw declares neither opacity feature, and lowering makes every colour opaque.
  • Determinism:
    • IDs are m followed by the paint-order index in base 36, padded to eight characters.
    • seed and versionNonce come from a 32-bit FNV-1a hash of the ID.
    • version and updated are 1.
    • An image's file ID is the first 40 hex digits of the SHA-256 of its SVG.
  • References: customData holds {"morphirRef": "node=A"}.
  • Version check: task 6.1 pins the Excalidraw release whose importer is used to check the scenes, and records it in the README.

OBS-1. The Obsidian note

The note has three parts:

  • front matter excalidraw-plugin: parsed
  • # Excalidraw Data with ## Text Elements, where each text is its exact content, multi-line where it has line breaks, followed by ␠^, its eight-character element ID and a blank line. The plugin parses block references of exactly eight characters, and the element IDs from EXC-1 are eight characters by construction.
  • %%, ## Drawing, a json code block with the scene, and %%

Text in the note matches the JSON exactly, so the plugin's habit of preferring the Markdown text changes nothing.

The plugin splits the section at each ␠^ followed by eight characters at the end of a line. A text that itself contains such a line would be split into two entries, so the renderer leaves it out of the section and the plugin reads it from the scene. Task 6.3 checks that the pinned release does this.

The renderer declares no SVG images. This is a decision to keep each note a single file. The plugin could import data URLs into the vault, but that would add files beside the note. Task 6.3 pins the plugin release that the notes are checked against.

TEST-1. How the tests prove the specs

The test-manager skill classifies these tests as follows:

  • Unit (tests/Morphir.Diagrams.Tests, TUnit):
    • the agreement test: the page-wide paint list, then references and owners, against the public SVG renderer's output (DRAW-1)
    • the route table over every combination of line features
    • a diagnostics test from the test assembly's own renderer
    • a separate text-box test against the theme's text-width estimate
    • the stream, cancellation and failure scenarios
    • a renderer defined in the test assembly
    • the approved API listing
  • Property (tests/Morphir.Diagrams.FSharp.Tests, Expecto with Expecto.FsCheck): lowering over corpus layouts and any subset of features. The corpus reader moves from PinnedCorpus into tests/Morphir.TestSupport so that both projects use the catalog.
  • Unit (tests/Morphir.Diagrams.Canvas.Tests, TUnit): structural checks on every corpus diagram and digests for each target. The checks against the applications run before any digest is recorded.
  • Smoke: the existing LibraryHosts.feature and NativeAot.feature scenarios run diagrams-smoke, which gains one export to each canvas target and asserts that each succeeds.
  • Review: the test-manager-reviewer agent reviews the test diff.

Migration plan

  • The change only adds API. Existing output is unchanged, so callers need no migration.
  • The new package joins LibraryPackages after Morphir.Diagrams.
  • To roll back, revert the change.

Open questions

  • The exact draw.io style for each family role. Task 5.2 settles it, and it changes only style strings.
  • Whether draw.io's async markers can draw the half heads. If task 5.2 finds that they can, draw.io can declare message heads later without other changes.
