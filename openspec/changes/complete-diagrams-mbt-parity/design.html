Context

See proposal.md for why. Today Morphir.Diagrams (F#, with a C# test project and an F# test project) reads a subset of Mermaid flowcharts and sequences, lays them out with its own simple rank layout, and writes themed SVG through Morphir.Svg. The offline player (Player.js, Viewport.js) plays authored-order connector motion and shows comments from the embedded RDF dataset. Element references, selections and the RDF mapping come from the open change add-diagram-linked-metadata on the same branch.

Upstream, diagrams.mbt at 60a8dd1, has about 1.5 MB of hand-written MoonBit for the missing families, plus generated BPMN schema code, raster fonts and an icon catalogue. Its specs promise identical output on four compilation targets. Here the equivalent promise is identical bytes on Linux, Windows and macOS, under JIT and Native AOT.

Constraints: every package stays trimmable and Native AOT compatible; F# public types follow the fsharp-csharp-interop rules; XML readers prohibit DTDs and use no resolver; tests follow the test-manager rules, with fixtures owned by FixtureCatalog and pinned in PROVENANCE.md.

Goals and non-goals

Goals: one reading entry point for every upstream family; one layout and connector engine that every family shares; the knowledge, theme and player features for every family; all of it delivered in PR #692, group by group, with CI green after each push.

Non-goals: executing diagrams (no guard, condition, timer or regex evaluation); a general-purpose SVG renderer (the rasteriser reads only SVG this library writes); the Python binding, the gallery site and the browser raster worker from upstream; Draw.io and Graphviz DOT, which upstream itself has not built; loading themes from JSON files.

Decisions

The decisions follow one source through the system: the state diagram from the proposal, read, laid out, coloured, annotated, played and exported.

PKG-1. Packages

Mermaid and PlantUML reading, the family models, layout, SVG, icons and the player stay in Morphir.Diagrams, because every family shares the theme, element-reference and player code there. Three new packages hold code that has no reason to load with every diagram:

PackageHoldsDepends on
Morphir.BpmnBPMN 2.0.2 documents: secure XML reading, typed model, validation, writing, traversal and graph queriesnone of the diagram packages, as upstream keeps moonrockz/bpmn independent
Morphir.Diagrams.QueryThe tree query language and its BPMN adapterMorphir.Bpmn
Morphir.Diagrams.RasterThe rasteriser, TrueType reader, PNG, JPEG and GIF encoders and the Noto fontsMorphir.Diagrams

Morphir.Diagrams references Morphir.Bpmn to render BPMN views. Alternatives: one package for everything (rejected: every caller would carry about 700 KB of fonts and the BPMN schema), or one package per family (rejected: themes, references and the player would need a shared core package, which is Morphir.Diagrams already).

SYN-1. Lossless readers

Each language gets a hand-written lexer and a recursive-descent parser that builds a lossless concrete syntax tree (every code unit, including trivia and invalid regions, belongs to exactly one token), then a typed syntax tree, then the family model. Parsers keep an explicit stack for nesting, so a 10,000-level input hits the depth limit, not the call stack. The existing flowchart and sequence readers move to the same shape; their public results do not change.

stateDiagram-v2          → CST: header token, newline trivia, statements…
  [*] --> Draft          → AST: Transition(Initial(scope=root), State "Draft")
  Draft --> Review : submit
                         → Model: states [Draft; Review], transitions [t0; t1] in source order

Alternatives: a parser-combinator library (rejected: no AOT-clean, lossless option in the dependency set) or generated parsers from the upstream grammars (rejected: upstream grammars are MoonBit code, not a portable grammar format).

LAY-1. One layered layout engine

Flowcharts, state diagrams, swimlanes and automatic BPMN layout share a layered engine: rank by longest path with cycle breaking in source order, keep subgraph and composite bands (as the current flowchart layout does), order each rank by barycentre sweeps with source order as the tie-break, and assign coordinates per rank. Architecture uses its own grid placement driven by ports and row and column constraints. Railroad and data-tree layouts are their own measured box layouts. Sequences keep their existing layout.

Moving flowcharts onto the shared engine changes some existing SVG. Each such change shows up as a diff of committed snapshots and is reviewed in the group that makes it. Alternative: keep the current flowchart layout and add a second engine (rejected: two layouts of the same graph shape would drift apart).

CON-1. Connectors after layout

Routing produces orthogonal points with shape-aware attachments (diamond points, spread side slots, declared ports). A separate pass styles the points (elbow, rounded, curve), reserves straight endpoint approaches, then finds crossings between unrelated connectors and inserts bridges, owned by the later connector in stable order. The result is a final path per connector, which the SVG, the player and the rasteriser all use. The route points stay available. This extends the one-turn routing already in FlowchartSvg.

THM-1. Colour families per element kind

No new theme tokens. Every element kind maps to one of the seven existing families, so all built-in and custom themes cover every family. For example: ordinary states, tasks, services and rules use backend; choices, gateways and decisions use cloud; stores, data objects and databases use database; events, queues and message flows use messagebus; error and terminate events use security; actors and clients use frontend; notes, annotations and pseudostates use external. Lanes, pools, composites and frames use --frame. The README documents the full table.

REF-1. Element references per family

The existing kind=value scheme gains kinds per family: state, region, transition, service, junction, connection, lane, task, event, gateway, flow, rule, occurrence, row and others, each with the same escaping and stability rules. BPMN references use the element ID; data-tree rows use a JSON-pointer path. Selections, annotations, carriage and the player need no change beyond accepting the new kinds.

ICN-1. Icon catalogue

A development script reads upstream's catalog.json and assets at 60a8dd1, checks every source digest, normalises each SVG into a compact path form (no runtime SVG parser), and writes one embedded resource plus a generated F# key table. Provider assets are copied unchanged in shape and colour. Technology logos are kept only when their SVG Repo licence allows redistribution; the script reads an allow-list recorded in the catalogue's provenance file, and every other key, along with externalsystem, uses an original drawing in the repository. THIRD-PARTY-NOTICES.md and a trademark notice ship in the package. Rendering emits only used symbols as <symbol> definitions prefixed with the diagram ID.

PLY-1. Player exploration

The motion data gains a connection graph per diagram: nodes, directed connections with kind and head flags, and node-visit targets. Route and reachability queries run in Player.js by breadth-first search with explicit limits, in the same order as the F# reference implementation, which tests use to compute expected answers. The exploration controls sit in a panel next to the notes panel and reuse its narrow-screen layout.

RAS-1. Managed rasteriser

The rasteriser reads the SVG this library writes (paths, rects, circles, ellipses, polygons, text, markers, masks, symbols and the CSS-variable theme blocks), resolves the export theme, flattens curves, and fills with a non-zero scanline coverage rasteriser with 4x4 anti-aliasing in fixed-point arithmetic, so output is identical on every platform. Glyphs come from a small TrueType reader over the embedded Noto fonts. PNG uses System.IO.Compression.ZLibStream at a fixed compression level; JPEG ports upstream's integer-DCT baseline encoder (adapted from mizchi/image under Apache-2.0, credited in the notice); GIF uses a fixed median-cut palette and LZW. Alternatives: SkiaSharp (rejected: native dependencies) and ImageSharp (rejected: not Apache-2.0).

TST-1. Fixtures and evidence

Upstream's compatibility corpora and expected outputs at 60a8dd1 are pinned under tests/Fixtures/diagrams-mbt/ with a PROVENANCE.md row and SHA-256 per file and a FixtureCatalog.Diagrams owner. Each family gets unit tests in the C# test project, F# tests where F# callers need them, and committed SVG snapshots. Every group ends with a Chromium check of its family in all built-in themes, dark and light, at desktop and 420 px widths.

PR-1. Delivery in PR #692

Work lands in the order of tasks.md: foundations, connectors and layout, then each family with its knowledge, theme and player support, then BPMN, queries, exploration and raster. Each group is test-first, committed and pushed, and must leave CI green. The pull request description gains a section per group and a heads-up to FINOS about the icon catalogue. The pull request merges after the last group once every check is green.

Risks and trade-offs

RiskMitigation
One very large pull request is hard to review.One commit or more per task group, each with its own tests and snapshot diffs, and a per-group summary in the description.
The shared layout changes existing flowchart SVG.Snapshot diffs reviewed in the group that changes them (LAY-1); element references and selections do not depend on geometry.
Raster output differs between platforms.Fixed-point rasterisation, a fixed zlib level and golden byte tests on all three CI operating systems (RAS-1).
Native AOT size grows with the icon catalogue and fonts.Fonts live in Morphir.Diagrams.Raster; the catalogue is one compressed resource read on first use; the AOT smoke tests record size.
Provider icon terms or SVG Repo licences change, or FINOS objects.Every symbol's source and terms are in the catalogue; any key can switch to an original drawing without changing the public API (ICN-1).
BPMN 2.0.2 coverage is broad.The typed model is generated from the OMG XSD by a committed script, and a test regenerates it to check it is current.
Upstream behaviour is only specified at 60a8dd1.Pinned fixtures and expected outputs from that commit are the reference; deviations are listed in the README's migration coverage.

Migration plan

All changes are additive to unreleased packages on the diagrams branch. No caller migration is needed. Rollback is reverting the group's commits on the branch before merge.

Open questions

Which SVG Repo technology logos allow redistribution is answered per icon while building the catalogue (ICN-1); the answer changes only which keys use an original drawing.
