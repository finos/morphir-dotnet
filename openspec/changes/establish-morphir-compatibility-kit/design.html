Context

See proposal.md, section Why. These facts constrain the design:

  • Upstream MCK (finos/morphir@cde7722eb, spec/mep/mck/). The Rust morphir mck mep guest-run and report-check record executable identity, a corpus SHA-256 and complete observations, and they never trust a stored qualified flag. These are good properties, and this design keeps them. The flaws are in the oracle and the plan:
    • The generic kit's expected IR "was recorded from the published Python 0.4.2 guest".
    • Its comparison ignores list order and accepts a Reference shorthand by default.
    • Every guest must pass a legacy 0.1 stage, and must be both frontend and backend.
  • Local precedent. dotnet-sdk-conformance already sets the oracle principle and the vocabulary: pinned evidence, classification (required, exclusion, known gap), basis, portable observations, and "shared evidence without shared implementation" (tests/Fixtures/MorphirSDK/cases.json, PROVENANCE.md). tests/Fixtures/MorphirIon pins upstream Ion kit features and mep/model-transport.cases.json with SHA-256 checks.
  • The seed. add-fsharp-compile (MCK-1) creates conformance/, the Morphir.Conformance runner and the cli, mep-guest and library adapters for the F# compile suite. This change generalizes them. It does not start a second runner.
  • Hosts. morphir is a Native AOT executable. dotnet-morphir is a JIT dotnet tool. The MEP protocol definition (Gleam/Smithy) stays upstream.

Goals and non-goals

Goals.

  • The oracle is reviewed case data. No implementation, including morphir-dotnet, is the oracle.
  • Any implementation in any language can run the kit through a process boundary.
  • A qualification report proves exactly what was tested, and anyone can check it again.
  • Upstream material is used through review with provenance, and corrections are visible and reported upstream.

Non-goals.

  • Changing the MEP protocol definition.
  • Moving the SDK and Ion corpora in this change.
  • Embedding the kit in the executable.
  • WASM guest hosting.
  • Certification or trust of remote reports. A report is evidence, not a signature.

Kit layout and what a case expresses

Cases are Gherkin features (MCK-FMT). The kit manifest is TOML, read by the existing configuration TOML reader.

conformance/
├── KIT.md                          # kit version, rules, authoring guide link
├── kit.toml                        # kitVersion, step vocabulary version, suites, profiles, normalization catalog
├── steps/
│   └── steps-1.md                  # normative MCK step vocabulary, version 1 (grammar + meaning of each step)
├── suites/
│   ├── ir-writing/                 # IR codecs and writers
│   ├── frontend-fsharp/            # seeded by add-fsharp-compile
│   │   ├── records.feature         # scenarios frontend-fsharp-0001 ...
│   │   └── records/                # sidecar files, e.g. 0007/expected-v4.json
│   ├── generation/
│   ├── cli/                        # compile, generate, task records, --json, --json-lines, exit codes
│   ├── mep-host/
│   └── mep-guest/
├── reviews/                        # review records for tool-assisted expectations
├── imports/
│   └── finos-morphir-cde7722eb/    # unchanged upstream bytes + PROVENANCE.md + disposition records
└── supersession log                # published with each kit release

Decisions

KIT-1. A content model that does not depend on the format, using the SDK conformance vocabulary, under its own kit version

  • This change fixes what a case must express (the table above), not the file syntax. The fields caseId, classification (required, exclusion, knownGap), basis and evidence mean what they mean in dotnet-sdk-conformance, so a later move of that corpus keeps its meaning.
  • The file format is Gherkin (MCK-FMT). The runner reads features into the content model through one corpus reader. The rest of the design (plans, adapters, comparison, reports, the command) uses only the content model.
  • kitVersion is SemVer and is separate from MEP, IR format and CLI versions. A stricter expectation is a breaking change.
  • Expected IR is a complete document for each exact format version, named by the IR's own spelling (4, 4.1.0-draft.1), never by a bare major number. Every case states for each version whether it applies.
  • Kinds of observation: IR document, diagnostics, CLI invocation (exit code, the --json report, --json-lines records, files written), and MEP exchange (request and response, after the response is checked against the contract shape).

MCK-FMT. Gherkin is the normative case format; literate Markdown is generated

Decided by the maintainer. The corpus is Gherkin, using the conventions of the upstream IR v4 kit pinned in tests/Fixtures/MorphirIon/kit: stable <suite>-NNNN ids in scenario names, tags such as @semantic and @spelling, and docstrings with a content type.

@suite:frontend-fsharp @requires:frontend:fsharp @basis:hand-authored @review:0007
Feature: Records
  Record types and record update lower to Morphir records.

  Scenario Outline: frontend-fsharp-0007 Record update keeps the other fields
    Given the package "acme/cars"
    And the source document "src/Cars.fs":
      """fsharp
      module Acme.Cars.Cars
      type Car = { Plate: string; Seats: int }
      let withSeats (car: Car) (n: int) = { car with Seats = n }
      """
    When the sources are compiled for IR version <version>
    Then compilation succeeds
    And the IR equals the file "records/0007/expected-v<version>.json"
    And there are no diagnostics except severities "info, hint"

    Examples:
      | version |
      | 4       |
      | 3       |
      | 2       |

    @excluded
    Examples:
      | version | reason                                                        |
      | 1       | classic v1 spelling is covered by suite ir-writing (case 0012) |
  • Location and identity. Features are in conformance/suites/<suite>/. Ids are unique in the kit and are never reused. A removed case keeps its id reserved in kit.toml.
  • A closed step vocabulary. conformance/steps/steps-1.md is the normative grammar: each step's pattern, parameters, docstring content types and meaning. kit.toml declares the vocabulary version. A linter rejects any step outside the grammar. Each runner declares the vocabulary versions it implements, and a run refuses a kit whose vocabulary it does not implement. Adding steps raises the vocabulary minor version, and changing a step's meaning raises its major version.
  • Portable parsing. Official Gherkin parsers (cucumber/gherkin) exist for many languages, so another implementation needs only a parser and the vocabulary document. morphir-dotnet uses the Gherkin package that Reqnroll already depends on. The runner does not use Reqnroll step bindings: the oracle is the feature data plus the vocabulary, not a binding assembly.
  • No adapter in features. The implementation under test is chosen when the runner starts. The linter rejects adapter or executable names in steps and tags.
  • Matrices. Scenario Outline with Examples. Excluded combinations are rows in @excluded Examples blocks with a non-empty reason column. Every combination that the outline's dimensions allow is either listed or excluded.
  • Inline and sidecar artifacts. Sources and small values are docstrings with a content type ("""fsharp, """json, """ion) or data tables. Large expectations, such as complete expected IR, are sidecar files beside the feature, referenced by a step. A sidecar that no step references fails validation. Sidecars are part of the case-set digest.
  • Provenance and review (EVD-1) use tags (@basis:, @review:, @import:, @knownGap:) at feature, rule or scenario level, the nearest level winning. Review records are sidecar Markdown files in conformance/reviews/. Imported upstream features, such as the Ion kit, keep their bytes under imports/. Their dispositions are recorded beside them.
  • Generated literate documentation. A generator renders each feature as a Markdown page for the documentation site, with the feature and scenario prose, the sources, the expectations (sidecars included) and the exclusions with reasons. The pages carry a "generated, do not edit" header. A CI check generates them again and fails when the committed pages differ.

Alternatives considered:

  • Literate Markdown as the normative format. It reads well, but it has no standard parser or outline and matrix structure. It is used for the generated pages instead.
  • JSON manifests. They are harder for reviewers to read, and the maintainer rejected them.
  • Reqnroll bindings as the oracle. They would tie the oracle to one language's step code.

KIT-2. Comparison is exact by default; leniency is named

Each kind of observation has one documented canonical form. IR uses the canonical writer form of its version, and JSON reports use canonical JSON (RFC 8785). The default comparison is byte equality of the canonical forms.

A case can name normalizations from the normalization catalog in the kit manifest, for example:

  • ignore-json-member-order;
  • classic-unordered-module-lists;
  • v4-reference-shorthand;
  • ignore-variable-members:completedAt.

Each normalization has a written justification, and the report says which normalizations applied. A failure reports the first difference as a JSON Pointer together with both values.

Alternative considered: upstream's fixed set of semantic rules for every case. It hides real differences, such as declaration order in a writer, that some suites must check.

EVD-1. Expectations have a basis and a review

Each expectation has a basis:

  • spec-derived: follows from contract or IR text, which the evidence cites;
  • hand-authored: written by a person from the source;
  • upstream-imported: admitted from an import without change;
  • upstream-superseded: an import corrected with evidence.

An expectation produced by a tool, for example a writer, needs a review record in conformance/reviews/. The record names the reviewer and checks the output against the source. Kit validation enforces that every expected observation has a basis and evidence, and that every tool-produced expectation has a review.

When morphir-dotnet fails a reviewed case, the code is fixed, or the case gets a named knownGap. The expectation is never edited to match the implementation, as in dotnet-sdk-conformance.

EVD-2. Upstream material is imported, given a disposition, and superseded in public

Upstream files are copied unchanged under conformance/imports/<source>-<revision>/, with a PROVENANCE.md (repository, immutable revision, license, path, SHA-256). Kit validation checks the digests.

A disposition record gives every imported case one disposition:

  • admitted;
  • superseded, with the corrected expectation, the reason and the evidence;
  • excluded, with the reason.

An unclassified imported case fails validation. The supersession log is published with each kit release, and every entry needs an upstream issue link. Release validation enforces this.

The first import is the pinned spec/mep/mck/ material: model-transport.cases.json, the generic and Python kits and the Smithy transcripts. Expected dispositions:

  • The legacy 0.1 stage is excluded from guest profiles that speak only 0.2.0-draft.1.
  • The frontend+backend round trip is excluded from frontend-only profiles.
  • Recorded Python IR expectations are kept only after review against the contract. Otherwise they are superseded.

RUN-1. Plans come from profiles and claims only

A profile names suites and the claims that select them. The runner reads the claims: the MEP describe and initialize results for guests, a CLI capability probe for cli, and registrations for library. It builds the plan as the intersection. A case is planned only when the implementation claims what it tests.

This removes upstream's coupling:

  • A frontend-only guest gets no generation cases.
  • A guest that speaks only 0.2.0-draft.1 gets no legacy stage.

The plan is part of the report, so report-check can rebuild it.

RUN-2. Three adapters; process adapters are the qualification path

  • cli starts any morphir executable with ArgumentList and no shell, in a fresh temporary workspace, with a fixed environment. It observes the exit code, the stdout report or records, stderr and the files written. The capability probe runs <exe> --version and the documented help JSON, when present.
  • mep-guest reuses the MEP session core from add-fsharp-compile (Morphir.Mep), including framing, envelope admission, limits, deadlines, stderr draining and process-tree cleanup. Every response is checked against the pinned contract shape before the case comparison.
  • library runs in process for fast local feedback. It is never the only evidence for a claim about the executable. Qualification of a published build uses cli or mep-guest.

RUN-3. The runner is part of the AOT executable

Morphir.Conformance is AOT-compatible. It has a source-generated JSON context for reports and JSON observations, a Gherkin corpus reader and step-vocabulary matcher with no reflection (the Gherkin parser is checked for AOT warnings first), no reflection-based loading, and comparisons over JsonElement and bytes. The library adapter is registered only in hosts that contain the libraries it calls. For F# compile cases, that is dotnet-morphir. A CI closure check keeps FCS out of morphir.

REP-1. Reports record everything; report-check trusts nothing stored

A report is one JSON document with reportVersion. It holds:

  • the kit version and the case-set SHA-256, which is the digest of the kit manifest plus every corpus file, in path order;
  • the profile and the plan;
  • the claims;
  • the runner identity, which is the morphir version and the SHA-256 of its executable;
  • the adapter;
  • the executable path, its SHA-256 and its ordered arguments;
  • the identity files;
  • for each case in plan order: the request, the observation, the applied normalizations, the verdict and the first difference.

report-check works in this order:

  1. verifies the kit digest;
  2. verifies the identity digests that are present;
  3. rebuilds the plan from the recorded claims;
  4. derives each verdict again.

It never reads a stored verdict as fact. Upstream reports can be checked as evidence only through an adapter for their format. That adapter is a follow-up, and it is not needed to qualify implementations.

CMD-1. morphir mck follows upstream options and exit codes, and this repository's output conventions

morphir mck list --kit conformance --profile fsharp-frontend-v1
morphir mck run --kit conformance --expect-kit-sha256 <sha> --profile cli-v1 \
  --adapter cli --host /usr/local/bin/morphir --report .dev/mck-cli.json
morphir mck run --kit conformance --profile mep-frontend-v1 --adapter mep-guest \
  --host "$(which morphir-fsharp-frontend)" --identity-file "$(which morphir-fsharp-frontend)" --report .dev/mck-guest.json
morphir mck report-check --kit conformance .dev/mck-guest.json
  • The option names follow upstream guest-run (--host, --host-arg, --identity-file, --expect-kit-sha256, --report), so existing scripts move easily.
  • The exit codes are upstream's: 0 qualified, 1 failure or operational error, 2 invalid invocation. These deliberately differ from compile's "2 for operational". Scripts for mck already depend on upstream codes, and a conformance run treats any inability to finish as "not qualified".
  • --json writes one summary. --json-lines writes one record per finished case and then one completed record, with the same streaming rule as morphir compile --json-lines in add-fsharp-compile (STRM-2).
  • The command is registered by a Tooling scenario in both hosts. Handlers are mediator handlers, as for generate and compile.

REL-1. Relation to add-fsharp-compile and the existing corpora

  • add-fsharp-compile lands first. Its corpus becomes suite frontend-fsharp, and its runner and adapters become Morphir.Conformance. This change adds the kit manifest, schemas, profiles, normalization catalog, imports, reports, report checking and the command. If a seed format detail conflicts with this design, this change migrates the seed in its first task group.
  • tests/Fixtures/MorphirSDK and tests/Fixtures/MorphirIon/kit stay where they are. Later changes import them as suites. The import rules here make that a data move, not a redesign.
  • The default-CLI decision record uses MCK reports for morphir-dotnet and the Rust CLI as evidence of parity and viability.

Delivery order

  1. Kit data. The step vocabulary 1, the Gherkin corpus reader and linter, kit.toml, the normalization catalog, the generated literate pages with the stale check, and migration of the seed suite from add-fsharp-compile to features.
  2. Evidence. The basis and review rules, the first upstream import with dispositions, and the supersession log.
  3. Execution. Plans from claims, the generalized adapters, isolation, and AOT checks.
  4. Reports. The report schema, report-check, and tamper tests.
  5. Command. morphir mck run, report-check and list, with output and exit codes.
  6. Suites. ir-writing, cli, mep-guest and mep-host, built from the work in add-fsharp-compile.
  7. Evidence runs. Run against the morphir-dotnet executables and the Rust CLI, and publish the reports.

Risks and trade-offs

RiskMitigation
Expectations written by hand are slow to produce and can be wrong.Review records are required, and the basis and evidence are checked. Small, focused cases. Tool-produced drafts are allowed only with a review. A wrong expectation is corrected through a kit version change, never in silence.
morphir-dotnet both implements and judges, so there is a conflict of interest.The oracle is data with cited evidence. The rule that an implementation is fixed, never the expectation, applies to morphir-dotnet too. Supersessions are public and linked to upstream issues. The kit runs against other implementations, and its reports can be checked by anyone.
Upstream and this kit diverge, which confuses the ecosystem.The protocol definition stays upstream, and every divergence is an explicit disposition with an issue link. The goal is for the corrected kit to become the shared one.
Exact comparison makes harmless differences fail.Named normalizations exist for real equivalences, each with a written justification. The report shows which ones applied.
The official Gherkin parser may give trim or AOT warnings in the Native AOT executable.Task 2.1 checks it first. If it warns, the corpus reader is a small AOT-safe parser for the Gherkin subset that the vocabulary uses, and the official parser checks it in CI: both must give the same parse for every kit file.
Running other executables is a security concern.The user names the executable explicitly. There is no shell, a fresh temporary workspace, no network by default, deadlines and process-tree cleanup.
Kit size and release overhead.The kit is a separate release archive with a SHA-256, not embedded in the AOT executable.

Migration plan

  • The additions do not change any existing command.
  • Existing conformance tests continue to run.
  • Scripts that use upstream morphir mck mep guest-run can move to morphir mck run --adapter mep-guest with the same identity and report options.
  • Rollback: remove the scenario registration. The kit data has no effect on other commands.

Open questions

  • Who besides the change author signs review records for the first suites. This is a maintainer process decision; it does not change the record format.
  • Whether the kit archive is also published as a NuGet content package, in addition to the release archive.
