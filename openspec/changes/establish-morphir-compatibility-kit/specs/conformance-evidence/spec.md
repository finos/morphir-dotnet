# Spec Delta

## Purpose

Keeps the Morphir Compatibility Kit an independent oracle. Every expectation has a reviewed source, upstream material is imported with provenance, and where this kit corrects upstream, the evidence is recorded.

## ADDED Requirements

### Requirement: Expectations are independent of implementations under test
An expectation SHALL NOT be recorded from the output of an implementation that the kit qualifies, unless an independent review accepts it. Each expected observation SHALL have a `basis` of `spec-derived`, `hand-authored`, `upstream-imported` or `upstream-superseded`, and SHALL link its evidence.

#### Scenario: Recorded output without review
- **WHEN** a contributor adds an expected IR that was generated by the .NET writer, with no review record
- **THEN** kit validation fails, because the basis is missing or not supported by evidence

#### Scenario: Implementation disagrees with the kit
- **WHEN** the morphir-dotnet implementation fails a reviewed case
- **THEN** the implementation is fixed, or the case is classified `knownGap` with a named gap. The expectation is not changed to match the implementation.

### Requirement: Upstream material is imported with provenance
Upstream kits, transcripts and fixtures SHALL be copied unchanged under `conformance/imports/<source>/`, with the source repository, the immutable revision, the license, the path and the SHA-256 of each file. Validation SHALL fail when a pinned file changes.

#### Scenario: Pinned bytes change
- **WHEN** an imported transcript is edited by hand
- **THEN** kit validation fails, naming the file and its expected digest

### Requirement: Every imported case has a disposition
Each imported case SHALL be `admitted`, `superseded` or `excluded`. A superseded case SHALL record the corrected expectation, the reason and the evidence, for example the contract text. An excluded case SHALL record why the kit does not use it.

#### Scenario: Legacy tier is excluded from frontend profiles
- **WHEN** the upstream generic guest kit's mandatory legacy `0.1` stage is imported
- **THEN** it is excluded from profiles of guests that claim only `0.2.0-draft.1`, with the reason that the contract does not require it

#### Scenario: Superseded expectation
- **WHEN** an upstream expected IR was recorded from an implementation and conflicts with the contract
- **THEN** the case is superseded with the contract evidence, and its supersession record names an upstream issue

### Requirement: Supersessions are published
The kit SHALL publish a supersession log that lists each superseded or excluded upstream case, with its reason, its evidence and the upstream issue link. A supersession without an upstream issue link SHALL fail release validation.

#### Scenario: Release check
- **WHEN** a kit release has a supersession record with no upstream issue link
- **THEN** release validation fails, naming the record
