Context

See the proposal for motivation and roadmap boundaries. The repository has classic distribution, package, module, type, value and pattern ADTs in Morphir.Models. Its JSON codecs cover names, literals and types, but not a full library distribution. The existing version detector belongs to verification tooling and defaults unknown inputs to v3, which is unsafe for generation. Existing v1/v2/v3 validation fixtures contain empty libraries.

Morphir.Internal.CodeGeneration is development tooling with generators that accept .fs and return empty ASTs. Its test helper uses a default GeneratorContext and accepts empty output. Neither is a working backend or evidence that a packaged plugin loads in Myriad. The older backend PRD proposes v3-only CLI generation and lossy open-record conversion; this change replaces those decisions for the first delivery.

The central dependency pins include Myriad.Core 0.85.0, Fabulous.AST 1.10.0 and Fantomas.Core 7.0.5. The cached Myriad.Core package records source revision 165a7e5b424a16b5d507797e9ed43e4c3da12f5b. Its generator contract has InputFilename, AdditionalParameters and Output.Source. The matching SDK targets demonstrate host invocation and selector parameters. Each invocation has one output path.

Goals and non-goals

Keep decoding, name resolution, dependency planning and translation independent of Myriad and MSBuild. Generate one file per Morphir module as requested, with an explicit ordered manifest. Use the compiler and executable examples to establish correctness rather than treating snapshots as proof.

Do not change public IR representations or route through document trees, the object-based IR pipeline, or Wolverine hosting. Do not add a Morphir CLI command. This pass does not promise every SDK operation, open row polymorphism, arbitrary external libraries, cross-module recursion, or an incremental compiler cache.

Decisions

ARCH-1. Separate backend, Myriad plugin and build coordinator

Add Morphir.CodeGeneration.FSharp with versioned JSON decoding and a pure generation API over classic ADTs. It returns a Result containing an ordered module manifest and source, or typed diagnostics. Add Morphir.Myriad for the .json generator named morphir-fsharp. Add Morphir.Myriad.Build for the MSBuild task that coordinates multiple outputs. File access, process execution and output publication live in the adapters. Keep the development-only generator package unchanged.

Alternatives: extending the internal plugin would mix internal .fs tooling with public model generation. A CLI-first backend would not satisfy the build integration. A document-tree conversion would expand the explicitly deferred scope.

IR-1. Explicit classic version decoding

Parse formatVersion before dispatch. Accept integer 1, 2 or 3 only and require the matching Library envelope, tags and version-specific layouts. Reuse version-aware primitive codecs, adding the missing pattern, value, module, package and distribution decoders within the backend without changing existing codec defaults. Preserve attributes needed for type information and reference checking; incidental metadata does not affect emitted names. Use canonical non-empty fixtures checked against the repository's versioned schemas and wire conventions. Do not lowercase tags globally or normalize lists into maps before checking duplicate keys.

Alternatives: verification's fallback to v3 can reinterpret future data; generic F# union deserialization does not establish Morphir wire compatibility. A universal modern-IR conversion would couple this initiative to IR 4+.

EMIT-1. One source file per module with stable ordering

Plan the entire library before emission. Resolve local references and build module and declaration dependency graphs. Topologically order modules with canonical module paths as the tie-breaker. Emit types before dependent values and use type-and and let-rec-and groups within a module. Reject cycles between distinct modules and irreducible initialization cycles with the involved symbols. This preserves the requested file boundaries without moving public definitions between modules.

Use each module path to derive its file beneath a model-specific directory, for example Domain/Types.fs and Domain/Rules.fs. A stable escaped model identity separates models with identical input basenames. Reject traversal segments, normalized-name collisions and case-insensitive path collisions before any writes. Emit package namespace and module qualification consistently in every file. An empty library has an empty manifest. No extra model definition file is needed.

Use Fabulous.AST computation expressions and Fantomas with a fixed formatter configuration. Return formatted text via Output.Source, avoiding FSharp.Compiler.Service versus Fantomas.FCS syntax-type conversions. The manifest and generated file contents contain no timestamps or absolute input paths. An alternative single combined file simplifies cycles but contradicts the requested module layout. Per-module side effects hidden inside Generate would bypass Myriad's output contract.

MAP-1. Explicit representations and SDK mappings

Map named closed record aliases to F# record declarations, custom types to unions, and anonymous closed structural records to consistent anonymous-record types and expressions. Carry expected types through construction, field access and updates. Reject open ExtensibleRecord nodes rather than erase their rows. Escape identifiers with F# double backticks and detect collisions after canonical casing. Bind local names through lexical scopes so escaping and shadowing never capture a different variable. Keep private model members inaccessible to external consumers, using assembly-internal visibility where package-local references require it.

The initial SDK table maps Int to int, Float to float, Bool to bool, String to string, Char to char, List to list, Maybe to option, and Result error/success parameters to F# success/error parameters. Use the existing SDK Order representation. Map add, subtract, multiply, divide, equality and ordered comparisons, List.map, Maybe.map and Result.map only after compiler and behavior tests establish their argument order and numeric behavior. Prefer standard F# operations when equivalent and explicit Morphir.SDK references when required. No suffix-based or reflection-based name guessing. Generated consumers reference Morphir.SDK when the emitted mapping requires it.

WholeNumberLiteral carries int64 in the model while Morphir.SDK.Basics.Int is int32. Reject literals outside the mapped range rather than narrow silently. Emit invariant escaped literals, decimal suffixes and correct float syntax; add tests for boundaries and arithmetic behavior. Unsupported SDK entries or specification-only external dependencies fail with their FQName. Alternatives: copying SDK implementations creates a second runtime to maintain; resolving every name to an F# spelling hides semantic differences.

BUILD-1. Coordinate one Myriad invocation per module

The proposed consumer-facing item is MorphirModel, with one JSON Include and optional output directory metadata. The package supplies a task and targets. The task resolves paths from MSBuildProjectDirectory, validates the whole model, obtains the ordered module plan and invokes the matched Myriad host once per module. Pass the original JSON as InputFilename and a stable encoded MorphirModule selector through AdditionalParameters; the plugin validates that selector and returns exactly that module. A direct host invocation without a valid selector fails. No marker .fs file is required.

Use the host's inputfile, outputfile, plugin, generator-filter and additionalparams arguments. Pass arguments without shell interpolation and direct plugin diagnostics to stderr. Package the compatible host/runtime assets or resolve them from the explicitly pinned Myriad.Sdk restore assets. Prove the exact restored executable path and dependency resolution in the first end-to-end slice. Do not depend on the SDK's private target names or let its automatic generation run a second time for coordinator-owned files.

The coordinator target runs before F# compilation and returns generated Compile items in manifest order ahead of handwritten files, preserving the latter's relative order. Run planning on every ordinary build initially; avoid rewriting identical output. This favors reliable regeneration and module additions/removals over speculative caching. Design-time builds may consume the last successful manifest without launching generation; a normal clean build establishes the outputs.

Alternatives: manual Compile/MyriadFile entries with selectors force users to maintain a module list. A generator writing arbitrary sibling files would leave compilation order and stale-output cleanup undefined. The coordinator keeps those responsibilities explicit.

BUILD-2. Publish a complete generation result

Validate all definitions and paths before host emission. Generate into a staging directory under the target intermediate directory, scoped by project, configuration, target framework and model. Publish the manifest only after every invocation succeeds. Add files to compilation only after successful publication. On failure, return a failed task result and block CoreCompile even if previous files exist. Reconcile the prior manifest after success and delete only obsolete files owned by that manifest inside the model output directory. MSBuild clean removes owned intermediate artifacts.

Use isolated staging paths for concurrent builds. Serialize publication for the same model output identity and reject duplicate model/output ownership in a project. No cross-process cache is needed. Alternatives: publishing each module immediately exposes partial output; relying on file timestamps alone can retain stale modules.

QA-1. Test real host and compiled behavior from the first slice

Keep complete IR text in fixture resources. Test projects embed the shared files under tests/Fixtures/MorphirIR and link the car rental models directly from the example. Load them through assembly resource helpers; standalone F# checks read the same files from disk. Use JsonNode for structural substitutions instead of inline JSON templates. Focused IR object builders remain useful for individual construct tests.

Begin with a failing BDD scenario that builds and executes a tiny non-empty v3 model through a locally packed plugin. Then implement that vertical slice before broader syntax coverage. Each subsequent group adds a failing focused test, minimal implementation and refactoring with green tests. Use Expecto for F# component tests, Verify.Expecto for reviewed source snapshots, and the repository's Reqnroll integration conventions for consumer builds. Never reuse the internal stub helper as generation evidence.

Cover non-empty v1/v2/v3 models, every listed type/value/pattern family, SDK result ordering, numeric and string escaping boundaries, module ordering, privacy from a separate assembly, malformed and unsupported inputs, deterministic output, module add/remove, repeat builds, paths containing spaces and stale output after failure. Compiler diagnostics determine syntax and type correctness; executed fixtures determine expected behavior. Include a local nupkg consumer without references to source-tree build output. Run trim/AOT publication on a representative generated consumer, not on the Myriad host.

EX-1. Use car rental as the runnable teaching example

Deliver examples/car-rental/ with a checked-in model JSON, equivalent version 1/2/3 fixtures, readable descriptions of its modules and rules, fixture provenance/update instructions and a thin F# console consumer. A fresh checkout and the documented .NET/package setup must be enough to run it. An optional upstream authoring tool must not become a prerequisite for the tutorial. Keep the tiny first build slice as an inventory or daily-rate function from this example, then expand the same example as the backend gains support.

All inventory, reservation, pickup, return and billing decisions belong to the Morphir model and execute through generated functions. Handwritten F# supplies explicit inputs, sequences calls and displays results. Use immutable state and typed Result errors. The supplied sample car has a daily rate of 5000 cents. Reserving an available car marks it reserved and captures that rate; pickup of the confirmed reservation marks it rented. Return of an active rental records positive whole billable days, completes the reservation and makes the car available. Billing the completed rental once uses the captured rate times actual billable days, so three days costs 15000 cents.

The example allows one active reservation per car and makes the car unavailable immediately when reserved. It uses explicit day counts and integer cents within the supported Int range. Future-dated booking calendars, time zones, taxes, discounts, payment collection, persistence and user interfaces are outside the example. These choices keep the workflow within the initial SDK mappings and avoid requiring new runtime integrations. Rejections include an unavailable car, pickup without a confirmed reservation, return without an active rental, nonpositive durations, billing before return and duplicate billing. Each rejection leaves the supplied state unchanged.

Risks and trade-offs

RiskMitigation
Myriad host, FSharp.Core and Fantomas assembly versions differ from the plugin's versions.Prove packaged loading first using the existing central pins; isolate build-task dependencies. A failed compatibility check blocks mapper expansion and requires a concrete dependency fix.
Historical JSON variants are only lightly exercised by current fixtures.Add canonical non-empty version-specific fixtures and strict decoder tests. Do not claim compatibility from empty schema-validation samples.
Separate files cannot represent arbitrary cross-module recursion.Reject those graphs explicitly. Support recursive declarations within a module and document the file boundary limitation.
SDK numeric and collection semantics may differ from a similarly named F# function.Use an explicit tested mapping table, reject integer narrowing, and document numeric/runtime limits. Reject unmapped references.
Re-decoding a library for each module increases build time.Accept this cost for the first delivery and measure it. Defer caching until correctness and invalidation behavior are established.
New module sets or failed generation leave old files.Publish a complete manifest, compile only that manifest and block compilation on any generation failure. Remove only previously owned obsolete paths.
The tutorial drifts from the model or quietly implements rules in handwritten F#.Use one shipped car rental example for the articles and automated checks. Assert lifecycle and invoice behavior through generated functions in clean package consumers.

Migration plan

  1. Reconcile the existing backend PRD and PRD index with this delivery, preserving the broader roadmap and marking implementation status as work starts.
  2. Add backend, plugin and coordinator projects and a package-consuming example. Prove the smallest real Myriad build before extending mappings.
  3. Expand supported classic constructs and version fixtures with tests and documentation alongside each change. Complete the strict compatibility and rejection matrix.
  4. Finish the car rental model and consumer, plugin reference, getting-started article and end-to-end tutorial. Verify the full workflow, business rejections, model-edit exercise and documentation-site navigation before declaring the example complete.
  5. Run repository format, unit, BDD and contract checks plus local package-consumer and generated-code trim/AOT checks. Update contribution notices as applicable.
  6. Publish or merge only under the repository's existing explicit authorization rules. Rollback is removal of the opt-in package references and MorphirModel item; generated files live under intermediate output. No existing IR files, APIs or development generators are migrated.
