## What was built

| Bound | How the host enforces it | Reported as |
| --- | --- | --- |
| Instruction budget | Fuel set before each call. `SessionLimits.ForProtocol` reads the budget for the MEP version from the pinned contract: 5,000,000,000 on `0.2.0-draft.1`, 1,000,000,000 on `0.1`. | `extension.budget_exhausted` |
| Call deadline | The epoch advances every 10 ms. The store's epoch callback (`Store.SetEpochDeadlineCallback`) runs at each tick on the call's thread and stops the call once the deadline has passed. | outcome `deadline` |
| Cancellation | The same callback stops the call at the first tick after the call's `CancellationToken` is cancelled. | outcome `cancelled` |
| Memory ceiling | Store limit of 256 MiB for each memory. A call that fails with the guest's memory at the ceiling is reported as a memory limit. An initial memory above the ceiling fails `Open`. | `extension.memory_limit` |
| Anything else | A trap, a host function that stops the call, or `proc_exit` with a code that is not 0 | `extension.guest_trap`, `extension.incomplete_session` |

Every failure carries the guest's memory size, the kernel's memory size and the ceiling. The codes come from
the contract's `faults` table. After a failed call the session is finished, and a later call returns
`HandleOutcome.NotRun` with the same failure without running the guest. The library README has the details.

## Ctrl+C and exit status 130

No command reaches the runtime yet, so this task checks cancellation in-process only. A token cancelled
300 ms into a spinning call stopped the call about 60 ms later, with outcome `cancelled`.

What exists in the CLI:

- `Program.Main` calls `MorphirCliApp.Run()`, which starts the generic host and calls `ParseResult.Invoke()`
  from System.CommandLine 2.0.14. In System.CommandLine, Ctrl+C cancels the token of an asynchronous action.
  The generic host is built with `Host.CreateApplicationBuilder`, which also installs the console lifetime's
  Ctrl+C handler.
- Exit status 130 is set by each feature. `GenerationReport` and `CompileContracts` map their `Cancelled`
  failure kind to 130, and `ModelValidation` maps an `OperationCanceledException` to 130.
- The tests cancel in-process: they pass a `CancellationTokenSource` to `MorphirCliApp.RunAsync`
  (`GenerationReportingTests`, `CompileCommandTests`, `CompileRunnerTests`, `ModelValidationTests`). No test
  sends Ctrl+C or SIGINT to a child process, on Windows or on Unix. `tests/Morphir.E2E.Tests` has no signal
  helper, and `ChildProcess` in `tests/Morphir.TestSupport` only stops process trees.

What task 4.1 must add:

1. In `morphir extension worker`, pass the command's cancellation token to `SessionStore.CallHandle`. Map
   `GuestFailure.Outcome == "cancelled"` to exit status 130, and decide whether a `fault` or `exited` event is
   written first. The worker README fixes exit statuses 0 to 3 only.
2. Check that the System.CommandLine handler and the console lifetime handler do not race. The console
   lifetime stops the host while the action is still running.
3. Add an E2E test for both executables. It starts the worker on `extism-spin.wasm` with an unlimited
   `--instructions`, so that only cancellation can stop it in time. It sends Ctrl+C while `handle` runs and
   checks that the process exits within one second with status 130 and writes no frame to stdout.
   - Unix: `kill -INT <pid>`.
   - Windows: `GenerateConsoleCtrlEvent` reaches only processes that share the sender's console, and it
     cannot send `CTRL_C_EVENT` to a single process group. So the child starts in a new process group
     (`CREATE_NEW_PROCESS_GROUP`, with no window), and a small helper process attaches to the child's console
     (`AttachConsole`) and sends `CTRL_BREAK_EVENT` to it. .NET reports Ctrl+Break as
     `PosixSignal.SIGQUIT` and `ConsoleSpecialKey.ControlBreak`, not as `SIGINT`. The worker must treat it
     as Ctrl+C, or the test does not exercise the Ctrl+C path.

I did not add a Ctrl+C mode to the AOT probe. Sending a console control event from a test needs the
process-group and console handling above, which I could not make reliable here without a visible console.

### The budgets and the open question on the fuel value

No guest comes near either budget. The largest call, 3,321,411 units, is 0.33 % of 1,000,000,000 and 0.07 % of
5,000,000,000. The kit's inputs are small, so this says nothing about large models.

A tight loop on Wasmtime uses about 1,000,000,000 units per second on this machine: `bounds/spin-extism` used
5,000,000,000 in 4.9 to 5.5 s. A runaway guest therefore holds a core for about 5 s on MEP `0.2.0-draft.1`
and about 1 s on `0.1` before the budget stops it. The parent design's figure 3 says that a busy loop "hits
the budget in tens of milliseconds"; with the contract's numbers on Wasmtime, that is not so. The budget still
ends the call well before the 30 s deadline, which is all the corpus requires.

## Differences between the specs, the contract and the corpus

1. **Cancelled is not a contract fault kind.** The .NET spec requires outcome `cancelled`, and the contract
   lists only `trap`, `memory-limit`, `budget-exhausted`, `call-deadline` and `failure`. The host keeps
   `cancelled` as an outcome with no fault kind and no code. The worker's event for it is open for task 4.1.
2. **Which failures the memory rule replaces is not stated.** The contract and the specs say that any call
   that fails at the ceiling is `memory-limit`. The specs also say that a passed deadline ends the session
   with outcome `deadline`, and that cancellation reports `cancelled`. The host applies the memory rule to
   the failures that have a code (trap, failure, budget exhausted) and keeps the two outcomes as they are.
   `GuestFailure.Signal` keeps the signal from before the rule. This needs a review.
3. **Which memory counts.** The rule names "the guest's memory". In an Extism session, the guest's input,
   output and allocations live in the kernel's memory, which also has the ceiling. The host decides on the
   guest's own memory only and reports the kernel's memory as well. When kernel memory is full, `alloc`
   returns 0, and a guest that then traps is reported as `extension.guest_trap`.
4. **The guest's memory may not be exported.** All four memory modules of the bounds cases, and 15 of the
   other 21 crafted Extism modules with a memory, define it without exporting it. Wasmtime gives the host a
   memory only through an export. To read the size, the host
   compiles a copy of such a module with one more export entry, `morphir:host/guest-memory`. The code and the
   memory are unchanged, and the digest and classification stay the original's. This reads section headers
   only, but it is still a change to the bytes that run. The parent's BND-2 rejected rewriting a module to
   report failed growth, and the local design says no managed WASM parser is added. This needs a review. No
   published guest needs the copy.
5. **The budget speed.** See the previous section: figure 3 of the parent design does not match Wasmtime.
6. **Group 3 negotiation.** A host that offers `0.2.0-draft.1` must send `modelTransport`, or the published
   guests refuse it with a message that misstates what they support. The local `mep-protocol` delta and the
   parent spec should say so.
