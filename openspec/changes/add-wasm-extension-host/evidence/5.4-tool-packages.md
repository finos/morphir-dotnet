# Task 5.4, first step: platform-specific tool packages with a fallback

Date: 10 November 2026. Branch `ci/tool-platform-packages`, commit `5ed6456`. SDK 10.0.403 everywhere:
`dotnet --version` printed `10.0.403` on this machine (Windows 11 on ARM64), on the `ubuntu-24.04` runner
and in the Alpine container.

## The question, and the answer

Can the pinned SDK publish the framework-dependent `dotnet-tool` offering as one package per platform that
has a WASM engine, plus a fallback package with no engine, under one package id?

**Yes, with one addition the SDK does not make by itself.** `dotnet tool install <id>` picks the right
package on Linux x64 (glibc) and on Linux musl, every package stays framework-dependent, and update and
uninstall work, globally and with a tool manifest. The addition is a small MSBuild target that takes the
engine out of the packages for platforms that have none. Without it the `any` fallback carries all six
engine libraries (51 MB), and the musl packages carry the glibc engine, because the RID graph makes
`linux-musl-x64` import `linux-x64`. No second, neutral package identity is needed.

A user needs the .NET 10 SDK to install it. SDK 8 and SDK 9 refuse the package.

## The spike

`spikes/extension-model/tool-platform-packages/` is a throwaway tool, `spike-platform-probe`, that references
`Wasmtime` 50.0.1. `--report` prints the runtime identifier, the engine libraries in the tool's own
directory, and whether `new Wasmtime.Engine()` works. It is not in `Morphir.slnx`, and its own
`Directory.Build.props` and `Directory.Build.targets` keep the repository's settings out. `pack.ps1` packs
it; `test.ps1` installs it; `.github/workflows/tool-platform-packages.yml` runs both on Linux.

### The properties

In `PlatformProbe/PlatformProbe.csproj`:

| Property | Value | Why |
| --- | --- | --- |
| `PackAsTool` | `true` | A .NET tool. |
| `RuntimeIdentifiers` | `win-x64;win-arm64;linux-x64;linux-arm64;osx-x64;osx-arm64;linux-musl-x64;linux-musl-arm64;any` | Restore needs a target for every tool RID. Without `any` here, the fallback's pack fails with `NETSDK1047: ... doesn't have a target for 'net10.0/any'`. |
| `ToolPackageRuntimeIdentifiers` | the same list | Turns on RID-specific tool packages (`CreateRidSpecificToolPackages` becomes `true`) and names the packages. |
| `SelfContained` | `false` | Framework-dependent, like the offering. This is also the SDK's default for these packages. |
| `UseAppHost` | `false` | Keeps the portable tool's runner, `dotnet <dll>`. With an apphost the SDK writes `Runner="executable"`, and the apphost finds the runtime through `DOTNET_ROOT` or the default install location. |
| target `SpikeDropEngineWhereUnsupported` | after `ResolvePackageAssets`, when the RID is not one of the six | Removes the `Wasmtime` package's native items from `NativeCopyLocalItems` and `RuntimeTargetsCopyLocalItems`. The library is then out of the package and out of its `deps.json`. |

One `dotnet pack` builds all of them. The inner builds each get only `RuntimeIdentifier=<rid>`
(`_CreateRIDSpecificToolPackages` in the SDK's `Microsoft.NET.PackTool.targets`). A build for `any` counts
as a portable build there, so it publishes `runtimes/<rid>/native` for all six platforms.

## The five questions

1. **How the SDK packs it.** `ToolPackageRuntimeIdentifiers` (or `RuntimeIdentifiers`) with `PackAsTool`
   makes one `dotnet pack` produce a pointer package `<id>.<version>.nupkg` and one package
   `<id>.<rid>.<version>.nupkg` per RID. The pointer holds only `tools/any/any/DotnetToolSettings.xml`,
   which lists the RID package ids. `any` in the list adds a framework-dependent fallback package
   `<id>.any`, and "on any other operating system or architecture, the framework-dependent `any` package is
   used". Seen here: a machine whose platform has no package of its own installed `any`. A musl machine
   **does** match `linux-x64` through the RID graph (`linux-musl-x64` imports `linux-musl` and `linux-x64`
   in the SDK's `PortableRuntimeIdentifierGraph.json`). So musl needs packages of its own to avoid the
   glibc engine.
   Source: [Create RID-specific, self-contained, and AOT .NET tools](https://learn.microsoft.com/en-us/dotnet/core/tools/rid-specific-tools)
   (updated 27 January 2026), sections "Opt in", "Provide a framework-dependent version" and
   "Package your tool".
2. **Framework-dependent RID packages.** Yes. The documentation says the SDK "creates self-contained
   packages for each specified RID", but SDK 10.0.403 does not. Its inner builds set only
   `RuntimeIdentifier`, and since .NET 6 a RID does not imply self-contained. Every RID package above has a
   `runtimeconfig.json`, no runtime of its own, and ran on the installed .NET 10.0.14. The
   [.NET 10 Preview 6 SDK notes](https://github.com/dotnet/core/blob/main/release-notes/10.0/preview/preview6/sdk.md#platform-specific-net-tools)
   name "framework-dependent, platform-specific" as one of the supported kinds. `SelfContained=false`
   states it, and `UseAppHost=false` keeps the `dotnet` runner. The offering's nature does not change.
3. **Install, update, uninstall from a local feed.** All work on both Linux machines, globally with
   `--tool-path` and locally with a manifest. The table above shows the package each machine chose and
   what is on disk. Only the pointer and one RID package are downloaded.
4. **Older SDKs and `dnx`.** The documentation says nothing about older SDKs. Measured: SDK 8.0.427 and
   9.0.320 refuse the pointer package (`Format version is higher than supported ... Update your SDK.`).
   `dnx` is new in SDK 10. The documentation says it picks the package the way `install` does, and it did,
   on both machines. **The minimum SDK for a user is the .NET 10 SDK.** The page "applies to .NET SDK 10
   and later". Only 10.0.403 was tried; no earlier 10.0 band was tested. Today's portable `Morphir.Tool` targets
   `net10.0` and so already needs a .NET 10 runtime. This arrangement adds the need for a .NET 10 SDK to
   install it.
5. **Versions.** "All RID-specific packages must have the exact same version as the top-level package"
   and should be pushed before it ([Publish your tool](https://learn.microsoft.com/en-us/dotnet/core/tools/rid-specific-tools#publish-your-tool)).
   The pointer names ids, not versions, and its nuspec has no dependencies. When the RID package of the
   pointer's version is missing, update fails by name, and the installed version stays and runs. The CLI
   does not fall back to `any`. A machine whose RID package is present updates normally (here `win-arm64`
   to 1.2.0).

## What task 5.4 should do

- Convert `Morphir.Tool` as in the spike: `RuntimeIdentifiers` and `ToolPackageRuntimeIdentifiers` with the
  six engine platforms, `linux-musl-x64`, `linux-musl-arm64` and `any`; `SelfContained=false`;
  `UseAppHost=false`; and a target that removes the `Wasmtime` native assets for the RIDs without an
  engine. One package id stays, `Morphir.Tool`. No neutral second identity is needed.
- Setting `RuntimeIdentifiers` on the project changes its ordinary restore too. Check the project's build,
  tests and the managed composition after the change, and coordinate with the work in flight on
  `Morphir.Tool.csproj`.
- `PackTool` (`build/Build.Packaging.cs`) then writes ten packages. The publish steps glob
  `Morphir.Tool.*.nupkg` (`build/Build.Publishing.cs`), which now matches all ten. They must push the nine
  RID packages first and the pointer last, all at one version.
- Verify `dotnet-morphir extension runtimes --json` from the released packages: available on `linux-x64`,
  `platform_unsupported` on Alpine and from `any`.
- In the install guide and release notes: the .NET 10 SDK is required to install the tool (SDK 8 and 9
  fail with "Format version is higher than supported"). Musl and other platforms get the tool without the
  WASM runtime. A RID package missing from a feed blocks install and update on that platform.
