Date: 10 November 2026. Machine: Windows 11 Home 10.0.26300 on ARM64, platform `win-arm64`. Branch
`feat/wasm-extension-host` at `d7de919` plus the uncommitted change this file describes. Release `0.4.0-alpha.4`,

### The runtime probe

`WasmRuntimeProbe.Probe` starts the engine first and asks whether the library file exists only after a
`DllNotFoundException`. With `DirectPInvoke`, the calls into Wasmtime are resolved at link time. The engine starts,
the probe returns `available`, and nothing looks for a file. The lone-executable run above confirms it. No code change
was needed.

### Default builds

`dotnet build src/Morphir` without the switch still puts all six `runtimes/<rid>/native/` libraries in its output. The
242 tests in `Morphir.Tooling.Tests` under `Features/Extensions` pass. So do the E2E engine cases against that build,
which find and delete the library as before.

### Linux

No workflow was changed. A Linux `native-aot` artifact built with these targets today is linked on the build machine,
not inside the pinned `ubuntu:22.04` image. From `5-linux-floor.md`: linked on an Ubuntu 24.04 runner, the executable
needs `GLIBC_2.38` (`fmod` and `fmodf` from libm), with the engine linked in or not. Linked inside `ubuntu:22.04`, it
needs at most `GLIBC_2.34`. The repository's floor for a released Linux executable is glibc 2.35. Only the container
lane, which another branch adds, meets it. Until then, nothing may claim the 2.35 floor for a Linux `native-aot`
artifact. This change adds no check of the floor.

## Part 2: what engine each artifact carries

### The record

`PackagedContents.Engines`, a list of `PackagedEngine`, written as `engines` in `<artifact>.build-contents.json`:

| Member | Separate library | Linked |
| --- | --- | --- |
| `path` | the library's path in the artifact | the executable it is linked into |
| `platform` | the RID: from `runtimes/<rid>/native/`, otherwise the artifact's | the artifact's RID |
| `sha256` | the library file's | the pinned C API archive's |
| `delivery` | `separate-library` | `linked` |
| `version` | the restored `Wasmtime` package's | `MorphirWasmtimeCApiVersion` |
| `source` | `Wasmtime <v> package, runtimes/<rid>/native/<file>` | the archive's URL |

The package's files are hashed from the package folder that the project's last restore resolved, read from
`obj/project.assets.json`. The build hard-codes no digest.

### The checks

`PackRelease` fails, deletes the artifact and names both digests or the reason, when:

- a separate library's SHA-256 differs from the package's file for its platform;
- an artifact for one platform carries a library for another platform: below another platform's
  `runtimes/<rid>/native/`, under another operating system's file name, or with another platform's bytes;
- an offering that carries the engine as a library has none for its platform, or has two;
- the portable tool package lacks one of the six platforms;
- a deployment that links the engine in also carries an engine library, or its platform has no pinned archive;
- an artifact declared `single-file` carries a separate engine library (task 5.3).

`PublishedLayout.Check` also refuses a `single-file` publish folder that holds any file besides the launch path.

## Notices

The form follows the notices thread (#584): one JSON declaration per library that no NuGet package provides, with its
licence text beside it. This branch does not read them. The pack step that does comes with #584.

| File | `name` | `version` | `license` | `sha256` of |
| --- | --- | --- | --- | --- |
| `wasmtime.<rid>.json`, six | `libwasmtime.a` (Linux, macOS) or `wasmtime.lib` (Windows) | 50.0.1 | `Apache-2.0 WITH LLVM-exception` | the static library inside that platform's pinned archive |
| `extism-kernel.json` | `extism-kernel.wasm` | 0.3.0 | `Apache-2.0` | the embedded module, as `PROVENANCE.md` and `ExtismKernel.Sha256` record |

- `wasmtime.LICENSE.txt` is `LICENSE` from the C API archives, unchanged (SHA-256 `268872b9…86bc5`, the same in all
  six). The `Wasmtime` NuGet package ships no licence file. The archives have no NOTICE.
- `extism-kernel.LICENSE.txt` is `Kernel/LICENSE`, byte for byte. `extism-kernel.NOTICE.txt` is `Kernel/NOTICE`, kept
  beside it rather than appended, because the form has one `licenseFile` member.
- `source` of each Wasmtime declaration is that platform's archive URL in `WasmtimeCApi.props`. For the kernel it is
  the package archive `https://download.mooncakes.io/user/moonrockz/extism/0.3.0.zip` that `PROVENANCE.md` names.

Digests of the linked files: each of the six pinned archives was downloaded into a scratch folder and checked against

`NativeNoticeDeclarationsTests` checks the following. There is one Wasmtime declaration per pinned archive and no
other. Each declaration's `name`, `version` and `source` agree with `WasmtimeCApi.props`. Its `sha256` is checked
against the extracted file when the build has fetched and verified that archive. Otherwise it cannot be derived from
the pin without a download, and the test checks only the version and source. The kernel's version and digest agree
with `ExtismKernel` and with the embedded file, and its licence and notice copies equal the originals. With one digit
of the `win-arm64` digest changed, the test fails.
