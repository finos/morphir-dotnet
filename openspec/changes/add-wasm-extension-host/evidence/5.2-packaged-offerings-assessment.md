What is missing for 5.2:

- **Released archives of the offerings.** No release lane publishes them. "Verify each released archive" cannot run
  until deployment task 2.5 adds one.
- **Linux builds at the floor.** `self-contained` and `framework-dependent` are published on the runner, glibc 2.39.
  `5-linux-floor.md` shows that a runner-linked .NET executable needs `GLIBC_2.38`, so it fails on Ubuntu 22.04 and
  Debian 12.
- **Clean Linux images.** The library needs OpenSSL for `SHA256.HashData` and `RandomNumberGenerator`. The managed
  offerings do not set `InvariantGlobalization`, so they need ICU. `runtime-deps:10.0` has both, so it hides the
  problem. A run must load a guest, because `--version` never touches OpenSSL.
- **A read-only install scenario** in the E2E suite. Nothing runs one today.
- **A WASM session from the clean environment.** The clean runs check `--version` only.
- **Clean Windows and macOS.** Hosted runners have .NET installed. For `self-contained` the host trace already shows
  that the machine's runtime is not used. A Windows runner with a registered location skips the scenario.
- **`osx-x64` and `win-arm64`.** 5.2 says six platforms. Releases ship four. The workflows can run all six on demand.

What would detect a mismatch today: little.

- The runtime report's `50.0.1` is the constant `WasmRuntimeIdentity.EngineVersion`. A test checks it against
  `Directory.Packages.props` and the loaded managed assembly. Nothing reads the native library, so a stale or foreign
  library beside the executable would still report `50.0.1`.
- For the static link, `build/wasmtime/WasmtimeStaticLink.targets` checks the C API archive's SHA-256 and its
  `WASMTIME_VERSION` against the package version, at build time.
- No pack-time check compares an artifact's engine library with the package's file for its RID, and no build output
  records the digest.

## Surprises

- On this branch the `native-aot` archive claims `single-file` and holds two files. Only the E2E run notices.
  `PackRelease` passes.
- The released legacy executable would ship without its engine, because `deployment.yml` copies only the executable.
  This is inferred from the workflow and `4.2-runtime-report.md`. I did not run `PublishSingleFile`.
- The reported engine version is a constant. It cannot detect a wrong native library.
