## Contract questions found while building the runner

These come from reading the pinned contract, the corpus conventions and the specs, not from the run.

1. **Worker arguments.** The pinned contract's worker table lists `--abi`, `--module`,
   `--build-identity`, `--request-bytes`, `--response-bytes`, `--call-ms`, `--instructions`,
   `--memory-pages`, `--json` and `--help`. The corpus convention sends
   `--abi <declaredAbi> --module <wasm> --build-identity <identity> --json`, with
   `--request-bytes` and `--response-bytes` when the case gives them; the runner sends exactly
   that and never `--call-ms`, `--instructions` or `--memory-pages`, which keep their defaults.
   The two agree. The example in this change's `wasm-host-qualification` spec
   ("starts `<host> extension worker --module <wasm> --json`") leaves out `--abi` and
   `--build-identity`; it is marked illustrative, but it should name them.
2. **Report identity has no source in the worker mode.** The spec requires the report to identify
   the host's "declared offering, platform and engine". The worker reports none of them: `started`
   has `abi`, `moduleSha256`, `buildIdentity` and `bounds`, and `--help --json` has `help` and
   `buildIdentity`. The runner takes them as inputs (`--offering`, `--platform`, `--engine`), as
   the corpus takes the profiles (`withoutCase` `hostSession:profiles-reported`), and
   `report-check` refuses a report without them. Parent task 1.4 should say where they come from.
3. **Guest output joining.** The convention says the strings occur "in the text of the run's output
   events joined in their order" without a separator. The runner joins with nothing between.
4. **Notification member.** The upstream corpus README says the notification cases advertise
   `capabilities.notificationDelivery` (`call`, `unlisted`). The pinned modules and the pinned
   contract use `capabilities.notifications.accept`, which the contract marks provisional. The README
   text is behind the pinned files.
5. **JSON equality.** The conventions say a frame matches when its body "parses to a JSON value
   equal to" the expectation, without defining equality. The runner ignores object member order,
   compares numbers by value (`1` equals `1.0`) and strings ordinally.

## What the .NET worker must do for this runner (task 4.1)

- Answer `extension worker --help --json` with one `morphir/command-result` on stdout whose
  `result.buildIdentity` is 64 hexadecimal digits, and exit 0.
- Accept the arguments above in any order, with `--json` writing one `morphir/command-event` line per
  event on stderr (`profile`, `event`, and the event's members).
- Keep stdout to Content-Length framed responses only, and keep reading stdin until its instance
  ends: the runner never closes stdin before the worker exits.
- Exit by itself after `morphir.exit`, a fault or a refusal; the runner stops a worker that is still
  alive one call deadline per frame plus 2 seconds after its last frame, and fails the case.
- Declare its bounds in every `started` event, the same way in every run: the runner derives the
  host's declaration from all started events and treats disagreement as an error.
