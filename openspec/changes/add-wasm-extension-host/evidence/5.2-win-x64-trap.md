# Task 5.2: why a trapping guest kills the process on win-x64

Date: 10 November 2026. Branch `ci/wasm-win-x64-trap`, from `feat/wasm-extension-host` at `f79632ed`. SDK 10.0.404 on
the runners, `Wasmtime` 50.0.1. Issue #563. This follows failure 1 of `5.2-offerings-on-six-platforms.md`.

## The cause

**Proven.** On x64 Windows, a process whose main executable is marked CET-compatible runs with hardware shadow stacks
and context IP validation. When a guest hits a hardware-detected trap, Wasmtime's vectored exception handler rewrites
the thread's `Rip`, `Rsp` and `Rbp` to the landing pad of the entry trampoline, in JIT code, and returns
`EXCEPTION_CONTINUE_EXECUTION`. When Windows continues the thread to that address, it refuses, because the address is
not on the shadow stack and not in any EH continuation table. It then ends the process with `0xC0000409`, subcode
`0x30` `FAST_FAIL_SET_CONTEXT_DENIED`.

The evidence:

- **The crash record.** The trap was run under `cdb` on the runner, once in the framework-dependent apphost and once
  in Native AOT. Both gave the same record:
  `Security check failure or stack buffer overrun - code c0000409 (!!! second chance !!!)`,
  `Subcode: 0x30 FAST_FAIL_SET_CONTEXT_DENIED`, `ExceptionAddress: ntdll!RcContinueExit+0x13`. The stack goes
  `ntdll!RcContinueExit` ← `ntdll!KiUserExceptionDispatch` ← a JIT address (the guest's code) ← `wasmtime!…` ←
  `wasmtime!wasmtime_func_call` ← `Wasmtime.Function.Invoke`. The same run under `cdb` with a host function that throws
  ended with exit code 0. WER wrote no minidumps: `WerSvc` is stopped on the image and did not start.
- **The policy in force**, read inside each process with `GetProcessMitigationPolicy(ProcessUserShadowStackPolicy)`.
  It is `0x105` (`EnableUserShadowStack, SetContextIpValidation, CetDynamicApisOutOfProcOnly`) in every process that
  died. It is `0x100` (shadow stacks off) in every process that lived through the same trap. That held in all 760 case runs on win-x64 across the two runs, with no exception. The machine-wide policy is `UserShadowStack: NOTSET`, so the enforcement
  comes only from the executable's mark.
- **One change at a time**, each of which takes the crash away with nothing else changed: the CET bit cleared in a
  copy of the launch executable; `Set-ProcessMitigation -Disable UserShadowStack` for that image name; a build with
  `CETCompat=false`; the engine built with `Config.WithSignalsBasedTraps(false)`. The reverse also holds:
  `Set-ProcessMitigation -Enable UserShadowStack` for `dotnet.exe`, which is not marked, makes the same DLL die under
  `dotnet.exe` with the same status.
- **The source.** Wasmtime 50.0.1,
  [`crates/wasmtime/src/runtime/vm/sys/windows/vectored_exceptions.rs`](https://github.com/bytecodealliance/wasmtime/blob/v50.0.1/crates/wasmtime/src/runtime/vm/sys/windows/vectored_exceptions.rs),
  on a wasm trap: `context.Rip = handler.pc; context.Rbp = handler.fp; context.Rsp = handler.sp; …
  EXCEPTION_CONTINUE_EXECUTION`. The handler is `last_wasm_entry_trap_handler`, the landing pad of the entry trampoline
  ([`traphandlers.rs`](https://github.com/bytecodealliance/wasmtime/blob/v50.0.1/crates/wasmtime/src/runtime/vm/traphandlers.rs),
  `entry_trap_handler`). A trap that Wasmtime raises itself, from a host call or a libcall, does not go through
  Windows: `resume_to_exception_handler` sets `rsp` and `rbp` and jumps
  ([`crates/unwinder/src/arch/x86.rs`](https://github.com/bytecodealliance/wasmtime/blob/v50.0.1/crates/unwinder/src/arch/x86.rs)).
  Windows has nothing to validate on that path, so those traps survive.
- **Microsoft's statement** of the rule
  ([CET supported by default, .NET 9](https://learn.microsoft.com/en-us/dotnet/core/compatibility/interop/9.0/cet-support)):
  "`apphost` and `singlefilehost` are now marked as Intel CET-compatible … Libraries aren't allowed to set thread
  context to a location with an instruction pointer that's not present on the shadow stack or in a table of allowed
  continuation addresses for exception handling … the process is terminated." The opt-out is `<CETCompat>false</CETCompat>`.
- **Upstream** reports the same thing. [wasmtime-dotnet #374](https://github.com/bytecodealliance/wasmtime-dotnet/issues/374)
  (open, August 2026) has the same trap matrix and the same fix by clearing the bit. It has no subcode, which this run
  adds. [wasmtime-dotnet #390](https://github.com/bytecodealliance/wasmtime-dotnet/pull/390) (merged 25 October 2026,
  in 50.0.1) added `Config.WithSignalsBasedTraps`, and its documentation names this case. I found no issue about CET
  or shadow stacks in the Wasmtime tracker itself.

The earlier diagnosis proved nothing because `editbin /CETCOMPAT:NO` did not clear the mark. There is a second trap:
an incremental publish with `-p:CETCompat=false` keeps the CET-marked apphost it made before in `obj`. On this machine
the mark stayed until `obj` was deleted. Every build here starts from a clean `obj`.

`run.ps1` builds it as each launch kind and runs the matrix.

### Launch kind by trap kind, win-x64

`ok`: the host got an exception (`TrapException` with the expected code, or `WasmtimeException` with the host's own
exception inside) and the process went on. `died`: exit `0xC0000409`. The executable column is `Environment.ProcessPath`.

| Launch kind | Executable | CET mark | Policy | Hardware traps (8 cases) | Host-raised traps (4 cases) |
| --- | --- | --- | --- | --- | --- |
| framework-dependent apphost | `TrapRepro.exe` | yes | `0x105` | **died** | ok |
| `dotnet TrapRepro.dll` | `dotnet.exe` | no | `0x100` | ok | ok |
| self-contained apphost | `TrapRepro.exe` | yes | `0x105` | **died** | ok |
| Native AOT | `TrapRepro.exe` | yes | `0x105` | **died** | ok |
| .NET tool, `--tool-path` shim | `dotnet-traprepro.exe` | yes | `0x105` | **died** | ok |
| .NET tool, `dotnet traprepro` (shim on `PATH`) | `dotnet-traprepro.exe` | yes | `0x105` | **died** | ok |
| .NET tool, local, `dotnet tool run` | `dotnet.exe` | no | `0x100` | ok | ok |

The hardware traps: `unreachable`, an out-of-bounds load, `i32.div_u` by zero, `INT_MIN / -1`, `call_indirect` to a
null entry, wasm stack overflow, and the corpus modules of `bounds/trap` and `bounds/grow-to-ceiling-then-trap`
through the product's `SessionStore`. The host-raised traps: a host function that throws (as `http_request` does), fuel
exhausted, an epoch deadline with no callback, and an epoch callback that throws (as the call deadline and
cancellation do). This is why only `bounds/trap`, `bounds/grow-to-ceiling-then-trap` and
`bounds/grow-refused-below-ceiling` failed: they end in `unreachable`, and every other bounds case is stopped by the
host. The control case, a guest that returns, was `ok` everywhere.

`dotnet morphir`, the form in the task, is the shim. The muxer finds `dotnet-morphir.exe` on `PATH` and starts it.
Only a local tool run with `dotnet tool run` runs in `dotnet.exe`.

### The marks

The spike's PE reader gives the `IMAGE_DLLCHARACTERISTICS_EX` value from the debug directory, type 20, and the load
configuration. `dumpbin /headers /loadconfig` agrees on every file.

| File (win-x64) | Default build | With `-p:CETCompat=false` |
| --- | --- | --- |
| apphost, framework-dependent and self-contained | CET compatible; CFG; 12 EH continuation targets | not CET compatible (value `0x0`) |
| Native AOT executable | CET compatible; CFG; no EH continuation table | no CET entry (the linker got `/CETCOMPAT:NO`) |
| tool shim (`dotnet tool install`) | CET compatible | **still CET compatible** |
| `C:\Program Files\dotnet\dotnet.exe` (10.0.404 SDK) | not CET compatible; 9 EH continuation targets | — |
| `wasmtime.dll` (package, win-x64) | not CET compatible; no EH continuation table | — |
| `morphir.exe`, framework-dependent | CET compatible | not CET compatible |

The opt-outs come from these places in the pinned SDK:

- The SDK sets `_DisableCetCompat` when `'$(CETCompat)' == 'false'` and passes `DisableCetCompat` to `CreateAppHost`
  (`Microsoft.NET.Sdk.targets`).
- ILCompiler 10.0.14, `Microsoft.NETCore.Native.Windows.targets`, lines 107 to 111:
  `<LinkerArg Condition="'$(CETCompat)' != 'false' and '$(_targetArchitecture)' == 'x64'" Include="/CETCOMPAT" />`,
  and `/CETCOMPAT:NO` when it is `false`.
- The tool shim is made at install time by
  [`AppHostShellShimMaker`](https://github.com/dotnet/sdk/blob/release/10.0.4xx/src/Cli/dotnet/ShellShim/AppHostShimMaker.cs),
  which calls `HostWriter.CreateAppHost` without `disableCetCompat`. A shim packed with
  `PackAsToolShimRuntimeIdentifiers` is made by
  [`GenerateShims`](https://github.com/dotnet/sdk/blob/release/10.0.4xx/src/Tasks/Microsoft.NET.Build.Tasks/GenerateShims.cs),
  which does not pass it either. **No project setting reaches the tool's shim.**

## The product on the runner

`morphir` was built framework-dependent from this branch and run through
`mck wasm-host run --kit conformance/suites/wasm-host`. The engine has an experiment switch, off by default:
`MORPHIR_WASM_EXPERIMENT_SIGNALS_BASED_TRAPS=false` in `WasmEngine`. Each row below was run twice in each run.

| Corpus host | win-x64 passed / failed | Seconds | win-arm64 |
| --- | --- | --- | --- |
| `morphir.exe` (apphost) | 46 / **3** (the three trap cases) | 16.3, 19.4–19.7 | 49 / 0 |
| `dotnet morphir.dll` (`--host dotnet --host-arg`) | 49 / 0 | 15.8, 19.2–19.4 | 49 / 0 |
| `morphir.exe`, signals-based traps off | 49 / 0 | 16.1–16.6, 19.9–20.6 | 49 / 0 |
| `dotnet morphir.dll`, signals-based traps off | 49 / 0 | 15.8–16.2, 20.2–21.0 | 49 / 0 |
| `morphir.exe` built with `CETCompat=false` | 49 / 0 | 16.7–17.0, 19.0–19.4 | 49 / 0 |

The first number is from run 42864924761 and the second from run 42867533674.

The corpus takes the same time with explicit checks. Its guests are small and the run is mostly process start-up.
The cost shows in a memory-heavy loop, the spike's `bench` (five loads and stores per iteration at generated
addresses, 100 million iterations, best of five):

| | Signals-based traps on | Off | Cost |
| --- | ---: | ---: | ---: |
| win-x64 (run 42867533674) | 543 ms | 717 ms | +32% |
| win-arm64 | 728 ms | 998 ms | +37% |

Wasmtime's documentation says "up to 2x slower". With signals-based traps off, Wasmtime also requires the Cranelift
heap and table Spectre mitigations to be off (`config.rs`, "when signals-based traps are disabled then spectre
mitigations must also be disabled"). With guard pages a bounds check is not needed. With explicit checks it is, and
the check is not hardened against speculation.

A spinning guest stops just as fast after its call is cancelled: the median overrun after a 300 ms cancel is 15.8 ms
with signals-based traps on and 12.3 ms with them off (ten sessions each).

### The engine's own tests

`Morphir.Extensions.Wasm.Tests` has 231 tests.

| Launch | Signals-based traps | win-x64 | win-arm64 |
| --- | --- | --- | --- |
| `dotnet exec` (how `build/Build.Testing.cs` runs it) | on | 231 passed | 231 passed |
| `dotnet exec` | off | 230 passed, 1 failed | 230 passed, 1 failed |
| the test project's apphost, `Morphir.Extensions.Wasm.Tests.exe` | on | **died `0xC0000409` within 1 s** | 230 passed, 1 failed |
| the test apphost | off | 230 passed, 1 failed | 230 passed, 1 failed |

The one failure is always `ChannelTests.Cancelling_during_a_call_throws_after_the_call_has_stopped`. It allows
300 ms + 1 s and took 2.8 to 7.8 s. Across both runs it failed in all 8 full-suite runs with the switch off. With the
switch on it failed in 2 of 6, both on ARM64 through the apphost. Run alone it passed 5 of 5 each way, on both
platforms. Each call runs on its own thread, but the 300 ms `CancellationTokenSource` timer fires on the thread pool.
The best-supported explanation is that the other tests' spinning guests load the four-core runner and delay that
timer, and slower guests load it longer. Measuring from the cancellation itself, or running that test on its own,
would settle it. This should be fixed before choosing explicit checks, or that change will look like a regression.

| --- | --- | --- | --- | --- | --- |
| A. `CETCompat=false` in the release profiles (ILCompiler `/CETCOMPAT:NO`, SDK apphost) | fixed | fixed | fixed (`morphir.exe`; `dotnet morphir.dll` already works) | **not fixed** (the shim) | The process loses hardware shadow-stack protection against return-oriented programming. Build from a clean `obj`, and check the mark in the packed artifact. |
| B. `WithSignalsBasedTraps(false)` always | fixed | fixed | fixed | fixed | Guest code about 32–37% slower on memory-heavy loops here, and up to 2x by Wasmtime's account. Spectre heap and table mitigations off. Same on every platform. |
| C. B only where the process enforces shadow stacks (`GetProcessMitigationPolicy(ProcessUserShadowStackPolicy)` bit `EnableUserShadowStack`, read when the engine is created) | fixed | fixed | fixed | fixed | B's cost, but only in CET-enforcing processes on x64 Windows. In all 760 runs this bit predicted the outcome. Windows sets a process's shadow stacks when it starts, and they cannot be turned on later, so the bit read when the engine is created stays true for the process's life. |
| A + C | fixed, fast | fixed, fast | fixed, fast | fixed, explicit checks | CET off for the executables this repository builds. The tool pays B's cost. |
| D. A, and document that the tool must run as a local tool (`dotnet tool run`) on x64 | fixed | fixed | fixed | only through `dotnet.exe` | A user who installs it globally gets a process that dies on a guest trap. |
| E. The engine out of process (a helper executable without the mark) | fixed | fixed | fixed | fixed | A second executable to ship and sign. IPC for every call. The helper loses CET too. Large change. |
| F. Upstream: Wasmtime registers its landing pads with `SetProcessDynamicEHContinuationTargets`, or resumes without `NtContinue` | fixed | fixed | fixed | fixed | Not available today. wasmtime-dotnet #374 asks for it. No Wasmtime issue exists yet. |

Any option also needs the Windows test fix below, or the next regression will be missed the same way.

**Recommendation: C.** It is the only option available today that fixes all four offerings, the tool included,
without turning off a security mitigation in any executable. It costs speed only in the processes where the fast
path cannot work at all. It is a few lines in `WasmEngine`. The policy query is two lines of P/Invoke, and it is
`false` on ARM64, Linux and macOS, so those platforms keep guard pages. If the maintainers would rather keep full
guest speed in the archives, A + C gives that, at the price of CET in `morphir.exe`. That trade belongs to the
maintainers and the deployment thread, which owns the release profiles. With either choice, file the upstream issue
(F) so that a later Wasmtime can drop the workaround. With C, `extension runtimes` should report which trap mode is in
force.

## Where the regression test should live

1. **Run `Morphir.Extensions.Wasm.Tests` through its own apphost on `windows-latest`** (`Morphir.Extensions.Wasm.Tests.exe`,
   in `build/Build.Testing.cs`). The existing trap tests in `BoundsTests` then become the regression test. The runs here
   show that this executable dies within a second on these machines when the defect is present.
2. **A worker test that starts the built `morphir.exe`** (the apphost, not `dotnet morphir.dll`) as a child process,
   with `extension worker` on `extism-trap`, and expects a `fault` event of kind `trap` and exit status 1. It belongs
   in `Morphir.Tooling.Tests` or a small Windows-only E2E step in the `Development` workflow. It covers the launch
   executable, which option 1 does not.
3. **A test that reports the shadow-stack policy of the test process** on x64 Windows: it is skipped where user CET is
   not available, and fails if CET is available but the trap tests run without it. A change of test launcher or
   runner image then cannot hide the case again.

The tool shim is exercised only by the packaged E2E suite and the six-platform run. Option 2 covers the same
mechanism, because the shim is an apphost with the same mark.

## The second finding: the flood guest's memory bound on linux-arm64

From reading the code; nothing was run on Linux. The scenario starts the worker twice, once with `flood-output` and
once with `extism-echo`. It sends five `initialize` frames to each, reads `Process.PeakWorkingSet64` (Linux `VmHWM`)
before `exit`, and requires that the flood peak exceed the echo peak by less than 64 MiB.

The guest needs almost no memory of its own. Its linear memory is one page (64 KiB). Per call it allocates one 1 KiB
kernel block, which it logs 10,240 times, and one 43-byte block for the reply, and the kernel is reset before each
call. The host keeps at most 64 KiB of guest output (`GuestOutputTail.TailBytes`) and drains it after each call. What
the 100 MiB does cost is short-lived garbage on the host. Each `fd_write` makes a `byte[1024]`, a 1,024-character
string and the prefixed copy (`WasiSandbox.Write`). Each output is then cut rune by rune with `rune.ToString()`
(`GuestOutput`), and each `log_info` decodes its block the same way. That is tens of thousands of objects per call,
all dead within the call.

So the peak working set measures how much garbage the GC lets build up before it collects. That is the gen0 budget,
which .NET sizes from the processor's last-level cache, plus the free regions it has not yet given back. Both depend on
the machine. A Linux ARM64 runner reporting a larger cache would give exactly a steady 65 to 74 MiB in every offering.
**64 MiB is an arbitrary number for this invariant, not a sound bound.** This is the best-supported explanation. The
runner's
`/sys/devices/system/cpu/cpu0/cache/index*/size`, or the same scenario with `DOTNET_GCgen0size` set, would settle it.

The real invariant is that the worker's memory does not grow with the amount the guest writes. The smallest test of
that: in the flood session, read the peak after the first answered call and again after the fifth. The second may
exceed the first by only a small, fixed margin, for example 8 MiB. Four more calls write 80 MiB more, so a leak
proportional to output would show as tens of MiB. Keep the 4,608-byte event-line bound and the 512 KiB stderr bound.
They already test the 64 KiB retention directly. The comparison with an echo session can go. I did not change the
scenario.
