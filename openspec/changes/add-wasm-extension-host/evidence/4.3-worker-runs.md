10.0.403. All four executables were built from commit `6ec3725` of this branch with a clean working tree. Reports are
not committed: they hold this machine's absolute paths.

Part A is the crafted corpus through `morphir mck wasm-host run`. Part B is the generic guest kit's **model tier
only**, through a session factory that has no command. Part B is **pending the maintainer's decision on who runs the
kit's model tier** against this host, and it is not a complete run of the generic guest kit.

### What differs from the third MoonBit run's command

The host path and the three identity inputs differ, as the task allows. **One more argument differs:
`--host-profile morphir-bytes-v1` is left out.** It is an identity input too. A worker does not report its profiles
(`withoutCase` `hostSession:profiles-reported`), so the runner takes them as input, and the .NET host runs
`extism-kernel-v1` only (design MEP-1). Giving the option would make the ten byte-profile cases apply to a host that
refuses every byte-profile module, so they would fail. The worker arguments the runner sends are the same for both
hosts.

### No runner change

`git log --oneline b3d7821..HEAD -- src/Morphir.Conformance/WasmHost src/Morphir.Tooling/Features/Mck` prints nothing,
and `git diff --stat 7ccc25e HEAD` over the same paths is empty. `b3d7821` records the third MoonBit run and `7ccc25e`
built that run's runner. The last commit to touch the runner is `333625b`, the kit commit the third run used. So the
runner that drove the four .NET executables is byte for byte the one that drove MoonBit.

The kit changed after that run in its generated headers only. Commits `d2d18bb` and `4829777` moved the pin to
`8b3c4c35` and then `938f798`, which rewrote the commit and SHA-256 lines of the eight features and of `case-ids.json`.
The corpus gained two `withoutCase` entries, `refusal:extension.runtime_unavailable` and `worker:start-order`, and no
case changed. `dotnet fsi scripts/generate-wasm-host-cases.fsx --check` passes.

### Another observation

The three `morphir` builds give one build identity, `f7a1abdb…6ebf`, although their bytes differ and one is Native
AOT. A worker therefore accepts the `--build-identity` of another `morphir` build of the same version. The corpus case
`worker/other-build-identity` still passes, because it changes a digit of the host's own identity. Whether the
identity should tell the deployments apart is a question for task 5.3 and the parent.

## Part B: the generic guest kit's model tier through the worker

**Model tier only. The legacy tier (19 cases) is not run, so this is not a complete run of the generic guest kit.
Pending the maintainer's decision on who runs the kit's model tier: no command exists, and this run is not cited as
the kit's run.**

The Rust `morphir mck mep guest-run` cannot be used, because it cannot skip the kit's MEP `0.1` tier. The piece that
makes the run possible is `WorkerSessions` in `src/Morphir.Conformance/GuestKit/WorkerSessions.fs`. That project
already references `Morphir.Mep` and holds the worker process code, so the factory adds no project reference. It does
not touch the crafted-case runner under `WasmHost/`. It reuses `Worker.buildIdentity` and
`CliAdapter.stopProcessTree`.

For each session `ModelTierRunner.RunAsync` asks for, the factory starts
`<host> extension worker --abi extism-kernel-v1 --module <module> --build-identity <identity> --json` with no window.
It returns `new HostSession(<stdout>, <stdin>, host, request.OfferOrNull())` and drains stderr. `EndAsync` waits for
each worker to exit, stops its process tree if it has not, and reports the exit status, the events and any problem.

Guest: the published Python `0.6.0` module from the cache `artifacts/wasm-guests/`, SHA-256
`ce0cba07f0395ff8179b42eb021ade05c68197f69b8e9c0c8bc369d2a035727c`, checked. Kit: `tests/Fixtures/MepGuestKit/`,
finos/morphir `8b3c4c35`, kit SHA-256 `f16f2a4c…98ae`. The test is `ExecutableGuestKitModelTierTests` in
`tests/Morphir.E2E.Tests`, run against each executable.

### Differences from the in-process run of task 3.5

- **No difference in outcome.** The same 16 steps pass, the compiled IR matches the kit's expectations at both
  versions, and the guest, language and model IR versions are the same.
- **One `handle` call per request is not observable through a worker.** In its place, each worker exited with 0 and
  wrote `started` and `exited` and no `fault`.
- **The first request of each session includes the worker's start.** `describe` and `model-initialize` take 0.5 to 1
  second, against 19 and 14 ms in-process. Each worker process starts the runtime and compiles the 4.8 MB module
  again, where the in-process run reuses one compiled module by digest. The other steps take 0.5 to 8 ms, against
  0.2 to 1.8 ms in-process; the managed build's `model-exit` took 30 ms.
- **The channel differs.** Through the worker, `HostSession` runs on a framed stream pair and the worker relays to its
  `WasmChannel`. In-process, `HostSession` runs on the `WasmChannel` directly. Request ids, the initialize params and
  the offer are the same.

### A limit of the factory

A worker that has ended cannot be written to. A later request, or the `morphir.exit` of its session, fails with an
`IOException` from the stream, and `ModelTierRunner` does not catch it, so the run throws. `EndAsync` still reports
the worker. The factory's tests cover a worker that exits early, one that writes a `fault`, one that never answers
(stopped at the session limit), and one that never exits, together with its child. Not reached in these runs: a
request that `Connection` registers after its `RunAsync` ended would never settle. That needs a worker that closes
stdout and keeps reading stdin.

## After the review of the session factory (10 November 2026)

The section "A limit of the factory" above describes the state when the runs were made. Since then a write to a worker that has ended raises `WorkerEndedException`, and the model-tier runner records the step as failed and the steps after it as not run, keeping the steps it had collected. The end-to-end test was run again after the change, against `dotnet-morphir` and the build of `src/Morphir`: 16 of 16 steps pass, and both workers exit with status 0.

The same review added a `ToString` override to `StderrLine` in `src/Morphir.Conformance/WasmHost/Worker.fs`. That is the only change under the runner's source since the third MoonBit run, and it changes no behaviour of a run.
