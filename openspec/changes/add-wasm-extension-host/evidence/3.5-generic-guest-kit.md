## SDK fixture

`describe` sent with `{"protocolVersions":["0.2.0-draft.1"]}` returned:

```json
{"code":-32011,"message":"No compatible Morphir Extension Protocol version. Host supports 0.2.0-draft.1; extension supports 0.1","data":{"extensionVersions":["0.1"],"hostVersions":["0.2.0-draft.1"]}}
```

The guest refuses the request before it describes itself, so the kit can plan nothing for it, and no model-tier
session was opened. Its source at that commit (`src/lib.rs`) claims IR `3` only and sets no `model_transport`
capability, so even a describe that included `0.1` would plan no model tier. To run its model tier, the fixture
needs a rebuild in finos/morphir-moonbit with `morphir-extension-sdk`'s model transport turned on, claiming
`0.2.0-draft.1` and JSON `compileModel` and `generateModel` tuples at `3.0.0`.

## Not run

| What | Why |
| --- | --- |
| The legacy tier: 19 cases for Python (`initialize` to `exit`, 5 for each IR version) | It negotiates MEP `0.1`, which this host does not speak (design MEP-1). |
| The describe case's check that the guest claims `0.1` | Part of the legacy tier. |
| The SDK fixture guest, every case | It speaks MEP `0.1` only; see above. |

Where this run differs from the kit's requests: `describe` offers `["0.2.0-draft.1"]`, not
`["0.2.0-draft.1","0.1"]`; `describe` runs in a session of its own, not in the legacy process; `HostSession`
assigns the request ids and writes the `morphir.initialize` params, with host kind `cli`; and the runner checks the
initialize result as `HostSession` read it into its types. `HostSession` also requires the guest to keep the offer's
order across operations, which the kit does not; the Python guest keeps it.
