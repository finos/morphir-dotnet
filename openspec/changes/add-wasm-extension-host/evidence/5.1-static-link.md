# Task 5.1: the engine's static link on six platforms

Date: 10 November 2026. Branch `ci/wasm-engine-static-link`, commit `3ec7bac`, on GitHub-hosted runners.

## What the task asks, and the result

"Try the static link of the engine into the Native AOT executable on all six platforms before other packaging
work, with the C API archive pinned by SHA-256 and its version checked against the managed package. Verify each
platform's result on its own runner and record, per platform, static link or separate library and the shipped
size."

**The static link works on all six platforms.** On each runner the probe was published with the engine linked
in, copied alone into an empty directory and run there. No engine library was beside it, and the executable does
not list one among its native dependencies. All seven of the probe's checks hold on every platform: claims 1 to
3 of task 2.2, the task 3.1 session, the task 2.5 bounds, the task 3.3 and 3.4 sandbox and the task 3.2
notifications.

- **Shipped** counts the executable and any native library in the publish output. Symbol files (`.pdb`, `.dbg`,
  `.dSYM`) and XML documentation are not shipped. With the static link the publish output has no engine library;
  the build removes the package's copy.
- **For comparison**, the dynamic build on `win-arm64` (this machine, same commit) ships a 6,676,992-byte
  executable plus `wasmtime.dll`, 22,821,888 bytes together. The static executable is 16,028,672 bytes, so it is
  smaller than the pair, most likely because the linker drops the parts of the static library nothing calls,
  where the dynamic library keeps every export. The parent design
  measured an increase of 10,647,232 bytes on macOS arm64; the dynamic builds of the other five platforms were
  not published in this run.
- **IL lines.** The same two on every platform: the FSharp.Core assembly summaries
  `warning IL2104: Assembly 'FSharp.Core' produced trim warnings` and
  `warning IL3053: Assembly 'FSharp.Core' produced AOT analysis warnings`, which the probe already accepts. No
  IL2026, no IL3050, no other IL line. No linker warning in any publish log. Nothing is suppressed, and the
  probe's suppression scan includes `build/wasmtime/`.
- **Native dependencies** of the static executables, from `readelf -d`, `otool -L` and `dumpbin /dependents`:
  Linux `libm.so.6`, `libgcc_s.so.1`, `libc.so.6` and the dynamic loader; macOS the system libraries and
  frameworks of any .NET Native AOT executable; Windows only Windows system DLLs and the universal CRT. No
  platform lists a Wasmtime library.
- **Reasons for failure:** none. No platform needed the dynamic fallback. The fallback was exercised on this
  machine by forcing a SHA-256 mismatch: the static publish failed with the mismatch recorded, the download was
  deleted, and the dynamic build was published and run. Run alone, the dynamic executable stopped with
  `DllNotFoundException` for `wasmtime`, which the result records.

## The Wasmtime release, and how it was matched to the managed package

The managed package is `Wasmtime` 50.0.1 (`Directory.Packages.props`), built from bytecodealliance/wasmtime-dotnet
commit `4aac1a5958f4da2dadca4ae84e16004516372dd6` (its `.nuspec`). Its native libraries are those of
bytecodealliance/wasmtime release **v50.0.1** (published 29 October 2026). The match is exact: each of the six
`runtimes/<rid>/native` libraries in the package has the same SHA-256 as the dynamic library in `lib/` of the
matching v50.0.1 C API archive, and each archive's `include/wasmtime.h` defines `WASMTIME_VERSION "50.0.1"`.

The version is checked twice. `WasmtimeCApiPinTests` (in `tests/Morphir.Extensions.Wasm.Tests`) fails without a
download when the pin's version differs from the `Wasmtime` package version, when a platform is missing, or when
an entry is not that version's release asset; a pin moved to 50.0.2 by hand fails two of its three tests. At
build time `build/wasmtime/WasmtimeStaticLink.targets` fails when the pin's version or the downloaded archive's
`WASMTIME_VERSION` differs from the package version, and when the SHA-256 differs (deleting the download).

## How the link is made

`-p:MorphirWasmtimeStaticLink=true`, off by default, makes the probe import
`build/wasmtime/WasmtimeStaticLink.targets`. Nothing else imports it, and the default build of every project is
unchanged. As the .NET documentation describes (Native code interop with Native AOT, "Direct P/Invoke calls" and
"Linking"), the targets add:

- `<DirectPInvoke Include="wasmtime" />`: all 240 P/Invokes of `Wasmtime.Dotnet` 50.0.1 import the module
  `wasmtime` (read from the assembly's metadata);
- `<NativeLibrary>` for the archive's static library;
- the system libraries the Wasmtime C API documentation lists for a static link: on Windows `ws2_32`,
  `advapi32`, `userenv`, `ntdll`, `shell32`, `ole32` and `bcrypt`; on Linux `-lpthread -ldl -lm`; on macOS none.

No other platform-specific setting was needed.

## Workflow runs

`.github/workflows/wasm-engine-static-link.yml`, triggered by `workflow_dispatch` and by a push to
`ci/wasm-engine-static-link` that touches the workflow, `scripts/wasm-engine-static-link.ps1`, `build/wasmtime/`,
the probe or `src/Morphir.Extensions.Wasm/`. Permissions `contents: read`, no secrets. Each job verifies the
Python `0.6.0` guest and the pinned archive, then the script publishes, runs and records.

- Run: <https://github.com/finos/morphir-dotnet/actions/runs/42801833498> (one run; all six jobs passed in about
  three and a half minutes). Each job uploads `wasm-engine-static-link-<rid>` with `result.json`, the publish log
  and the probe's output, and prints the result in its job summary.

## What this means for tasks 5.2 to 5.4

- **5.2 and 5.3.** The `native-aot` offering can claim single-file delivery on all six platforms, provided the
  released `morphir` is linked the same way and its release qualification checks the same things. No platform
  needs the "separate library" case of the spec's scenario "Platform where static linking failed" today. The
  release metadata still needs the field, for a future platform or engine version where the link fails. Linking
  the product executable is not done here (design SEQ-1); it can reuse `build/wasmtime/` as it is.
- **`self-contained` and `framework-dependent`** are not affected: they still carry the package's dynamic
  library, from the same release, so the engine version is the same in every offering.
- **5.4.** Nothing changes. musl has no archive in the package, and this task did not try one, although the
  release publishes `x86_64-musl` and `aarch64-musl` C API archives.
- The Linux static executables need `libgcc_s.so.1`, which glibc systems have.
