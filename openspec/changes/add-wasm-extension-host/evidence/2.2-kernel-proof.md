## What the proof does, and what it does not

Claim 2 runs two stores. In the small one the limiter's ceiling is the guest's minimum memory plus
16 pages (51 pages). The kernel's own `alloc`, running inside WASM, asks for more than the ceiling, its
`memory.grow` is refused, and it returns 0. A host-side `Memory.Grow` of the guest's memory past the ceiling
is refused as well. In a store with four times the ceiling, the same alloc and the same grow succeed, so
the limiter is what refused them, not the kernel or the guest. The guest check grows the memory from the
host side. It does not run guest code that grows memory; the bounds cases of task 2.5 should do that.

Claim 3 does what an Extism host does: `reset`, then `alloc` and a write into kernel memory for the
input, then `input_set` and the call of `handle`. After that the host calls `error_get` and, when it is
non-zero, `length`, and reads `output_offset` and `output_length` and then the bytes from kernel memory.
No managed code takes the place of a kernel function. The guest's 8 imports are bound straight to the
kernel instance's exports.

## Facts for later tasks

- **The kernel imports nothing.** It exports `memory`, with 16 initial pages and no maximum, and the 20
  functions above with the upstream Extism signatures. It needs no host callback.
- **Two memories, two instances.** The store holds the kernel instance and the guest instance. The guest
  owns its own memory (35 pages at start, about 2.2 MiB) and imports no memory. Input, output, errors and
  every `alloc` live in the kernel's memory. A guest copies bytes between its memory and the kernel's
  through `load_*`, `store_*` and `input_load_*`, inside WASM. One store ceiling applies to each memory
  separately, so a session's resident linear memory can reach twice the ceiling. That is the bound task
  3.5 documents.
- **Python 0.4.2 imports only 8 kernel functions** (`alloc`, `error_set`, `output_set`, `input_length`,
  `input_load_u64`, `input_load_u8`, `store_u64`, `store_u8`). It imports no WASI, no other Extism host
  function and nothing from `extism:host/user`. The probe's callbacks for unprovided imports and its WASI
  linking never ran with this guest; tasks 3.3 and 3.4 must test them with the crafted modules.
- **No start-up export.** The guest exports no `_initialize`, `__wasm_call_ctors` or `hs_init`, so no
  initialization ran. Besides `handle` it exports `morphir_extension_info` and
  `morphir_extension_capabilities`, both `() -> i32`.
- **Kernel addresses.** In a fresh kernel the first `alloc` returns 77: the 1-byte gap and the 64-byte
  root record, then a 12-byte block header. After `reset` and the input, the initialize reply was at
  offset 258.
- **AOT-safe API surface.** These Wasmtime .NET calls gave no trim or AOT diagnostics:
  `Module.FromBytes`, `Linker.Instantiate`, `Linker.Define(module, name, Function)`, the untyped
  `Linker.DefineFunction(module, name, UntypedCallbackDelegate, parameters, results)`, `Linker.DefineWasi`,
  `Store.SetWasiConfiguration`, `Store.SetLimits`, `Instance.GetFunction(string)`, `Instance.GetMemory`,
  `Function.Invoke(ReadOnlySpan<ValueBox>)`, `Memory.GetSpan`, `Memory.Grow`. The library avoids the
  generic typed wrappers (`GetFunction<…>`, `CallerFunc<…>`); the earlier spike found that they produce AOT
  warnings, and this proof did not try them.
- **A refused grow.** From the host, Wasmtime throws `WasmtimeException` with the message
  `failed to grow memory by `17``. Inside WASM, `memory.grow` returns -1, and the kernel turns that into
  `alloc` = 0.
- **Native AOT on win-arm64 works on this machine**, which bears on issue 264. One setting is needed: the
  first publish failed at the link step with `MSB3073 … 'vswhere.exe' is not recognized …`. The reason is
  that `vcvarsall.bat` calls `vswhere.exe` from `PATH`, and the error text it printed ended up in the
  linker command line that ILCompiler's `findvcvarsall.bat` captures. Adding
  `%ProgramFiles(x86)%\Microsoft Visual Studio\Installer` to `PATH` for the publish process fixed it. The
  code did not change. ILC itself had already run, with no diagnostics.
- **Lock files.** The committed `packages.lock.json` files come from a plain restore, as for
  `tests/Morphir.Mep.AotProbe`. A `-r win-arm64` publish adds a `net10.0/win-arm64` section and an
  `ILCompiler` entry to the probe's lock file. The publish was run with `RestoreLockedMode` false, and
  the plain lock files were put back afterwards. A locked restore then passes. Task 5.1 must decide how
  the per-RID publish restores in CI.
