## What was added

### Packaged E2E scenarios

`tests/Morphir.E2E.Tests/Features/Packaged/PackagedArtifacts.feature` has four new scenarios. They run for whichever
offering the E2E run selects (`MORPHIR_EXECUTABLE_TYPE`). Each one installs into a directory whose path has a space,
as the feature already did, and runs from a working directory whose path has a space.

| Scenario | Requirement | What it checks |
| --- | --- | --- |
| The engine files are those the build contents record | "Packaged engine is qualified", scenario "Platform where static linking failed" | The installed files named `wasmtime.dll`, `libwasmtime.so` or `libwasmtime.dylib` are exactly the `separate-library` entries under `engines` in `<artifact>.build-contents.json`, each with its recorded SHA-256. A `linked` engine has no library file, and its path is an executable of the artifact. An archive records one engine, for this platform. The tool package records one library per platform, each under `runtimes/<rid>/native/`, including this platform. The number of platforms is read from the record. |
| The runtime report of the installed artifact | "Runtime availability is reported", scenario "Supported platform" | `extension runtimes --json`: host as expected, `platform` equal to the runner's, `wasm` available, engine `wasmtime` at the version in `Directory.Packages.props`, profile `extism-kernel-v1`. Every recorded engine has that version. |
| A WASM worker session from the installed artifact | "Worker mode", scenario "Conformance runner drives a guest" | Build identity from `extension worker --help --json` (64 hex digits). Session on a copy of the pinned `extism-echo.wasm`, its SHA-256 checked against the corpus pin. Frames `initialize, initialized, shutdown, exit`. Stdout holds only the two echo frames, stderr has the events `started, exited`, exit status 0, and the session's own temporary directory is empty afterwards. |
| A WASM guest runs from a read-only install directory, and its first run extracts nothing | task 5.2, "first-run extraction with a read-only install directory" | A second installation of the same artifact, made read-only before its first run. Windows: the read-only attribute on every file and a deny rule for the current user (create files and folders, write, delete) that everything below inherits. Linux and macOS: every write bit cleared, so folders are `r-x` and files `r--` or `r-x`. A probe write into each folder and each file must fail first. Then the runtime report and the worker session as above, and the installation's file list, with sizes, is the same as before the first run. Permissions are given back in an `[AfterScenario]` hook. |

### The corpus and the workflow

`scripts/wasm-offerings.ps1` runs these steps for each offering on the machine's platform:

1. `PackRelease`.
2. `TestE2E` for that offering.
3. Installs the artifact as the E2E suite does: extracted into a directory with a space in its path, or the tool
   installed with `dotnet tool install --tool-path` from a local feed.
4. Runs `mck wasm-host run --kit conformance/suites/wasm-host`, with the packaged executable as both runner and host,
   and then `report-check --expect-offering --expect-platform`.
5. On Linux, finds the highest `GLIBC_x.y` that the launch executable and this platform's engine library need
   (`readelf -V`).

It writes one JSON result per offering and a job summary. A failing offering does not stop the others.

`.github/workflows/wasm-offerings.yml` runs the script on `ubuntu-24.04`, `ubuntu-24.04-arm`, `macos-15-intel`,
`macos-15`, `windows-2025` and `windows-11-arm`. Its settings:

- It runs on `workflow_dispatch`, which takes platforms and offerings as inputs, and on a push to `ci/wasm-offerings`
  that changes the workflow or its script.
- `contents: read`, no secrets, and the action pins the other workflows use.
- `fail-fast: false`, and a newer push cancels a running one.
- The last step fails the job after the results are uploaded.

`workflow_dispatch` works only once the file is on the default branch. Until then, a push run picks its platforms
from `PUSH_PLATFORMS` in the file, which is now `linux-x64`.

## What failed and why

1. **`win-x64`: a guest trap kills the process.** This happens in all four offerings, `native-aot` included. Three
   corpus cases fail, `bounds/trap`, `bounds/grow-to-ceiling-then-trap` and `bounds/grow-refused-below-ceiling`, and so
   does the E2E corpus case `bounds/trap`. The worker writes `started` and then exits with status −1073740791
   (`0xC0000409`, a fail-fast), with no `fault` event. The same cases pass on `win-arm64` and on every other platform.
   This breaks the requirement "Worker events and exit status", scenario "Guest traps", on `win-x64`.
   - A likely cause is the CET shadow stack: Wasmtime recovers from a trap by redirecting the thread's context, which
     a CET-enforcing process refuses with this status. ARM64 has no CET.
   - The diagnosis run confirmed that both launch executables, `morphir.exe` of `native-aot` and the `self-contained`
     apphost, carry the CET-compatible mark (`dumpbin /headers`). `editbin /CETCOMPAT:NO` did not clear the mark, so
     the rerun proved nothing either way. **The cause is not proven.**
   - A fix that turns the mark off (`CetCompat=false`) would go in the release profiles or the project files, which
     are reserved for the deployment thread.
2. **`linux-arm64`: the flood guest's memory bound.** This is the older worker scenario "A guest that writes 20 MiB
   per call keeps stdout to frames and its report bounded" (task 4.1). The worker's peak working set exceeds an echo
   session's by 65 to 74 MiB; the bound is 64 MiB. The overshoot appears in all four offerings and in both Linux runs,
   so it is steady, not flaky. I did not change the bound.
3. **macOS, both architectures: "Reading an input file".** This is an older packaged scenario (#556). `validate`
   refuses the input `…/var/folders/…/work dir/model inputs/daily-rate-v3.json` with `unsupported-input-entry`:
   "Links and special input entries are unsupported". On macOS `/var` is a link to `/private/var`, so an input below a
   linked parent folder is refused. It has nothing to do with the engine.
4. **Fixed on this branch.** `PackagedArtifact.Find` named two artifacts in file-system order, so
   `PackagedArtifactTests.TwoArtifactsForOnePairAreRefused` failed on Linux.

## What this shows and what it does not

- Each offering, packed with the repository's targets on each of the six platforms, carries the engine its build
  record says, reports it, and runs a WASM session from a normal and from a read-only installation. On every platform
  but `win-x64` it also passes the crafted corpus.
- No offering extracts anything into its installation at first run. A worker session leaves nothing in its
  temporary directory.
- These are runner checks with the SDK installed, not clean machines. The shared clean-machine check that the
  deployment thread is building will add the clean Linux images.
- No released archive exists yet. Every artifact here was packed on the runner from the branch.
- Linux `native-aot` is linked on the runner and needs `GLIBC_2.38`. It is not at the repository's 2.35 floor. The
  container lane that links at the floor comes with another change.
- On a Linux machine without OpenSSL the engine does not start (`5-linux-floor.md`). No run here has a machine
  without OpenSSL.
