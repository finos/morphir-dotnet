Goals and non-goals

Goals. Give the parent tasks 2.1 to 6.2, and the runner parts of 1.5 and 4.3, a place in this codebase, with their numbers kept so that completion can be reported against the parent. Change this repository's two existing specs that the runtime contradicts. Record the four decisions of 9 November 2026 where a later reader of this repository will find them.

Non-goals. This page does not reopen a parent decision. It does not restate the shared profile rules; those stay in the parent capability and reach this repository by pin. It adds no product command that runs a configured WASM extension: the runtime is reachable only through the worker mode in this change, as the parent's migration section states.

Decisions made in this repository

The running example is the parent's: the published Python extension 0.6.0, one 4.8 MB Extism module (MEP-1). Each decision below is a point where the parent design meets this codebase and something had to be chosen.

ADPT-1. Carry the .NET host's own requirements; pin the shared ones

The parent has three capabilities. extensions/dotnet-wasm-host was written for this host, so its eighteen requirements (at 970dce7b) are carried into the local capability dotnet-wasm-host with their text and in their order. The one edit is that "as mep/wasm-execution-profiles defines" becomes "as the pinned WASM execution profile contract defines".

mep/wasm-execution-profiles is different. It is shared by every host, it is still a draft, and its own first decision exists to stop a third description from drifting. So its 20 requirements are not copied. One local requirement binds the host to the pinned contract, and the crafted corpus is how conformance to it is tested. This repository already treats the MEP contract this way.

mck/wasm-host-qualification is split by owner. The corpus rules stay with finos/morphir, which owns the data. The runner rules are carried into the local capability wasm-host-qualification, because the runner now lives here.

Alternative. Copy all three, as add-deployment-and-acquisition did with an approved parent. That parent was final. This one is still being revised, and a copy of all 48 requirements would need each revision twice. The revision of 10 November 2026 showed the cost: three of the carried requirements changed and three were added.

ORD-1. Extism first, the byte profile never

The PRD says "morphir-dotnet hosts morphir-bytes-v1 first, because any WASM runtime can host it", places that in step 2a and places Extism in step 5. The maintainer reversed this on 9 November 2026. The host runs extism-kernel-v1 only. It still classifies a byte-profile module, so that the refusal is extension.abi_unsupported with the profile named, and not a confusing import error.

Three consequences for existing text in this repository, all handled by task 0.1:

  • The PRD's Runtimes section, step 2a and step 5 change. Step 2a keeps its analyzer scope but its guests are Extism modules. Step 5 keeps host grants only.
  • The PRD's step 2a reference guest, the morphir-elm morphir-bytes-v1 release, can no longer run in this host. The published Python extension takes its place as the guest this repository did not write (release 0.6.0, see MEP-1).
  • The spike's advice to write a LibraryImport binding for three per-byte callbacks is void. An Extism guest moves its bytes through the kernel, inside WASM, and the host is called only for the rare functions. Untyped callbacks, which give zero AOT warnings, are fast enough for those.

MEP-1. MEP 0.2.0-draft.1 only

Maintainer, 9 November 2026: morphir-dotnet targets MEP 0.2.0-draft.1 and does not implement, bridge or test MEP 0.1. The decision came after this change was approved. The parent recorded it on 10 November 2026 as its own MEP-1, with the requirement "Protocol line"; read the reasons there. Four things follow here:

  • One instruction budget, the contract's 5,000,000,000 for a session.
  • The reference guest is the Python extension 0.6.0, the release finos/morphir pins in .config/published-extension-bundles.toml. Release 0.4.2 speaks 0.1 only (measured in the bounds evidence). The kernel proof first ran on 0.4.2 with a raw 0.1 message, then on 0.6.0; both runs are in the evidence.
  • A published guest accepts 0.2.0-draft.1 only when morphir.initialize carries a model transport offer. Without the offer, the pinned bundles refuse with error -32011. Sessions on these guests always send the offer.
  • The generic guest kit's legacy tier is not run against this host. The Rust guest-run cannot leave that tier out. Only the model tier is run, and how task 4.3 does that is an open question; the legacy cases are recorded as not run, and the result is not reported as a complete run of the kit. Whether the kit drops the tier is an open maintainer question in the parent (RUN-2, open questions).

Since 48d10706f the parent's task wording agrees with this: tasks 2.2 and 3.5 name 0.6.0, and 3.5 and 4.3 say "the kit's model tier".

MEM-1. Run a copy with the memory exported when a module does not export it

The memory rule (parent BND-2) needs the size of the guest's memory on every failure. Wasmtime gives the host a memory only through an export. The published guests export their memory. Most crafted modules that have a memory do not (19 of 25 when counted at 7b049c223), among them the module of the case bounds/grow-to-ceiling-then-trap.

Maintainer, 9 November 2026: for a module that defines a memory and does not export it, the host compiles a copy with one more entry in the export section, the memory under the name morphir:host/guest-memory. Code and memory are unchanged. The digest, the classification and every report use the original bytes. A module that exports its memory runs byte for byte as published.

This is now a parent requirement too, "Reading a memory the module does not export", carried into the local spec, and the parent's BND-2 records it (10 November 2026). The local reasoning, briefly: the copy changes no instruction and leaves the published guests untouched, and the alternative, an unknown size and never extension.memory_limit for such modules, fails the crafted case.

LAY-1. One new C# project for the runtime

The runtime goes into src/Morphir.Extensions.Wasm, a C# project marked trimmable and AOT-compatible, with tests/Morphir.Extensions.Wasm.Tests (TUnit) and tests/Morphir.Extensions.Wasm.AotProbe. It references Morphir.Mep for the channel and the wire types. Nothing references it except Morphir.Tooling and tests.

C# is chosen because almost every line touches the Wasmtime .NET API or native memory: delegates as host callbacks, spans over linear memory, disposal order. The closed sets the domain needs (profile, refusal, fault kind, outcome) are small and are modeled as sealed record hierarchies, as AGENTS.md shows. The F# types it consumes from Morphir.Mep follow the fsharp-csharp-interop skill, and the reviewer agent runs on each diff that crosses that boundary.

Alternatives. Put it in Morphir.Mep: that would give every MEP consumer, including the F# frontend guest, a native dependency. Write it in F#: possible, but it buys little for interop code and adds FSharp.Core closures on a hot native boundary.

CHAN-1. The channel lives in Morphir.Mep, and the guest's runtime owns notification delivery

Take the first request of a session:

{"jsonrpc": "2.0", "id": 1, "method": "morphir.initialize", "params": {"protocolVersions": ["0.2.0-draft.1"]}}

For a process guest, HostSession frames it and writes it to a pipe, and a reader loop matches the reply by id later. For the Python module it is one handle call that returns the reply. HostSession should not know the difference, so it is changed to hold a channel with two operations: send a request and get its response, and send a notification. The existing Connection over two streams becomes the first channel, with its constructor kept, so every process-guest caller compiles unchanged. The WASM adapter is the second.

The protocol rules that differ for a single-message guest are now written in the mep-protocol delta: one reply at most, the reply must be the response with the same id, a notification returns nothing, and cancellation stops the call and ends the session without a $/cancelRequest. One rule is deliberately left to the channel: whether a notification reaches the guest at all. HostSession always sends morphir.initialized; the WASM channel drops it for a guest that did not advertise call delivery (NTFY-1).

A single-message guest cannot send the host a message of its own, so morphir.progress never arrives from one. The PRD already says the host drops guest notifications for WASM.

KPF-1. Prove the kernel under Native AOT before building on it

Parent task 2.2 is a gate, and it is the first implementation task. The proof is a small console program, tests/Morphir.Extensions.Wasm.AotProbe, published with PublishAot in the same way as tests/Morphir.Mep.AotProbe. It loads the embedded kernel and the Python module into one store, sends morphir.initialize and prints what it observed. It ran on 0.4.2 first and then on 0.6.0, the release the parent's task now names (MEP-1). Three things must hold:

ClaimHow the probe shows it
Zero IL2026 and IL3050 warnings, no suppressionsThe publish log is checked for IL warnings, and the project files are checked for NoWarn, UnconditionalSuppressMessage and TrimmerRootDescriptor entries.
The store limit covers the kernel's memoryWith a small test ceiling, a kernel alloc larger than the ceiling returns 0 and the kernel's memory does not grow past it. The guest's memory is checked the same way.
The host reads the result of handle directlyThe probe prints the i32 that handle returned, the output it read from the kernel and the kernel's error value.

The kernel bytes come from moonrockz/extism at the version finos/morphir-moonbit pins, 0.3.0 today. The task records the version, the SHA-256 of the module and how the bytes were obtained, and adds the Apache-2.0 licence and notice beside them. The Python module is downloaded from its release and checked against its published digest; it is not committed.

If any of the three fails, work stops and KRN-1 returns for review. The implementation does not switch to libextism, to upstream's kernel or to managed kernel functions on its own.

Note on this machine. Development here is Windows ARM64, and Native AOT on ARM64 has an open question in issue 264. The proof must run where a Native AOT publish works. If it cannot be published locally, it runs on a CI runner, and that is recorded with the evidence.

NTFY-1. Implement the advertisement the contract names

The first draft of this decision waited for the parent to fix the member, because this repository's mep-protocol forbids adding a member to the contract. The parent fixed it on 10 November 2026 (its task 1.1 and NTF-1): the string capabilities.notificationDelivery of the guest's morphir.initialize result. The value call asks for delivery. An absent member, none and any value the contract does not list, the reserved poll among them, mean no delivery.

{"jsonrpc": "2.0", "id": 1, "result": {"protocolVersion": "0.2.0-draft.1", "capabilities": {"notificationDelivery": "call"}}}

Task 3.2 implements that rule against the pin at 8d678d2b, with the corpus case for an unlisted value. Task 3.1 already delivers what every published bundle needs: no notification reaches the guest.

REG-1. The registry learns the value; the list does not grow yet

The registry's delivery set becomes built-in and wasm, and a wasm entry is unavailable in a host whose WASM runtime is unavailable. That is all the registry change. morphir extension list prints the same entries after this change as before, because nothing registers a WASM entry: listing a configured module would mean running its describe on every list, and which commands consult configured extensions is the business of the change that adds the first such command.

The value is still worth adding now. Session diagnostics and the loader name a delivery, and the availability rule gives the later change one place to ask.

The listing itself is planned, not dropped. It is tracked in finos/morphir-dotnet#565 and lands with whichever comes first: installation (PRD step 3), where the catalog stores the describe result so that listing runs no guest, or the first command that consumes configured extensions (PRD step 2a). Task 0.1 writes that into the PRD.

Overlap. PR #559 modifies the same requirement to say that a host value names a command and not an offering. The two edits do not conflict in meaning. The change that archives second keeps both sentences.

CFG-1. Two optional keys for a declared ABI and digest

The parent requires that a declared ABI confirms the classified profile and that a declared digest refuses other bytes. Configuration has nowhere to declare either. Two optional keys are added to the extension table as a recorded local amendment to the generated schema, in the same way frontend.<language>.extension was:

[extensions.python]
path = "extensions/morphir-python-binding.wasm"
abi = "extism-kernel-v1"                   # optional; must equal the classified profile
sha256 = "10acafa0...22b5"                 # optional; other bytes are refused before classification

Both keys are proposed upstream for the shared configuration schema. Task 2.6 confirms how the configuration layer resolves a relative path today and documents that rule; it does not add a second one.

RPT-1. The runtime report is morphir extension runtimes

The parent leaves the command and field names to the implementation. The command is morphir extension runtimes [--json], beside extension list, in both executables. Its JSON follows this repository's convention of one document with no envelope:

{
  "host": "morphir",
  "platform": "linux-x64",
  "runtimes": [
    {
      "kind": "wasm",
      "available": true,
      "engine": {"name": "wasmtime", "version": "50.0.1"},
      "profiles": ["extism-kernel-v1"],
      "bounds": {"memoryBytes": 268435456, "deadline": "enforced", "budget": "enforced"}
    }
  ]
}

The report has no deployment member. This page first planned one, under the name PR #559 gives the offering in extension list, but a .NET executable does not know its offering at run time, and at 938f798 the parent dropped the offering from its sample and from the requirement "Unavailable runtime fails by name", which now names the host, the platform and the reason. The unavailable reasons are three: platform_unsupported, engine_missing and engine_load_failed. There is no switch that turns the runtime off, so the earlier fourth reason, disabled, is gone. The engine is probed once, on first need, and never at start-up.

The bounds are the contract's defaults. A worker run can set other values with --call-ms, --instructions and --memory-pages. Its started event states only whether each bound is enforced, not the value, so a runner sees a value take effect only from what the worker then does (WRK-2).

The engine identity is in this report and in session diagnostics. No worker event carries it, as the parent requirement "Module identity in every report" says since 8b3c4c35: the engine is part of the worker's build identity, and a qualification runner is given it as an input.

WRK-2. The worker relays messages; it is not a second MEP host

In worker mode the MEP host is the runner at the other end of stdio. The worker reads one frame, passes its body to the WASM channel and writes the reply as a frame. It does not negotiate, and it does not use HostSession: the crafted cases send frames that a session would never send, and the worker must carry them as they are. The worker's instruction budget is the contract's session value unless --instructions sets another, and the worker is not told which MEP version the runner speaks (MEP-1).

The worker looks inside a message only where the profile contract requires it: the method name, to know a notification from a request and to see morphir.exit; and the morphir.initialize result, for the notification advertisement. It does not read the protocol version: the budget does not depend on it (MEP-1). The channel, the adapter, the bounds and the policy are the same objects a product command will use, which is what the parent means by "not a second implementation".

It takes every argument the contract lists, as the parent requirement "Worker mode" names them since 10 November 2026: --abi, --module, --build-identity, --request-bytes, --response-bytes, --call-ms, --instructions, --memory-pages, --json and --help. A request frame over --request-bytes is fault failure and the guest is not called; a module file that cannot be read or is not well formed is fault failure before started. Both exit with 1.

Since 8b3c4c35 the contract and the parent requirements also say the following, and the worker does it. --build-identity is required: without it the worker serves nothing and exits with 2 (parent requirement "Worker build identity"). An invalid --memory-pages is a usage error with exit status 2, before the module is read; the MoonBit worker at 89f8924 reads the module and exits with 1. The range of --instructions, 1 to 9,007,199,254,740,991, is read from the contract's worker.arguments; the other ranges are not stated there and stay this host's own. started carries the module's digest, the declared profile and the build identity, and says whether each bound is enforced, not its value. No event carries the engine identity (RPT-1). --memory-pages sets the ceiling of the guest's memory; this host's store limit applies to every memory of a session, so it bounds the kernel's memory too, which the contract allows of such an engine. The two differ only below the default. The contract fixes the event names and their members; the rest of morphir/command-event and morphir/command-result, the help text and the usage-failure document follow the MoonBit CLI until a shared contract states them.

Since 938f798 the contract also lists extension.runtime_unavailable among the worker's refusals, and its worker rule start-order fixes the order the worker already followed: the arguments, the build identity, a usable engine, then the module, with the first failure reported. A worker without a usable engine refuses, exits with 3 and does not read the module. The contract reader requires the worker refusals to be exactly the two codes the worker gives and holds the rule's text word for word, so a change to either fails the load until the worker is reviewed against it.

Interrupted while a guest is inside handle, the worker stops the guest within one second and exits with 130. It writes no fault event, because the guest did not fail (parent requirement "Worker interruption"). cancelled stays a host-session outcome with no fault kind. On Windows a test can only send Ctrl+Break to a child in its own process group, so the worker must treat Ctrl+Break as Ctrl+C (the bounds evidence).

The command is registered in both entry points before the CLI host is built, so that no log line or banner can reach stdout. It is hidden from help and documented in the contributor guide as internal and experimental.

PIN-1. Pin the contract and the corpus by commit, and expect the pin to move

The profile contract (wasm-execution-profiles.json and .md), the crafted corpus (wasm-host.cases.json) and its modules are copied unchanged into tests/Fixtures/MepWasm/ with a PROVENANCE.md that records the upstream commit and each file's SHA-256, as tests/Fixtures/Mep/ does. The first pin is a commit of the draft PR's branch, 7b049c223, with 56 cases and 49 modules.

The parent revised these files again at 48d10706f, on 10 November 2026, in answer to findings from this implementation: one budget value, the corrected memory rule, the fixed notification member, the classification order, the 46 WASI preview 1 functions named by their witx definition and loading errors. At 8d678d2b, the same day, it applied the memory rule to a trap only, in answer to a question from this implementation, and added bounds/error-at-ceiling: a corpus of 59 cases and 51 modules (49 for extism-kernel-v1, 10 for morphir-bytes-v1). At 8b3c4c35, again the same day, it changed only the worker section of the contract and the .NET requirement text, in answer to four points from this implementation (WRK-2); the corpus and its modules did not change. At 938f798 it added the worker refusal extension.runtime_unavailable and the worker rule start-order to the contract, and both to the corpus's withoutCase list; no case, module, expectation or convention changed. The pin moves to 938f798 in the pull request that carries this revision. This change reads the parent at 970dce7b but pins 938f798: the two differ because the last parent commit changed only its tasks and its design, and no pinned file. The parent is still a draft. So:

  • Where the pinned JSON and the parent specs differ, the parent specs win. At 938f798 they agree on the instruction budget (5,000,000,000 for a session), on negotiated notifications, on the memory rule and on the worker refusal extension.runtime_unavailable.
  • A task that depends on a detail re-reads the parent first. If the detail is unsettled, the implementer asks; it does not guess.
  • The pin moves as one change, and qualification (group 6) runs only against a pin of a merged parent commit.

RUN-1. The crafted-case runner is new code in Morphir.Conformance, and its cases are Gherkin

The corpus has no runner anywhere. It gets one here: an adapter that starts <host> extension worker --module <wasm> --json with the case's arguments, writes the frames, and collects stdout frames, stderr events, the exit status and timings, and a comparer for the kit's matchers. It reuses the project's process handling and report code.

Maintainer, 9 November 2026: the crafted cases are converted to Gherkin, and the compatibility kit as a whole is planned to move from JSON to Gherkin. The first draft of this change read the upstream JSON directly. This one generates features from it:

  • Source and direction. While finos/morphir publishes the corpus as JSON, that JSON stays the hand-reviewed source and the features are generated from the pin. No expectation is ever written or changed in a feature by hand. When the kit itself moves to Gherkin, the features become the source and the generator is retired.
  • Guard. A test reads the pinned JSON and the generated features into one case model and requires them equal for every case. A check generates the features again and fails when they differ, so a generator defect cannot change an expectation unseen.
  • Vocabulary. Step vocabulary 1.1 is closed to the F# frontend suite. A new vocabulary version adds the wasm-host suite: a module with its declared ABI and worker limits, the frames to send, and one step for each matcher of the corpus (exit status, stdout byte count, stdout frames, stderr events, absent events, guest output, a timing range). Frames are json docstrings. This pulls a slice of establish-morphir-compatibility-kit forward (its tasks 1.2 and 2.1) and does not generalise the rest.
  • Ids. The kit's rule is <suite>-NNNN. A scenario is named wasm-host-0001 classification/unknown-namespace: a number that never changes and is never reused, and the upstream case id. A committed id map assigns the numbers.
  • Conditions. A case that applies only to a host that declares a profile, or whose expectation depends on what the host declares, becomes tagged scenarios (@requires:), one for each alternative. The runner selects by what the host's started event declares, as the corpus's conventions say. Since 48d10706f a run passes when it satisfies one alternative whose condition matches, and two alternatives may have the same condition: under the default budget, bounds/spin-extism accepts budget-exhausted or call-deadline from a metering host. So two scenarios of one case may carry the same tags, and the case passes when one applicable scenario is satisfied.
  • Worker arguments. A case's worker object gives arguments for its runs. requestBytes and responseBytes become --request-bytes and --response-bytes, and since 48d10706f instructions becomes --instructions, which the new case bounds/small-budget sets to 1,000,000. Each is a step of its own in the scenario.

An example of a generated scenario is in the qualification spec.

What this change does not do. It converts the crafted host corpus only. Moving the rest of the kit to Gherkin (the generic guest kit, the model-transport cases, and the data in finos/morphir itself) is the maintainer's stated direction and belongs to the kit's own migration, with establish-morphir-compatibility-kit. That migration also decides which repository holds the Gherkin source. Since 10 November 2026 the parent's QUAL-1 and its qualification spec say that a runner may execute the corpus in a form derived from the JSON and checked against it, and that the .NET runner does so with Gherkin.

The command surface is small and marked experimental, so that the compatibility-kit change can fold it into its general command:

$ morphir mck wasm-host run \
    --kit conformance/suites/wasm-host \
    --host /path/to/morphir \
    --report .dev/wasm-host-dotnet.json
$ morphir mck wasm-host report-check --kit ... --report .dev/wasm-host-dotnet.json

Exit codes follow upstream mck: 0 qualified, 1 failed or operational error, 2 invalid invocation. The report shape follows the host qualification report that parent task 1.4 defines. That task is not done; until it is, the runner writes per-case observations and no qualification verdict.

Parent task 1.5 asks that the corpus first be run against the MoonBit native CLI's worker mode, because that host exists. Each difference is recorded as a contract question or a MoonBit issue before any .NET result is compared. That needs a MoonBit native CLI build on the machine that runs it.

RUN-2. The generic guest kit keeps today's runner

Positive evidence comes from the generic guest kit: describe, a legacy tier on MEP 0.1, a model tier on 0.2.0-draft.1, generate, and compiling the generated files again, with semantic IR comparison. The runner cannot leave its legacy tier out. Against this host only the model tier is run (how, through this runner, is an open question): the legacy cases are recorded as not run, and the result is not reported as a complete run of the kit (MEP-1). Whether the kit drops the tier is an open maintainer question in the parent. Its runner is the Rust morphir mck mep guest-run. That runner already drives any stdio host by path and arguments, so driving the .NET worker needs no new runner code, and parent task 4.3 asks exactly that the invocation differ only in the host path.

This change therefore does not port guest-run. Porting it is part of moving the kit, which establish-morphir-compatibility-kit owns. The host qualification report cites the generic kit run by its report digest, and the check ties both to the same host executable digest.

Task 3.5 runs the same kit package's model tier in-process, in this repository's tests, on 0.2.0-draft.1, the one version HostSession speaks. It reuses the kit's documents and expected IR as fixed data and the conformance project's JSON comparison with the kit's three stated comparison rules.

SEQ-1. Packaging waits for the offerings

Group 5 packages the engine in four offerings. Three of them do not exist as release profiles until add-deployment-and-acquisition lands its tasks 2.1 to 2.4, and that work edits the same files: build/Build.cs, build/Build.Packaging.cs, src/Morphir.Tool/Morphir.Tool.csproj and the entry points. The order is:

  1. Groups 2, 3 and 4 need none of it. They add a project, commands and tests, and touch the entry points only to register two commands.
  2. Task 5.1, the static-link trial on six platforms, is a workflow of its own that publishes the AOT probe per runner. It can start once group 2 exists and does not touch the release profiles.
  3. Tasks 5.2 to 5.4 start only after the deployment change's publish profiles have merged. Before starting, the state of PR #559, of the branches feat/managed-composition and feat/fsharp-frontend-self-contained, and of finos/morphir PR 1147 is checked again and reported in the tracking issue.
  4. The runtime report's deployment value comes from the build identity the deployment change adds. Until that merges, task 4.2 reports the two identities that exist today and says so.

Migration plan

No existing command changes behavior, and no configuration key changes meaning. The two new configuration keys are optional. The runtime ships dark: only the hidden worker command and the runtime report reach it.

The tool packaging change (task 5.4) is the one step a user can notice. It ships with release notes and updated installation guidance in the same release. Rollback is the next release with the previous single package; the fallback package keeps the tool installable in between.

There is no switch that turns the runtime off. An engine defect found after release is fixed by a patch release. Until then a user avoids it by not configuring a WASM extension: nothing else in the CLI loads the engine, so every other command is unaffected. An earlier revision of this page planned a release-level switch and the reason disabled; the parent dropped both at 938f798.

Open questions

The first two are maintainer questions that change what tasks 4.3 and 6.1 can claim. The rest change neither the specs nor the task breakdown, and each is settled with evidence inside the task named.

  • Does the generic guest kit drop its legacy tier? An open maintainer question in the parent since 10 November 2026. Until it is answered, a .NET run of the model tier alone is not a complete run of that kit, and it is unclear whether the qualification rule "A host does not qualify on crafted cases alone" accepts it.
  • How task 4.3 runs the model tier alone through the worker, since guest-run cannot leave the legacy tier out. Either the Rust runner gains a way to select a tier, although the parent's decision record 0004 gives crates/morphir-mck no new runner features, or the model tier gets a .NET runner, which changes the answer to review question 1. This repository asks; it does not choose.
  • Should loading errors have codes? Raised in the parent on 10 November 2026. Until it is answered, the loader reports them with a diagnostic and no code (IMPL-1).
  • Which shared contract states the morphir/command-event and morphir/command-result documents? Raised in the parent at 8b3c4c35. The profile contract fixes only the event names and their members. Until a shared contract states the rest, with the help text and the usage-failure document, the worker follows the MoonBit CLI (WRK-2).
  • How the WASI surface is supplied (task 3.4). The engine's own WASI is the first choice if it can capture stdout and stderr into a bounded buffer and return an error code for every other call. If it cannot, the preview 1 imports are defined as host functions in managed code, which gives exact control at the cost of more code. Either way the crafted sandbox cases decide.
  • Where the Python 0.6.0 module and the SDK fixture are cached for tests, and whether a test without them skips outside CI and fails in CI, as the MoonBit tests do (task 2.2).
  • The fuel value. The contract's number comes from another engine and the unit is engine-defined. Task 2.5 measured the published guests' fuel use and recorded it. Settled for qualification, 10 November 2026: the parent keeps one session budget of 5,000,000,000, lets a runaway case under that budget end at the budget or at the deadline, and tests exhaustion with a budget of 1,000,000 in bounds/small-budget. A .NET-specific default would still need no contract change.
