Context

This local adoption depends on #570 at 1e244a7c and preserves its history. The approved parent decision narrative, running Python example, case table and SVG below are retained from finos/morphir#1154 at 9e7d90e2fb5708580baef7cdd323cd994030c237. References to the old plan describe the parent baseline. Local implementation choices and ownership follow the parent RUN-1 section. Development command requirements supplement the adopted profile. Existing source at this base opens a separate describe session and model session and records legacy cases as not-run.

See proposal.md for the reason. The requirements are in specs/mep/generic-guest-profile/spec.md.

The profile generic-json-library-v1 lets any extension show that it compiles and generates one small Bool library. Today the runner, morphir mck mep guest-run in crates/morphir-mck, reads the guest's describe result and builds a plan with two tiers, each in its own guest process:

  • The legacy tier negotiates MEP 0.1 and uses morphir.frontend.compile and morphir.backend.generate. It is required of every guest: the describe case fails when the guest does not claim 0.1. It also holds the only checks of a malformed source, an unknown method, an unknown notification, an unchanged describe and a request after shutdown.
  • The model tier negotiates 0.2.0-draft.1 and uses compileModel and generateModel with JSON tuples. It runs only when the guest claims it.

The running example is the published Python extension 0.6.0. It claims IR 3.0.0 and 4.0.0 with JSON tuples at both. Under today's plan it would run 35 cases: describe, 19 in the legacy tier and 15 in the model tier. finos/morphir-dotnet#570 ran it through the .NET worker, which offers the 0.2 line only, and recorded the 16 cases that do not need 0.1 as passing.

Goals and non-goals

Goals: a guest that speaks only the MEP 0.2 line can qualify; a run through a host that offers no 0.1 is a complete run; no check that the legacy tier made is lost.

Non-goals:

  • The other two guest profiles, moonbit-model-stable-v1 and python-json-library-v1. Both also negotiate 0.1 in some cases. They have no OpenSpec capability and are not changed here.
  • The MEP contract itself. The Smithy model, the session-legacy transcript and the model transport corpus still describe 0.1.
  • The command names in the capability's Purpose and in "Recheck from the recorded claim". The .NET runner's command names are that repository's choice; a later change aligns the text if they differ.
  • New kit languages or a larger fixed package.

Decisions

The decisions follow one run of the Python 0.6.0 guest, from its claim to its last case.

TIER-1. One session, on MEP 0.2.0-draft.1, required of every guest

The runner starts the guest once. It asks for the description with protocolVersions ["0.2.0-draft.1"], then initializes with the same version and a model transport offer. It never sends 0.1. The describe case now fails when the guest does not claim 0.2.0-draft.1, where it used to fail when the guest did not claim 0.1. A guest that claims both is unaffected: the extra claim is not read.

For the Python guest the plan becomes 21 cases in one process, in this order:

The case ids do not change. The 16 cases that a .NET run records today keep their names, and the five that move keep the names they had in the legacy tier. Request ids are still numbers counted from 1; there is one count now, since there is one process.

Alternatives considered:

  • Keep the legacy tier and let a host that declares the 0.2 line skip it. The maintainer rejected this: it keeps a 0.1 path that nothing else supports.
  • Keep morphir.frontend.compile and morphir.backend.generate as extra cases inside the 0.2 session. They would compare the same IR a second time, and the model transport contract lets a provider that offers only the model methods leave those two flags false, so the cases could not be required.

LIFE-1. The lifecycle checks move into the session

Five checks ran only in the legacy tier. Each says something about the guest that does not depend on the protocol version, so each moves to the one session and none is dropped. Four need no change beyond the session they run in. The fifth, malformed-source, called morphir.frontend.compile; it now calls compileModel with the tuple of the first selected IR version. The model transport contract already fixes the answer: a failed compile is success false with diagnostics and no model. The profile keeps its stricter rule that one diagnostic is an error.

The checks go after the last model case and before shutdown, so that a guest which fails one of them has already shown its compile and generate results. unknown-notification-silent stays with the other notification, directly after initialize.

Alternative considered: drop the five checks and rely on the Python and MoonBit profiles for them. Those profiles are tied to one extension each, so a guest in another language would have no lifecycle check at all.

SEL-1. An IR version needs the JSON tuple pair

Today an IR version is selected when the frontend and the backend both claim it, and the model tier then covers the selected versions that also have a JSON compileModel and generateModel tuple. With the legacy tier gone, a selected version without the tuple pair would have no case at all. So the pair becomes part of the selection: a version is tested when the frontend claims it, the backend claims it and the guest claims both tuples for it. When that leaves no version, the describe case fails, as it does today when the frontend and backend share no version.

The frontend and backend claims stay in the rule. The model transport contract says the IR version restrictions of the frontend and backend capabilities still apply to the model methods, so a tuple alone does not make a version usable.

The requirement does not ask for the frontend.compile and backend.generate flags to be true. The Rust runner does ask for them. A runner for the changed profile must not, because those flags authorize only the two methods this change stops calling.

Alternative considered: let the tuples alone select the versions. That is simpler, but it would test a version the frontend or backend does not claim.

KIT-1. The kit file does not change

spec/mep/mck/guest-generic-json.json holds the package, the expected IR for 3.0.0 and 4.0.0, and the sources of each language. None of it belongs to the legacy tier, so the file, its contractVersion 0.1.0-draft.1 and its digest stay as they are. The expected IR was recorded from Python 0.4.2, which speaks only 0.1; Python 0.6.0 returns the same IR through the model methods at both versions (finos/morphir-dotnet#570).

Alternative considered: raise contractVersion to 0.1.0-draft.2, so that a runner written for the earlier plan refuses the file. The Rust runner's tests read this file, so the change would force work in crates/morphir-mck, which RUN-1 avoids. The report check gives the same protection where it matters: a report made under the earlier plan has other cases than the plan the check rebuilds, and fails.

RUN-1. The .NET runner carries the changed profile; the Rust runner is left alone

Decision record 0004, merged through #1148 on 10 November 2026, moves the conformance runner to finos/morphir-dotnet and leaves the Rust morphir mck open to fixes only. On 10 November 2026 the maintainer also decided that the Rust CLI is to be deleted from this repository (recorded on #1146). So the changed plan is built once, in the .NET runner, and crates/morphir-mck is not touched.

Until the Rust CLI is deleted, morphir mck mep guest-run with this kit still runs the earlier plan. spec/mep/mck/README.md says so, and says that such a report does not pass the changed check. The two runners cannot be confused in a stored report, because the report check rebuilds the plan from the recorded claim and compares the case order.

Alternatives considered:

  • Change the Rust runner to the new plan. That is new work on a tool that is being deleted, against decision record 0004.
  • Remove the generic profile from the Rust runner now. That is a Rust change with test and generated documentation updates, and the deletion of the CLI makes it unnecessary.

DEV-1. A separate development executable calls the shared runner

Confirmed campaign decision: product #590 forwards every morphir mck invocation before parsing to separately installed morphir-mck. The new C# src/Morphir.Mck/ executable references Conformance and System.CommandLine directly. Adapt the preserved Tooling command donor without ICommandProvider, MckScenario, product mediator or console helper dependencies. Existing WasmHostCommands.RunAsync, CheckReport and UsageError continue to implement crafted commands. Add generic commands alongside them, with new GuestKit plan/report code inside the same library. This avoids a second checker and keeps the engine outside the product closure. Alternatives of embedding in Tooling or publishing Conformance solely for Tooling contradict the confirmed boundary.

morphir-mck wasm-host run --kit <crafted-kit-directory> --host <host> ...
morphir-mck wasm-host report-check --kit <crafted-kit-directory> --report <file> ...
morphir-mck mep guest-run --kit <guest-generic-json.json> --host <host> --module <python.wasm> --report <file>
morphir-mck mep report-check --kit <guest-generic-json.json> --report <file>

The host's repeatable --host-arg values precede its extension worker arguments. Explicit identity/digest inputs and validation remain at the runner boundary. The final command guide must give working pinned .NET and MoonBit examples and distinguish the Rust transitional command. Its existing IR/package gates remain unchanged; RUN-1 does not authorize replacing the whole Rust runner.

PROC-1. Reuse the worker edge and keep its defects visible

Continue through WorkerSessions and the existing MEP HostSession, with one factory opening and one worker record. Describe must not end that session; initialize and every later case reuse it. Numeric request IDs count from 1 across the run. Preserve transport evidence for actual sent requests, notification silence, post-shutdown errors, exit and stdout closure. A locally suppressed notification cannot prove that the guest accepted it. If the worker cannot expose a required raw lifecycle observation through its current contract, report the precise blocker to the runtime and parent owners rather than invent success or bypass checks.

The HELD generated-file branch at 34fcc6dc has unresolved native-process review defects and an uncompiled watchdog fix. It is not a reusable helper. Do not copy its Types, Runner, CliAdapter, Workflow or BoundedProcess work. Do not add another process launcher. Review and correct defects on the existing owned edge under an agreed source boundary, with hermetic process tests through TestSupport, before accepting real evidence. Builds and tests require a separate CPU2 grant; each burst uses two processors, -m:1, no shared compiler or node reuse and a 240-second whole-tree kill-and-await deadline. No protection setting changes belong here.

EVID-1. Rebuild reports from fixed data and recorded observations

New generic report code belongs under GuestKit. It records the kit digest, runner identity, host executable path/arguments/digest, guest module digest, one process/session, original describe claims, selected language and versions, ordered case requests/responses and outcomes. The checker rebuilds selection and order using the same plan and comparison functions as execution, verifies each request and response, and refuses unknown, missing, duplicated, legacy or unrun required cases. It does not trust stored outcome or qualified fields. Fixed test transcripts must be authored independently of the runner, including invalid transcripts that do not qualify.

Generic profile success is separate from crafted host qualification. WasmHost/HostReport.fs currently explicitly refuses a verdict. The deployment root owns parent task 1.4's normative verdict/schema/fixed data, and parent tasks 1.6/1.7 documentation/Smithy. This change neither invents those rules nor treats successful generic tests as package, RID, minimum-OS, acquired-release or release qualification.
