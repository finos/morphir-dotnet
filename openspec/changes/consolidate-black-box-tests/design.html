Goals and non-goals

Goals:

  • One place and one form for a black-box test, so that a person or an agent knows where a new one goes.
  • One way to start, contain and stop the product in a test, used by the new project and by the tests that have not moved yet.
  • The build runs a purpose group as a unit, in parallel with other units, with its own time in the report.
  • The same scenario runs against the development build and against each published form.
  • Rules that a program can check are guard tests, so the skill is not the only enforcement.

Non-goals:

  • No single large pull request. The change is the complete migration, in six pull requests (migration plan).
  • No change to the compatibility kit, its suites or its step vocabulary.
  • No in-process run of the CLI (DRV-3).
  • No change of a unit test, a property test or a time-budget test into Gherkin.
  • No new CI job. The groups run in the existing test jobs, and the Native AOT checks keep their step in the Linux job.

Decisions

PROJ-1. One C# project, four folders

tests/Morphir.BlackBox.Tests is one TUnit project with Reqnroll. The folders Integration, EndToEnd, Smoke and Journeys hold the feature files. Steps holds the step classes, one for each capability, shared by the four groups.

Why: the groups share steps and drivers. Four projects need a fifth for the shared steps, compile the Reqnroll generator four times, and give an agent four places to choose from. The cost of one assembly is that the build must split it; GRP-1 does that.

Alternatives: four projects (rejected: above). Folders in the existing projects (rejected: the build cannot select them, and the black-box rule cannot hold in a project that references product assemblies).

PROJ-2. No assembly from src/ is visible, also not through the kit

The project references Morphir.TestSupport only. It names src/Morphir and src/Morphir.Tool with ReferenceOutputAssembly="false", so a build of the project builds the development target first, and no product type is visible to a step. It does not reference Morphir.Conformance: that library references Morphir.Compilation and Morphir.Mep, and they would be visible through it.

A test that needs the kit library in the test process (it judges the output of an executable with kit types) is a conformance test. It stays in a project that can reference the kit, and it gets its executable from the target of the testing library (DRV-2). A check of the kit through the CLI (morphir mck ...) needs only the artifact and can be a black-box test.

Why: a compile error is the strongest form of the black-box rule. Two guard checks keep it: the project file has no reference below src/ that exposes an assembly, and the compile dependencies in obj/project.assets.json of the project have no project from src/, which also finds an assembly that comes through another reference.

The machine tripwire. AGENTS.md requires the MachineTripwire assembly hook for a project that starts many processes. The project has it from task 2.1: it captures the home and machine locations of the developer before the first test and fails the run if a Gherkin scenario or a framework test changed them.

GRP-1. A group is a tag, and the build runs a tag as a suite

Each feature has one of @integration, @e2e, @smoke, @journey. Reqnroll.TUnit turns a tag into a TUnit category (verified in #612). TestPlan gets a suite form with a group:

TestSuite.TUnit("Morphir.BlackBox.Tests").InGroup("integration"),   // --treenode-filter "/*/*/*/*[(Category=integration)&(Category!=lane)]"
TestSuite.TUnit("Morphir.BlackBox.Tests").InGroup("smoke"),
TestSuite.TUnit("Morphir.BlackBox.Tests").InGroup("journey"),

The runner starts one process for each group. Each process has its own result directory, hang dump and row in the report. A TUnit run that selects no test exits with 8, so an empty group fails (the rule that #612 added).

Why: this is the smallest change to the runner that makes a group a unit of scheduling, and it reuses the rules WithSourceProjects() and Alone() for a group.

One filter for each process. A process gets exactly one --treenode-filter. A group suite uses its group filter in both scopes and never the PlatformSpecific filter, because the assembly-level category makes each of its tests platform-specific.

Lanes. A test that needs more than the development build has the tag @lane and exactly one of @packages, @native-aot or @published. The lane, not the group, decides where it runs:

Before the first step of a test, one function of the testing library, TestEligibility.Decide, makes one decision from the tags of the test and the run. A test is eligible, or it is skipped with exactly one reason, the first in the order. So no run executes a test of another lane, with or without the exclusion in the filter, and a test with no lane runs in the development run and in a published run. The report counts the skips by the kind of reason (lane, host, capability). The filter only keeps tests of another lane out of the report; task 2.3 proves the two filter forms (one category; a category and not lane) on the pinned TUnit before a suite uses them. If the engine does not accept the exclusion, a group run selects the lane tests and the lane check skips them.

The packed packages. TestBuild gives the packages lane the output folder of PackAll in MORPHIR_TEST_PACKAGES. The driver reads only that folder. A packages run with no package there stops before the first test with the pack command; it does not pack and does not search.

Developer option. ./build.sh --target Test --test-group integration runs only the suites of that group: no other suite, and not the Myriad package-consumer scripts, which the Test target runs after the suites until pull request 4 moves them. A suite is registered in the plan in the pull request task that adds its first test, so no registered suite is empty.

Alternative: one process with all groups (rejected: it is the slowest-assembly problem again).

Alternative: one IMorphirDriver with all commands (rejected: each target must then implement or refuse every command, and the interface changes in every slice).

Resolution. Each target resolves its artifacts once, before the first test. A missing artifact stops the run with the build command that makes it. A target never uses another form: the locator of today can test the untrimmed executable when the trimmed one is missing, and the new one cannot.

The development build. One MSBuild file, tests/Morphir.TestSupport/build/Morphir.CliArtifacts.targets, adds the build-order references to src/Morphir, src/Morphir.Managed and src/Morphir.Tool, asks each for its GetTargetPath with the configuration and framework of this build, and writes the three paths into the test assembly as assembly metadata. Each project that uses the CLI driver imports it: Morphir.BlackBox.Tests, Morphir.TestSupport.Tests (for the real-process tests of the driver), Morphir.Tooling.Tests (which references the tooling library but no entry point, and depends on the solution build for them now), and in pull request 2 Morphir.Frontend.FSharp.Tests, whose kit test uses the DotnetTool host by default because its cases need the F# frontend in the host. Morphir.TestSupport reads the metadata of the test assembly; no path is computed from the repository root. So a Debug test build runs the Debug hosts, and a missing file is an error, not a search. The driver starts an assembly with dotnet, not dotnet run: 0.02 s against 0.35 s for one start.

Why: the repository rule is to parse into a closed type, not to pass a string and check it later. Two variables replace five when their tests move. The managed host has its own tests now (Morphir.Managed.Tests), and a model with one default host would run them on another entry point or not at all. A kit test that stays (Morphir.Frontend.FSharp.Tests/CliAdapterTests.fs) uses the same parser and resolution, so MORPHIR_DOTNET_TOOL_CLI and MORPHIR_AOT_CLI get no reader that stays.

DRV-3. No in-process CLI driver in this change

MorphirApplication.Run writes to the process console and reads the process working directory and environment. A driver that calls it must redirect global state, so two scenarios cannot run at the same time, and it does not check argument parsing through the real entry point, exit codes or the two output streams.

Why not now: it needs a product change (the composition takes its output writers and its environment) that is not a test change. The direct start in DRV-2 gives most of the gain with no product change. Tests of a handler in the same process stay unit tests in their project.

DRV-4. One workspace and one driver set for each scenario

Reqnroll makes one context for each scenario. A [BeforeScenario] hook makes the IScenarioWorkspace and registers the drivers for the selected target; step classes get them through their constructors. An [AfterScenario] hook stops the processes of the scenario and removes the workspace. MORPHIR_TEST_KEEP=failed keeps the workspace of a failed scenario and prints its path. The session factory in Morphir.TestSupport reads the environment and makes the resources, so a hook and a step need no call to the machine.

The process limit. ProcessGate.Shared is one semaphore in one test process. The build runner starts several test processes at the same time, so each would have its own full limit. The runner therefore gives each test process a fixed share, computed once before the first suite starts:

machine = MORPHIR_TEST_MAX_PROCESSES of the caller, or the default of the gate
lanes   = min(--test-parallelism, machine)        // never more test processes than the limit
share   = machine / lanes, rounded down           // at least 1, because lanes <= machine
a suite in a lane gets MORPHIR_TEST_MAX_PROCESSES = share
a suite that runs alone gets MORPHIR_TEST_MAX_PROCESSES = machine   // no other test process runs then

The share does not depend on how many suites run at the moment a suite starts, so a suite that starts first does not keep a larger limit than the next. At each moment at most lanes test processes run, so the sum is at most lanes * share, which is at most machine. The pure function is in TestPlan, with tests for 8 and 2 lanes (4 each), 8 and 3 lanes (2 each), a limit of 1 with 2 lanes (1 lane), a suite that runs alone, and a suite that starts in a lane that another suite left. A coordination between processes (lock files) was considered and rejected: the runner already knows the lanes.

Why: no scenario shares a folder with another, so the scenarios of a group run in parallel with no lock. This is the rule that #612 wrote in docs/contributing/ci-os-matrix.md, in one place in code.

DRV-5. Capabilities and the skipped result

DriverCapability is a closed set (for example Generation, SelfContainedFrontend, NativeEngine). A scenario states a need with a tag (@needs-self-contained-frontend). The capability check is the third check of the one eligibility decision (GRP-1): an unsupported capability ends the test as skipped with the capability, the target and the host in the reason. A guard test checks, for each test that a pull request must run (a test with no lane, with the packages lane or with the Native AOT lane, in any group), that the pull request run of its lane selects the test and supports the complete set of its capabilities on an operating system of that run: the development build on each operating system, the packages run on each operating system, the Native AOT step on Linux. The check includes the host: the run must have the host that the test names. A test of the published lane is run by the release and manual workflows. The check is for each test, not for each capability: a test that needs two capabilities fails the guard when one run supports only the first and another only the second. So a skip cannot hide a test in pull request CI. The report shows the count of skipped tests with their reasons.

ASRT-1. One result type; general assertions apart from report checks

CommandResult has the command line, the exit code, standard output, standard error, the duration and the files that the command wrote in the workspace. Two layers check it:

LayerWhereChecks
GeneralCommandResultAssertionsThe exit code; standard output is exactly one JSON document and nothing else (the CLI logging rule of AGENTS.md); a file was written; text on standard error. It knows no field of a report.
Report of one commandThe capability, for example GenerationReport and VerificationReportThe status field of that report and its diagnostics. The verification report states validity in IsValid; the generation report has success and diagnostics, and success must agree with the exit code. extension list has its own form.

Each failure message has the command line, the exit code and both streams. Task 1.3 tests the general layer, and task 1.7 tests each report type against a real report of its command.

Why: CliExecutionResult, ExecutableExecutionResult and CliRun.ShouldExitWithOneJsonReport are three forms of this, and the last one assumes a field that not every command has.

STEP-1. A small step vocabulary, recorded and checked

A step is reused before a new one is written. tests/Morphir.BlackBox.Tests/README.md has a table of the step patterns, by capability. A guard test reads the step attributes from the step sources and fails when the table and the sources differ, and when two steps have the same pattern.

The kit suites in conformance/suites/ keep their own vocabulary and their own runner.

FORM-1. Framework tests in the black-box project for three exceptions

Gherkin is the default. A loop over a corpus, a property test and a test with a time budget are framework tests (TUnit). When such a test reaches the product through an artifact, it is in the black-box project, in the folder of its group, with [Category("e2e")] (or its group) and with the drivers. Examples that move in slice 2: the worker corpus of ExecutableExtensionWorkerTests, and the one test of ExecutableRunnerTests that runs the built tool. The other eight tests of ExecutableRunnerTests test the log filter of the helper and go to Morphir.TestSupport.Tests with the driver that replaces it. A test that also needs a product assembly is split: the comparison stays in the unit test project (for example the wire-form rows of CSharpCliGenerationTests, which call CSharpGenerator.Generate).

Why: the owner agreed that these forms do not fit Gherkin. Without this rule the removal of Morphir.E2E.Tests loses its 58 framework test methods. The 41 of them that test a helper (InfrastructureTests/) move to Morphir.TestSupport.Tests with the driver that replaces the helper, or are removed with a helper that has no successor, and the move table says which.

After the class, a black-box test gets a lane only if it needs more than the development build: the packed packages, a Native AOT publish, or a published executable (GRP-1). A test that needs both a product assembly and an artifact is two tests (FORM-1).

MARK-1. The PlatformSpecific marker shrinks with each slice

A slice removes the marker from the tests that it moves, because they leave the unit project. A unit test that uses the operating system keeps the marker. The mechanism of #612 stays. When the last slice is done, the count of marked unit tests is the measure of what is still platform-sensitive outside the black-box project.

DRV-4, the process limit The fixed share is implemented as written. With the default limit of the gate, a run on a CI runner (3 or 4 processors, 2 test processes at the same time) gets a share of 1, where each test process had 2 before. The two slowest suites then take almost two times as long (Morphir.Tooling.Tests 112 s against 58 s, Morphir.Frontend.FSharp.Tests 200 s against 124 s, alone on an 18-processor machine). So the test jobs of development.yml set MORPHIR_TEST_MAX_PROCESSES: 4: the caller gives the limit of the machine, as the formula permits, and each test process keeps 2. On a developer machine the default limit costs about 10 % of the Test run (247 s against 224 s). slice-1-times.md
