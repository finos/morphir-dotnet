Context

Observed today in morphir-dotnet:

  • Morphir.Models reads and writes single-file models: ClassicJson/ClassicJsonWriter for classic versions 1 to 3 (the writer writes integer versions only and refuses Specs) and V4Json/V4JsonWriter for IR 4. It targets net11.0;net10.0;netstandard2.0, because the C# source generator and the MSBuild task load it into a compiler host, and it makes no file-system calls.
  • VFile, VFileTree and PropertyBag live in Morphir.IR.Pipeline (net11.0;net10.0 only). The draft Ion tree reader in Morphir.Ion reads trees through VFileTree and owns TreeStems.fs (escaping, truncation, dependency directories), with its own private file-kind types.
  • morphir ir verify is the only ir command. compile refuses ir.layout = "document-tree"; generate and validate refuse JSON trees.
  • Unknown commands route to an external morphir-<name> tool on the search path.

The parent repository specifies v3 (3.1.0 only) and v4 document trees, ships 17 kit tree cases, and proposes ir/name-compaction in its add-bounded-model-access change. Constraints: no Rust code changes; the kit is due for a redesign and must not shape this work; Native AOT with zero trim or AOT warnings; each milestone about five hours of review.

Goals and non-goals

Goals: a model layer that splits, joins, stores and compacts models with one source of truth per concern; a store boundary that keeps file paths and bytes out of the model; tests that trace one to one to the specs.

Non-goals: the YAML profile and writing Ion trees; changing a model's IR version; tree support in compile, generate and validate (the library is shaped for it); bounded or paged reading, snapshots and access sessions; the daemon's VFS manager; MoonBit; moving v3 decorator sidecars.

Decisions

The worked example throughout: package acme/demo, module Billing with type Invoice and value total, and dependency morphir/sdk with module Basics, stored as morphir-ir.json.

CLI-1. A model group replaces the IR group

A model is the IR plus decorators, metadata and later additions, so the group is morphir model with verify and convert. ir verify becomes model verify unchanged. No alias: the project is pre-1.0 and the changelog states the rename. ir then behaves as any unknown command, including tool routing. The parent's release qualification runs morphir ir verify (tools/cli-release.ts), so a companion finos/morphir change updates it with the pin move that brings the rename. Alternative: keep ir as an alias. Rejected: it keeps two names for one thing and nothing older needs protecting.

CLI-2. One convert command with two output axes

A layout change keeps the version and the content, so it is a conversion, not a migration; project migrate and workspace migrate stay as they are. The output has two independent axes: layout (--layout, default the input's) and encoding (--compact[=<mode>], default plain). A run that changes neither exits 2.

morphir model convert --input morphir-ir.json --output tree --layout document-tree
morphir model convert --input morphir-ir.json --output compacted.json --compact
morphir model convert --input compacted-tree --output plain.json --layout single-file

Option values are given only with =. A probe of System.CommandLine 2.0.15 showed that an optional value takes the next token greedily (--json model.json took model.json as the value). convert has no positional argument, but the rule matches the CLI-wide --json[=stream|document] rule of adopt-streaming-json, which rewrites a bare flag before parsing. Machine output follows that change from milestone 1, with a fileWritten event per file. Alternatives: a --compact-names flag (no room for further compactions); migrate (wrong meaning).

VER-1. Verify checks every stored form

Observed: ir verify validates single files against embedded v1, v2 and v3 JSON Schemas only. It defaults to v3 when formatVersion is missing, and --schema-version accepts 1 to 3. A model that convert writes must be verifiable, so model verify gains three inputs:

v3 single filea file that says "3.1.0", the form of a v3 Specs, against the parent's 3.1.0 schema (website/static/schemas/morphir-ir-v3.json), pinned with provenance as morphir-ir-v3.1.0.json; the integer 3 against the older v3 schema. Then a file that states 3 or "3.1.0" is read with ClassicJson.readDistributionStrict, as convert reads it, so a member that the classic model has no place for is unknown_member1

Verify reuses the store rather than a second tree walker, so a tree that convert accepts is exactly a tree that verify accepts. Errors carry the tree-relative file path and the JSON path inside it. For a tree the version comes from the manifest, and a --schema-version that contradicts it exits 2. Alternative: schema checks only (would miss the cross-file rules such as a listed value with no file; rejected).

CONV-1. Convert through the typed model

The single file is decoded with the existing codecs, split into typed documents, and written per document; a tree is read back into the same typed model. The input is checked, there is one source of truth, and later commands can reuse the reader and writer. Equality is semantic, which is what the kit checks.

AlternativeWhy not
Move JSON nodes without decoding (#214's first idea)Tree files are their own format (per-file formatVersion, name lists, fileNames, access, dependency directories); it would duplicate schema knowledge, need position-based surgery on v3 arrays, could write invalid trees, and nothing else could reuse it.
Port the Rust tree code line by lineIts structure does not fit the .NET typed models, and the Rust CLI is being retired. It stays a reference for edge cases only.

FILES-1. Extract Morphir.Files for every target

.NET has no general virtual file system in the base library. The repository already has one: VFile/VFileTree, documented as the primary multi-file abstraction. Morphir.Models cannot reference it today because of its netstandard2.0 target. Property.fs, File.fs and FileTree.fs (about 1,640 lines) move to a new Morphir.Files targeting $(MorphirLibraryTargetFrameworks);netstandard2.0. Morphir.IR.Pipeline keeps the processor and builder and references it.

A trial netstandard2.0 build of those three files gave 82 errors, all in them, from fewer than 20 gaps: ReadOnlyMemory, ImmutableDictionary, HashCode, the three-argument File.Move, ReadAtLeast, DirectoryInfo.LinkTarget, OperatingSystem.IsWindows, Path.TrimEndingDirectorySeparator, Convert.ToHexString and char overloads; about 34 were inference cascades. They are closed with the Polyfill.fs and #if NETSTANDARD2_0 pattern of Morphir.Models. System.Memory and System.Collections.Immutable come from the compiler and MSBuild hosts.

VFileTree implements Microsoft's IFileProvider (read view, no-op Watch) and can be built from any provider. Physical, embedded and composite providers become sources (embedded kit fixtures, for example), and anything that accepts a provider can read a tree. Alternatives: System.IO.Abstractions (third-party, models a mutable disk; rejected); extracting for net11.0;net10.0 only (then tree code needs a home outside Morphir.Models; rejected); porting all of Morphir.IR.Pipeline (pulls the pipeline into the compiler host; rejected).

TREE-1. Three layers: address, document tree, store

Only the store sees Morphir.Files. All three layers live in Morphir.Models:

type ModuleDocumentAddress =
    | Module of ModulePath
    | TypeDef of ModulePath * Name
    | ValueDef of ModulePath * Name

type DocumentAddress =
    | Manifest
    | Own of ModuleDocumentAddress                         // pkg/…; the manifest names the package
    | Dependency of PackageName * ModuleDocumentAddress   // deps/<package>/@/…

type DocumentTree<'manifest, 'module, 'typ, 'value> =
    { Manifest: 'manifest
      Documents: Map<DocumentAddress, TreeDocument<'module, 'typ, 'value>> }

module DocumentTree =
    val split : Distribution -> DocumentTree
    val join  : DocumentTree -> Result<Distribution, TreeError>

module DocumentTreeStore =
    val read  : ReadOptions  -> VFileTree -> Result<DocumentTree * ReadReport, StoreError>
    val write : WriteOptions -> DocumentTree -> VFileTree

In the example, Own (TypeDef (Billing, Invoice)) is the address; pkg/acme/demo/billing/invoice.type.json is only what the store writes for it. Dependency (morphir/sdk, Module Basics) becomes deps/morphir/sdk/@/basics/module.json. The address has no version, since the v4 model carries none; the store writes the bare @ and refuses a versioned segment (decision 0015). It maps one to one onto the daemon's morphir:// URIs. The tree holds decoded, typed documents: convert decodes every document to check it anyway, and bounded reading is a separate later reader (CMP-1). TreeStems.fs moves from Morphir.Ion into the store, with shims for SHA256.HashData and Convert.ToHexString, and the Ion reader uses it from there. Alternatives: expose VFileTree to the model (couples the domain to storage); lazy encoded documents (adds caching and late error rules now; rejected as 10B).

TREE-2. Version labels and members follow the tree specs

Every v3 tree file says "3.1.0". A v3 Library tree joins to "formatVersion": 3 (kit cases document-tree-0011, 0012, 0014, 0015, 0017); a Specs tree stays "3.1.0" (document-tree-0013). A Library round trip returns the original label without a notice. A declared 3.1.0 Specs writer is added, as ir-model-writing requires new versions to be added by declaring a writer. A v4 manifest's layout and pathBudget are dropped (they describe the tree; writing uses a budget of 4000), and version and created are dropped with a notice naming each. Everything else the model cannot carry is refused. $meta is ignored and never written (decision 0014).

CMP-1. Whole-file compaction now, bounded reading later

Milestones 2 and 3 meet the correctness part of ir/name-compaction: exact round trip, typed name positions only, the refusals, deterministic output, and the table-size and name-length limits. A context after the document is refused, not spilled. Resolving one name without building the document, bounded spill and byte pass-through stay with bounded model access. The parent spec marks that split and records tasks 2.2 and 2.3 as partly done. Compaction applies to every file kind and both layouts, so a v3 or v4 single file can be compacted and stay one file. In the store it is a write option, and reading reports which files were compacted. Alternative: all of ir/name-compaction now (several days per milestone, and it would decide the bounded reader early; rejected as 3B).

CMP-2. The envelope is identified by a schema URL

The envelope is identified by a $schema URL under https://morphir.finos.org/schemas/<family>/<version>/<document>.schema.json instead of contextVersion, matching the project's move to schema URLs. The parent edits ir/name-compaction and completes task 1.1 (grammar, tables names, packagePaths, modulePaths and fqNames, {"$name": …}, critical, a JSON Schema under website/static/schemas, valid and invalid examples) before .NET reads it. .NET pins those examples and moves the pin when the parent merges. .NET never defines the envelope or policy itself.

CMP-3. Canonical bytes are RFC 8785 JSON

Parent task 1.4 forbids expectations produced by an implementation, and the policy's "alias only when it saves space" rule needs a byte count that does not depend on the host. Utf8JsonWriter escapes non-ASCII by default (é as six bytes), so two hosts could disagree. Compacted files are therefore written in RFC 8785 JCS (sorted keys, raw non-ASCII, the JCS number form, no whitespace), and the policy counts the UTF-8 bytes of that form. The parent's fixed cases (a v3 and a v4 single file, v3 and v4 files of each tree kind, a name used once, a non-ASCII name, alias allocation, ties, table order, look-alike literals, a loss case) are worked out by hand and reviewed there. A small AOT-safe JCS writer in Morphir.Models is tested against the RFC's examples. Plain tree files keep the typed writers' output. Alternative: semantic expectations with name-only sizes (simpler, but output deterministic only up to formatting; rejected as 4B).

TEST-1. Every scenario has a test, built on drivers and mothers

Each OpenSpec scenario has a test with the same name. It is a Gherkin scenario where the test-manager skill gives integration or journey, and an Expecto or TUnit test for laws and corpus loops. tasks.md ends with the traceability table.

TEST-2. The kit is reference data

The parent kit is tied to the Rust implementation (runner, step grammar, adapter protocol, CI gates) and is due for a redesign. This work uses none of that. The kit's tree cases are pinned from one commit as data, and ModelConversionKitCases.feature has one .NET-owned scenario per case, named with its kit id. YAML spellings are translated to JSON by FixtureCatalog with a test-only parser. The parent's compaction contract is published as plain spec artifacts, not kit cases, so the parent's Rust gates are untouched.

REL-1. One branch, inspectable milestones

All work is on feat/model-convert. Each milestone ends with a commit that builds and passes its tests, and a note saying what to try. The maintainer decides after each milestone whether it ships as its own pull request. Order: step zero (Morphir.Files), milestone 1 (plain trees, model group), milestone 2 (read compacted files, after the parent's task 1.1), milestone 3 (write compacted files, after the parent's task 1.4). adopt-streaming-json lands before milestone 1's command or with it.

Kit data changes shape in the redesign.Only FixtureCatalog's source changes; the scenarios are .NET-owned.

Migration plan

  • Users replace morphir ir verify with morphir model verify; the changelog states it. There is no alias to remove later.
  • Code that used VFile, VFileTree or PropertyBag from Morphir.IR.Pipeline references Morphir.Files. The builder chooses whether the namespace changes; consumers inside the repository are updated in step zero.
  • Rollback: each milestone is one or more commits on the branch and can be reverted alone. Step zero can be reverted only together with the later milestones.

Open questions

  • The exact schema URL and policy id (working names ir-context/0.1.0-draft.1 and morphir.compact/0.1.0-draft.1) are fixed by the parent edit.
  • Whether a bare --compact widens when a second mode arrives is decided then.
  • The namespace of Morphir.Files (keep Morphir.IR.Pipeline or move to Morphir.Files) is the builder's call in step zero.
