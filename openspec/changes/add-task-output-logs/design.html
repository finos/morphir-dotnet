Context

See proposal.md, section Why. Facts that shape the approach:

  • Both hosts (morphir and dotnet-morphir) build the CLI in MorphirCli. Serilog writes every log line to Console.Error through its console sink. Command output goes to Console.Out or to an injected writer, such as ICompileOutput for compile.
  • The out root and the task location are known only after the settings stage: CompileTaskLocator resolves --out-dir, MORPHIR_OUT_DIR, workspace.out_dir and the member path.
  • compile holds compile.lock exclusively from the settings stage to the end of the run. generate holds compile.lock shared while it reads the IR, and has no lock of its own. validate resolves no out root today.
  • Environment variables map to keys by the standard rule: MORPHIR_WORKSPACE__TASK_LOGS becomes workspace.task_logs. The pinned upstream schema has no such key, so scripts/configuration/generate-schema.py adds it, as it already adds [frontend.<language>].project_file.

Goals and non-goals

Goals: capture both streams with no change to what the streams receive; write the files for success, failure and cancellation; never leave a file that mixes two runs; keep the cost bounded.

Non-goals: log rotation or history of earlier runs; a log of the child processes (the MSBuild provider, MEP guests) beyond what the command itself prints; a morphir command that reads the files; a new command-line option (the setting is enough, per the request).

Decisions

CAP-1. Capture at the process edge with tee writers

MorphirCli replaces Console.Out and Console.Error, before it configures logging, with tee writers. A tee writer writes through to the original stream at once, and also appends to a bounded in-memory buffer. Injected writers such as ConsoleCompileOutput use Console.Out and Console.Error, so they are captured too. Nothing that a command writes changes.

Alternatives: a Serilog file sink catches log lines but not the command output or the --json report. A wrapper per command misses log lines and output written outside the command.

CAP-2. Buffer until the task location is known, then write once

The out root is not known when the process starts, so each tee keeps its bytes in memory, up to 16 MiB for each stream (the spec bound), and then counts the bytes that it leaves out. A task command reports its task location to a TaskOutputLogs service when its settings resolve. At the end of the run, also after a failure or a cancellation, the service writes each buffer to a temporary file beside the target and renames it over <task>.stdout.log and <task>.stderr.log. A run that never reports a location writes nothing.

Alternative: stream to the file as the run goes. That keeps the output of a process that is killed, but the location is not known at the start, a reader could see a half-written file, and two runs would need a lock for the whole run. The rename gives the "never mixes two runs" requirement with no new lock for compile.

CAP-3. Locks: write under the task's exclusive lock

compile writes the files before it releases compile.lock. generate and validate take their own exclusive lock, generate/<target>.lock and validate.lock, only for the short time of the write. The lock follows the out-directory rule that a task's files beside its record are written under <task>.lock.

CFG-1. One setting, the standard levers

workspace.task_logs, boolean, default true, read through the existing layered resolution, so the project file, the user configuration and MORPHIR_WORKSPACE__TASK_LOGS all work with no new code path. A value that is not a boolean fails the settings stage with compile.invalid_setting (or the generate and validate equivalent), exit code 2, naming the key and its source.

Alternative: a short alias such as MORPHIR_TASK_LOGS. The out root has its own variable, MORPHIR_OUT_DIR, because the upstream specification defines it. No upstream text defines a log variable, so this change adds no alias.

CFG-2. Turned off means no write, no delete

With task_logs = false, a run writes no files and leaves earlier files. Deleting them would destroy evidence that a user may still need, and the files carry no run identity that a reader could confuse with a newer run, because the record beside them does.

FMT-1. File content

The files hold the stream bytes as written, UTF-8, with the console's line endings. A file that reaches the bound ends with one line: [morphir: N more bytes not kept; the limit is 16 MiB]. ANSI styling in human mode is kept, because the files hold what the stream received.

Risks and trade-offs

  • [A killed process (SIGKILL, power loss) writes no log] → accepted for this change (CAP-2). A later change can spill the buffer to a temporary file once the location is known.
  • [Memory: up to 32 MiB of buffer] → bounded per stream; most runs write a few kilobytes.
  • [The guest's stderr in a MEP compile is copied to the host's stderr] → it is captured as host stderr output, which is what the user saw.
  • [Tests that capture Console.Out in process] → the tee writes through, so captured output is unchanged; tests with an injected writer are not affected.

Migration plan

None. The files are new. Turning them off restores the current out-root contents exactly.

Open questions

None that change what gets built. An upstream request to add the files to the shared out-directory specification is a workflow follow-up.
