Context

See proposal.md for motivation. The requirements are in diagram-linked-metadata, svg-metadata and rdf-datasets.

The current code has these properties:

  • Morphir.Knowledge provides Iri, DocumentId, DocumentVersion, TextSnapshot, TextSelection, and the generic Annotation<'Target,'Body> and KnowledgeLink<'Source,'Target> records.
  • Morphir.Knowledge.Rdf provides RdfDataset and N-Quads only. Its writer already reports lossy output (empty named graphs) as a typed error, with an explicit EmptyGraphHandling.Omit option. This design follows that pattern.
  • Morphir.Diagrams parses Mermaid flowcharts and sequence diagrams. Nodes, groups and participants have authored DiagramIds. Edges, messages, notes and frames have no identifier, only a source span. The SVG writer already emits data-node, data-group, data-source and data-target.
  • Morphir.Svg names are unqualified XML names (SvgName). The document writer uses XmlWriter, so text content is escaped already. There is no reader.
  • The offline player inlines the SVG string in a JSON payload, so whatever the SVG contains travels with the player page.
  • Every package involved is IsAotCompatible, and the diagrams and SVG packages have not been released yet.

Goals and non-goals

Goals:

  • One data model, the RDF dataset, whether the data is in a sidecar file or embedded in the SVG.
  • Reuse the knowledge types rather than adding parallel comment and link records.
  • Byte-stable output, so rendered SVGs can be checked in and diffed.
  • Player JavaScript never parses RDF.

Non-goals:

  • Metadata written inline in Mermaid source.
  • JSON-LD and Turtle.
  • Finding sidecar files on disk.
  • CLI commands.
  • Editing comments in the player. It only displays them.
  • Carrying references across revisions when an element is renamed.

Worked example

The same example runs through every decision. A team keeps checkout.mmd with this content:

flowchart LR
  Cart --> Billing
  Cart --> Billing
  Billing --> Ledger

A reviewer comments on the first Cart → Billing edge. An author links Billing to lines 10–24 of src/Billing.fs at a git commit. A tool records an owner fact about Ledger that no Morphir code knows about. All of it lives in checkout.mmd.nq. The renderer embeds the dataset into checkout.svg, and the player shows it.

Decisions

REF-1. Element references use authored identifiers plus per-kind ordinals

Every element gets a reference string of the form kind=key. It is written on the element's outer <g> as data-ref, and is the fragment of the element IRI (REF-2).

ElementReferenceExample
Flow nodenode=<id>node=Billing
Group (subgraph)group=<id>group=payments
Flow edgeedge=<source>/<target>/<n>edge=Cart/Billing/0, edge=Cart/Billing/1
Participantparticipant=<id>participant=Api
Messagemessage=<sender>/<receiver>/<n>message=Api/Db/2
Note, framenote=<n>, frame=<n>frame=0
Playback stepstep=<n>step=3

The ordinal n starts at 0 and counts in source order, among elements of the same kind and, for edges and messages, the same endpoint pair. Adding an edge elsewhere does not change Cart/Billing/0. Inside keys, %, /, = and every character outside RFC 3987 ifragment are percent-encoded as UTF-8, so parsing is unambiguous.

Alternatives considered:

  • Global positional indices. Rejected, because any insertion renumbers everything after it.
  • Hashes of label content. Rejected, because fixing a typo in a label would orphan every comment on that element.
  • Mermaid's e1@--> edge identifiers. The reader does not parse these today. When it does, an authored edge id becomes edge=@e1. The leading @ cannot be confused with the endpoint form, so this extension is backward compatible.

Notes and frames have no authored identity or natural endpoints, so their ordinals are fragile. The risks section covers this, and the dangling-target warning surfaces it.

REF-2. The diagram is a knowledge document. Its revision defaults to a content hash.

The caller supplies a DocumentId, for example https://example.org/diagrams/checkout. An element IRI is {document IRI}#{reference}, for example https://example.org/diagrams/checkout#edge=Cart/Billing/0. A document IRI that already has a fragment is rejected, because the element reference must own the fragment.

The revision is a RevisionId. The caller can supply one, such as a git blob id. Otherwise it defaults to sha256: followed by the lowercase hex SHA-256 of the UTF-8 source text. The hash is over the exact text, including line endings, which matches what DiagramDocument.Source keeps.

Alternative considered: making the revision mandatory. Rejected, because a one-off render should not need a version-control concept, and the hash is stable and free.

SEL-1. DiagramSnapshot and DiagramSelection mirror the text types

type DiagramElementRef        // REF-1 value; Parse / TryParse / ToString
type DiagramSnapshot =        // like TextSnapshot
    static member Create : DocumentVersion * DiagramDocument -> DiagramSnapshot
    static member FromSource : DocumentId * DiagramDocument -> DiagramSnapshot  // sha256 revision
    member Version : DocumentVersion
    member ElementIri : DiagramElementRef -> Iri
    member TryResolve : Iri -> DiagramElementRef option

type DiagramSelection =       // like TextSelection
    static member TryCreate : DiagramSnapshot * seq<DiagramElementRef>
                              -> Result<DiagramSelection, DiagramSelectionError>
    member Version : DocumentVersion
    member Elements : ImmutableArray<DiagramElementRef>   // deduplicated, kind order then source order
    member TryRead : DiagramSnapshot -> Result<..., DiagramSelectionError>   // VersionMismatch

In the worked example, the comment target is DiagramSelection.TryCreate(snapshot, [edge=Cart/Billing/0]), and the comment is an Annotation<DiagramSelection, string>. The code link is a KnowledgeLink<DiagramSelection, TextSelection>, with a TextSelection over Billing.fs at the commit's revision.

DiagramSelectionError mirrors SelectionError, with the cases Empty, UnknownElement of ref and VersionMismatch. Construction is the only check. A selection is immutable and never re-resolved silently.

RDF-1. Comments use Web Annotation. Links use a link node plus a direct triple.

Statements for the worked example, using prefixes oa: (W3C Web Annotation), dcterms:, xsd: and md: (the Morphir diagram vocabulary, see open questions):

<urn:review:1> a oa:Annotation ;
    oa:motivatedBy oa:commenting ;
    oa:bodyValue "Is this call idempotent?" ;
    dcterms:creator <urn:reviewer:one> ;
    dcterms:created "2026-11-18T09:00:00Z"^^xsd:dateTime ;
    oa:hasTarget _:t .
_:t a oa:SpecificResource ;
    oa:hasSource <https://example.org/diagrams/checkout> ;
    md:revision "sha256:9f2c…" ;
    oa:hasSelector [ a oa:FragmentSelector ; rdf:value "edge=Cart/Billing/0" ] .

<urn:link:billing-impl> a md:Link ;
    md:linkSource _:s ; md:linkPredicate ex:implementedBy ; md:linkTarget _:code .
_:code a oa:SpecificResource ;
    oa:hasSource <https://example.org/src/Billing.fs> ; md:revision "4be1…" ;
    oa:hasSelector [ a oa:TextPositionSelector ; oa:start 312 ; oa:end 901 ] .
<https://example.org/diagrams/checkout#node=Billing> ex:implementedBy <https://example.org/src/Billing.fs> .

<https://example.org/diagrams/checkout#node=Ledger> ex:owner "payments-team" .

The mapping works as follows:

  • Selections. A diagram selection is one oa:SpecificResource with the document as its source, the revision, and one oa:FragmentSelector per element. A text selection is the same, with one oa:TextPositionSelector per range.
  • Text offsets. Web Annotation counts code points, so offsets are converted from UTF-16 on write and back on read.
  • Links. A link has its own identity, so it is a node. When the source is a single element and the target resolves to an IRI, the writer also emits the direct triple. Consumers that know nothing about Web Annotation can then query ?element ex:implementedBy ?x.
  • Reading. The reader reconstructs annotations and links from their nodes. It recognizes the direct triples that match a link, and leaves every other statement in the dataset untouched. ex:owner above is an example: it stays as it is, and the player shows it as a property (UI-1).

Alternatives considered:

  • Direct triples only. Rejected, because it loses link identity and revision pinning.
  • RDF-star. Not in RDF 1.1, and the dataset model would need quoted triples.
  • A Morphir-only comment vocabulary. Rejected, because Web Annotation is the W3C standard for exactly this, and existing annotation tools understand it.

RDF-2. N-Triples and RDF/XML codecs, with RDFC-1.0 for canonical output

N-Triples reuses the N-Quads grammar with the graph term disabled. It adds an NTriples type with Read, TryRead, Write and TryWrite, following the NQuads shape.

The RDF/XML writer produces a fixed striped form:

  • One rdf:Description per subject, using rdf:about or rdf:nodeID.
  • Property elements with rdf:resource or rdf:nodeID, or literal content with rdf:datatype or xml:lang.
  • No abbreviations, no rdf:parseType, no typed-node shorthand.
  • Predicates split at the longest suffix that is a valid NCName. If no such suffix exists, the write fails with a typed error.
  • Namespace prefixes are well-known (rdf, rdfs, xsd, oa, dcterms, md), then ns0, ns1, … in sorted namespace order.

The writer can produce a document, or an element written into a caller's XmlWriter for embedding.

The RDF/XML reader implements the full RDF 1.1 XML Syntax grammar over XmlReader, or over an XElement that inherits namespace bindings. The grammar includes:

  • parseType Resource, Literal and Collection
  • xml:base
  • rdf:li
  • Reification through rdf:ID
  • Property attributes

It is tested against the pinned W3C rdf-xml suite, with a PROVENANCE.md like the one for the N-Quads fixtures. DtdProcessing.Prohibit and XmlResolver = null are always set. The few suite tests that declare entities in a DTD are listed as excluded in the provenance file, with that reason.

Canonical output: blank nodes are Guid identities, fresh per read, so two reads of one sidecar would otherwise serialize differently. RdfCanonicalization.Canonicalize(dataset, limits) implements RDFC-1.0, tested against the W3C rdf-canon suite. Each writer gets a canonical option that sorts quads and uses canonical labels, which _:c14n0 becomes in RDF/XML rdf:nodeIDs. The diagram renderer always writes canonically.

Alternatives considered:

  • A hand-rolled one-hop hash labelling. Rejected, because it is nondeterministic on symmetric graphs and has no test suite.
  • Making determinism depend on the caller keeping identities stable. Rejected, because it is easy to break silently.

SVG-1. Namespaced SvgName, an escaped text payload, and a safe reader

SvgName gains an optional namespace and prefix, through SvgName.Qualified(prefix, local, namespace). The existing unqualified cases are unchanged. The scene validates the following:

  • NCName local names and prefixes.
  • No xmlns prefix.
  • The xml prefix is bound only to its namespace.
  • One prefix per namespace for each element.

The writer emits each declaration once, at the outermost element that uses it. SvgDocument gets an optional Metadata node, written as the root's first child. Text payloads go through XmlWriter.WriteString, which escapes them rather than using CDATA, so ]]> needs no special handling.

SvgMetadataReader.TryRead(ReadOnlyMemory<byte>) uses an XmlReader with these settings:

  • DTD processing prohibited
  • No resolver
  • A MaxCharactersInDocument limit

It returns the metadata content as XElements and text, reports no metadata separately from an error, and gives typed errors with a line and column.

Alternative considered: returning SvgNode trees from the reader. Rejected, because Morphir.Knowledge.Rdf cannot depend on Morphir.Svg, and XElement is the common type both packages already reach through the BCL.

CAR-1. The caller supplies the dataset, and the renderer embeds it

var dataset = NQuads.Read(File.ReadAllBytes("checkout.mmd.nq")).ResultValue;   // any codec
var options = SvgRenderOptions.Default
    .WithDocument(DocumentId.Create(Iri.Create("https://example.org/diagrams/checkout")))
    .WithMetadata(dataset, MetadataEmbedding.RdfXml, NamedGraphHandling.Reject);
var svg = Mermaid.RenderSvg(source, options);            // diagnostics: dangling refs, lossy graphs

if (DiagramMetadata.TryRead(svgBytes, out var extracted, out var error)) { ... }

The library does not look for sidecar files. The suggested naming, which a future CLI can adopt, is <diagram>.<ext>.nq, .nt or .rdf.

Embedding formats:

  • RDF/XML (default). An rdf:RDF element inside <metadata>. This is the form SVG and RDF tooling expect.
  • N-Quads or N-Triples. A <md:dataset media-type="application/n-quads"> text element. N-Quads is the choice when named graphs matter.

DiagramMetadata.TryRead detects which form is present.

Failure paths:

  • A dataset supplied without a document identity is an error.
  • Named graphs combined with RDF/XML or N-Triples are an error, unless NamedGraphHandling.DropNamedGraphs is set. The rendered result then lists the dropped graphs.
  • A statement under the document IRI that resolves to no element is a warning, and the statement is embedded anyway, so a renamed node never loses its comments.

UI-1. The player gets a JSON projection and an annotation layer

The renderer projects the dataset into a new annotations array in the player's existing motion-data JSON. The array is keyed by element reference, and each entry has a kind (comment, link or property), an author, a time, a body or value, and a target IRI with an isWeb flag. JavaScript never sees RDF.

Player.js adds the following:

  • A focusable marker button on each annotated element's bounding box.
  • A side panel, which becomes a bottom sheet at narrow widths.
  • Highlighting of the target element when an annotation is focused.
  • Esc closes the panel.

Text is set with textContent only. Only http: and https: targets become <a rel="noopener noreferrer"> links. The styling comes from the theme variables and the redesigned controls the main diagrams branch is adding. Print hides markers, as it hides the other controls.

Static SVG adds no visual change for metadata, which keeps it byte-stable and printable. It carries the data only.

PKG-1. Diagrams reference the knowledge packages directly

  • Morphir.Diagrams references Morphir.Knowledge and Morphir.Knowledge.Rdf.
  • Morphir.Svg gains no dependencies.
  • The public F# API follows the fsharp-csharp-interop skill: TryCreate and TryRead overloads with out parameters, nullness annotations, Match on public unions, and ImmutableArray collections.
  • The fsharp-csharp-interop-reviewer agent reviews each group's diff.

Alternative considered: a Morphir.Diagrams.Knowledge bridge package. Deferred, because both dependencies are small and AOT-clean, and a bridge would split the public types across two packages for little benefit. It remains possible if measured size says otherwise.

Risks and trade-offs

RiskMitigation
Renaming a node, or reordering notes and frames, orphans the annotations on them.Statements are never dropped. The render warns with the orphaned IRI. Authored edge ids (edge=@id) and re-anchoring tools can come later.
A full RDF/XML reader is large, and the grammar has subtle cases.Implement it in its own task group against the pinned W3C suite, before any diagram work depends on reading RDF/XML. The writer and N-Triples are not blocked by it.
RDFC-1.0 is exponential on adversarial blank-node graphs.A caller-set work limit stops it with a typed failure. The renderer uses a conservative default.
XML input can be hostile: entity expansion, external entities, huge documents.DTDs are prohibited and there is no resolver in every reader. Character limits apply. Tests cover these cases explicitly.
Comment bodies could carry script into the player.Bodies are set with textContent only, links are limited to an http/https allowlist, and the JSON encoder already escapes script terminators.
Adding data-ref changes every SVG's bytes.The diagrams packages are unreleased. Golden outputs are updated once in the first group.
The player panel conflicts with the player redesign in progress.The player group (UI-1) starts only after the redesign has landed.

Migration plan

This change is additive and unreleased, so there is no data migration. The N-Quads API is unchanged. Rollback is a revert of the change's commits. The task groups are ordered so that each one can land independently.

Open questions

  • The final IRI for the Morphir diagram vocabulary (md:). The proposal is https://morphir.finos.org/ns/diagram#. This needs agreement from the project owners and a dereferenceable page later. It changes no requirement or task.
  • Whether a future CLI should find sidecars by the suggested naming convention or require an explicit flag.
