Context

See proposal.md for motivation. Classic loading normalizes three manifest fields and may warn about ignored legacy dependency/decorations shapes. That compatibility reader alone cannot prove a conversion is lossless. Shared discovery, scoped editing, and write preconditions are available from prior campaigns.

Goals and non-goals

Migrate one project with a complete source-field ledger and verify the TOML independently of its classic source. Keep classic files, project source code, IR versions, workspace membership changes, and batch coordination outside the operation.

Decisions

MIG-1. Use a project-owned shared planner

Add a pure project migration planner and an IO apply coordinator reusing the edit boundary. project migrate accepts one directory or morphir.json, with current unambiguous project fallback. Reject morphir-ir.json and sibling batches. Support dry-run, JSON, and a supported same-project TOML output layout. Keep config focused on settings operations; no config migrate alias is needed for an unshipped interface. Alternative considered: Placing migration under config was rejected because adopting a project system is broader than editing one setting.

MAP-1. Account for every original field

Keep the original parsed manifest alongside normalization results. Record mapped, equivalently retained, or blocking status for each setting. Map name/sourceDirectory/exposedModules and materialize the Elm/checkpoint defaults that arose from recognizing a classic manifest. Preserve supported extras and path anchors. Nonempty unsupported dependency/decorations shapes block application; warning-and-ignore reader behavior cannot authorize dropping them. Alternative considered: Converting only the normalized effective document was rejected because ignored fields would disappear.

EQ-1. Verify a candidate without the legacy file

Construct before and candidate snapshots using declared base workspace context. Remove the classic source from the candidate and exclude ambient machine, personal, environment, CLI, and activated-profile overlays from both comparisons. Compare typed project values and resolved path meaning; report provenance changes separately. This prevents a global or profile override from hiding a conversion error and prevents the preserved classic source from supplying forgotten values. Alternative considered: Comparing ordinary ambient effective configuration was rejected because personal/runtime values can mask errors.

CNFL-1. Merge only equivalent or missing target entries

Use the token-preserving editor to add missing values to an existing target, retain equal values, and block conflicting values with source/target origins. Reject alternate-primary ambiguity and output layouts that change project-relative paths. Identical repeat plans have no writes. Never add an automatic overwrite or drop-unsupported option. Alternative considered: Automatically overwriting target conflicts was rejected because it would discard deliberate existing settings.

APPLY-1. Reuse preconditioned application and keep the source

The plan fingerprints classic source, target, and relevant workspace evidence. Apply rechecks the full set and uses the editor's staged atomic target replacement and explicit recovery outcome. The source remains byte-identical. Legacy consumers can continue using it until a separate deliberate source-removal decision; success does not imply those consumers have switched. Alternative considered: Deleting the classic manifest during migration was rejected because older consumers may still require it.

Migration plan

Ship project migrate only after discovery and editing have landed. Begin with standalone/member dry-run fixtures, then apply/no-op/conflict cases using unchanged classic sources. Document before/after files and manual blockers. Rollback leaves source manifests usable and preserves any TOML the user has subsequently edited; it does not delete generated configuration automatically.
