Context

See proposal.md for the motivation. These facts shape the approach:

  • The F# compiler (fsc) and FSharp.Compiler.Service (FCS) have no analyzer or plugin hook. Roslyn analyzers do not run on F#.
  • FSharp.Analyzers.SDK 0.41.0 (net10.0) is the community analyzer framework. It depends on FSharp.Compiler.Service exactly [43.12.402] and FSharp.Core exactly [10.1.402]. Its command-line tool is the fsharp-analyzers dotnet tool 0.41.0, which can write SARIF. FsAutoComplete loads analyzers in editors when FSharp.enableAnalyzers is on and FSharp.analyzersPath names their folder. FsAutoComplete is the language server of Ionide for VS Code and of other LSP editors.
  • We assume that Visual Studio and Rider do not load FSharp.Analyzers.SDK analyzers. This is not yet verified (see Open questions). The MSBuild target (BLD-2) covers these IDEs in either case.
  • The repository pins FSharp.Compiler.Service 43.12.403 and FSharp.Core 10.1.403 (add-fsharp-compile FSF-5), with central transitive pinning. NU1608 is not suppressed.
  • The admission catalog (add-fsharp-compile FSF-3, task 3.3) is in src/Morphir.Frontend.FSharp/Admission.fs. Its detectors read only FCS syntax, syntax trivia and checked symbol uses. Today it also uses Morphir.Compilation (DiagnosticCode, Diagnostic) and the frontend's CheckedDocument and CompilerEdge.

Goals and non-goals

Goals: one rule catalog with three hosts; the same code, message and range in every host; no FCS version conflict in any one restore graph; no change to MEP.

Non-goals: new refusal rules; quick fixes; a language server; refusal through [<CompilerMessage>] attributes; support for analyzer hosts other than FsAutoComplete and the fsharp-analyzers tool.

Decisions

CAT-1. The catalog is shared source with string codes

Split the admission code in src/Morphir.Frontend.FSharp into these parts:

  • TextLines.fs (already shared-safe): line index and UTF-16 offsets.
  • AdmissionCatalog.fs: an input shape AdmissionDocument = { Uri; Path; Text; Lines; Syntax }, the symbol lookup function, the rule records, the detectors, the findings and the nested-refusal reduction. Codes are plain strings, such as "fsharp.unsupported_mutable". The file opens only FCS namespaces and FSharp.Core.
  • Admission.fs (frontend only): converts findings to Morphir.Compilation diagnostics with DiagnosticCode.Create, and orders them.

The analyzer project includes TextLines.fs and AdmissionCatalog.fs as linked Compile items. A test in each test project compiles every catalog example and checks the code and the flagged text.

Alternatives considered: a project reference from the analyzer to Morphir.Frontend.FSharp puts two exact FCS and Core pins in one graph (NU1608, or a downgrade error). A separate catalog assembly has the same problem, because it must reference one FCS. A source generator for each host adds a build step for a few hundred lines.

ANZ-1. The analyzer builds against the SDK's compiler pin

src/Morphir.FSharp.Analyzers references FSharp.Analyzers.SDK 0.41.0 and sets VersionOverride for FSharp.Compiler.Service 43.12.402 and FSharp.Core 10.1.402. No other project references it. The analyzer host (FsAutoComplete or the fsharp-analyzers tool) supplies FCS at run time, so the package does not ship FCS. The package puts the analyzer assembly in analyzers/dotnet/fs/, the folder that the SDK documents for analyzer packages. One function has both [<CliAnalyzer>] and [<EditorAnalyzer>]. It builds an AdmissionDocument from the context's parse tree, source text and symbol uses.

A CI job builds the analyzer and the frontend in the same run. A compile error in either one shows FCS API drift in the shared source. Renovate puts FSharp.Analyzers.SDK and FSharp.Analyzers.SDK.Testing in one group, separate from the fsharp-compiler group, because each follows a different FCS version.

Alternatives considered: move the whole repository to the SDK's FCS pin. That couples the frontend to the analyzer release cadence, and the SDK is often one patch behind the compiler. Fork the SDK: too much upkeep.

ANZ-2. A Morphir project is found by its morphir.toml

FsAutoComplete loads the analyzer for every F# document in the workspace. The analyzer reports only when the document's directory or an ancestor directory holds morphir.toml. It does not read the file. The search stops at the file-system root, and its result is cached for each directory. This is the same file that morphir compile project discovery uses.

Alternatives considered: an MSBuild property (an analyzer cannot read MSBuild properties); a define constant (it changes compilation, and #if is refused anyway); report for all F# code (noise in ordinary projects).

ANZ-3. The analyzer checks only documents that type-check

When the check results of a document hold an F# error, the analyzer reports nothing for it. This matches the frontend, where compiler errors stop the run before admission. The editor already shows the compiler error. Some detectors (active-pattern use, unit-of-measure types) need checked symbols, which are not complete when the document has an error.

BLD-1. Check-only is a host option of compile

morphir compile --check runs source selection, the frontend and every diagnostic stage. Then it stops before IR writing, output installation, task records and generation. The frontend request is unchanged: in process it is the same CompileRequest, and for a MEP frontend it is a standard compileModel call. The host discards the returned model. The JSON report has output set to null and a check: true member that consumers can ignore.

Alternatives considered: a new top-level morphir check verb. It can clash with a future ecosystem command, and it repeats every compile setting. A typesOnly or dryRun MEP option: MEP 0.2.0-draft.1 has no such member, and this change must not add one.

BLD-2. MSBuild reads canonical lines from stderr

--diagnostic-format msbuild changes only the human-mode diagnostic lines on stderr. Each line has the form <uri>(<line>,<column>,<endLine>,<endColumn>): error <code>: <message>, with one-based lines and columns (the zero-based UTF-16 values plus one). The MSBuild Exec task recognizes canonical error and warning lines in its output by default and logs them as MSBuild errors and warnings. So no custom MSBuild task assembly is needed. Stdout stays empty in human mode, and --json output does not change (AGENTS.md: stdout is data, stderr is diagnostics).

The diagnostic URI is relative to the selected source root, and the source root can differ from the project directory (for example, an .fsproj at the repository root with project.source_directory = "src"). So the MSBuild line does not use the URI unchanged. It uses the absolute file-system path of the document: the selected source root joined with the URI. MSBuild and every IDE then open the right file from any working directory. A document that has no file-system path (an in-memory source) keeps its URI. The JSON report and the model keep the root-relative URI. Columns count UTF-16 code units, which is how Visual Studio counts characters on a line.

Alternatives considered: a custom MSBuild task that reads --json. It loads into the MSBuild process, needs its own assembly for each MSBuild version, and gives no better result. A SARIF file only: build error lists do not read SARIF.

BLD-3. The build target is opt-in and incremental

<Target Name="MorphirCheck" AfterTargets="CoreCompile"
        Condition="'$(MorphirCheck)' == 'true'"
        Inputs="@(Compile);$(MorphirConfigFile);$(MSBuildProjectFullPath)"
        Outputs="$(IntermediateOutputPath)morphir-check.stamp">
  <!-- 1. probe: dotnet tool run dotnet-morphir -- --version; failure gives build.tool_unavailable -->
  <!-- 2. write @(Compile) in order to $(IntermediateOutputPath)morphir-check.rsp -->
  <!-- 3. Exec: dotnet tool run dotnet-morphir -- compile --check
              --diagnostic-format msbuild @morphir-check.rsp -->
  <!-- 4. touch the stamp only when the check passes -->
</Target>
  • It runs after CoreCompile, so an F# error fails the build first, as in the frontend.
  • It passes the Compile items through --input in MSBuild order, written to a response file. This avoids a second project evaluation and command-line length limits. System.CommandLine reads @file response files.
  • The package name comes from MorphirPackageName, else from morphir.toml.
  • Exit code 1 means refusals, which the canonical lines already logged. Exit code 2 is an operational failure, which the target logs as one error with the command's stderr summary.

Alternatives considered: run before CoreCompile (duplicates compiler errors); pass --project-file (a nested MSBuild evaluation inside a build); a global tool (versions drift between machines; the local tool manifest pins one version).

AOT-1. Both packages are JIT-only

The analyzer runs inside FsAutoComplete or the analyzers tool. The build package has no assembly and calls the JIT dotnet-morphir tool. The AOT morphir executable does not reference either one. The existing CI check that keeps FSharp.Compiler.Service out of the morphir assembly closure stays in force. --check and --diagnostic-format are host options, so they are also available in morphir with a configured MEP frontend.

Risks and trade-offs

RiskMitigation
The FsAutoComplete in a user's editor uses a different SDK version, and does not load the analyzer.Publish one analyzer release for each SDK minor version. Document the matching Ionide and FsAutoComplete versions. Test with FSharp.Analyzers.SDK.Testing at the same version.
The shared catalog uses an FCS API that differs between 43.12.402 and 43.12.403.The CI job builds both hosts (ANZ-1). Each test project checks every catalog example.
The analyzer and the frontend report different ranges, because the SDK gives a different source text or symbol set.A parity test runs both hosts over the same example documents and compares codes and ranges (spec: Catalog parity).
The build check adds a second FCS check and a process start to every build.The check is opt-in and incremental (BLD-3).
Visual Studio or Rider does not load the analyzer.The MSBuild target gives the same errors in their error lists after a build.
F# code under a morphir.toml that is not part of the model (for example tests) gets refusals in the editor.Document that Morphir models go in their own project directory. An exclusion setting can come later without a spec change to the rules.

Migration plan

Both packages are new and opt-in. To roll back, remove the package reference, or set MorphirCheck to false, or remove the analyzer path from the editor settings. The catalog refactor (CAT-1) does not change frontend behavior. The existing frontend tests must pass unchanged before and after it.
