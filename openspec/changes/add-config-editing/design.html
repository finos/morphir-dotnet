Context

See proposal.md for motivation. The inspection campaign supplies segmented key paths, scoped queries, and CLI result formatting. CsToml's existing dictionary reader does not establish comment-preserving editing. The repository's safe-tree-publication capability writes generated output trees and may prune manifest-owned output; it is not a transaction system for user configuration.

Goals and non-goals

Provide shared plan/apply editing that targets one file, preserves presentation, and detects stale observations. This campaign establishes the write boundary reused by migrations. YAML/JSON remain readable input formats; writes are TOML.

Decisions

EDIT-1. Separate pure plans from adapter-owned writes

Add immutable edit requests, target evidence, before/after typed values, diagnostics, and preconditions to Morphir.Configuration. Shared planning combines source ownership, key grammar, input typing, validation, and candidate resolution. IO adapters render and apply the plan. CLI set/unset only parse options and present results; a non-CLI editor can preview without a write adapter. Alternative considered: Writing files directly in CLI handlers was rejected because other hosts need identical planning and validation.

TOML-1. Use token-preserving TOML updates

Implement or select a token/CST-preserving editor behind Morphir.Configuration.IO and verify it with byte-level fixtures. Patch only the named entry/table and required whitespace; never deserialize and rewrite the whole document. Reparse the rendered candidate through the canonical reader and compare intended typed changes. Preserve line endings, unrelated comments, ordering, and formatting. A scope with no TOML primary receives its corresponding TOML file; direct YAML/JSON file targets fail. Alternative considered: Whole-document deserialize/serialize editing was rejected because it would discard presentation.

TGT-1. Capture target selection and source evidence

Resolve exactly one project/workspace/personal/global/system/explicit TOML target. Capture content identities and relevant listings used for absence and ambiguity decisions. Revalidate those observations immediately before commit under the adapter's overlapping-writer coordination. Checking only the target's last-write time would miss a new alternate primary or a changed source that invalidates the preview. Alternative considered: Timestamp-only preconditions were rejected because they miss content and candidate-inventory changes.

TXN-1. Stage then atomically replace one destination

The native IO adapter validates and stages candidate bytes on the destination filesystem, checks preconditions, and uses an atomic per-file replacement primitive. Keep recovery state until the outcome is known. An ordinary validation/conflict failure writes nothing; an uncertain post-replacement failure reports recovery required. Remove owned temporary artifacts only on success or proven rollback. Do not use generated-output publication or its pruning manifests. Alternative considered: Using the generated-output publisher was rejected because user-file editing requires different ownership and recovery guarantees.

RES-1. Report the effective result after the scoped edit

Resolve the candidate and committed evidence through the same canonical service. Return target, written/unchanged state, effective value/origin, and the overriding source when applicable. Unset removes only the target entry; it can reveal lower layers. A byte-identical repeat does not rewrite the file. Dry-run reports the same plan without application. Alternative considered: Reporting only the written value was rejected because it would hide higher-precedence winners.

Risks and trade-offs

RiskMitigation
Comment-preserving patch changes an unrelated keyReparse candidate bytes, compare the intended typed diff, and assert unrelated fixture spans remain byte-identical.
Concurrent writer invalidates a previewUse source/listing/content preconditions and one coordination protocol for all configuration writers; reject stale plans.
Filesystem error leaves outcome uncertainReturn typed recovery state with retained owned journal/backups rather than claiming rollback or deleting recoverable data.

Migration plan

Add set/unset to the existing configuration scenario after inspection lands. No files are touched until an explicit edit request is applied. Validate malformed values and conflicts before writes, exercise injected staging/replacement failures, and document recovery behavior. Rollback removes command registration but must preserve any outstanding recovery data.

Campaign completion

This campaign is complete only after one reviewable PR has landed on main and the campaign-owned worktree and local/remote branches have been removed. Passing tests or opening a PR alone is not completion.

  1. Start from current main after the prerequisite campaigns have landed. Use one owned branch and worktree for this campaign, and record their identities.
  2. Complete behavior, tests, documentation, relevant formatter/AOT checks, and the repository's required checks. Update the PR description and evidence for its final head; address verified review findings.
  3. When implementation is complete, sync/archive this OpenSpec change in the campaign PR, preserve the reviewable design and specs, and validate the resulting planning state.
  4. Merge through the repository's normal review and required-check policy. No force push, admin bypass, deployment, or release is implied by this plan.
  5. Verify authoritative PR merged state, capture its landed commit SHA, and verify the change is present on main. After confirming the worktree has no unique uncommitted/unmerged work, remove that campaign's worktree and local/remote branches through the owning workspace/forge tools. Check they are absent. Do not force removal or prune unrelated artifacts.
  6. Report the PR URL, landed SHA, check/review evidence, archive/spec-sync outcome, and cleanup results. Preserve unrelated work and unresolved recovery journals; if cleanup or recovery is blocked, report it and keep the campaign unfinished.
