Implementation update, 11 November 2026

This plan merged as #567; parent #1147, #1150, #1151 and #1152 are merged. Parent group 1 is still publishing seven schemas, normative member tables, identity/package cases and the publication audit. The older inspection and worked examples below are planning evidence, not permission to invent catalog, lock or package formats before those inputs publish.

Tasks 2.2, 2.3 and 2.10 now have implementation and targeted tests. Task 2.1 has its library, tests, C# probe and manual lane, but stays unchecked pending Native AOT qualification. The library reuses ExtensionId, toolchain path/channel/platform/SemVer values, Semver 3.0.0 and the actual MEP lifecycle. It adds no handwritten version parser or second implementation list.

Multi-file packages follow merged #1151: VERIFY-B and LAUNCH-A. Full checks at install and explicit verification, structural checks at activation, launch from the shared tree and a process-tree lease are separate from the raw single-file private-copy rule. Q-ARCHIVE's one-executable target recommendation below is superseded; its outer release-assets packaging question remains open. No package is implemented by this initial tranche.

The remaining levels, overlay/configuration, commands and developer-policy choices stay with the maintainer. All later mutating commands need --dry-run. Full installer and user/technical docs remain the destination. No repository mutation, signature verification or WASM runtime is added by these pure values.

What "shared" means for today's extensions

The first version of this change said that each CLI sees the other's global installs. For today's extensions that is wrong. The two CLIs share the format of Morphir Home's files. They share use of an installed extension only when both can run it, and today almost no extension satisfies that.

Observed Every Rust command that needs extensions lists them first.finos/morphir crates/morphir/src/commands/compile/prepare.rs:248, generate.rs:207, extension.rs:153.

So one .NET global install of a guest built on Morphir.Mep into catalog/extensions.json would make every Rust compile, generate and extension list on that Morphir Home fail. The reverse gives nothing either: an extension the Rust CLI installed that speaks only 0.1 cannot run in .NET. The failure is in the catalog only. Rust reads a lock file only for an id the catalog names. It lists locks/extensions/ only to find *.json.transaction journals, whose bytes it writes to the lock path and to the one catalog path without parsing ids (state_io.rs:209-252), and it never lists the store. The first revision of this page said Rust never lists that directory, which was wrong. Index records reach a Rust reader only through a repository it is configured to read, and its resolver filters MEP versions per release (resolver.rs:49-64), so an incompatible record fails only the install of that id.

The maintainer decided on 9 November 2026 that every global install goes to that shared catalog, and that this cost is accepted: a released Rust CLI cannot list a Morphir Home that the .NET host has installed into (Q-SHARED). The Rust product CLI is to be deleted (Decision 16). Current hosts, .NET now and MoonBit later, share what is installed. A home an older CLI wrote is not read at all: the host offers to move it aside (Decisions 10 and 11). Store objects are shared as before. A user who needs the Rust CLI again gives it its own MORPHIR_HOME.

Goals and non-goals

Goals.

  • Install, update, remove and select external extensions in both .NET hosts.
  • Write Morphir Home's shared files in the upstream format, and never write anything there that breaks an upstream reader.
  • Share global installs with the Rust CLI wherever both can run the extension.
  • Give morphirup the seams the approved change names: an in-process hand-over of authenticated files, and a generation-scoped overlay.
  • Make every place where the parent contract is silent visible, and leave the decisions to the maintainer rather than to an implementer.

Non-goals at the design level. No network client. No signature checks. No new extension store layout. No change to MEP. No WASM runtime. The full list is in Deliberately left out.

What happened, in order (Figure 2):

  1. Resolve. The installer read the history, took the newest stable release that lists an MEP version this host speaks and has an artifact for windows/x86_64, and kept the SHA-256 of the exact history bytes as the index revision.
  2. Stage. It copied the executable into %USERPROFILE%\.morphir\tmp\morphir-extension-probe-…\, hashing while copying, and compared the digest.
  3. Probe. It started the staged copy with a cleared environment, called morphir.extension.describe, and compared the answer with the record's claim set over the typed projection.
  4. Store. It copied the staged bytes into store/extensions/sha256/1111…/acme-backend.exe, hashing again while copying, so a guest that rewrote its staged file during the probe is caught, and published without replacing anything.
  5. Commit. Under locks/extensions.state.lock it applied any journal left by an earlier run, wrote a journal, wrote locks/extensions/acme-backend.json and catalog/extensions.json, removed the journal, and wrote the inventory record data/morphir-dotnet/extensions/installed/acme-backend/1111….json.

5. A morphirup generation selects its own versions

This step depends on Q-OVERLAY and on the shared toolchain contract. When morphirup run -- generate … launches the host for a project toolchain generation, it sets MORPHIR_EXTENSION_OVERLAY to %USERPROFILE%\.morphir\toolchains\generations\g7f3a\. That directory's extensions\selection.json pins the providers of the generation (SEL-2). The host resolves those ids from the overlay and every other id as before. The global selection is untouched, so two projects can use two generations at once (approved UP-2, task 4.4).

Decisions

These are this change's own choices. Each names the alternatives. Where a choice depends on a maintainer answer, it names the question.

INST-1. A separate F# installation library that both hosts and morphirup reference

Put the installer in a new F# project, src/Morphir.Extensions.Installation, referencing Morphir.Extensions and Morphir.Mep but not Morphir.Tooling. Pure modules (identifiers, records, claim comparison, resolution, archive entry rules, pin files) carry most tests without I/O. Edge modules (store, state lock, journal, archive reading, probe launch) sit behind small interfaces. The C# CLI edge stays in src/Morphir.Tooling/Features/Extensions. F# code that C# calls follows the fsharp-csharp-interop skill. JSON is read and written with JsonDocument and Utf8JsonWriter, because the reader must keep unknown members and the writer must emit exact member sets; no reflection serialization, so the library stays trim- and AOT-clean.

Alternatives: inside Morphir.Tooling (rejected: morphirup must not reference it, adoption MGR-1); inside Morphir.Extensions (rejected: it would pull file system and process code into the registry domain).

INST-2. Every source becomes one resolved record before any byte is stored

A named repository, a package archive, a staged file and a morphirup hand-over each produce the same value: release record, selected artifact, selection, index provenance, and a separate source description for the .NET inventory and report. Staging, hashing, probing, storing and committing are then one code path (Figure 2). Alternative: separate pipelines per source, as the old handlers had. Rejected because checks drift.

STORE-1. Shared files carry the members and values the shared contract defines

The bar for the catalog, locks, journal, repositories file and index records is the members and values the shared contract defines. Byte equality with any other writer is not a goal. Today much of that contract is specified only by the Rust source. Where it is, this change follows that behavior until the contract pages say otherwise: finos/morphir#1149's task 1.4 makes distribution-and-acquisition.md the authority for the members, and finos/morphir#1150 (merged) proposes the rest of the shared-file rules, which the specs follow as provisional. Where Rust has a quirk the contract does not need, such as the Windows verbatim path spelling, this host does not copy it. Every document carries its family $schema and no schemaVersion (Decision 15A).

Writers write critical and requires on an entry whose release has requires.host. This host never writes an entry converted from a version 1 record, and never reads a catalog an older CLI wrote: that is old state, offered a move aside (DOC-1, Decisions 10 and 11).

Catalog and record readers keep unknown optional members and refuse unknown critical ones; lock, journal and repositories readers refuse unknown members. Documents are I-JSON with integer numbers only. .NET-only facts (true source, archive digest, level) go to the .NET inventory, never into shared files.

STORE-2. The state lock uses the contract's primitive, bound directly

merged finos/morphir#1150 defines one primitive for every lock file, and this change follows it as provisional:

  • on Unix, blocking flock with LOCK_EX on a descriptor opened with O_RDWR | O_CREAT | O_CLOEXEC, mode 0644;
  • on Windows, blocking LockFileEx with LOCKFILE_EXCLUSIVE_LOCK from offset 0 over the whole range, on a handle opened with read and write access and FILE_SHARE_READ | FILE_SHARE_WRITE | FILE_SHARE_DELETE.

A lock file is created when absent, and never written or removed. The repositories lock uses the same primitive, and a host never holds both lock files at once. .NET binds both calls through LibraryImport, which is AOT-safe. FileShare.None and FileStream.Lock are not that lock: on Unix .NET takes flock with LOCK_NB for FileShare.None, and FileStream.Lock takes a byte range that is not the whole one. That replaces this page's earlier assumption about FileStream.Lock. Poll with the TaskLock waiting line. Task 3.1 proves the primitive against a helper process that calls the same functions.

Alternative: reuse TaskLock unchanged. Rejected: on Windows its share mode makes another host's open fail, and another host's lock is invisible to it.

STORE-3. One journal, checked before it is applied

The journal is locks/extensions/<id>.json.transaction. As merged finos/morphir#1150 defines:

  • it has exactly the members $schema, nextLock and nextCatalog;
  • each of the last two is null for an absent file, or the file's exact bytes as an array of integers;
  • one journal exists at a time.

Under the state lock, a host first detects old state. Only when there is none does it recover a journal: it validates the saved lock and catalog in full as current documents, then writes the lock, then the catalog, then removes the journal. A journal at an earlier version, more than one journal, or a journal whose saved bytes are not current documents is old state, and nothing is written from it. The reference's own journal, schemaVersion 1 (state_io.rs:10-18, 249-252), is therefore old state.

The inventory record is written after the pair, under the same lock. A missing inventory record for a shared entry is rebuilt from the pair on the next read.

STORE-4. A .NET inventory of every installed version

data/morphir-dotnet/extensions/installed/<id>/<digest>.json keeps the entry and lock the installer would write globally, plus the source and, for target archives, the archive digest. It exists because shared files carry only the members the contract defines, and a lock refuses any other: it holds the .NET-only facts they cannot carry, and every installed version that level pins and overlays need.

The key is the id and the artifact digest. The same bytes installed again with other args, claims or index replace the record, and the report warns. A pin binds a digest, not the metadata around it. For a shared entry the catalog and lock always win over the record. A record rebuilt from a Rust-written pair says source kind shared-catalog, because the true source cannot be known.

Alternative: several entries per id in the shared catalog. Rejected: upstream readers refuse duplicate ids (state.rs:557-563, as StateMismatch).

SEL-1. Portable pins at levels, resolved against the local inventory

Provisional: it follows Q-LEVELS and serves a contract that belongs in the toolchain specifications, raised upstream in task 1.2.

A level's .morphir/extensions/selection.json pins the id, version, runtime and a digest per platform, and nothing machine-specific. Precedence is overlay, project, workspace, shared catalog, system (Figure 3). A broken pin never falls through to a lower layer. Isolation omits the system pin and the shared catalog. Pin writes take a lock below locks/ in Morphir Home, keyed by the canonical pin path.

SEL-2. The overlay arrives by an environment variable that morphirup sets

Provisional: it follows Q-OVERLAY and belongs in the toolchain contract, raised upstream. MORPHIR_EXTENSION_OVERLAY names an absolute directory below toolchains/generations/ in Morphir Home. It is an environment variable, not a command-line option, because morphirup run must pass the user's arguments unchanged (approved project-toolchains, "Explicit command dispatch"). The host never writes there. This is the seam approved task 4.4 needs; 4.4 itself writes the generation directories.

SEL-3. Activation verifies offline and runs a private copy written from the verified read

Before a guest starts, the host:

  1. loads the selected record, and its lock for a shared entry, under the state lock, and checks that they agree;
  2. canonicalizes the store path inside Morphir Home, and checks the Unix mode and the MEP version;
  3. reads the store object once, hashing it as it writes tmp/extensions/morphir-dotnet-run-<random>/<filename>, or from verified in-memory bytes as the reference does;
  4. launches the copy only if the digest matched.

There is no second read between the check and the launch. The guest gets a cleared environment holding the probe's variables plus those the command documents, and an explicit working directory: the project directory for project commands, otherwise the copy's directory (parent rule, distribution-and-acquisition.md:461).

.NET copies have their own prefix. The host removes them after the process exits, and sweeps its own stale copies, never morphir-extension-*. A private copy also keeps store objects free of Windows file locks, so uninstall and update work while a guest runs.

Alternative: launch the store object in place. Rejected for all of these reasons.

PROBE-1. The probe is a bounded describe on the staged copy

Use the Morphir.Mep host peer's DescribeAsync on the staged copy, with:

  • a fresh private working directory;
  • a cleared environment holding only PATH, SYSTEMROOT on Windows, and TMP/TEMP/TMPDIR naming a private directory;
  • the framing limits of the MEP core;
  • a 30 second request deadline, after which the whole tree is ended with Process.Kill(entireProcessTree: true).

The reference clears the environment and passes no variable by default (morphir-host-native/src/process/child.rs:51-52, launch.rs:61), and its default request timeout is 30 seconds (launch.rs:10). The short list of variables is a recorded difference, because .NET guests and single-file extraction need a system root and a temporary directory.

The probe falls back to a session on -32601 and -32014 only. The reference also falls back on lifecycle refusals that it recognizes by message, with code -32600 or in -32000..-32099 (morphir-host/src/probe.rs:273-295). Those come from guests released before MEP assigned -32014, which predate 0.2.0-draft.1, so under MEP-1 this host does not carry that code. This is a recorded difference from the reference.

Claim sets are compared over the typed claim set projection, as check_claims does (agreement.rs:31-60): unknown top-level members drop out, an absent critical equals an empty one, and numbers compare with serde_json equality (Q-NUMBERS). claimCheck records this install's action only (Q-CLAIMCHECK). WASM is never probed, as upstream decided on 21 October 2026.

ARC-1. Archives are read with the base class library, with recorded limits

Archives are read with System.IO.Compression.ZipArchive, and with System.Formats.Tar.TarReader over GZipStream. The entry list is checked before anything is extracted. Extraction writes only into private staging, and only the descriptor, checksums and the selected artifact are extracted.

Entry names:

  • must be ASCII, because every expected name is ASCII;
  • are compared ignoring ASCII case, which is simpler than, and stronger than, the NFC and ordinal-ignore-case rule of the first version;
  • must not be Windows device names such as CON.exe;
  • in a zip, must have a local header name equal to the central directory name (the pinned submodule commit is itself a fix for an advisory about zip header names).

The limits:

  • archive file 1 GiB, 1024 entries, 256 MiB per entry (the store's limit), and 1 GiB extracted in total;
  • PAX and GNU extension headers 1 MiB, as the Rust tool archive reader (tool_archive.rs:15);
  • a ratio of 200 for entries over 1 MiB, measured on a gzip stream as tar bytes over compressed bytes read so far.

Limits apply at each nesting level, and inner bytes count toward the outer totals. Only the 256 MiB limit has a parent source. The others are this change's choice, lower than the Rust tool archive prior art (10 000 entries, 4 GiB), because extension packages hold a handful of files.

Assumed Both readers publish with no trim or AOT warnings. Task 5.1 confirms it.

ARC-2. The automatic staged pass is narrow

The pass runs before commands that resolve extensions, only in auto mode, and installs only WASM packages. Process packages never install automatically, because installing one runs its describe, which is running code from whatever was cloned. Until this host has a WASM runtime, those entries are listed as unavailable. The pass writes nothing on stdout, turns failures into stderr warnings, and skips a file whose digest is already selected at its level.

CMD-1. Upstream verbs, the PRD's additions, and one report shape

Following Q-COMMANDS, the verbs are:

  • install (--repository <name> <id>, or <file>, or --staged; --channel|--version, --no-probe, --level);
  • update, with the same source forms and --repository required for a repository, as in the parent README;
  • uninstall, with the alias remove;
  • list, info, use, which, and repository add|list|remove.

Only list keeps --platform, as a filter over recorded artifacts. Installs are for the running platform only, so --platform on any other verb is a usage error.

Results go to stdout, one JSON document with --json; everything else goes to stderr. Exit codes are 0, 1 for a refusal and 2 for usage. Codes start with extension. (Q-DIAG).

An entry installed from a generated repository cannot be updated by the Rust CLI, which needs a configured repository. The .NET host updates it from the same kind of source it was installed from.

CMD-2. Retire the download handlers for extensions, and supersede #492

The extension handlers, their command records and the extension use of ArtifactPathResolver and OsPaths are removed when the new commands land. dist and tool keep their stubs. Recommendation: close #492 as superseded, because wiring it would publish unchecked downloads into a folder no other Morphir CLI reads.

TRUST-1. Authentication is a caller's fact; the installer checks integrity and claims

The installer never verifies a signature or a repository identity. For CLI sources, its own report says authentication kind local-developer with policy developer.

That label lives only in the installer's reports and the .NET inventory. At finos/morphir#1147 (60d363059), local-developer is no longer a receipt authentication value, and a receipt that uses it is refused (installation-receipt.md:43). The page also says why: a lock names only artifacts an authenticated recipe binds by digest. So bytes equal to a locked digest are recipe-digest, whoever built them, and an unsigned developer artifact is never part of a generation. It is "installed outside generations, under the extension installer's explicit developer policy" (installation-receipt.md:51), which is exactly this installer's CLI path. That settles the receipt question this change raised earlier (review M7); it is no longer an upstream ask.

For a morphirup hand-over, the installer takes the caller's statement and returns it unchanged. The statement is repository-target with repositoryId and targetsVersion, or recipe-digest. Any other kind, including local-developer, is refused, because a hand-over is always a generation install. The one-repository-per-binding check and repository_mismatch stay with the manager.

Two more manager rules touch the installer:

  • The plan covers everything. A plan must cover everything its command writes, so before writing, the installer answers "what would this install write": the store path, the catalog and lock or the pin, the inventory record, and whether the guest runs with the user's rights. It then writes nothing else. This is provisional pending the toolchain contract.
  • Revocation is the manager's job. A learned revocation of a recipe target is the manager's check before run launches a generation, and the installer does not learn revocations. Bytes the user installed globally outside a generation are not revoked by a recipe revocation, even when their digest is the same. The installer's docs say so.

This is where the installer touches the TUF client: the client authenticates the targets and hands over bytes and a statement, and the installer rechecks the bound digests. The shared lock has no member for authentication, so this fact lives only in the manager's receipt and the .NET inventory.

MEP-1. MEP 0.1 is not supported; the MEP 0.2 line is (maintainer decision)

Decision. On 9 November 2026 the maintainer decided three things, in this order:

  1. To cut support for MEP 0.1: "we don't have users to support the cost of maintaining 2 versions".
  2. The scope of that cut: "we can still have the global, we just have decided to cut support for MEP 0.1". "The global" meant that global installs still exist, in the shared catalog (Q-SHARED).
  3. What is supported instead: "We should support 0.2.0 all prerelease and final 0.2.x releases".

So MEP 0.1 is not supported, and the supported protocol is the whole 0.2 line: every prerelease of 0.2.0 and every final 0.2.x release. Today the only version of that line that exists is 0.2.0-draft.1. Nothing a host can speak changes yet. What changes is the policy: as later versions of the line appear, a host keeps the earlier ones instead of replacing one exact draft with the next.

Observed Upstream calls 0.1 "the frozen legacy protocol" (finos/morphir docs/design/draft/extensions/protocol.md:878 on main at 04143a238) and does not yet say it is deprecated. Recording the decision there is an upstream ask (task 1.2).

What the decision means in this change:

  • The supported line. The supported MEP versions are those the comparators >=0.2.0-0 and <0.3.0 match, under the prerelease rule of npm's node-semver, of Rust's semver crate used by the reference, and of the Semver NuGet package's SemVersionRange. That rule is: a prerelease version matches only when some comparator names the same major, minor and patch with a prerelease. Because 0.2.0-0 is the lowest prerelease of 0.2.0, the pair matches exactly what the maintainer said, every prerelease of 0.2.0 and every final 0.2.x, and nothing else:
    • in the line: 0.2.0-draft.1, 0.2.0-rc.1, 0.2.0 and 0.2.7;
    • outside it: 0.1, 0.1.0, 0.2.1-rc.1, 0.3.0-draft.1 and 0.3.0.
  • Supported is not the same as implemented. The host implements a set of exact versions inside the line: today {0.2.0-draft.1}. It never drops a version of the line it has implemented. A session still agrees on one exact version, and an entry is runnable only when its mepVersions holds a version the host implements. An entry that names only a version of the line the host does not implement yet, such as 0.2.0-draft.2, is listed as unavailable because that version is not implemented yet. That is different from 0.1 or 0.3.0, which are not supported at all. Both refusals use extension.no_compatible_mep_version, and the reason tells them apart.
  • An explicit exception. The general contract rule in finos/morphir's protocol.md ("Version numbers") and in this repository is that a prerelease matches only exactly, because drafts are refined in place and promise no compatibility with each other. That rule still decides what each session uses. MEP's 0.2 line has this explicit maintainer exception for what a host supports and keeps. The exception does not make two drafts compatible with each other.
  • Not DOC-1. DOC-1 drops the earlier transient drafts of the extension document formats, while MEP keeps every version of its 0.2 line: they are separate decisions about separate contracts.
  • Nothing implements 0.1. Nothing here implements, bridges or tests 0.1.
  • No legacy code paths. The probe does not carry the reference's fallback for refusals that older guests signal only by message (PROBE-1). An extension that speaks only 0.1 is refused at install with extension.no_compatible_mep_version, and is listed as unavailable when the Rust CLI installed it. Both messages say that MEP 0.1 is not supported.
  • The Rust product CLI is to be deleted (Decision 16). No Rust host work is planned or needed by this change.

A shared entry this host cannot run, for example one the Rust CLI installed, is listed as unavailable instead of failing the listing. That is robustness, not protocol support. DOC-1 applies the same "no transient compatibility" reasoning to old document formats.

DOC-1. Only the current contract drafts are read (maintainer decision)

Decision. On 9 November 2026 the maintainer decided to stop reading the older document formats, because "we are paying too much of a cost to support transient pre 1.0 contracts".

Decision 15A then put the extension documents on one family version. What this host reads and writes:

  • every document of the extension state family (descriptor, index record, catalog, lock, journal, repositories configuration, standalone claim set) with its required $schema at 0.1.0-preview.1, compared as exact text, and no schemaVersion;
  • embedded claim sets with no version of their own; a claim set that describe returns carries the claims $schema in place of claimsVersion.

The URLs are those merged finos/morphir#1150 defines, and the specs mark them provisional.

What it no longer reads, and never converts: everything else. That is version 1 records and descriptors, every schemaVersion draft (2.0.0-draft.1, .2 and .3, lock "1.0" and 2.0.0-draft.1), and claim sets with claimsVersion. This history is kept here because those documents still exist in published releases and older homes.

Where old documents still appear, and what happens:

  • A history with old lines. It is read whole, and refused when any line is not current, naming the first such line (#1150). This replaces the earlier rule of this page, which used old lines only for the history checks.
  • A descriptor in an old format is refused with extension.unsupported_contract_version.
  • A catalog, lock, journal or repositories configuration in an old format is old state: never read, offered a move aside (Decisions 10 and 11). This replaces the earlier rule of this page, which carried converted entries through.
  • Published releases at earlier drafts stay uninstallable until they are republished at the family version, which morphir-dotnet's bundle authoring is to do (Decision 13).

The cost removed: no draft conversion, no mixed-draft detection, no version switch, no per-line history rule, and no converted-entry writer.

ID-1. The id rule is finos/morphir#1149's, and every id shares one catalog

The registry keeps its dotted rule for built-ins. The installer checks every id with the rule of finos/morphir#1149 (merged): one or more lowercase portable tokens joined by ., at most 238 characters, with a first segment that is not a Windows device name. A document at an earlier version is refused by version before its id is read (DOC-1), so there is no version-dependent id rule any more.

Every id, dotted or not, lives in the one catalog/extensions.json, locks/extensions/ and repository extensions/; there are no separate dotted files or directories. Every id starting with morphir. is reserved for built-in frontends and backends and refused at install, which grants nothing to any id (maintainer decision, 9 November 2026; #1150 allows a host such a prefix). org.finos.morphir.* is not reserved.

Task 8.1 runs #1149's shared id cases through the kit runner once its task 1.2 publishes them.

Q-LEVELS. What a level file is (PRD superset; belongs in the toolchain contract)

Options.

  • (a) Level directories hold copies of catalog entries and locks, including absolute index paths. They are then machine-local and must not be committed.
  • (b) Portable pins (id, version, runtime, a digest per platform), resolved against a local inventory. This is recommended (SEL-1).
  • (c) Drop level files, and let the project toolchain lock pin providers. That leaves analyzers, which recipes do not cover, without a project selection.

Option (b) also answers the PRD's open point about a project lock that refers to a staged file: both are committed, and a second machine installs the staged file and satisfies the pin.

Generation directories and receipts belong to docs/spec/toolchain, so the pin format is raised there instead of becoming a .NET-only parallel design.

Blocks: 6.1 to 6.3, the non-global --level values, and the project, workspace and system staged folders in 5.5. Task 3.4's inventory is needed in any case, for archive digests and true sources.

Q-OVERLAY. How the generation overlay reaches the host (approved UP-2 is silent; belongs in the toolchain contract)

Options.

  • (a) MORPHIR_EXTENSION_OVERLAY, set by the proxy. This is recommended (SEL-2).
  • (b) A command-line option, which breaks argument pass-through.
  • (c) The host finds the project's generation pointer itself, which ties the host to manager state.

On precedence, the recommendation is to put the overlay above the project pins, because the generation was resolved from the project's own request.

Blocks: 6.4, and through it approved task 4.4. The task also waits on the toolchain contract.

Q-PROVENANCE. Index provenance for sources that are not a named repository (PRD conflict)

The PRD says a staged install writes provenance kind staged. Upstream IndexKind has only local-directory (local.rs:12-17), and an unknown kind would fail the whole catalog.

Options.

  • (a) For a global install, generate a one-release local repository below data/morphir-dotnet/extensions/repositories/, never added to the repositories file, and install from it. Its history omits platform for WASM artifacts. This is recommended.
  • (b) Keep file and staged installs out of the shared catalog, and allow them only at project, workspace and system levels.
  • (c) Wait for upstream to add a kind.

The consequence of (a): nothing in shared state ties back to the publisher's descriptor or archive, only the .NET inventory does, and the Rust CLI cannot update the entry.

Blocks: 5.4.

Q-ARCHIVE. Package and target archives (silent upstream; includes the former Q-DESCNAME)

Option A, not taken: single-file self-contained publish with extraction

What would have to change:

  1. Publish with PublishSingleFile and IncludeAllContentForSelfExtract, so that every assembly is extracted to disk at start. Assumed With full extraction, Assembly.Location names the extracted file, so CompilerEdge gets real paths. A qualification test confirms this before anything depends on it.
  2. Check that CompilerEdge.selectReferences finds the deps files and assemblies in the extraction directory, so NoFileLocation does not fire, and test that application assemblies such as Morphir.* never become references of the user's code. Assumed With full extraction, the deps files are on disk; the qualification test confirms it.
  3. Give extraction a directory under the probe's restricted environment. Extraction needs DOTNET_BUNDLE_EXTRACT_BASE_DIR, or the temporary and home variables the runtime derives a default from. The probe now passes only TMP/TEMP/TMPDIR naming a private directory (PROBE-1).

    • or the host sets DOTNET_BUNDLE_EXTRACT_BASE_DIR to a .NET-owned directory keyed by the store digest, for example tmp/morphir-dotnet/bundles/<digest>/, and reuses it.
    The second is faster, but the extracted files are not rehashed at activation. They have the trust of user-owned Morphir Home, the same as the store, and that is recorded rather than hidden.

An uncompressed bundle is about the size of the folder, roughly 115 MiB, so it fits with about 140 MiB to spare. A compressed bundle is smaller but starts more slowly. The probe's 30 second deadline must also cover the first extraction. Both are measured in the qualification task.
  5. Ship the bundle raw, or as a one-file target archive (Q-ARCHIVE (a)).
  6. Settle the id, which #1149 has since done.

Cost: one build change and one qualification task in the adoption change (a single-file publish profile beside #569's folder profile, qualified in its own task). No contract change, no Rust change and no store change. The integrity gap of reused extraction is documented.
