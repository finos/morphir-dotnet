What "shared" means for today's extensions

The first version of this change said that each CLI sees the other's global installs. For today's extensions that is wrong. The two CLIs share the format of Morphir Home's files. They share use of an installed extension only when both can run it, and today almost no extension satisfies that.

StepEvidence
Observed The Rust host supports only MEP 0.1.morphir-extension-sdk/src/protocol.rs:14,17: MEP_VERSION = "0.1", SUPPORTED_MEP_VERSIONS = &[MEP_VERSION]. The SDK has the 0.2.0-draft.1 model draft (model/negotiation.rs:8), but the installed-state checks use only the supported list.
Observed The .NET host speaks only 0.2.0-draft.1.src/Morphir.Mep/Peers.fs:222; the PRD says not to implement 0.1.
Observed Listing validates every catalog entry and stops at the first error.morphir-distribution/src/state.rs:722-737 maps each entry through validate_installed_pair and collects into a Result.
Observed An entry without a supported MEP version is an error.state.rs:782-791 returns NoCompatibleMepVersion.
Observed Every Rust command that needs extensions lists them first.finos/morphir crates/morphir/src/commands/compile/prepare.rs:248, generate.rs:207, extension.rs:153.

So one .NET global install of a guest built on Morphir.Mep into catalog/extensions.json would make every Rust compile, generate and extension list on that Morphir Home fail. The reverse gives nothing either: an extension the Rust CLI installed that speaks only 0.1 cannot run in .NET. The failure is in the catalog only. Rust reads a lock only for an id the catalog names, and never enumerates locks/extensions/ or the store (no read_dir over either in morphir-distribution). Index records reach a Rust reader only through a repository it is configured to read, and its resolver filters MEP versions per release (resolver.rs:49-64), so an incompatible record fails only the install of that id.

This change therefore admits to the shared catalog only entries that the pinned reference reader can read and run, and puts every other global install in a .NET global layer beside it (SHARE-1, Q-SHARED). Store objects stay shared, because they are content-addressed and nothing enumerates them. Today an extension enters the shared catalog only if it also speaks 0.1. For the extensions this repository builds, "shared" means a shared store and a shared format, not shared use.

Goals and non-goals

Goals.

  • Install, update, remove and select external extensions in both .NET hosts.
  • Write Morphir Home's shared files in the upstream format, and never write anything there that breaks an upstream reader.
  • Share global installs with the Rust CLI wherever both can run the extension.
  • Give morphirup the seams the approved change names: an in-process hand-over of authenticated files, and a generation-scoped overlay.
  • Make every place where the parent contract is silent visible, and leave the decisions to the maintainer rather than to an implementer.

Non-goals at the design level. No network client. No signature checks. No new extension store layout. No change to MEP. No WASM runtime. The full list is in Deliberately left out.

What happened, in order (Figure 2):

  1. Resolve. The installer read the history, took the newest stable release that lists an MEP version this host speaks and has an artifact for windows/x86_64, and kept the SHA-256 of the exact history bytes as the index revision.
  2. Stage. It copied the executable into %USERPROFILE%\.morphir\tmp\morphir-extension-probe-…\, hashing while copying, and compared the digest.
  3. Probe. It started the staged copy with a cleared environment, called morphir.extension.describe, and compared the answer with the record's claim set over the typed projection.
  4. Store. It copied the staged bytes into store/extensions/sha256/1111…/acme-backend.exe, hashing again while copying, so a guest that rewrote its staged file during the probe is caught, and published without replacing anything.
  5. Admit. The admission rule found no MEP version that the reference reader supports, so the entry may not enter catalog/extensions.json.
  6. Commit. Under locks/extensions.state.lock it applied any journal left by an earlier run, then wrote the inventory record data/morphir-dotnet/extensions/installed/acme-backend/1111….json and the .NET global layer data/morphir-dotnet/extensions/global.json. Nothing below catalog/ or locks/extensions/ changed.

Decisions

These are this change's own choices. Each names the alternatives. Where a choice depends on a maintainer answer, it names the question.

INST-1. A separate F# installation library that both hosts and morphirup reference

Put the installer in a new F# project, src/Morphir.Extensions.Installation, referencing Morphir.Extensions and Morphir.Mep but not Morphir.Tooling. Pure modules (identifiers, records, claim comparison, resolution, admission, archive entry rules, pin files) carry most tests without I/O. Edge modules (store, state lock, journal, archive reading, probe launch) sit behind small interfaces. The C# CLI edge stays in src/Morphir.Tooling/Features/Extensions. F# code that C# calls follows the fsharp-csharp-interop skill. JSON is read and written with JsonDocument and Utf8JsonWriter, because the reader must keep unknown members and the writer must emit exact member sets; no reflection serialization, so the library stays trim- and AOT-clean.

Alternatives: inside Morphir.Tooling (rejected: morphirup must not reference it, adoption MGR-1); inside Morphir.Extensions (rejected: it would pull file system and process code into the registry domain).

INST-2. Every source becomes one resolved record before any byte is stored

A named repository, a package archive, a staged file and a morphirup hand-over each produce the same value: release record, selected artifact, selection, index provenance, and a separate source description for the .NET inventory and report. Staging, hashing, probing, storing, admission and committing are then one code path (Figure 2). Alternative: separate pipelines per source, as the old handlers had. Rejected because checks drift.

SHARE-1. The shared catalog admits only what every supported reader can run

Following the recommendation of Q-SHARED, provisional until it is answered. A global install writes a shared catalog entry and lock only when three conditions hold:

  • the entry's mepVersions holds a version the pinned reference reader supports;
  • its id is valid at the catalog version that reader reads;
  • writing it leaves the catalog at a version that reader reads.

The supported set is one constant recorded with its source (["0.1"] at c9f79da) and moves only with the submodule pin.

Every other global install goes to the .NET global layer: an inventory record, plus an entry in data/morphir-dotnet/extensions/global.json that maps the id to that record's digest. That layer ranks above the shared catalog for .NET hosts. One id is never globally selected in both places: a global install refuses an id that the other place holds.

Store objects are shared by both. The reverse direction is also defined: a shared entry this host cannot run is listed as unavailable with a reason, and never stops the listing.

Alternatives: write every install to the shared catalog (rejected: it breaks every Rust command on that Morphir Home); keep every .NET install out of the shared catalog (rejected: it gives up shared use for extensions that speak both versions, and makes the shared catalog pointless for .NET).

STORE-1. Shared files are written with the upstream member sets and read with must-ignore

Writers emit exactly the members the Rust implementation writes, in its spelling, pretty-printed with a final newline. That includes critical and requires on an entry whose release has requires.host. It also includes no claims, claimCheck or probeSource on an entry whose claims were only converted from a version 1 record (extension_format/claims.rs:82-87, 243-251). Writing converted claims would also flip the catalog to "2.0.0-draft.2".

Readers keep unknown optional members and refuse unknown critical ones. .NET-only facts (true source kind, archive digest, level, layer) go to the .NET inventory, never into shared files. Byte-for-byte equality with Rust output is not required; member-set and value equality is. Tasks 2.7, 3.5 and 9.1 check it against the pinned Rust CLI.

STORE-2. The state lock uses the reference primitive

Open locks/extensions.state.lock for read and write, create without truncate, and take an exclusive lock that fs2 respects:

  • on Linux and macOS, flock, which is what .NET takes for FileShare.None;
  • on Windows, a byte-range lock over the whole file: FileStream.Lock on a handle opened with FileShare.ReadWrite | FileShare.Delete, which overlaps LockFileEx over 0..2^64-1.

Poll with the TaskLock waiting line. The repositories lock uses the same primitive.

Assumed FileStream.Lock(0, long.MaxValue) conflicts with an fs2 lock on Windows. Task 3.1 proves it with a helper process that calls LockFileEx directly.

Alternative: reuse TaskLock unchanged. Rejected: on Windows a .NET holder makes the Rust CLI fail instead of wait, and a Rust holder is invisible to it.

STORE-3. The reference transaction journal, applied by every holder

The journal follows the reference format exactly:

  • it is <id>.json.transaction, with schemaVersion 1 and exactly the members nextLock and nextCatalog;
  • each member is a JSON number array of the bytes to write, or null for a deletion, which is what uninstall writes for the lock.

Recovery does not decide between completing and rolling back. It writes whatever bytes the journal holds and removes it, as the reference does. A failed write first rewrites the journal with the previous bytes (state_io.rs:180-187, 249-252). Every acquisition of the state lock recovers journals before it reads.

The inventory record and the .NET global layer are written after the pair, under the same lock. A missing inventory record for a shared entry is rebuilt from the pair on the next read.

STORE-4. A .NET inventory of every installed version

data/morphir-dotnet/extensions/installed/<id>/<digest>.json keeps the entry and lock the installer would write globally, plus the source and, for target archives, the archive digest. It backs the .NET global layer, level pins and overlays.

The key is the id and the artifact digest. The same bytes installed again with other args, claims or index replace the record, and the report warns. A pin binds a digest, not the metadata around it. For a shared entry the catalog and lock always win over the record. A record rebuilt from a Rust-written pair says source kind shared-catalog, because the true source cannot be known.

Alternative: several entries per id in the shared catalog. Rejected: upstream readers refuse duplicate ids (state.rs:557-563, as StateMismatch).

SEL-1. Portable pins at levels, resolved against the local inventory

Provisional: it follows Q-LEVELS and serves a contract that belongs in the toolchain specifications, raised upstream in task 1.2.

A level's .morphir/extensions/selection.json pins the id, version, runtime and a digest per platform, and nothing machine-specific. Precedence is overlay, project, workspace, .NET global layer, shared catalog, system (Figure 3). A broken pin never falls through to a lower layer. Isolation omits the system pin and both global layers. Pin writes take a lock below locks/ in Morphir Home, keyed by the canonical pin path.

SEL-2. The overlay arrives by an environment variable that morphirup sets

Provisional: it follows Q-OVERLAY and belongs in the toolchain contract, raised upstream. MORPHIR_EXTENSION_OVERLAY names an absolute directory below toolchains/generations/ in Morphir Home. It is an environment variable, not a command-line option, because morphirup run must pass the user's arguments unchanged (approved project-toolchains, "Explicit command dispatch"). The host never writes there. This is the seam approved task 4.4 needs; 4.4 itself writes the generation directories.

SEL-3. Activation verifies offline and runs a private copy written from the verified read

Before a guest starts, the host:

  1. loads the selected record, and its lock for a shared entry, under the state lock, and checks that they agree;
  2. canonicalizes the store path inside Morphir Home, and checks the Unix mode and the MEP version;
  3. reads the store object once, hashing it as it writes tmp/extensions/morphir-dotnet-run-<random>/<filename>, or from verified in-memory bytes as the reference does;
  4. launches the copy only if the digest matched.

There is no second read between the check and the launch. The guest gets a cleared environment holding the probe's variables plus those the command documents, and an explicit working directory: the project directory for project commands, otherwise the copy's directory (parent rule, distribution-and-acquisition.md:461).

.NET copies have their own prefix. The host removes them after the process exits, and sweeps its own stale copies, never morphir-extension-*. A private copy also keeps store objects free of Windows file locks, so uninstall and update work while a guest runs.

Alternative: launch the store object in place. Rejected for all of these reasons.

PROBE-1. The probe is a bounded describe on the staged copy

Use the Morphir.Mep host peer's DescribeAsync on the staged copy, with:

  • a fresh private working directory;
  • a cleared environment holding only PATH, SYSTEMROOT on Windows, and TMP/TEMP/TMPDIR naming a private directory;
  • the framing limits of the MEP core;
  • a 30 second request deadline, after which the whole tree is ended with Process.Kill(entireProcessTree: true).

The reference clears the environment and passes no variable by default (morphir-host-native/src/process/child.rs:51-52, launch.rs:61), and its default request timeout is 30 seconds (launch.rs:10). The short list of variables is a recorded difference, because .NET guests and single-file extraction need a system root and a temporary directory.

The probe falls back to a session on -32601, on -32014, and on the lifecycle refusals the reference recognizes by message, with code -32600 or in -32000..-32099 (morphir-host/src/probe.rs:273-295).

Claim sets are compared over the typed claim set projection, as check_claims does (agreement.rs:31-60): unknown top-level members drop out, an absent critical equals an empty one, and numbers compare with serde_json equality (Q-NUMBERS). claimCheck records this install's action only (Q-CLAIMCHECK). WASM is never probed, as upstream decided on 21 October 2026.

ARC-1. Archives are read with the base class library, with recorded limits

Archives are read with System.IO.Compression.ZipArchive, and with System.Formats.Tar.TarReader over GZipStream. The entry list is checked before anything is extracted. Extraction writes only into private staging, and only the descriptor, checksums and the selected artifact are extracted.

Entry names:

  • must be ASCII, because every expected name is ASCII;
  • are compared ignoring ASCII case, which is simpler than, and stronger than, the NFC and ordinal-ignore-case rule of the first version;
  • must not be Windows device names such as CON.exe;
  • in a zip, must have a local header name equal to the central directory name (the pinned submodule commit is itself a fix for an advisory about zip header names).

The limits:

  • archive file 1 GiB, 1024 entries, 256 MiB per entry (the store's limit), and 1 GiB extracted in total;
  • PAX and GNU extension headers 1 MiB, as the Rust tool archive reader (tool_archive.rs:15);
  • a ratio of 200 for entries over 1 MiB, measured on a gzip stream as tar bytes over compressed bytes read so far.

Limits apply at each nesting level, and inner bytes count toward the outer totals. Only the 256 MiB limit has a parent source. The others are this change's choice, lower than the Rust tool archive prior art (10 000 entries, 4 GiB), because extension packages hold a handful of files.

Assumed Both readers publish with no trim or AOT warnings. Task 5.1 confirms it.

ARC-2. The automatic staged pass is narrow

The pass runs before commands that resolve extensions, only in auto mode, and installs only WASM packages. Process packages never install automatically, because installing one runs its describe, which is running code from whatever was cloned. Until this host has a WASM runtime, those entries are listed as unavailable. The pass writes nothing on stdout, turns failures into stderr warnings, and skips a file whose digest is already selected at its level.

CMD-1. Upstream verbs, the PRD's additions, and one report shape

Following Q-COMMANDS, the verbs are:

  • install (--repository <name> <id>, or <file>, or --staged; --channel|--version, --no-probe, --level);
  • update, with the same source forms and --repository required for a repository, as in the parent README;
  • uninstall, with the alias remove;
  • list, info, use, which, and repository add|list|remove.

Only list keeps --platform, as a filter over recorded artifacts. Installs are for the running platform only, so --platform on any other verb is a usage error.

Results go to stdout, one JSON document with --json; everything else goes to stderr. Exit codes are 0, 1 for a refusal and 2 for usage. Codes start with extension. (Q-DIAG).

An entry installed from a generated repository cannot be updated by the Rust CLI, which needs a configured repository. The .NET host updates it from the same kind of source it was installed from.

CMD-2. Retire the download handlers for extensions, and supersede #492

The extension handlers, their command records and the extension use of ArtifactPathResolver and OsPaths are removed when the new commands land. dist and tool keep their stubs. Recommendation: close #492 as superseded, because wiring it would publish unchecked downloads into a folder no other Morphir CLI reads.

TRUST-1. Authentication is a caller's fact; the installer checks integrity and claims

The installer never verifies a signature or a repository identity. For CLI sources it reports authentication kind local-developer with policy developer, using the receipt's vocabulary for bytes no one authenticated.

That label is not a receipt. The receipt contract admits a developer artifact "only into manager-owned storage" (installation-receipt.md:49 at efdbc34da), and it has no ownership case for an extension the user installed with the host CLI. A manager can copy the label only for an install it drove itself. This gap is raised upstream.

For a morphirup hand-over, the installer takes the caller's statement and returns it unchanged. The statement is repository-target with repositoryId and targetsVersion, or recipe-digest. The one-repository-per-binding check and repository_mismatch stay with the manager.

This is where the installer touches the TUF client: the client authenticates the targets and hands over bytes and a statement, and the installer rechecks the bound digests. The shared lock has no member for authentication, so this fact lives only in the manager's receipt and the .NET inventory.

ID-1. The id rule is chosen by document version, and dotted ids follow finos/morphir#1149

The registry keeps its dotted rule for built-ins. The installer parses ids with the rule of the version it reads. For 1.0, 2.0.0-draft.1 and 2.0.0-draft.2, an id is one token of at most 238 characters that is not a Windows device name by the reference rule (domain/identity.rs:237-286, which also refuses CONIN$, CONOUT$ and superscript-digit forms).

Dotted ids are read from the drafts #1149 introduces once it is approved: the descriptor, index record and catalog at 2.0.0-draft.3, and the lock at 2.0.0-draft.1. Where a dotted-id install is written follows the Q-SHARED answer and the revised #1149. #1149 adds the device-name rule for the first segment, which morphir-dotnet adopts in its task 5.1.

Questions

The first version of this page listed 25 questions with one status. They are now grouped by what they need.

  • Needs the maintainer: product and contract choices. The affected requirements are marked provisional in the spec text, and each question says what it blocks.
  • Deliberate divergence: this change departs from the reference on purpose, and the maintainer may veto it.
  • Follows the reference: the specs copy the reference implementation, the gap is raised upstream, and no maintainer answer is needed to start.
  • Settled: earlier questions answered by a decision already made or by an upstream decision.

Needs the maintainer

Q-SHARED. What may enter the shared catalog? (new; critical; one answer for MEP versions and dotted ids)

The problem. A Rust reader fails its whole listing on any catalog entry it cannot read or run (the evidence). Two planned writes hit that today:

  • a .NET install of a guest that speaks only MEP 0.2.0-draft.1, which is every guest built on Morphir.Mep;
  • a dotted id under finos/morphir#1149 as drafted, which writes the catalog at 2.0.0-draft.3. Because the catalog is one file with one schemaVersion, that would make the whole catalog unreadable to every host that reads only 2.0.0-draft.2.

Both are the same failure: a write that a released reader cannot understand, in a single shared file that the reader must read completely.

Options.

  • (a) Admit to the shared catalog only entries that the pinned reference reader can read and run, and install every other global install into a .NET global layer beside it: the inventory plus data/morphir-dotnet/extensions/global.json (SHARE-1). This works today with every released Rust CLI and changes nothing upstream. Cost: a second global place in .NET, a stderr note when it is used, and no shared use until extensions speak a common version.
  • (b) Wait for an upstream change that makes list_installed skip entries it cannot run and report them, instead of failing. It is cheaper for .NET, but released Rust CLIs keep failing on a shared Morphir Home. It also does not help #1149, because a reader that skips entries still cannot read a catalog whose schemaVersion it refuses.
  • (c) Make the .NET guests also speak MEP 0.1. Rejected: the PRD forbids implementing the legacy protocol, and it does not help dotted ids.

One mechanism for both problems. Option (a) answers both, if the side layer is treated as the place for entries that need newer readers. The upstream ask that goes with it is to standardize that layer as a catalog file that only readers of the new drafts open, beside a legacy catalog that every released reader can still read. #1149 could then write dotted ids there instead of promoting catalog/extensions.json. Readers of the new drafts would read both files, and old readers would read only the legacy file. If upstream adopts that file, the .NET global layer moves into it in a single transaction under the state lock. Until then it stays .NET-owned.

Recommendation: (a) now, with the specs written to it as provisional. Raise (b) and the standard side layer upstream in task 1.2, as an issue and as a review comment on #1149.

Blocks: 2.9 and 3.5, and so everything that writes global state (4.2 onwards, 5.4, 6.5, 7.1). It also blocks adoption task 3.3: the F# guests speak only 0.2 and have dotted ids, so under (a) they install into the .NET global layer, never the shared catalog.

Q-LEVELS. What a level file is (PRD superset; belongs in the toolchain contract)

Options.

  • (a) Level directories hold copies of catalog entries and locks, including absolute index paths. They are then machine-local and must not be committed.
  • (b) Portable pins (id, version, runtime, a digest per platform), resolved against a local inventory. This is recommended (SEL-1).
  • (c) Drop level files, and let the project toolchain lock pin providers. That leaves analyzers, which recipes do not cover, without a project selection.

Option (b) also answers the PRD's open point about a project lock that refers to a staged file: both are committed, and a second machine installs the staged file and satisfies the pin.

Generation directories and receipts belong to docs/spec/toolchain, so the pin format is raised there instead of becoming a .NET-only parallel design.

Blocks: 6.1 to 6.3, the non-global --level values, and the project, workspace and system staged folders in 5.5. Under Q-SHARED (a), task 3.4's inventory is needed whatever this question decides.

Q-OVERLAY. How the generation overlay reaches the host (approved UP-2 is silent; belongs in the toolchain contract)

Options.

  • (a) MORPHIR_EXTENSION_OVERLAY, set by the proxy. This is recommended (SEL-2).

On precedence, the recommendation is to put the overlay above the project pins, because the generation was resolved from the project's own request.

Q-PROVENANCE. Index provenance for sources that are not a named repository (PRD conflict)

Q-ARCHIVE. Package and target archives (silent upstream; includes the former Q-DESCNAME)

The path to installing the F# frontend without .NET

Two blockers apply whatever is chosen:

  • The guest reports org.finos.morphir.fsharp-frontend (src/Morphir.Frontend.FSharp.Extension/FSharpGuest.fs:61). The probe compares extension.id, and dotted ids wait for #1149. So the frontend cannot be installed under any id today, even as one file, unless the maintainer accepts a temporary single-token id.
  • It speaks only MEP 0.2.0-draft.1, so under Q-SHARED (a) it installs into the .NET global layer, never into the shared catalog.

Both options below assume the frontend is built self-contained, with FSF-1's fix applied: framework references come from an explicit list instead of "everything in the runtime folder".

Option A: single-file self-contained publish with extraction (the cheapest path)

Adoption task 3.1 explicitly did not qualify a single-file publish. Today the frontend refuses a single-file bundle, because CompilerEdge gives the F# compiler file locations for its references. In a bundle, Assembly.Location is empty for bundled assemblies, so FSharp.Core and the annotations reference would be empty paths (FSF-1).

What would have to change:

  1. Publish with PublishSingleFile and IncludeAllContentForSelfExtract, so that every assembly is extracted to disk at start. Assumed With full extraction, Assembly.Location names the extracted file, so CompilerEdge gets real paths. A qualification test confirms this before anything depends on it.
  2. Take the reference list from the extraction directory with FSF-1's explicit framework list, and test that application assemblies such as Morphir.* never become references of the user's code.
  3. Give extraction a directory under the probe's restricted environment. Extraction needs DOTNET_BUNDLE_EXTRACT_BASE_DIR, or the temporary and home variables the runtime derives a default from. The probe now passes only TMP/TEMP/TMPDIR naming a private directory (PROBE-1).
    • Either the host extracts into a fresh private directory for every probe and run, which writes about 121 MB each time;
    • or the host sets DOTNET_BUNDLE_EXTRACT_BASE_DIR to a .NET-owned directory keyed by the store digest, for example tmp/morphir-dotnet/bundles/<digest>/, and reuses it.
    The second is faster, but the extracted files are not rehashed at activation. They have the trust of user-owned Morphir Home, the same as the store, and that is recorded rather than hidden.
  4. Check the size against the 256 MiB artifact limit (store.rs:14). Assumed The self-contained folder reported for adoption 3.1 is about 121 MB. That is not measured here. An uncompressed bundle is about the size of the folder, roughly 115 MiB, so it fits with about 140 MiB to spare. A compressed bundle is smaller but starts more slowly. The probe's 30 second deadline must also cover the first extraction. Both are measured in the qualification task.
  5. Ship the bundle raw, or as a one-file target archive (Q-ARCHIVE (a)).
  6. Settle the id: wait for #1149, or accept a temporary single-token id.

Cost: one build change and one qualification task in the adoption change (3.1 is re-scoped from "folder archive" to "single file with extraction"). No contract change, no Rust change and no store change. The integrity gap of reused extraction is documented.

Option B: an upstream package form for multi-file extensions

This needs:

  • a descriptor member for an entry point and a per-file manifest;
  • a store layout for trees, and activation that verifies every file;
  • a catalog and lock member for trees;
  • the Rust reader, writer and activation changes;
  • a new draft, which brings back the legacy-reader problem of Q-SHARED.

Benefits: no extraction, every file verified at each activation, and one form for any multi-file guest (other self-contained runtimes, Python, JVM).

Cost: a contract change and implementation work in two repositories before the first F# frontend install, and the frontend still could not enter the shared catalog until a reader speaks 0.2.

Recommendation: Option A for the first F# frontend delivery. Re-scope adoption task 3.1, and make adoption task 3.3 depend on 3.5, 5.3 and the id. Raise Option B upstream as the long-term form. Decide before adoption task 3.3 starts.

Not defended:

  • A malicious process extension that the user installs and runs has the user's rights. That is the PRD's stated trust model for process guests, and is documented, not solved, here.
  • A same-user process can change a private run copy between the hash and the launch.
  • Option A's reused extraction directory is not rehashed. Both of these rest on Morphir Home being user-owned.

Findings for the approved and adoption changes

  1. A .NET install of a 0.2-only guest would break the Rust CLI. The approved toolset-setup requirement says setup "SHALL use the host's extension configuration, store, claims and locks". Read naively, that writes the F# guests into the shared catalog, which breaks every Rust command on that Morphir Home (the evidence). Adoption task 3.3 must install them under the Q-SHARED answer.
  2. Multi-file frontend versus single-file store. Adoption FSF-1 ships the self-contained F# frontend as a folder, and the store holds one file per digest. Approved task 3.3 cannot complete as written until Q-MULTIFILE is answered. The cheapest path re-scopes adoption 3.1 (the F# frontend section).
  3. Dotted ids. Both F# guests report dotted ids, so neither can be installed until #1149 lands. #1149 as drafted promotes the catalog to a draft that older hosts cannot read, which is the same class of problem as finding 1, and Q-SHARED proposes one answer for both.
  4. Target archives. The approved recipe binds win-x64.zip process archives, but nothing upstream says how an installer turns one into an installed artifact (Q-ARCHIVE). Under the recommendation, the shared lock records the inner file's digest and a generated repository, so only the .NET inventory ties the install back to the publisher's archive, and the Rust CLI cannot update it.
  5. "Duplicate ids cannot enter one registry" (approved 4.4). The same id is expected across layers. The rule applies after precedence and within one layer. This change states that rule in a MODIFIED "Extension ids are unique", with exit code 1 for a refused selection.
  6. PRD step 3 corrections.
    • Provenance kind staged would break upstream readers (Q-PROVENANCE).
    • describe for WASM packages conflicts with the upstream decision.
    • The global level is the shared catalog plus a .NET global layer, not one file.
    • "Sharing global installs" means sharing format and store until both hosts speak a common MEP version.
  7. #492 as written contradicts step 3. Recommend closing it as superseded (CMD-2).
  8. Receipt launch path. A receipt's launch.program for an installed provider would be the store path, while the host runs a private copy (SEL-3). Raised upstream with the overlay and pins.
  9. The developer label and manager-owned storage. The receipt admits a developer artifact only into manager-owned storage (installation-receipt.md:49). An extension that the user installed with the host CLI has no ownership case, so a manager cannot copy the host's local-developer label into a receipt for it.
  10. requires.host across implementations. A provider's requires.host cannot say which implementation it targets (Q-REQHOST).
  11. MEP 0.1-only extensions. This host speaks only 0.2.0-draft.1, so the published process extensions pinned upstream resolve to extension.no_compatible_mep_version, and Rust-installed ones are listed as unavailable. The approved qualification matrix should not count them for .NET.
  12. Two changes modify one registry requirement. This change's MODIFIED block for "An entry states its delivery and hosts" is now written against the adoption change's text on main, and adds deployments and reason for installed entries.

Migration plan

  1. Group 1 records the maintainer's answers and raises the upstream asks. Groups 2 and 3 add the library and shared-state code with no command change, and 3.5 runs the first interoperability gate.
  2. Group 4 replaces the stubs. No release ever installed anything through them, so there is no user data to migrate. Files the old handlers could have written below the OsPaths folders are not read or deleted.
  3. Groups 5 to 7 add archives, staged folders, levels, activation and the hand-over. Group 8 waits for #1149.
  4. The PRD's feature table and step 3 text are updated in the group that lands each part; docs/content/docs/cli/management.md is rewritten in task 4.8.
  5. Rollback: until group 4, each group adds code paths beside the old ones, and reverting a group's commits restores the stubs. Entries in the shared catalog are in the upstream format, so a Rust CLI can still read, update or uninstall the admitted entries a reverted .NET host installed. Entries in the .NET global layer stay on disk, readable by the next .NET host that has this code.
  6. If upstream standardizes a catalog for entries that need newer readers, the .NET global layer moves into it in one transaction under the state lock.

Deliberately left out

  • Any network acquisition: HTTP, Git, GitHub releases, mirrors, proxies, credentials. morphirup owns acquisition, and the TUF client is evaluated separately.
  • Signature, provenance or repository-identity verification of any kind.
  • Repository authoring: repository init, publish, bundle; also search, repository enable|disable|inspect|verify.
  • A WASM runtime, and bare .wasm install until step 2a supplies one.
  • Multi-file extension artifacts and any new store layout (Q-MULTIFILE).
  • MEP 0.1 support in .NET guests or in this host.
  • Dotted ids before #1149 is approved.
  • Store cleanup, yanking and revocation of extensions.
  • External generator and analyzer selection in generate and validate; only the frontend reference (extension_id) is wired.
  • dist and tool commands (#490, #491) and the tool store.
  • Daemon extensions and JVM artifacts.
  • The toolchain generation directories themselves (approved 4.4 and 4.5).
