Goals and non-goals

Goals. Install, update, remove and select external extensions in both hosts, sharing global installs with the Rust CLI byte for byte where the files are shared. Give morphirup the seams the approved change names: an in-process hand-over of authenticated files and a generation-scoped overlay. Make every place where the parent contract is silent visible and decided by the maintainer, not by an implementer.

Non-goals at the design level. No network client. No signature checks. No new extension store layout. No change to MEP. No WASM runtime. The full list is in Deliberately left out.

What happened, in order (Figure 2):

  1. Resolve. The installer read the repository's history, took the newest stable release that lists MEP 0.2.0-draft.1 (the only version this host speaks) and has an artifact for windows/x86_64, and kept the SHA-256 of the exact history bytes as the index revision.
  2. Stage. It copied the executable into %USERPROFILE%\.morphir\tmp\morphir-extension-probe-…\, hashing while copying, and compared the digest. It never opens the repository file again.
  3. Probe. It started the staged copy, called morphir.extension.describe, and compared the answer with the record's claim set as parsed values.
  4. Store. It published the bytes to store/extensions/sha256/1111…/morphir-fsharp-backend.exe without replacing anything.
  5. Commit. Under locks/extensions.state.lock it finished any journal left by an earlier run, wrote a journal, wrote locks/extensions/morphir-fsharp-backend.json and catalog/extensions.json, removed the journal, and wrote the .NET inventory record data/morphir-dotnet/extensions/installed/morphir-fsharp-backend/1111….json.

Decisions

These are this change's own choices. Each names the alternatives. Where a choice depends on a maintainer answer, it names the question.

INST-1. A separate F# installation library that both hosts and morphirup reference

Put the installer in a new F# project, src/Morphir.Extensions.Installation, referencing Morphir.Extensions and Morphir.Mep but not Morphir.Tooling. Pure modules (identifiers, records, claim comparison, resolution, archive entry rules, pin files) carry most tests without I/O. Edge modules (store, state lock, journal, archive reading, probe launch) sit behind small interfaces. The C# CLI edge stays in src/Morphir.Tooling/Features/Extensions. F# code that C# calls follows the fsharp-csharp-interop skill, and the reviewer agent checks those pull requests. JSON is read and written with JsonDocument and Utf8JsonWriter, because the reader must keep unknown members and the writer must emit exact member sets; no reflection serialization, so the library stays trim- and AOT-clean.

Alternatives: inside Morphir.Tooling (rejected: morphirup must not reference it, adoption MGR-1); inside Morphir.Extensions (rejected: it would pull file system and process code into the registry domain); generated codecs from Morphir.Myriad.SystemTextJson (kept for typed views such as the MEP claim set, rejected for the shared files whose unknown members must survive).

INST-2. Every source becomes one resolved record before any byte is stored

A named repository, a package archive, a staged file and a morphirup hand-over each produce the same value: release record, selected artifact, selection, index provenance, and a separate source description for the .NET inventory and report. Staging, hashing, probing, storing and committing are then one code path (Figure 2). This keeps every check in one place and makes each source's tests about reading, not about storage.

Alternative: separate pipelines per source, as the old handlers had one per artifact type. Rejected because checks drift.

STORE-1. Shared files are written with the upstream member sets and read with must-ignore

Writers emit exactly the members the Rust implementation writes, in its spelling, pretty-printed with a final newline. Readers keep unknown optional members (catalog entries, records) and refuse unknown critical ones. .NET-only facts (true source kind, archive digest, level) go to the .NET inventory, never into shared files. Byte-for-byte equality with Rust output is not required; member-set and value equality is, and tasks 2.7 and 9.1 check it against files the Rust CLI wrote.

STORE-2. The state lock uses the reference primitive

Open locks/extensions.state.lock for read and write, create without truncate, and take an exclusive lock that fs2 respects: on Linux and macOS flock (what .NET takes for FileShare.None); on Windows a byte-range lock over the whole file (FileStream.Lock on a handle opened with FileShare.ReadWrite | FileShare.Delete), which overlaps LockFileEx over 0..2^64-1. Poll with the TaskLock waiting line. Assumed FileStream.Lock(0, long.MaxValue) conflicts with an fs2 lock on Windows; task 3.1 proves it with a helper process that calls LockFileEx directly. Alternative: reuse TaskLock unchanged. Rejected: on Windows a .NET holder makes the Rust CLI fail instead of wait, and a Rust holder is invisible to it.

STORE-3. The reference transaction journal, recovered by every holder

Write <id>.json.transaction with schemaVersion 1 and the next lock and catalog bytes as JSON number arrays, then the lock, then the catalog, then delete the journal; roll back on failure as Rust does. Every acquisition of the state lock recovers journals before reading. The .NET inventory record is written after the pair, under the same lock; a missing inventory record for a catalog entry is rebuilt from the pair on the next read, so a crash between them loses nothing.

STORE-4. A .NET inventory of every installed version

The global catalog holds one record per id, but level pins and overlays need older and newer versions to stay installed. data/morphir-dotnet/extensions/installed/<id>/<digest>.json keeps the catalog entry and lock the installer would write globally, plus the source kind and, for target archives, the archive digest. The directory name morphir-dotnet marks component ownership under the upstream data directory. Alternative: several entries per id in the shared catalog. Rejected: upstream readers refuse duplicate ids.

SEL-1. Portable pins at levels, resolved against the local inventory

Following the recommendation of Q-LEVELS: a level's .morphir/extensions/selection.json pins id, version, runtime and a digest per platform, and nothing machine-specific. The global level is the shared catalog. Precedence is overlay, project, workspace, global, system (Figure 3). A broken pin never falls through to a lower layer, matching the approved rule that a broken project selection does not use the default. Isolation omits the system pin and global catalog. Pin writes take a lock below locks/ in Morphir Home keyed by the canonical pin path, as TaskInstaller keys install locks.

SEL-2. The overlay arrives by an environment variable that morphirup sets

Following Q-OVERLAY: MORPHIR_EXTENSION_OVERLAY names an absolute directory below toolchains/generations/ in Morphir Home. An environment variable, not a command-line option, because morphirup run must pass the user's arguments unchanged (approved project-toolchains, "Explicit command dispatch"). The host never writes there. This is the seam approved task 4.4 needs; 4.4 itself writes the generation directories.

SEL-3. Activation verifies offline and runs a private copy

Before a guest starts: load the selected record pair (under the state lock for the global layer), check agreement, canonicalize inside Morphir Home, rehash, check the Unix mode and the MEP version, then copy the verified bytes to tmp/extensions/<random>/<filename> and launch that copy by absolute path. The Rust host also hands the activated bytes to a private staging directory. This closes the gap between check and use, keeps store objects free of Windows file locks so uninstall and update work while a guest runs, and keeps the launched path short. Alternative: launch the store object in place. Rejected for all three reasons.

PROBE-1. The probe is a bounded describe on the staged copy

Use the Morphir.Mep host peer's DescribeAsync over Content-Length framing on the staged copy, working directory a fresh private folder, environment limited to an allow-list that the builder records (at least PATH, and SYSTEMROOT on Windows, which processes need to start), framing limits of the MEP core (64 MiB payload, 8192-byte headers), and a 30-second deadline (builder's call, recorded; Q-PROBELIMITS). On timeout, end the tree with Process.Kill(entireProcessTree: true). Fall back to a session only on -32601 or -32014. Compare claim sets as parsed values with ordered arrays and Rust number equality (Q-NUMBERS). Record claimCheck from this install's action only (Q-CLAIMCHECK). WASM is never probed, as upstream decided on 21 October 2026.

ARC-1. Archives are read with the base class library, with recorded limits

System.IO.Compression.ZipArchive, and System.Formats.Tar.TarReader over GZipStream, as the PRD requires. The entry list is checked before anything is extracted; extraction writes only into private staging, and only the descriptor, checksums and the selected artifact are extracted. The limits the PRD leaves to the builder are recorded here and in the spec: archive file 1 GiB, 1024 entries, 256 MiB per entry (the store's artifact limit), 1 GiB extracted in total, and a ratio of 200 for entries over 1 MiB. The Rust tool archive reader is the prior art (10 000 entries, 4 GiB, Unicode case-folded collision checks); extension packages hold a handful of files, so the counts are lower. Duplicate detection uses NFC normalization and ordinal-ignore-case folding. Assumed both readers publish with no trim or AOT warnings; task 5.1 confirms it, as the PRD asks.

ARC-2. The automatic staged pass is narrow

The pass runs before commands that resolve extensions (compile, generate, validate, and extension list, which, info, use), only in auto mode, and installs only WASM packages (Q-AUTOPROCESS). Until this host has a WASM runtime, those entries are listed as unavailable. It writes nothing on stdout, turns failures into stderr warnings, and skips a file whose digest is already selected at its level. A staged file stays in place after install.

CMD-1. Upstream verbs, the PRD's additions, and one report shape

Following Q-COMMANDS: install (--repository <name> <id>, or <file>, or --staged; --channel|--version, --no-probe, --level), update, uninstall with alias remove, list, info, use, which, and repository add|list|remove. Repository authoring (init, publish, bundle), search and repository enable|disable|inspect|verify are left out. Results go to stdout, one JSON document with --json; everything else to stderr; exit 0, 1 for a refusal, 2 for usage. Codes start with extension. (Q-DIAG).

CMD-2. Retire the download handlers for extensions, and supersede #492

The extension handlers, their command records and the extension use of ArtifactPathResolver and OsPaths are removed when the new commands land, with their tests in tests/Morphir.Tooling.Tests/Features/Management. dist and tool keep their stubs; #490 and #491 are unchanged by this change. Recommendation: close #492 as superseded by this change, because wiring it would publish unchecked downloads into a folder no other Morphir CLI reads.

TRUST-1. Authentication is a caller's fact; the installer checks integrity and claims

The installer never verifies a signature. For CLI sources it reports authentication kind local-developer with policy developer, the installation receipt's case for bytes that no one authenticated, so the manager can copy it unchanged. For a morphirup hand-over it takes the caller's statement (repository-target with repository id and targets version, or recipe-digest with the recipe reference) and returns it unchanged in its result, so the manager can copy it into the receipt beside claimCheck. This is where the installer touches the TUF client: the client authenticates the descriptor and artifact targets and hands over bytes and a statement; the installer then rechecks the bound digests. The global lock has no member for authentication, so this fact lives only in the manager's receipt and the .NET inventory.

ID-1. The id rule is chosen by document version

The registry keeps its dotted rule for built-ins. The installer parses ids with the rule of the version it reads: for 1.0, 2.0.0-draft.1 and 2.0.0-draft.2, one token of at most 238 characters that is also a portable file name (no device names). A future descriptor version that allows dotted ids switches the rule for documents of that version, and only then may a dotted id be written to shared files, at the version the change defines (Q-IDRULE).

Contract gaps and questions for the maintainer

Each item says where the gap is, the options, and a recommendation. The specs follow the recommendations and name the question; tasks that would change with another answer say so. "Upstream" marks a gap to raise in finos/morphir.

Q-LOCKPRIM. Which OS lock is the state lock? (Rust-only, upstream)

The PRD names locks/extensions.state.lock. The primitive is only in state_io.rs: fs2::lock_exclusive, blocking. Options: (a) match fs2 on each platform (recommended, STORE-2); (b) use TaskLock and accept that the CLIs do not exclude each other on Windows; (c) ask upstream to move to share modes. Recommendation: (a) now, and ask upstream to state the primitive in the contract.

Q-JOURNAL. The transaction journal format (Rust-only, upstream)

The parent says only "staging and atomic publication". Rust writes <id>.json.transaction holding byte arrays and recovers at every lock. A CLI that does not recover the other's journals leaves catalog and lock disagreeing. Recommendation: implement the Rust format exactly and ask upstream to document it with fixtures.

Q-STRICTLOCK. Lock readers refuse unknown members (Rust-only, contradicts must-ignore, upstream)

ExtensionLock uses deny_unknown_fields; a code comment says released readers since beta.5 do. That contradicts the parent's must-ignore rule. Options: (a) write exactly the upstream members and keep extras in the .NET inventory (recommended); (b) ask upstream to relax the reader, then add members. Recommendation: (a), and raise the contradiction upstream so the documents say which rule a lock follows.

Q-CATVER. Catalog schema version switching (Rust-only, upstream)

The catalog is written as "2.0.0-draft.2" when any entry has supplied claims and "1.0" otherwise; the lock stays "1.0" with claims in index.claims. No document says so. Recommendation: do the same, and ask upstream to document it.

Q-ARCHIVE. Process artifacts that are target archives (silent, upstream)

Real process releases (elm-classic) and the toolchain recipe fixtures bind .zip/.tgz target archives, but Rust repository publish refuses archives, the version 2 descriptor has no entry-point member, and the store holds single files. Nothing says which digest the installed lock records. Options: (a) require exactly one regular file, install it, record its digest in the lock and the archive digest in the .NET inventory (recommended, as the PRD's "Each target archive holds only the executable"); (b) store the archive and extract at each activation; (c) wait for an upstream archive form. Recommendation: (a), proposed upstream with an explicit rule.

Q-MULTIFILE. Multi-file process artifacts (silent; conflicts with adoption FSF-1)

The adoption change publishes the self-contained F# frontend as a folder archive, because a single file breaks its compiler references. The extension store, records and activation have one file per extension. Options: (a) qualify a single-file self-contained frontend with extraction, then install it as one file; (b) propose an upstream package form for extensions, modeled on the tool store's packages with an entry point and a per-file manifest; (c) a .NET-only tree store, which upstream CLIs cannot read. Recommendation: refuse multi-file artifacts in this change (extension.multi_file_artifact), raise (b) upstream now, and decide between (a) and (b) before approved task 3.3 starts. Do not take (c): it breaks the PRD anti-goal that the store format does not differ from upstream.

Q-PROVENANCE. Index provenance for sources that are not a named repository (PRD conflict, upstream)

The PRD says a staged install writes provenance kind staged. Upstream IndexKind is a closed enum with only local-directory, and the catalog reader would refuse the whole catalog, so a Rust extension list would fail for every extension. Options: (a) generate a one-release local repository below data/morphir-dotnet/extensions/repositories/ and install from it, so provenance is a valid local-directory with a real revision (recommended); (b) keep file and staged installs out of the shared files; (c) wait for upstream to add a kind. Recommendation: (a) now, and propose a staged kind upstream with the PRD's superset proposal.

Q-IDRULE. Ids in shared files (decided direction; detail Rust-only)

The maintainer decided that the descriptor contract will allow dotted ids in a separate change. Until it exists, the shared files require one token that is also a portable file name; the device-name part (con, aux, com1) is only in Rust identity.rs. Consequence: the real F# frontend guest org.finos.morphir.fsharp-frontend cannot be installed through the shared store until that change lands (the toolchain fixtures use morphir-fsharp-frontend). Recommendation: ID-1, and add the device-name rule to the upstream text.

Q-PLATFORM. Platform spellings (partly specified)

The toolchain contracts give RID to triple. The index os/arch spelling is Rust's std::env::consts, and cannot say musl. Recommendation: use the toolchain table plus windows|macos|linux and x86_64|aarch64, refuse musl with extension.platform_unrepresentable, and ask upstream to put the index spelling in the table.

Q-CLAIMCHECK. What claimCheck means after an update (ambiguous, upstream)

The parent says a record's claimCheck says how its writer checked the claims. Rust extension update installs without a probe and copies the index's value, which may be probed from publication on another host. Recommendation: an installed record says probed only when this install or update ran the probe; update probes by default and takes --no-probe. Raise the Rust behavior upstream.

Q-PROBELIMITS. Probe environment and limits (silent)

The protocol says hosts should limit the environment, choose the working directory and enforce timeouts, without values. Recommendation: PROBE-1's values, recorded by the builder; ask upstream to set common values.

Q-REQHOST. Whose version does requires.host compare? (ambiguous, upstream)

requires.host is a SemVer range "over the host version" with no implementation identity. The .NET release (0.4.0-alpha.3) and the Rust CLI (0.4.0-beta.x) are different products on one axis, so a range written for one is meaningless for the other. Recommendation: compare with this host's release version and name the range on refusal now; ask upstream for an implementation-qualified requirement.

Q-NUMBERS. Number equality in claim comparison (Rust-only, upstream)

Claims compare as parsed values with ordered arrays and "the Rust host's parsed JSON value equality". In serde_json an integer token and a fraction or exponent token differ (1 is not 1.0), while 1.0 equals 1.00. Recommendation: replicate that rule (integer tokens compare as integers, others as doubles) and ask upstream for fixture pairs.

Q-LEVELS. What a level file is (PRD superset; PRD open point)

Options: (a) level directories hold copies of catalog entries and locks, including absolute index paths, so they are machine-local and must not be committed; (b) portable pins (id, version, runtime, digest per platform) resolved against a local inventory (recommended, SEL-1); (c) drop level files and let the project toolchain lock pin providers. Option (b) answers the PRD's open point about a project lock that refers to a staged file: the staged file and the pin are both committed, and a second machine installs the staged file and satisfies the pin. Option (c) leaves analyzers, which recipes do not cover, without a project selection. Also decide whether isolation omits the global catalog (recommended: yes, like other machine inputs).

Q-OVERLAY. How the generation overlay reaches the host (approved UP-2 is silent)

Options: (a) MORPHIR_EXTENSION_OVERLAY set by the proxy (recommended, SEL-2); (b) a command-line option, which breaks argument pass-through; (c) the host finds the project's generation pointer itself, which ties the host to manager state. Precedence recommendation: overlay above project pins, since the generation was resolved from the project's own request.

Q-AUTOPROCESS. Does auto apply to process guests? (PRD open point)

Installing a process package runs its describe, which is running code from whatever was cloned. Options: (a) never automatically (recommended); (b) automatically with --no-probe semantics, which installs unchecked code that a later command runs; (c) a separate opt-in setting. Recommendation: (a), with a stderr note naming extension install --staged.

Q-WASMDESCRIBE. WASM install and describe (PRD conflict)

The PRD says install runs describe for every package and takes a bare module's identity from describe. Upstream decided that WASM installation does not probe, and this host has no WASM runtime until step 2a. Recommendation: WASM packages install unchecked from the descriptor; bare .wasm waits for step 2a and is refused until then. Correct the PRD.

Q-DEVPOLICY. What is the explicit developer policy for unsigned installs?

The maintainer's decision: an unsigned developer extension needs explicit developer policy and stays labelled. Options: (a) an explicit command naming a local repository or file is the policy, and the configured staged mode is the policy for staged files; every such record is labelled local-developer (recommended); (b) also require --allow-unsigned, which the Rust CLI does not, so the same repository behaves differently in the two CLIs. Recommendation: (a).

Q-COMMANDS. Command names

The .NET stubs have use, remove, which; upstream has update, uninstall, search, repository …. Recommendation: CMD-1, keeping remove as an alias and giving use and which the level meaning above.

Q-CONFIGREF. How configuration names an installed extension

Configuration has paths ([frontend.<language>].extension, extensions.<name>.path). Options: (a) new members, extension_id in a frontend table and id in an extensions table (recommended, unambiguous); (b) treat a value without a path separator as an id, which makes extension = "tool" mean two things. Generator selection waits on the adoption change's review question 4; this change only wires frontends.

Q-DESCNAME. Descriptor and checksum file names (Rust-only for bundles)

A bundle directory requires release.json and checksum files of exactly <sha256> <filename>\n; release assets use <name>-<version>.release.json. Recommendation: in package archives accept exactly one *.release.json, and accept a checksum file of 64 lowercase digits, white space and the entry name; propose the PRD's archive suffix question upstream as the PRD says.

Q-WINLAUNCH. Windows launch rules (silent)

Nothing says a Windows process artifact must end in .exe, or how long its launched path can be. Assumed process creation refuses executable paths over 260 characters without long-path support; task 6.4 checks it and drops the check if wrong. Recommendation: refuse non-.exe Windows executables at install, launch from the short private copy, and refuse an over-long copy path with advice.

Q-GC. Store cleanup (silent)

Uninstall leaves bytes; nothing removes unreferenced objects, and pins in projects this machine cannot see may still reference them. Recommendation: no cleanup in this change.

Q-DIAG. Stable codes (silent)

The toolchain contracts have stable codes; extension acquisition has none. Recommendation: the extension.* codes in the specs, offered upstream.

Q-FIXTURES. No language-neutral fixtures for acquisition documents (upstream)

finos/morphir has schemas and fixtures for the toolchain documents, and none for index records, descriptors, catalogs, locks or journals. Two Rust test fixtures exist (frontend-catalog-v1.json, frontend-lock-v1.json). Recommendation: propose a fixture set in finos/morphir (positive and negative records, a Rust-written catalog, lock and journal pair, archive cases), kept as data like the kit cases; until it lands, pin copies with provenance in this repository's tests.

Findings for the approved and adoption changes

  1. Multi-file frontend versus single-file store. Adoption FSF-1 ships the self-contained F# frontend as a folder archive; approved toolset-setup requires setup to use the host's extension store, which holds one file per extension. Approved task 3.3 cannot complete as written until Q-MULTIFILE is answered.
  2. Dotted frontend id. The approved lock example uses org.finos.morphir.fsharp-frontend; the descriptor contract cannot carry it yet. The toolchain recipe page already records this; this change makes the installer refuse it until the descriptor change lands.
  3. Target archives. The approved recipe binds win-x64.zip process archives, but nothing upstream says how an installer turns one into an installed artifact (Q-ARCHIVE).
  4. "Duplicate ids cannot enter one registry" (approved 4.4). Across layers the same id is expected (a project pin over the global catalog). The rule applies after precedence and within one layer. The adoption note that ExtensionCatalog.Build "already refuses duplicate ids" covers built-ins only.
  5. The overlay seam is unnamed. Approved UP-2 says hosts read an overlay but not how it arrives (Q-OVERLAY).
  6. PRD step 3 corrections. Provenance kind staged would break upstream readers (Q-PROVENANCE); describe for WASM packages conflicts with the upstream decision (Q-WASMDESCRIBE); the global level's selection is the shared catalog, not a second file.
  7. #492 as written contradicts step 3. Recommend closing it as superseded (CMD-2). The adoption proposal lists it only as "not step 3".
  8. Receipt launch path. A receipt's launch.program for an installed provider would be the store path, while the host runs a private copy (SEL-3). The receipt contract should say which path it records.
  9. requires.host across implementations. Recipes bind providers to hosts of different implementations; a provider's requires.host cannot say which (Q-REQHOST).
  10. MEP 0.1-only extensions. This host speaks only 0.2.0-draft.1, so the published process extensions pinned upstream (elm 0.4.x) resolve to extension.no_compatible_mep_version. The approved qualification matrix should not count them for .NET.

Migration plan

  1. Group 1 records the maintainer's answers. Groups 2 and 3 add the library and shared-state code with no command change.
  2. Group 4 replaces the stubs. No release ever installed anything through them, so there is no user data to migrate. Files the old handlers could have written below the OsPaths folders are not read or deleted.
  3. Groups 5 to 7 add archives, staged folders, levels, activation and the hand-over; group 8 waits for the dotted-id descriptor change.
  4. The PRD's feature table and step 3 text are updated in the group that lands each part; docs/content/docs/cli/management.md is rewritten in group 4.
  5. Rollback: each group adds code paths beside the old ones until group 4; reverting a group's commits restores the stubs. Files written to Morphir Home are in the upstream format, so a Rust CLI can still read, update or uninstall what a reverted .NET host installed.

Deliberately left out

  • Any network acquisition: HTTP, Git, GitHub releases, mirrors, proxies, credentials. morphirup owns acquisition; the TUF client is evaluated separately.
  • Signature or provenance verification of any kind.
  • Repository authoring: repository init, publish, bundle; also search, repository enable|disable|inspect|verify.
  • A WASM runtime, and bare .wasm install until step 2a supplies one.
  • Multi-file extension artifacts and any new store layout (Q-MULTIFILE).
  • Dotted ids in shared files before the descriptor change.
  • Store cleanup, yanking and revocation of extensions.
  • External generator and analyzer selection in generate and validate (adoption 3.2 and PRD steps 2a, 2b); only the frontend reference (extension_id) is wired.
  • dist and tool commands (#490, #491) and the tool store.
  • Daemon extensions and JVM artifacts.
  • The toolchain generation directories themselves (approved 4.4 and 4.5).
