What "shared" means for today's extensions

The first version of this change said that each CLI sees the other's global installs. For today's extensions that is wrong. The two CLIs share the format of Morphir Home's files. They share use of an installed extension only when both can run it, and today almost no extension satisfies that.

StepEvidence
Observed The Rust host supports only MEP 0.1.morphir-extension-sdk/src/protocol.rs:14,17: MEP_VERSION = "0.1", SUPPORTED_MEP_VERSIONS = &[MEP_VERSION]. The SDK has the 0.2.0-draft.1 model draft (model/negotiation.rs:8), but the installed-state checks use only the supported list.
Observed The .NET host speaks 0.2.0-draft.1, the only version of the MEP 0.2 line that exists today.src/Morphir.Mep/Peers.fs:222; the PRD says not to implement 0.1.
Observed Listing validates every catalog entry and stops at the first error.morphir-distribution/src/state.rs:722-737 maps each entry through validate_installed_pair and collects into a Result.
Observed An entry without a supported MEP version is an error.state.rs:782-791 returns NoCompatibleMepVersion.
Observed Every Rust command that needs extensions lists them first.finos/morphir crates/morphir/src/commands/compile/prepare.rs:248, generate.rs:207, extension.rs:153.

So one .NET global install of a guest built on Morphir.Mep into catalog/extensions.json would make every Rust compile, generate and extension list on that Morphir Home fail. The reverse gives nothing either: an extension the Rust CLI installed that speaks only 0.1 cannot run in .NET. The failure is in the catalog only. Rust reads a lock file only for an id the catalog names. It lists locks/extensions/ only to find *.json.transaction journals, whose bytes it writes to the lock path and to the one catalog path without parsing ids (state_io.rs:209-252), and it never lists the store. The first revision of this page said Rust never lists that directory, which was wrong. It is also why #1149 gives dotted journals their own directory. Index records reach a Rust reader only through a repository it is configured to read, and its resolver filters MEP versions per release (resolver.rs:49-64), so an incompatible record fails only the install of that id.

The maintainer decided on 9 November 2026 to cut support for MEP 0.1 in this host (MEP-1), and to keep released Rust CLIs working on a shared Morphir Home. So this change admits to a shared catalog only entries that every host reading it can read and run, and puts every other global install in a .NET global layer beside it (SHARE-1). Store objects stay shared, because they are content-addressed and nothing lists them. Today an extension enters catalog/extensions.json only if it also lists 0.1. For the extensions this repository builds, "shared" means a shared store and a shared format until the Rust host speaks 0.2.0-draft.1; after that, it means shared use.

Goals and non-goals

Goals.

  • Install, update, remove and select external extensions in both .NET hosts.
  • Write Morphir Home's shared files in the upstream format, and never write anything there that breaks an upstream reader.
  • Share global installs with the Rust CLI wherever both can run the extension.
  • Give morphirup the seams the approved change names: an in-process hand-over of authenticated files, and a generation-scoped overlay.
  • Make every place where the parent contract is silent visible, and leave the decisions to the maintainer rather than to an implementer.

Non-goals at the design level. No network client. No signature checks. No new extension store layout. No change to MEP. No WASM runtime. The full list is in Deliberately left out.

What happened, in order (Figure 2):

  1. Resolve. The installer read the history, took the newest stable release that lists an MEP version this host speaks and has an artifact for windows/x86_64, and kept the SHA-256 of the exact history bytes as the index revision.
  2. Stage. It copied the executable into %USERPROFILE%\.morphir\tmp\morphir-extension-probe-…\, hashing while copying, and compared the digest.
  3. Probe. It started the staged copy with a cleared environment, called morphir.extension.describe, and compared the answer with the record's claim set over the typed projection.
  4. Store. It copied the staged bytes into store/extensions/sha256/1111…/acme-backend.exe, hashing again while copying, so a guest that rewrote its staged file during the probe is caught, and published without replacing anything.
  5. Admit. The admission rule found no MEP version that the reference reader supports, so the entry may not enter catalog/extensions.json.
  6. Commit. Under locks/extensions.state.lock it applied any journal left by an earlier run, then wrote the inventory record data/morphir-dotnet/extensions/installed/acme-backend/1111….json and the .NET global layer data/morphir-dotnet/extensions/global.json. Nothing below catalog/ or locks/extensions/ changed.

5. A morphirup generation selects its own versions

This step depends on Q-OVERLAY and on the shared toolchain contract. When morphirup run -- generate … launches the host for a project toolchain generation, it sets MORPHIR_EXTENSION_OVERLAY to %USERPROFILE%\.morphir\toolchains\generations\g7f3a\. That directory's extensions\selection.json pins the providers of the generation (SEL-2). The host resolves those ids from the overlay and every other id as before. The global selection is untouched, so two projects can use two generations at once (approved UP-2, task 4.4).

6. A package archive and a staged folder

Dana's teammate Eli receives acme-backend-0.2.0.zip, a zip of the release assets:

Decisions

These are this change's own choices. Each names the alternatives. Where a choice depends on a maintainer answer, it names the question.

INST-1. A separate F# installation library that both hosts and morphirup reference

Put the installer in a new F# project, src/Morphir.Extensions.Installation, referencing Morphir.Extensions and Morphir.Mep but not Morphir.Tooling. Pure modules (identifiers, records, claim comparison, resolution, admission, archive entry rules, pin files) carry most tests without I/O. Edge modules (store, state lock, journal, archive reading, probe launch) sit behind small interfaces. The C# CLI edge stays in src/Morphir.Tooling/Features/Extensions. F# code that C# calls follows the fsharp-csharp-interop skill. JSON is read and written with JsonDocument and Utf8JsonWriter, because the reader must keep unknown members and the writer must emit exact member sets; no reflection serialization, so the library stays trim- and AOT-clean.

Alternatives: inside Morphir.Tooling (rejected: morphirup must not reference it, adoption MGR-1); inside Morphir.Extensions (rejected: it would pull file system and process code into the registry domain).

INST-2. Every source becomes one resolved record before any byte is stored

A named repository, a package archive, a staged file and a morphirup hand-over each produce the same value: release record, selected artifact, selection, index provenance, and a separate source description for the .NET inventory and report. Staging, hashing, probing, storing, admission and committing are then one code path (Figure 2). Alternative: separate pipelines per source, as the old handlers had. Rejected because checks drift.

SHARE-1. A shared catalog admits only what every host that reads it can run (maintainer decision)

The maintainer cut support for MEP 0.1 in this host (MEP-1), and kept the .NET global layer, so released Rust CLIs keep working on a shared Morphir Home. The rule, for every shared catalog, is this: a global install writes an entry and lock into a shared catalog only when every host that reads that catalog can read and run the entry. Store objects are shared by everyone, because they are content-addressed and nothing lists them.

  • For catalog/extensions.json, its readers include the released Rust CLIs. So an entry needs an mepVersions member holding a version the pinned reference reader supports, and a single-segment id. The supported set is one constant recorded with its source (["0.1"] at c9f79da), and it moves only with the submodule pin.
  • For #1149's catalog/extensions-dotted.json (provisional), its readers are the hosts that implement #1149. An entry needs a version they all run, unless #1149 requires them to list and skip entries they cannot run (Q-SHARED).
  • Everything else goes to the .NET global layer: an inventory record, plus an entry in data/morphir-dotnet/extensions/global.json that maps the id to that record's digest. That layer ranks above the shared catalogs for .NET hosts. One id is never globally selected in two places: a global install refuses an id that another place holds.

The reverse direction is defined too. A shared entry this host cannot run is listed as unavailable with a reason, and never stops the listing.

The .NET global layer shrinks on its own as hosts converge. When the pinned reference reader speaks 0.2.0-draft.1, the constant moves, and new installs of 0.2 guests enter the shared catalog.

Alternatives: write every install to the shared catalog (rejected by the maintainer: it breaks every released Rust command on that Morphir Home); keep every .NET install out of the shared catalog (rejected: it gives up shared use for extensions both hosts can run).

STORE-1. Shared files are written with the upstream member sets and read with must-ignore

Writers emit exactly the members the Rust implementation writes, in its spelling, pretty-printed with a final newline. That includes critical and requires on an entry whose release has requires.host. This host never writes an entry converted from a version 1 record (DOC-1). When it rewrites a catalog that holds one the Rust CLI wrote, it carries that entry through with its members and values unchanged, because the reference writes such entries without claims, claimCheck or probeSource (extension_format/claims.rs:82-87, 243-251).

Readers keep unknown optional members and refuse unknown critical ones. .NET-only facts (true source kind, archive digest, level, layer) go to the .NET inventory, never into shared files. Byte-for-byte equality with Rust output is not required; member-set and value equality is. Tasks 2.7, 3.5 and 9.1 check it against the pinned Rust CLI.

STORE-2. The state lock uses the reference primitive

Open locks/extensions.state.lock for read and write, create without truncate, and take an exclusive lock that fs2 respects:

  • on Linux and macOS, flock, which is what .NET takes for FileShare.None;
  • on Windows, a byte-range lock over the whole file: FileStream.Lock on a handle opened with FileShare.ReadWrite | FileShare.Delete, which overlaps LockFileEx over 0..2^64-1.

Poll with the TaskLock waiting line. The repositories lock uses the same primitive.

Assumed FileStream.Lock(0, long.MaxValue) conflicts with an fs2 lock on Windows. Task 3.1 proves it with a helper process that calls LockFileEx directly.

Alternative: reuse TaskLock unchanged. Rejected: on Windows a .NET holder makes the Rust CLI fail instead of wait, and a Rust holder is invisible to it.

STORE-3. The reference transaction journal, applied by every holder

The journal follows the reference format exactly:

  • it is <id>.json.transaction, with schemaVersion 1 and exactly the members nextLock and nextCatalog;
  • each member is a JSON number array of the bytes to write, or null for a deletion, which is what uninstall writes for the lock.

Recovery does not decide between completing and rolling back. It writes whatever bytes the journal holds and removes it, as the reference does. A failed write first rewrites the journal with the previous bytes (state_io.rs:180-187, 249-252). Every acquisition of the state lock recovers journals before it reads.

The inventory record and the .NET global layer are written after the pair, under the same lock. A missing inventory record for a shared entry is rebuilt from the pair on the next read.

STORE-4. A .NET inventory of every installed version

data/morphir-dotnet/extensions/installed/<id>/<digest>.json keeps the entry and lock the installer would write globally, plus the source and, for target archives, the archive digest. It backs the .NET global layer, level pins and overlays.

The key is the id and the artifact digest. The same bytes installed again with other args, claims or index replace the record, and the report warns. A pin binds a digest, not the metadata around it. For a shared entry the catalog and lock always win over the record. A record rebuilt from a Rust-written pair says source kind shared-catalog, because the true source cannot be known.

Alternative: several entries per id in the shared catalog. Rejected: upstream readers refuse duplicate ids (state.rs:557-563, as StateMismatch).

SEL-1. Portable pins at levels, resolved against the local inventory

Provisional: it follows Q-LEVELS and serves a contract that belongs in the toolchain specifications, raised upstream in task 1.2.

A level's .morphir/extensions/selection.json pins the id, version, runtime and a digest per platform, and nothing machine-specific. Precedence is overlay, project, workspace, .NET global layer, shared catalog, system (Figure 3). A broken pin never falls through to a lower layer. Isolation omits the system pin and both global layers. Pin writes take a lock below locks/ in Morphir Home, keyed by the canonical pin path.

SEL-2. The overlay arrives by an environment variable that morphirup sets

Provisional: it follows Q-OVERLAY and belongs in the toolchain contract, raised upstream. MORPHIR_EXTENSION_OVERLAY names an absolute directory below toolchains/generations/ in Morphir Home. It is an environment variable, not a command-line option, because morphirup run must pass the user's arguments unchanged (approved project-toolchains, "Explicit command dispatch"). The host never writes there. This is the seam approved task 4.4 needs; 4.4 itself writes the generation directories.

SEL-3. Activation verifies offline and runs a private copy written from the verified read

Before a guest starts, the host:

  1. loads the selected record, and its lock for a shared entry, under the state lock, and checks that they agree;
  2. canonicalizes the store path inside Morphir Home, and checks the Unix mode and the MEP version;
  3. reads the store object once, hashing it as it writes tmp/extensions/morphir-dotnet-run-<random>/<filename>, or from verified in-memory bytes as the reference does;
  4. launches the copy only if the digest matched.

There is no second read between the check and the launch. The guest gets a cleared environment holding the probe's variables plus those the command documents, and an explicit working directory: the project directory for project commands, otherwise the copy's directory (parent rule, distribution-and-acquisition.md:461).

.NET copies have their own prefix. The host removes them after the process exits, and sweeps its own stale copies, never morphir-extension-*. A private copy also keeps store objects free of Windows file locks, so uninstall and update work while a guest runs.

Alternative: launch the store object in place. Rejected for all of these reasons.

PROBE-1. The probe is a bounded describe on the staged copy

Use the Morphir.Mep host peer's DescribeAsync on the staged copy, with:

  • a fresh private working directory;
  • a cleared environment holding only PATH, SYSTEMROOT on Windows, and TMP/TEMP/TMPDIR naming a private directory;
  • the framing limits of the MEP core;
  • a 30 second request deadline, after which the whole tree is ended with Process.Kill(entireProcessTree: true).

The reference clears the environment and passes no variable by default (morphir-host-native/src/process/child.rs:51-52, launch.rs:61), and its default request timeout is 30 seconds (launch.rs:10). The short list of variables is a recorded difference, because .NET guests and single-file extraction need a system root and a temporary directory.

The probe falls back to a session on -32601 and -32014 only. The reference also falls back on lifecycle refusals that it recognizes by message, with code -32600 or in -32000..-32099 (morphir-host/src/probe.rs:273-295). Those come from guests released before MEP assigned -32014, which predate 0.2.0-draft.1, so under MEP-1 this host does not carry that code. This is a recorded difference from the reference.

Claim sets are compared over the typed claim set projection, as check_claims does (agreement.rs:31-60): unknown top-level members drop out, an absent critical equals an empty one, and numbers compare with serde_json equality (Q-NUMBERS). claimCheck records this install's action only (Q-CLAIMCHECK). WASM is never probed, as upstream decided on 21 October 2026.

ARC-1. Archives are read with the base class library, with recorded limits

Archives are read with System.IO.Compression.ZipArchive, and with System.Formats.Tar.TarReader over GZipStream. The entry list is checked before anything is extracted. Extraction writes only into private staging, and only the descriptor, checksums and the selected artifact are extracted.

Entry names:

  • must be ASCII, because every expected name is ASCII;
  • are compared ignoring ASCII case, which is simpler than, and stronger than, the NFC and ordinal-ignore-case rule of the first version;
  • must not be Windows device names such as CON.exe;
  • in a zip, must have a local header name equal to the central directory name (the pinned submodule commit is itself a fix for an advisory about zip header names).

The limits:

  • archive file 1 GiB, 1024 entries, 256 MiB per entry (the store's limit), and 1 GiB extracted in total;
  • PAX and GNU extension headers 1 MiB, as the Rust tool archive reader (tool_archive.rs:15);
  • a ratio of 200 for entries over 1 MiB, measured on a gzip stream as tar bytes over compressed bytes read so far.

Limits apply at each nesting level, and inner bytes count toward the outer totals. Only the 256 MiB limit has a parent source. The others are this change's choice, lower than the Rust tool archive prior art (10 000 entries, 4 GiB), because extension packages hold a handful of files.

Assumed Both readers publish with no trim or AOT warnings. Task 5.1 confirms it.

ARC-2. The automatic staged pass is narrow

The pass runs before commands that resolve extensions, only in auto mode, and installs only WASM packages. Process packages never install automatically, because installing one runs its describe, which is running code from whatever was cloned. Until this host has a WASM runtime, those entries are listed as unavailable. The pass writes nothing on stdout, turns failures into stderr warnings, and skips a file whose digest is already selected at its level.

CMD-1. Upstream verbs, the PRD's additions, and one report shape

Following Q-COMMANDS, the verbs are:

  • install (--repository <name> <id>, or <file>, or --staged; --channel|--version, --no-probe, --level);
  • update, with the same source forms and --repository required for a repository, as in the parent README;
  • uninstall, with the alias remove;
  • list, info, use, which, and repository add|list|remove.

Only list keeps --platform, as a filter over recorded artifacts. Installs are for the running platform only, so --platform on any other verb is a usage error.

Results go to stdout, one JSON document with --json; everything else goes to stderr. Exit codes are 0, 1 for a refusal and 2 for usage. Codes start with extension. (Q-DIAG).

An entry installed from a generated repository cannot be updated by the Rust CLI, which needs a configured repository. The .NET host updates it from the same kind of source it was installed from.

CMD-2. Retire the download handlers for extensions, and supersede #492

The extension handlers, their command records and the extension use of ArtifactPathResolver and OsPaths are removed when the new commands land. dist and tool keep their stubs. Recommendation: close #492 as superseded, because wiring it would publish unchecked downloads into a folder no other Morphir CLI reads.

TRUST-1. Authentication is a caller's fact; the installer checks integrity and claims

The installer never verifies a signature or a repository identity. For CLI sources, its own report says authentication kind local-developer with policy developer.

That label lives only in the installer's reports and the .NET inventory. At finos/morphir#1147 (60d363059), local-developer is no longer a receipt authentication value, and a receipt that uses it is refused (installation-receipt.md:43). The page also says why: a lock names only artifacts an authenticated recipe binds by digest. So bytes equal to a locked digest are recipe-digest, whoever built them, and an unsigned developer artifact is never part of a generation. It is "installed outside generations, under the extension installer's explicit developer policy" (installation-receipt.md:51), which is exactly this installer's CLI path. That settles the receipt question this change raised earlier (review M7); it is no longer an upstream ask.

For a morphirup hand-over, the installer takes the caller's statement and returns it unchanged. The statement is repository-target with repositoryId and targetsVersion, or recipe-digest. Any other kind, including local-developer, is refused, because a hand-over is always a generation install. The one-repository-per-binding check and repository_mismatch stay with the manager.

Two more manager rules touch the installer:

  • The plan covers everything. A plan must cover everything its command writes, so before writing, the installer answers "what would this install write": the store path, the shared catalog and lock, the .NET global layer or the pin, the inventory record, and whether the guest runs with the user's rights. It then writes nothing else. This is provisional pending the toolchain contract.
  • Revocation is the manager's job. A learned revocation of a recipe target is the manager's check before run launches a generation, and the installer does not learn revocations. Bytes the user installed globally outside a generation are not revoked by a recipe revocation, even when their digest is the same. The installer's docs say so.

This is where the installer touches the TUF client: the client authenticates the targets and hands over bytes and a statement, and the installer rechecks the bound digests. The shared lock has no member for authentication, so this fact lives only in the manager's receipt and the .NET inventory.

MEP-1. MEP 0.1 is not supported; the MEP 0.2 line is (maintainer decision)

Decision. On 9 November 2026 the maintainer decided three things, in this order:

  1. To cut support for MEP 0.1: "we don't have users to support the cost of maintaining 2 versions".
  2. The scope of that cut: "we can still have the global, we just have decided to cut support for MEP 0.1". The .NET global layer stays (SHARE-1).
  3. What is supported instead: "We should support 0.2.0 all prerelease and final 0.2.x releases".

So MEP 0.1 is not supported, and the supported protocol is the whole 0.2 line: every prerelease of 0.2.0 and every final 0.2.x release. Today the only version of that line that exists is 0.2.0-draft.1. Nothing a host can speak changes yet. What changes is the policy: as later versions of the line appear, a host keeps the earlier ones instead of replacing one exact draft with the next.

Observed Upstream calls 0.1 "the frozen legacy protocol" (finos/morphir docs/design/draft/extensions/protocol.md:878 on main at 04143a238) and does not yet say it is deprecated. Recording the decision there is an upstream ask (task 1.2).

What the decision means in this change:

  • The supported line. The supported MEP versions are those the comparators >=0.2.0-0 and <0.3.0 match, under the prerelease rule of npm's node-semver, of Rust's semver crate used by the reference, and of the Semver NuGet package's SemVersionRange. That rule is: a prerelease version matches only when some comparator names the same major, minor and patch with a prerelease. Because 0.2.0-0 is the lowest prerelease of 0.2.0, the pair matches exactly what the maintainer said, every prerelease of 0.2.0 and every final 0.2.x, and nothing else:
    • in the line: 0.2.0-draft.1, 0.2.0-rc.1, 0.2.0 and 0.2.7;
    • outside it: 0.1, 0.1.0, 0.2.1-rc.1, 0.3.0-draft.1 and 0.3.0.
  • Supported is not the same as implemented. The host implements a set of exact versions inside the line: today {0.2.0-draft.1}. It never drops a version of the line it has implemented. A session still agrees on one exact version, and an entry is runnable only when its mepVersions holds a version the host implements. An entry that names only a version of the line the host does not implement yet, such as 0.2.0-draft.2, is listed as unavailable because that version is not implemented yet. That is different from 0.1 or 0.3.0, which are not supported at all. Both refusals use extension.no_compatible_mep_version, and the reason tells them apart.
  • An explicit exception. The general contract rule in finos/morphir's protocol.md ("Version numbers") and in this repository is that a prerelease matches only exactly, because drafts are refined in place and promise no compatibility with each other. That rule still decides what each session uses. MEP's 0.2 line has this explicit maintainer exception for what a host supports and keeps. The exception does not make two drafts compatible with each other.
  • Not DOC-1. DOC-1 drops the earlier transient drafts of the extension document formats, while MEP keeps every version of its 0.2 line: they are separate decisions about separate contracts.
  • Nothing implements 0.1. Nothing here implements, bridges or tests 0.1.
  • No legacy code paths. The probe does not carry the reference's fallback for refusals that older guests signal only by message (PROBE-1). An extension that speaks only 0.1 is refused at install with extension.no_compatible_mep_version, and is listed as unavailable when the Rust CLI installed it. Both messages say that MEP 0.1 is not supported.
  • Released Rust CLIs are still not broken. Cutting 0.1 here does not mean writing entries they cannot run into the files they read. The admission rule keeps them working; that costs one constant and the .NET global layer.
  • The path out is upstream. The ask is for the Rust host to move to the MEP 0.2 line. When the pinned reader speaks a version of it, the admission constant moves, and new 0.2 installs enter the shared catalog.

A shared entry this host cannot run, for example one the Rust CLI installed, is listed as unavailable instead of failing the listing. That is robustness, not protocol support. DOC-1 applies the same "no transient compatibility" reasoning to old document formats.

DOC-1. Only the current contract drafts are read (maintainer decision)

Decision. On 9 November 2026 the maintainer decided to stop reading the older document formats, because "we are paying too much of a cost to support transient pre 1.0 contracts".

What this host reads and writes:

  • index records, release descriptors and catalog entries at exactly 2.0.0-draft.2, plus the drafts finos/morphir#1149 adds for dotted ids;
  • claim sets at 0.1.0-draft.2;
  • catalog and lock files at the versions the reference writes today: catalog "1.0" or "2.0.0-draft.2" (Q-CATVER), and lock "1.0", the only lock version there is.

What it no longer reads, and never converts: version 1 index records and descriptors (integer 1 or "1.0"), records and descriptors at 2.0.0-draft.1, and claim sets at 0.1.0-draft.1 (statement, statementSource). Those formats mostly carried MEP 0.1-era extensions, which MEP-1 already leaves out.

Where old documents still appear, and what happens:

  • A history with old lines. A line at a version this host does not read takes part only through its schemaVersion, id and version, so the history checks still hold, and it is never selected. Asking for such a release gives extension.unsupported_contract_version.
  • A descriptor in an old format is refused with extension.unsupported_contract_version.
  • A Rust-written catalog entry this host does not read (converted from a version 1 record, or with claim set draft.1) is listed as unavailable with a reason, never activated, and carried through unchanged when this host rewrites the catalog. The file stays readable; only those entries are unavailable.

The cost removed: no draft.1 conversion, no mixed-draft detection, no version 1 descriptor or record codecs, and no converted-entry writer.

ID-1. The id rule is chosen by document version, and dotted ids follow finos/morphir#1149

The registry keeps its dotted rule for built-ins. The installer parses ids with the rule of the version it reads. At 2.0.0-draft.2, an id is one token of at most 238 characters that is not a Windows device name by the reference rule (domain/identity.rs:237-286, which also refuses CONIN$, CONOUT$ and superscript-digit forms).

Dotted ids are read and written at #1149's drafts once it is approved: descriptor, index record and dotted catalog at 2.0.0-draft.3, and a dotted lock at 2.0.0-draft.1. #1149 also adds the device-name rule for the first segment, which morphir-dotnet adopts in its task 5.1. Where dotted entries live depends on #1149's question 8:

  • With the partition (as #1149 is written), they live in catalog/extensions-dotted.json and locks/extensions-dotted/, and histories in a repository's extensions-dotted/. The store spec says this, as a provisional requirement.
  • With one catalog, they live in the existing files, which move to 2.0.0-draft.3 when they first hold a dotted id.

Either way, admission (SHARE-1) decides first: a dotted extension that a reader of its catalog cannot run goes to the .NET global layer. Task 8.1 covers both answers.

Q-LEVELS. What a level file is (PRD superset; belongs in the toolchain contract)

Options.

Option (b) also answers the PRD's open point about a project lock that refers to a staged file: both are committed, and a second machine installs the staged file and satisfies the pin.

Generation directories and receipts belong to docs/spec/toolchain, so the pin format is raised there instead of becoming a .NET-only parallel design.

Q-PROVENANCE. Index provenance for sources that are not a named repository (PRD conflict)

The consequence of (a): nothing in shared state ties back to the publisher's descriptor or archive, only the .NET inventory does, and the Rust CLI cannot update the entry.

Q-ARCHIVE. Package and target archives (silent upstream; includes the former Q-DESCNAME)

Options for target archives.

  • (a) Require exactly one regular file, install it, record its digest in the lock and the archive digest in the .NET inventory. This is recommended, and matches the PRD's "each target archive holds only the executable".
  • (b) Store the archive and extract it at each activation.
  • (c) Wait for an upstream archive form.

For the package archive. Accept exactly one *.release.json at the root, and checksum files of 64 lowercase digits, white space and the entry name. The reference bundle directory instead requires exactly release.json and the line <sha256> <name>\n (repository_authoring.rs:334-365).

Deliberate divergence

Q-CLAIMCHECK. claimCheck after an update: this change departs from the reference on purpose

The parent text: "An index record and an installed record say in claimCheck how their writer checked the claims: probed when it ran the artifact and read them, and unchecked when it did not" (distribution-and-acquisition.md:377-380).

Q-SHARED. What may enter a shared catalog? Settled: SHARE-1; the id half is #1149's question 8

Settled. The maintainer kept the .NET global layer while cutting MEP 0.1 in this host. A shared catalog admits only entries that every host that reads it can read and run, and the .NET global layer holds the rest (SHARE-1).

How the .NET global layer relates to #1149's dotted partition. They are two layers that apply one principle, not one layer with two reasons. The principle: a file that some host reads whole holds only entries that host can read and run, and anything else goes where that host never looks.

  • #1149's partition applies it to ids. It holds catalog/extensions-dotted.json at 2.0.0-draft.3, with locks and journals in locks/extensions-dotted/ and histories in a repository's extensions-dotted/. It admits by id form, and every host that implements #1149 reads it.
  • The .NET global layer applies it to MEP versions: data/morphir-dotnet/extensions/global.json plus the inventory. It admits by "the readers of the shared catalog cannot run this", and only .NET reads it.

#1149's partition cannot also carry the MEP-version case, for three reasons:

  1. It refuses a single-segment id in the dotted files, so a single-token 0.2 guest cannot go there.
  2. An MEP version belongs to a release, not to an id. An update from a release that also lists 0.1 to one that speaks only 0.2.0-draft.1 would move the id between partitions, but #1149 changes one partition per operation.
  3. #1149's writer rule puts 2.0.0-draft.3 only on documents that name a dotted id.

The one decision. The maintainer has already answered, for MEP versions, the question both documents ask: a Morphir home keeps released hosts working by putting what they cannot read where they never look. That is SHARE-1. Giving the same answer for ids means #1149's question 8 takes the partition, not one catalog that switches version home-wide, because the home-wide switch would make catalog/extensions.json unreadable to released hosts the first time it held a dotted id.

One thing joins the two. Every dotted extension known today is a .NET guest that speaks only versions of the MEP 0.2 line (today 0.2.0-draft.1), while the Rust host that would read the dotted partition speaks only 0.1 until it moves. So #1149 should require its new readers to list an entry they cannot run as unavailable and keep going. That costs released hosts nothing, because they never read the new files. With that rule, the .NET dotted guests go to catalog/extensions-dotted.json and new Rust hosts can see them. Without it, admission sends them to the .NET global layer, where only .NET sees them.

Recommendation: answer #1149's question 8 with the partition, and add that rule.

What #1149 needs to say so the two documents agree:

  1. Readers of catalog/extensions-dotted.json and locks/extensions-dotted/ list an entry they cannot run, for its MEP versions or any other reason, as unavailable, and keep reading. Without this, morphir-dotnet keeps its dotted 0.2 guests in its own global layer.
  2. "A reader of the new drafts SHALL also read every version it read before" should allow a host to drop earlier transient drafts. morphir-dotnet drops them (DOC-1), so its scenario reading 2.0.0-draft.1 descriptors describes the Rust host only.
  3. Its Impact line and task 5.3 say this installer writes the home files "byte for byte" and "byte-identical to the Rust host's". This change promises equal members and values (STORE-1); #1149 should say that, unless the maintainer wants this installer to take on byte identity.
  4. "An older host keeps working on a home that holds dotted extensions" can cite morphir-dotnet's admission rule as why it also holds on homes that a .NET host wrote. Task 5.3's mixed-home check should read the entries the Rust host can run, and list the others as unavailable.

The path to installing the F# frontend without .NET

At finos/morphir#1147 (60d363059), the managed offerings have the built-in F# frontend morphir-dotnet.fsharp in every fsharp recipe, so only the native-aot offering needs this installed process frontend. The recipe's question M2 recommends the same first delivery as Option A below: a single-file self-extracting frontend at the archive root, with the recipe and lock binding the archive digest. That matches Q-ARCHIVE (a): the toolchain lock binds the archive, and the extension lock binds the one file inside it.

Two facts apply whatever is chosen:

  • The guest reports org.finos.morphir.fsharp-frontend (src/Morphir.Frontend.FSharp.Extension/FSharpGuest.fs:61). The probe compares extension.id, and dotted ids wait for #1149. So the frontend cannot be installed under any id today, even as one file, unless the maintainer accepts a temporary single-token id.
  • It speaks only versions of the MEP 0.2 line (today 0.2.0-draft.1), so a global install goes to the .NET global layer, or to the dotted partition if #1149 adds the list-and-skip rule, and never to catalog/extensions.json.

Observed Adoption task 3.1 has landed on main as a folder (#569, 4b14b0d). SelfContainedProcess.pubxml publishes a self-contained folder with PublishSingleFile false, "because the compiler references are files of the folder". CompilerEdge now takes the framework references from the host's deps files, and it refuses a single-file bundle with NoFileLocation when FSharp.Core or the annotations have no file location. Both options below build on that.

Option A: single-file self-contained publish with extraction (the cheapest path)

Adoption task 3.1 did not qualify a single-file publish, and #569 makes the frontend refuse one on purpose (NoFileLocation). CompilerEdge gives the F# compiler file locations for its references, and in a bundle Assembly.Location is empty for bundled assemblies (FSF-1).

What would have to change:

  1. Publish with PublishSingleFile and IncludeAllContentForSelfExtract, so that every assembly is extracted to disk at start. Assumed With full extraction, Assembly.Location names the extracted file, so CompilerEdge gets real paths. A qualification test confirms this before anything depends on it.
  2. Check that CompilerEdge.selectReferences finds the deps files and assemblies in the extraction directory, so NoFileLocation does not fire, and test that application assemblies such as Morphir.* never become references of the user's code. Assumed With full extraction, the deps files are on disk; the qualification test confirms it.
  3. Give extraction a directory under the probe's restricted environment. Extraction needs DOTNET_BUNDLE_EXTRACT_BASE_DIR, or the temporary and home variables the runtime derives a default from. The probe now passes only TMP/TEMP/TMPDIR naming a private directory (PROBE-1).
    • Either the host extracts into a fresh private directory for every probe and run, which writes about 121 MB each time;
    • or the host sets DOTNET_BUNDLE_EXTRACT_BASE_DIR to a .NET-owned directory keyed by the store digest, for example tmp/morphir-dotnet/bundles/<digest>/, and reuses it.
    The second is faster, but the extracted files are not rehashed at activation. They have the trust of user-owned Morphir Home, the same as the store, and that is recorded rather than hidden.
  4. Check the size against the 256 MiB artifact limit (store.rs:14). Assumed The self-contained folder reported for adoption 3.1 is about 121 MB. That is not measured here. An uncompressed bundle is about the size of the folder, roughly 115 MiB, so it fits with about 140 MiB to spare. A compressed bundle is smaller but starts more slowly. The probe's 30 second deadline must also cover the first extraction. Both are measured in the qualification task.
  5. Ship the bundle raw, or as a one-file target archive (Q-ARCHIVE (a)).
  6. Settle the id: wait for #1149, or accept a temporary single-token id.

Cost: one build change and one qualification task in the adoption change (a single-file publish profile beside #569's folder profile, qualified in its own task). No contract change, no Rust change and no store change. The integrity gap of reused extraction is documented.

Option B: an upstream package form for multi-file extensions

This needs:

  • a descriptor member for an entry point and a per-file manifest;
  • a store layout for trees, and activation that verifies every file;
  • a catalog and lock member for trees;
  • the Rust reader, writer and activation changes;
  • a new draft of the descriptor, catalog and lock.

Benefits: no extraction, every file verified at each activation, and one form for any multi-file guest (other self-contained runtimes, Python, JVM).

Cost: a contract change and implementation work in two repositories before the first F# frontend install.

Recommendation: Option A for the first F# frontend delivery, for the native-aot offering only. Add a single-file profile and its qualification task beside #569's folder profile, and make adoption task 3.3 depend on 3.5, 5.3 and the id. Raise Option B upstream as the long-term form. Decide before adoption task 3.3 starts.

Findings for the approved and adoption changes

  1. A .NET install of a 0.2-only guest would break the Rust CLI. The approved toolset-setup requirement says setup "SHALL use the host's extension configuration, store, claims and locks". Read naively, that writes the F# guests into the shared catalog, which breaks every Rust command on that Morphir Home (the evidence). Adoption task 3.3 installs them under SHARE-1: into the .NET global layer, or into #1149's dotted partition if it adds the list-and-skip rule.
  2. Multi-file frontend versus single-file store. Adoption FSF-1 ships the self-contained F# frontend as a folder, and the store holds one file per digest. Approved task 3.3 cannot complete as written until Q-MULTIFILE is answered. The cheapest path re-scopes adoption 3.1 (the F# frontend section).
  3. Dotted ids. Both F# guests report dotted ids, so neither can be installed until #1149 lands. #1149 now keeps dotted extensions in their own partition, which applies SHARE-1's principle to ids. Q-SHARED gives the one decision and what #1149 needs to say.
  4. Target archives. The approved recipe binds win-x64.zip process archives, but nothing upstream says how an installer turns one into an installed artifact (Q-ARCHIVE). Under the recommendation, the shared lock records the inner file's digest and a generated repository, so only the .NET inventory ties the install back to the publisher's archive, and the Rust CLI cannot update it.
  5. "Duplicate ids cannot enter one registry" (approved 4.4). The same id is expected across layers. The rule applies after precedence and within one layer. This change states that rule in a MODIFIED "Extension ids are unique", with exit code 1 for a refused selection.
  6. PRD step 3 corrections.
    • Provenance kind staged would break upstream readers (Q-PROVENANCE).
    • describe for WASM packages conflicts with the upstream decision.
    • The global level is the shared catalog plus a .NET global layer, not one file.
    • "Sharing global installs" means sharing format and store until both hosts speak a common MEP version.
  7. #492 as written contradicts step 3. Recommend closing it as superseded (CMD-2).
  8. Receipt launch path. A receipt's launch.program for an installed provider would be the store path, while the host runs a private copy (SEL-3). Raised upstream with the overlay and pins.
  9. The developer label and receipts: settled upstream. At finos/morphir#1147 (60d363059), local-developer is no longer a receipt value, and developer artifacts never appear in a generation (installation-receipt.md:43, 51). This change matches that: the label stays in the installer's own reports, and a hand-over refuses it.
  10. requires.host across implementations. A provider's requires.host cannot say which implementation it targets (Q-REQHOST).
  11. MEP 0.1-only extensions. MEP 0.1 is not supported (MEP-1). So the published process extensions pinned upstream resolve to extension.no_compatible_mep_version, and Rust-installed ones are listed as unavailable. The approved qualification matrix should drop them, and their publishers need releases that speak 0.2.0-draft.1.
  12. Two changes modify one registry requirement. This change's MODIFIED block for "An entry states its delivery and hosts" is now written against the adoption change's text on main, and adds deployments and reason for installed entries.
  13. "Keeps old global catalogs readable" (approved UP-2, task 4.4) is narrowed by DOC-1. An old catalog file is still read, and the ids an overlay does not select still resolve. But a catalog entry converted from a version 1 record, or one carrying claim set draft.1, is now listed as unavailable and never activated. The approved wording should say "readable", not "usable in full".
