Context

The approved finos/morphir change add-deployment-and-acquisition (approved 9 November 2026) is the source of truth. This page maps its decisions DEP-1, UP-1, UP-2, FS-1, LOCK-1, PATH-1 and QUAL-1 onto this repository. It does not change their meaning and adds no product decision. Where this page and the approved change disagree, the approved change wins and this page is wrong.

See the proposal for why. The approved design inspected main at 4e3321f. This page inspected main at d819bac. Between the two, the frontend guest project became Morphir.Frontend.FSharp.Extension (#552), the release v0.4.0-alpha.3 was prepared (#555), and single-file executables load System.Native by the runtime's name (#556). No build ran for this inspection. Facts that only a build or a published artifact can give are marked as such.

The approved distinction still frames everything: the host a user runs, the runtime arrangement of that host (the offering), the channel that installed it and the language toolset it can use. Today the code knows only two of these, and only by command name.

Status: planned, with no tracking issue yet; #492 wires the existing handlers and is not step 3. Goals and non-goals

Goals. Give each approved task in groups 2 to 6 a home in this codebase: the projects and files it touches, what it must extract or add first, the test project that carries its failing test and the narrowest command that runs it. Keep the approved behavior and examples unchanged. Name every place where the code makes the approved plan harder.

Non-goals. The shared contracts and fixed examples (approved group 1, finos/morphir). The WASM join (approved group 7). Choosing names, endpoints, signing-key custody or size targets that the approved design leaves to release preparation.

Adopted decisions and their mapping

Each heading below is an approved decision. The first paragraph restates its meaning in short. The rest says where it lands here.

DEP-1. Separate deployment from acquisition and toolsets

Approved meaning. Ada downloads Morphir on a machine without .NET and can choose AOT or managed self-contained execution. Both expose morphir. Ben keeps a .NET runtime and chooses the framework-dependent apphost. Chen keeps dotnet tool install Morphir.Tool. One shared command layer and one separate managed composition that includes FCS. The AOT entry point excludes FCS and uses the process frontend. Managed profiles with FCS start untrimmed. Archives distinguish implementation, release, deployment and platform, for example morphir-dotnet-1.2.3-native-aot-win-x64.zip (1.2.3 is illustrative). Existing release assets are not renamed in place.

OfferingInvocationRuntime arrangementF# frontend defaultBuilt from, after this change

Here. Task 2.1 extracts the composition (COMP-1). Task 2.2 replaces the three publish targets and two scripts with four named profiles in Nuke (REL-1). Task 2.3 adds the offering to host identity and to extension list as the wire member deployment (HOST-1, and the registry delta). Task 2.4 qualifies native dependencies from packaged artifacts. The System.Native fix in #556 is the kind of single-file loading behavior that needs that evidence. Task 2.5 extends the release with a catalog of the four offerings and six platforms.

UP-1. Make morphirup a small standalone coordinator

Approved meaning. Ada first gets morphirup, a Native AOT executable built in morphir-dotnet that needs no Morphir or .NET. It owns bootstrap, selection and lifecycle. A pure resolver produces a plan, and bounded adapters authenticate, download, extract, install extensions and activate. The manager contains no compiler or generator. It coordinates the existing tool and extension authorities and writes no new extension installer. NuGet and package managers keep ownership of what they installed. Interrupted self-update stages a new manager executable and replaces it only through a platform-qualified helper after the old executable exits.

Here. A new project (MGR-1) that does not reference Morphir.Tooling, because that project brings the generators and the compile pipeline. It can reference Morphir.Configuration and Morphir.Configuration.IO for Morphir home and discovery boundaries. The "existing extension authority" in .NET is the PRD step 3 installer, which does not exist yet. The tool authority needs an AOT-safe client for the tool release metadata profile, which also does not exist. Both are dependencies of group 4 (see questions).

UP-2. Plan, verify and activate one complete generation

Approved meaning. Planning can refresh metadata but never runs a downloaded artifact or changes the selection. Applying setup stages the whole candidate and runs readiness checks before activation. Public recipes are authenticated targets binding host and extension descriptors and artifact hashes. Immutable generations live under MORPHIR_HOME/toolchains/generations/<id>/ with user-default and project pointers. Hosts read a generation-scoped selection overlay and keep reading the global catalog. --yes authorizes the displayed setup operation in automation. It never means bypass signatures, ignore incompatibility, modify unrelated installations or install a system SDK. If the resolved plan changes before execution, the final receipt records the actual exact plan; an --expect-plan digest refuses a mismatch for approval-sensitive automation.

# Proposed interface. These commands do not exist yet.

morphirup setup --implementation dotnet --deployment native-aot --preset fsharp --channel stable --yes

Here. Activation publishes with the stage-then-move pattern of safe-tree-publication and serializes on an interprocess lock built the same way as TaskLock, under MORPHIR_HOME/locks. The overlay that the managed and AOT hosts read is a change to the extension selection code that PRD step 3 adds. Task 4.4 cannot finish before that code exists.

FS-1. Deliver F# as capabilities with a standalone process option

Approved meaning. With the AOT host, setup resolves the self-contained morphir-fsharp-frontend process guest, which carries FCS and its runtime and uses the existing Content-Length MEP transport. The default generator stays the built-in morphir.fsharp. A separate self-contained F# backend process guest, proposed morphir-fsharp-backend, reuses Morphir.CodeGeneration.FSharp and the existing MEP backend methods, with exact claims and no invented protocol members. Compilation means supported F# source to Morphir IR, not arbitrary .fsproj builds.

Here. Task 3.1 publishes a folder-layout self-contained archive from Morphir.Frontend.FSharp.Extension and first fixes how CompilerEdge picks references (FSF-1). Task 3.2 adds the pinned contract's generateModel records to Morphir.Mep, a backend guest project, and a host-side backend adapter with explicit selection (FSB-1).

LOCK-1. Keep requests, portable locks and local receipts distinct

Approved meaning. Ada commits the project request and portable lock. The request can say stable. The lock records the exact resolved host and providers per platform. Frozen restore refuses a platform absent from the lock. Request identity is SHA-256 of the request file's UTF-8 bytes. Selection order is CLI selector, MORPHIRUP_TOOLCHAIN, nearest project file within established discovery boundaries, then the user default. Existing [toolchain.<name>] sections in morphir.toml keep their meaning. Toolchains live in Morphir home, build outputs in the configured out root. The local receipt binds the SHA-256 of the exact lock bytes, the platform and every installed object identity. Generation ids are local opaque ids, not public release versions.

PATH-1. One proxy, explicit ownership and predictable dispatch

Approved meaning. The manager owns a bin folder with morphirup and an optional morphir proxy. It never renames the NuGet tool. An external tool install stays externally owned. On Windows the proxy is a real executable that spawns the selected absolute path with an argument vector and no shell, suppresses child windows and kills the owned process tree on cancellation. Persistent PATH edits need morphirup env --install.

Here. Process start code exists in MepFrontend.ConnectAsync and in the conformance cli adapter. Both use argument lists without a shell and set CreateNoWindow. Neither ties the child to a Windows job object for process-tree cleanup, so task 5.4 adds that. A selected dotnet-tool generation launches the installed tool's dotnet-morphir by absolute path. The E2E tests do something different: ExecutableLocator.GetToolPath finds the built apphost under src/Morphir.Tool/bin, not an installed tool, so dispatch to an installed tool needs its own test.

QUAL-1. Verify language readiness and runtime hosting separately

Approved meaning. Setup reports acquired, verified, capability-checked and workflow-qualified states. It never calls a toolchain ready because it extracted archives. A process probe runs with the user's rights. The fixed smoke workflow compiles known F# to known IR and known generated F#. A failed probe keeps the previous generation. WASM ABIs qualify separately. Broad platform qualification belongs in manual or release lanes, not a new pull request job per profile.

Here. The fixed F# package and expected outputs come from approved task 1.4 in finos/morphir. The shared runner is finos/morphir's morphir mck (Rust, crates/morphir-mck), driven with an explicit --adapter. This repository supplies the .NET adapter. src/Morphir.Conformance has cli, library and mep-guest adapters and a local runner for the F# frontend suite. No morphir mck adapter exists here yet. Which of these carries tasks 3.2 and 6.1, and how this relates to establish-morphir-compatibility-kit, is review question 5. Release qualification extends deployment.yml and the manual workflows, and keeps the pull request lane to the closure test, the AOT probes and focused unit tests.

Repository mapping

These notes choose how to carry out the approved decisions in this code. Each is reviewed in the task named. Some are repository-level choices beyond the approved text, listed in the proposal under "Repository-level choices for review".

COMP-1. Move the shared composition out of the executable project (task 2.1)

The managed morphir offerings need the F# composition and the assembly name morphir. src/Morphir already produces morphir.dll, and Morphir.Tool references it. A second executable named morphir that references it would put two morphir.dll files in one output. So the bodies of Program.CreateApp, Program.Run, the info command and the --version path move into the shared library Morphir.Tooling as MorphirApplication. FSharpFrontendScenario moves into a managed composition library, src/Morphir.Tooling.Managed (ManagedComposition), the only command-line project that references Morphir.Frontend.FSharp. Morphir.Program stays in src/Morphir with the same public signatures (Main, NativeComposition, Run, CreateApp) and delegates to MorphirApplication. A new JIT-only entry point, src/Morphir.Managed (assembly morphir), and Morphir.Tool reference the two libraries. Morphir.Tool no longer references src/Morphir. Each entry point keeps generating its own VersionInfo, and tests of the managed entry point live in their own project, because no output folder can hold both morphir.dll files. Task 2.1 implements this arrangement on its own branch (feat/managed-composition), reviewed as a separate pull request.

Alternative: one project with an MSBuild switch that adds the F# reference for managed builds. Rejected because the same project would have two dependency graphs, the closure test could not tell them apart, and a wrong property during publish would put FCS in the AOT output. The approved DEP-1 also asks to extend the reference arrangement rather than risk FCS in the AOT graph.

Cost: none to public API. Morphir.Program keeps its public surface, and Morphir.Tooling gains a public type. Only if this arrangement proved infeasible would the type have to move, which is a breaking change to the Morphir package and needs maintainer review under AGENTS.md section 2 first.

HOST-1. Add the deployment beside the host, not as a host case (task 2.3)

MorphirHost stays two cases with wire values morphir and dotnet-morphir. A new closed union for the offering (native-aot, self-contained, framework-dependent, dotnet-tool) joins HostIdentity. Its wire member is deployment, the name every approved document shape uses (--deployment, deployment = "native-aot"). Execution mode and platform join HostIdentity with it. Each entry point states its offering at compile time. A runtime check guards the value: for example, a build that claims native-aot but has dynamic code supported fails a test. HostAvailability becomes availability by offering, which ExtensionEntry.IsAvailableIn uses. The MorphirHost.Native comment changes, because that case also runs in the two managed morphir offerings. --version keeps printing only the version string, which HostVersionTests assert. The full identity report needs a separate form (see questions). F# code that C# calls follows the fsharp-csharp-interop skill.

Alternative: add cases NativeAot, SelfContained and FrameworkDependent to MorphirHost. Rejected because it changes what the top-level host string means, which the approved change forbids.

REL-1. Four named release profiles, legacy assets kept (tasks 2.2 and 2.5)

One Nuke target per offering and RID, with the publish settings in one table: Native AOT for src/Morphir; self-contained untrimmed and framework-dependent for the managed entry point; PackTool unchanged for Morphir.Tool. Archives follow the approved naming pattern. Morphir.Build.Tests checks that names and launch metadata are unique across release, offering and platform. scripts/publish-single-file*.cs go away or become thin wrappers over the targets, and the README files say which. PackPlatformTarballs and CreateGitHubRelease either take over the inline steps in deployment.yml or go away, so one code path builds release assets. The existing morphir-{rid}[.exe] and morphir-{rid}-v{version}.tar.gz assets of published releases stay as they are. Metadata for them states what they are: managed, trimmed, self-contained, single file, without the F# frontend.

FSF-1. A folder-layout self-contained frontend archive (task 3.1)

CompilerEdge reads compiler references from the trusted platform assemblies in the runtime folder. In a self-contained folder publish, the runtime folder is the application folder, so the list would also hold Morphir.*, Morphir.Mep and other application assemblies. Those would become references of the user's F# code and could change name resolution. In a single-file publish, Assembly.Location is empty for bundled assemblies, so FSharp.Core and the annotations reference would be empty paths. The first failing test therefore runs the published self-contained guest with no dotnet on PATH, no DOTNET_ROOT and no NuGet cache, compiles the fixed package, and compares IR and diagnostics with the framework-dependent tool. The fix selects framework references from an explicit list (the runtime's own framework assemblies) instead of "everything in the runtime folder". The archive is a folder, not a single file, until a single-file arrangement is qualified with extraction. FCS stays untrimmed.

FSB-1. The backend guest needs pinned wire types and a host adapter (task 3.2)

Three pieces, in order. First, add GenerateModelRequest, GenerateResult and Artifact to src/Morphir.Mep/Wire.fs from the pinned contract, with generated codecs, and extend ContractTests.fs to cover them. This invents no member, because the pinned contract defines them. Second, a guest project beside the frontend guest, executable morphir-fsharp-backend, calling Transpiler.generateModelWith and returning artifacts with relative paths, with its own version line. Third, a host-side MEP backend adapter in Morphir.Tooling that checks artifacts and publishes them through GenerationPublisher, with an explicit selection that never replaces morphir.fsharp as the default. The extension-model PRD step 4 ("Generator first") plans the same capability, so this task should record that it delivers that step's generator part for F#.

MGR-1. A separate Native AOT manager project (group 4)

A new executable project for morphirup and a test project beside it. Pure modules (plan, resolution, lock reading, selection precedence) carry most tests without I/O. Adapters (download, verify, extract, install through the .NET extension installer, activate) sit behind interfaces with fixture implementations. Archive extraction follows the rules already written in the PRD's extension package archive section: no absolute paths, no .., no links, size and ratio limits, digest checks before the store. The project gets its own AOT probe in the pull request lane, like Morphir.Mep.AotProbe, because its whole point is to run without .NET.

Migration plan

  1. Tasks 2.1 to 2.4 and 3.1 land first, in any order; 2.5, the shared-runner check of 3.2 and 3.3 follow their group 1 tasks. Existing commands, the Morphir.Tool package id, the dotnet-morphir command and the frontend tool keep working throughout.
  2. The first release with named profiles publishes the new archives beside the legacy asset names. The proto plugin and install scripts keep working until they move to the new names.
  3. Group 4 starts when the shared contracts from finos/morphir group 1, PRD step 3 and the tool metadata client are available. Then group 5, then group 6.
  4. Rollback: every group adds new entry points or targets beside existing ones. Reverting a group's commits restores the earlier release shape. Published artifacts are never rewritten.

Questions for review

These questions change the order or content of tasks, so they need answers before the named task starts. The approved change does not settle them.

  1. Legacy release names (task 2.2, 2.5). Future releases can keep publishing morphir-{rid}[.exe] and morphir-{rid}-v{version}.tar.gz for the proto plugin and install scripts. Which offering's bytes should those names carry from then on, or should they stop with an announced migration?
  2. Extension installation (tasks 3.3, 3.4, group 4). The approved plan reuses the host's extension store, claims and locks. In .NET they are the planned PRD step 3, not code. Should step 3 land as its own change first, or does this change take it on?
  3. Identity report form (task 2.3). --version prints one line that tests assert. Where should the full identity (implementation, release, offering, platform, execution mode) appear, for example a JSON form of --version or of info?
  4. External backend selection (task 3.2). The compile command selects an external frontend with --extension and [frontend.<language>].extension. Should generate follow the same pattern, and what extension id does the backend guest take (the frontend uses org.finos.morphir.fsharp-frontend)?
  5. Shared runner and adapters (tasks 3.2, 6.1). The shared runner is finos/morphir's morphir mck, driven with an explicit --adapter, and this repository supplies the .NET adapter, which does not exist yet. src/Morphir.Conformance has its own cli, library and mep-guest adapters and a local runner, and establish-morphir-compatibility-kit plans more. Which of these carries tasks 3.2 and 6.1, and does the .NET adapter belong to that change or to this one?
  6. Public registry id morphir-dotnet.fsharp (task 2.3). The registry delta makes the in-process F# frontend a built-in entry with the id morphir-dotnet.fsharp, the frontend identity that the compile report shows today. The approved change does not ask for frontend entries or name this id. Should it become a public registry id, and under that name?
    7. Should the frontend guest keep the repository release version, or move to an independent version as the backend guest does?

Open questions

  • Exact names of the projects that later tasks add (the backend guest, the manager). Task 2.1 settled its own names on its branch. Each task settles them in review without changing the specs.
  • Signing-key custody, endpoint names and size targets, which the approved design leaves to release preparation.
  • Whether the manual AOT workflow or the release workflow carries the published-files FCS check. Either satisfies QUAL-1.
