Context

See proposal.md for the motivation. The requirements are in mep-protocol, model-analyzers and extension-registry.

  • There is no MEP code in the repository. The add-fsharp-compile change plans src/Morphir.Mep in its group 7 (DTOs, framing, envelopes), group 8 (the guest) and group 9 (the host client). None of it is written. Its branch feat/fsharp-compile has done groups 1.1 to 1.3 (fixtures and the conformance seed).
  • The pinned upstream contract is on main in tests/Fixtures/Mep/, from finos/morphir@cde7722eb: mep.ir.json (56 types), three Smithy transcripts and model-transport.cases.json.
  • The JSON-RPC spike decided our own layer on System.Text.Json and listed the tests to keep.
  • The registry domain is F# (src/Morphir.Extensions), with parsed types and closed unions. The CLI edge is C# (src/Morphir.Tooling). The fsharp-csharp-interop skill has the rules for the boundary.
  • TypeValidator (src/Morphir.IR.Pipeline.Plugins/TypeValidator.fs) checks a classic package and reports VMessage values with the rule id type-mismatch. No CLI command runs it now.
  • morphir generate reads a model through GenerationModelLoader, with bounded capture and the classic and V4 readers. Its exit codes are 0, 1, 2 and 130.

Goals and non-goals

Goals:

  • One MEP implementation that the F# frontend guest, the host client, the WASM host (step 2a) and the .NET guest SDK (step 2b) all use.
  • A complete session over an in-memory transport, tested against the pinned transcripts, with zero AOT warnings.
  • A user-visible result: morphir validate with the built-in type validator.
  • An upstream draft for the validate payload, so step 2 has a contract to pin.

Non-goals:

  • Starting a guest process, the stderr pump and process-tree cleanup. add-fsharp-compile task 9.1 and step 2b add them on top of the stream transport.
  • The WASM runtime (step 2a), external analyzers, and the compileModel and generateModel request types (they stay in add-fsharp-compile and step 4).
  • Validator request types on the wire. They wait for the upstream contract (UP-1).
  • Registering the transform plugins (Optimizer, ExactScalarFolding) or PrettyPrinter. No command runs them.
  • An MCK suite. The compatibility kit runner is not ready (#505). This change keeps its cases as data-driven tests that can move into the kit.

Decisions

MEP-1. One MEP layer, owned by this change

This change builds the shared part of Morphir.Mep: the JSON-RPC layer, the session lifecycle, model-transport negotiation, envelope admission and Diagnostic. The add-fsharp-compile plan then adds only what is special to frontends: the compileModel types, the context digest, the frontend guest and the process host client. The pull request for this plan also edits that plan's group 7 to say so.

Alternative considered: let add-fsharp-compile build Morphir.Mep first and step 1 add to it. Rejected: the F# frontend path is large (53 tasks) and its MEP groups come last, so step 2 would wait for groups 1 to 6. The shared core has no frontend dependency.

MEP-2. F# with generated JSON converters

Morphir.Mep is F#, as the add-fsharp-compile design (its project table) and the "F# for the domain" decision say. System.Text.Json source generation does not run on F# code. So the JSON converters and the MepJson context come from the Myriad JSON generator of add-myriad-json-codecs, which this change depends on.

  • The MEP types are F# records and unions with attributes. Most use the project defaults: camel-case members, skippable option fields (absent, never null), and string tags for fieldless unions such as ExtensionType ("validator") and DiagnosticSeverity.
  • Parsed values (protocol versions, extension ids, SHA-256 digests) use JsonParsedValue, so a reader never builds an invalid value (parse, don't validate).
  • RequestId and the untyped json value use Untagged with SelectByTokenKind; integers keep their exact range.
  • Unknown members follow the contract: ignored where the contract allows extension, refused where it does not.
  • Hand-written code is left only where no encoding fits: the classification of a JSON-RPC message by its members (RPC-1). Raw params stay a JsonElement until a method binds them through its type info.

Alternatives considered: hand-written codecs for each type (the first version of this plan; rejected by the product owner: slow to write and easy to get wrong for 56 types); a C# DTO project with a JsonSerializerContext (rejected: a second layer of nullable DTOs, no unions); F# with reflection serialization (rejected: not AOT-safe).

MEP-3. Types written against the pinned contract, then checked

The 2026-11-08 implementation check found that the published F# generator stops at Morphir.SDK.Dict.Dict, producing no artifacts. The published Myriad JSON generator also lacks missing-field defaults, empty-collection omission, flattened extension data and claims-version migration. The maintainer approved extending generated-code support first. New annotations opt into these behaviors; existing contexts retain their encodings. Protocol version values and member/path names live in annotated input, not in the generator. The approved API follow-up uses ordinary scalar literals, empty-collection defaults, and typed static provider calls for decimals and domain values. Raw JSON has an explicit annotation. Providers run only during deserialization for absent members; generated calls are compiler-checked and preserve null, canonical-version and critical-path rules. Constructor-based model support remains deferred. The prerequisite lands separately and is verified under Native AOT before the MEP types use it.

The PRD asks to generate the MEP types from mep.ir.json if the generators can. Task 2.1 runs the Morphir F# generator on the pinned contract and records the result in the PRD. That generator makes F# types, but not the attributes that the wire rules need. So the plan is to write the annotated types by hand and add a contract test: for each implemented type, read its constructor from mep.ir.json, map the kebab-case field names to wire names, and check that the generated converter writes and requires the same members. The test fails when the pin changes and the code does not. A later change can teach the Morphir F# generator to emit the attributes.

RPC-1. Four layers, one dispatcher

LayerShapeUsed by
Message codecJsonRpcMessage = Request | Notification | Response | ErrorResponse; read from bytes, write to bytes. Params stay raw (JsonElement) until a method binds them.all
DispatcherDispatchAsync(message bytes, ct) : ValueTask<byte[] option>. A method table maps method names to typed handlers through their codecs.stdio guest, WASM guest (later), tests
FramerContent-Length read and write on a Stream, with the header limit 8192 bytes and the body limit 64 MiB (from frame.rs in finos/morphir-rust).process host and guest
ConnectionReads frames, calls the dispatcher for inbound requests, and matches inbound responses to a pending-request table for outbound requests. Handles $/cancelRequest both ways.process host and guest

The stdio connection reads a frame, calls DispatchAsync and writes the reply. A single-message caller calls DispatchAsync directly. So both paths give the same bytes (spec: "One dispatch path serves streams and single messages"). A params object binds as one value through its codec; the layer never unwraps a one-member object (the CurlyRpc defect from the spike).

RPC-2. Request ids and error replies

[<RequireQualifiedAccess>]
type RequestId =
    | Number of uint64      // read with Utf8JsonReader.TryGetUInt64
    | Text of string
  • A reply writes the id from the parsed value, so 18446744073709551615 stays exact. A negative number, a fraction or a number over the u64 range gets -32600.
  • Bad JSON gets -32700 with "id": null. A bad message keeps the connection open. A bad frame closes it, because the reader cannot find the next frame boundary.
  • Error codes are a closed union with the contract's error-code values (-32700, -32600, -32601, -32602, -32603, -32800, -32011, -32013, -32014 and the others in the pin). No local code is added.

SES-1. One pure session state machine

Hosts and guests share one lifecycle, as add-fsharp-compile MEP-2 planned:

type SessionState =
    | Created                                   // describe and initialize only
    | Initialized of NegotiatedSession          // protocol version, peer info, capabilities, tuples
    | ShutDown                                  // exit only
    | Exited

val step : SessionState -> Inbound -> SessionState * Outbound list

The guest view uses step to decide the reply (-32014, -32011, -32013). The host view uses the same rules to refuse a request before it sends it. The methods are those of the pinned method type that the lifecycle needs: morphir.extension.describe, morphir.initialize, morphir.initialized, morphir.ping, morphir.extension.info, morphir.extension.capabilities, morphir.shutdown, morphir.exit, $/cancelRequest and progress. Task 3.1 takes the exact wire strings from the pin.

The lifecycle tests replay lifecycle-violations.md, protocol-errors.md and the session part of session-model-transport.md. The transcripts are reviewed inputs. Where a transcript and the contract text disagree, the test follows the contract and the deviation goes into conformance/deviations.md with an upstream issue.

SES-2. Transports, not processes

This change has two transports: a framed Stream pair, and single-message dispatch. Tests connect a host session and a test guest through in-memory pipes. Starting a child process (no shell, deadlines, the stderr pump, process-tree cleanup) is a thin edge on the stream transport, and add-fsharp-compile 9.1 and step 2b add it. The host session API takes a transport, so that edge needs no change to the core.

MT-1. Envelope admission is one ordered pure function

admit : NegotiatedTuple -> Limits -> MorphirModel -> Result<AdmittedModel, AdmissionFailure> runs the checks in the spec order and stops at the first failure. AdmittedModel holds the verified UTF-8 IR bytes, and only it can reach an IR reader. The function does not decode the IR into Morphir types; the caller passes the bytes to the existing classic or V4 reader. Every case in the pinned model-transport.cases.json is a test. The limit defaults come from the contract; a negotiated limit is the smaller of the two peers' values.

ANA-1. The analyzer contract

The contract lives in Morphir.Extensions, beside the registry, because each analyzer is a registered extension:

type AnalyzerDiagnostic =
    { Extension: ExtensionId
      Diagnostic: Morphir.Mep.Diagnostic }      // severity, code, message, location, related, data

type IModelAnalyzer =
    abstract Entry: ExtensionEntry              // identity and the validator claim
    abstract AnalyzeAsync: model: DistributionModel * ct: CancellationToken
                           -> Task<IReadOnlyList<AnalyzerDiagnostic>>
  • The diagnostic is the MEP type, not a copy. So an external analyzer in step 2 returns the same type, and the merge needs no mapping.
  • The runner (in F#) selects the analyzers whose claim covers the model's family and version and that configuration does not turn off. It runs them one at a time, in id order, and catches an exception per analyzer as a "failed" outcome. Parallel runs can come later; the order of the result does not depend on them.
  • Location: an IR analyzer often has no source position. A VMessage with a path and a position maps to a MEP location (the path as a file: URI, the position made zero-based). Without them, the location is absent, and the IR node name stays in the message. The data member is not used in this change.

Alternative considered: put the contract in Morphir.IR.Pipeline as a plugin kind. Rejected: pipeline plugins change a VFile tree; analyzers must not change anything, and they must share a type with external analyzers.

ANA-2. Built-in analyzers in their own project

A new F# project, src/Morphir.Analyzers, holds the built-in analyzers and their entries. It references Morphir.Extensions and Morphir.IR.Pipeline.Plugins. The type-validator analyzer calls TypeValidator on the classic package and maps each VMessage (severity, rule id as the code, message, location). The project follows interop rule 1 (nullness, warnings as errors, trim and AOT). Morphir.IR.Pipeline.Plugins does not change, so it does not need the nullness work that Morphir.Models needed.

Alternatives considered: put the adapter in Morphir.IR.Pipeline.Plugins (it would then depend on the registry and need nullness turned on), or in Morphir.Extensions (the registry domain would depend on the pipeline).

CLI-1. morphir validate

morphir validate --input <file-or-directory> [--input-format auto|json|ion] [--json]
  • A C# slice Features/Validate in Morphir.Tooling, registered by a scenario in both hosts. It reuses GenerationModelLoader and its limits; the loader moves to a shared place if its name or namespace ties it to generation.
  • Configuration: the command resolves the layered configuration of the invocation directory with the existing resolver, and reads only extensions."<id>".enabled. Unlike generate, it needs configuration, because the user turns analyzers off there.
  • Output: a TUI table through TerminalTable (columns: severity, code, location, message, extension), then a summary line with the counts. Plain mode when stdout is redirected, as in extension list. --json writes one report from a source-generated C# context in Morphir.Tooling. Logs go to stderr.
  • Exit codes follow generate: 0, 1 (an error diagnostic), 2 (invocation, input or analyzer failure), 130.
  • The name validate is the upstream Rust CLI's reserved command. It is different from morphir ir verify, which checks the JSON schema. The documentation says when to use each.

REG-1. Registry entries for analyzers and the MEP mapping

  • ExtensionCapability gets a Validator of ValidatorClaim case. ValidatorClaim holds a non-empty set of IR format versions (Versioning.FormatVersion, never an integer). The validator type comes from the claim, as the step 0 rule requires.
  • The built-in sources become one list: backends (existing) and analyzers (from Morphir.Analyzers).
  • ExtensionEntry.ToMep() returns a Morphir.Mep.ExtensionInfo. The claims mapping writes only the contract's claim kinds, so a validator claim stays out of MEP until UP-1 lands.
  • extension list shows the validator entry. Its text table gets no new column; the capability summary column shows validator (1, 2, 3).

UP-1. The upstream validate payload proposal

MEP 0.2.0-draft.1 has the validator type, the validate method name and the ValidationError code, but no request, result or capability for it. The proposal follows the model tier, as compileModel and generateModel do:

  • a model operation morphir.validator.validateModel, negotiated with the same tuples and limits;
  • ValidateModelRequest: one MorphirModel envelope and optional options (JSON);
  • ValidateModelResult: diagnostics (a list of Diagnostic). There is no success flag: the host decides from the severities, and a failure to run is a JSON-RPC error;
  • a validator capability claim with the supported tuples, in the claim set;
  • the legacy morphir.validator.validate stays reserved and is not defined by this proposal.
{"jsonrpc": "2.0", "id": 7, "method": "morphir.validator.validateModel",
 "params": {"model": {"envelopeVersion": "0.1.0-draft.1", "irVersion": "4.0.0", "...": "..."}}}

{"jsonrpc": "2.0", "id": 7, "result": {"diagnostics": [
  {"severity": "warning", "code": "naming.module", "message": "...", "related": []}]}}

The proposal is a pull request against spec/mep in finos/morphir (Smithy model, generated mep.ir.json, a transcript and model-transport cases). The text is written in this repository first (task 7.1) and opened upstream only after the maintainer approves it. Steps 2a and 2b pin the draft by commit.

Risks and trade-offs

The pull request for this plan edits that plan's group 7 on main. The branch has not started group 7.

Migration plan

Additive. A new command, a new registry entry and new projects. No setting, file format or existing output changes, except that extension list shows one more entry. Rollback is a revert.

Open questions

  • The exact text of the second-initialize refusal. The pinned transcripts do not show it; the test checks only that it fails and that the session stays initialized.
  • Whether upstream wants the validate payload in 0.2.0-draft.1 (edited in place) or in the next draft. This decides only the version string that step 2 pins.
