# MCK step vocabulary 1.2: the wasm-host suite

> The runner reads the `wasm-host` suite with [version 1.3](steps-1.3.md) since the pin moved to finos/morphir `48d10706f`. This page keeps the meaning of version 1.2 unchanged.

Version 1.2 adds the `wasm-host` suite to [vocabulary 1.1](steps-1.md). It
changes nothing in version 1.1 or in the F# frontend suite: the frontend suite
keeps its steps and is read with version 1.1, and the steps below are valid only
in features under `suites/wasm-host/`. The kit version is still `0.1.0-draft.1`.

The `wasm-host` suite holds the crafted cases of the WASM host qualification kit
(`morphir/mep-wasm-host-kit` `0.1.0-draft.1`). The features are generated from
the corpus pinned in `tests/Fixtures/MepWasm/wasm-host.cases.json` by
`dotnet fsi scripts/generate-wasm-host-cases.fsx`, and are never edited by hand
(see [Generated features](#generated-features)). The vocabulary below is closed:
`Morphir.Conformance.WasmHost.FeatureReader` refuses any other step, tag or
description line, naming the file and line.

## Files and ids

- One feature for each group of upstream case ids, the part before the first
  `/`: `classification.feature`, `bounds.feature` and so on.
- `case-ids.json` assigns each upstream case id its number. A scenario is named
  `wasm-host-NNNN <upstream case id>`, for example
  `wasm-host-0001 classification/unknown-namespace`.
- A number never changes and is never reused. A case added to the corpus takes
  the number after the highest one in the map, retired numbers included, and no
  existing number moves. A case removed from the corpus loses its scenario and
  keeps its number in the map with `"retired": true`. A case that comes back
  gets its own number again.

The id map:

```json
{
  "suite": "wasm-host",
  "corpus": {
    "path": "tests/Fixtures/MepWasm/wasm-host.cases.json",
    "commit": "<finos/morphir commit of the pin>",
    "sha256": "<SHA-256 of the corpus>"
  },
  "cases": [
    { "id": "wasm-host-0001", "caseId": "classification/unknown-namespace" },
    { "id": "wasm-host-0057", "caseId": "bounds/removed-upstream", "retired": true }
  ]
}
```

## Feature layout

```gherkin
# Generated from the pinned WASM host corpus. Do not edit this file by hand.
# Change the corpus in finos/morphir, move the pin, then run: dotnet fsi scripts/generate-wasm-host-cases.fsx
# Corpus: tests/Fixtures/MepWasm/wasm-host.cases.json
# Commit: 7b049c223d2fc7309eec5ac81976f9cae845b522
# SHA-256: 67efed87fcb8aeed0524becb4b092d5090b4abceed4fa36fc5c39cd013e72232
@suite:wasm-host
Feature: WASM host cases: classification
  Kit: "morphir/mep-wasm-host-kit" "0.1.0-draft.1"
  Contract: "morphir/mep-wasm-execution-profiles" "0.1.0-draft.1" "spec/mep/wasm-execution-profiles.json"
  Deadline margin: 2 seconds

  @requires:profile:extism-kernel-v1
  Scenario: wasm-host-0001 classification/unknown-namespace
    Requirement: "Classification before instantiation"
    Spec scenario: "Import from an unknown namespace"
    Contract element: "refusal:extension.abi_unsupported"
    Gap: "The contract does not say how a runner observes that the module was not instantiated; exit status 3 with no started event is the observable part."

    Given the module "env-open-socket" assembled from "fixtures/wasm/env-open-socket.wat" as "fixtures/wasm/env-open-socket.wasm" with SHA-256 "bebbfeda31c2703c2022bf4ba27206fc0fcf22a540dda195476569c973e7addd"
    And the worker is given the ABI "extism-kernel-v1"
    When a new worker is started
    And the worker is sent the frame "initialize":
      """json
      {"jsonrpc":"2.0","id":1,"method":"morphir.initialize","params":{"protocolVersion":"0.2.0-draft.1"}}
      """
    Then the worker exits with status 3
    And stdout has 0 bytes
    And stderr has an event "refused" with code "extension.abi_unsupported" whose message includes "env.open_socket"
    And stderr has none of the events "started", "fault"
```

- The header comments name the pin: the corpus path, the finos/morphir commit
  and the SHA-256 of the corpus bytes.
- The feature has the one tag `@suite:wasm-host`, and its description names the
  kit, the contract (id, version and path in finos/morphir) and the corpus's
  deadline margin.
- Scenarios sit directly under the feature: no Background, Rule or Examples.

Every quoted value in a step, a description line or the feature description is
a JSON string literal, so any text can be written: `"a \"quoted\" word"`. A
list is one or more JSON strings separated by `, `. `<n>` is a decimal integer
without leading zeros. `<s>` is a non-negative decimal number of seconds, such
as `30` or `0.5`. `<json>` is compact JSON text to the end of the line. Ordinals
(`frame 1`, `sent frame 2`) count from 1. The Given/When/Then/And keywords are
Gherkin syntax, not part of the step text.

## Tags

| Tag | Meaning |
| --- | --- |
| `@requires:profile:<profile>` | Exactly one on every scenario: the case's `appliesTo`. The case applies to a host that declares the profile, and is recorded as `not_applicable` for any other. Every host runs `extism-kernel-v1`, so its cases apply to every host. |
| `@requires:runs:<profile>`, `@requires:does-not-run:<profile>` | The scenario is the alternative for a host that declares (does not declare) that it runs the profile: `when: {hostRuns, runs}`. |
| `@requires:enforced:<bound>`, `@requires:not-enforced:<bound>` | The scenario is the alternative for a host whose `started` event declares the bound enforced (not enforced): `when: {bound, enforced}`. |
| `@bound:<bound>` | A bound the case exercises (`bounds`). When the host declares it not enforced, the case is recorded as `not_enforced`. |

Profiles are `extism-kernel-v1` and `morphir-bytes-v1`. Bounds are
`memoryCeiling`, `instructionBudget` and `callDeadline`.

A run with alternatives becomes one scenario for each alternative, in corpus
order, all with the same name. Each has one alternative tag, and the scenarios
differ only in that tag and in the run's matchers. Version 1.2 writes
alternatives only for a case with one run; the corpus reader refuses a case with
alternatives in a case of several runs, so that a newer corpus fails loudly.

## Description lines

Each line of a scenario's description is one of these, in this order:

| Line | Corpus member |
| --- | --- |
| `Requirement: "<text>"` | `tests.requirements`, one line each |
| `Spec scenario: "<text>"` | `tests.scenarios`, one line each |
| `Contract element: "<text>"` | `tests.contract`, one line each |
| `Gap: "<text>"` | `gaps`, one line each |

## Steps

Set-up steps come first, then one or more runs. A run is a new worker process.
It starts with `a new worker is started`, then the frames it is sent, then its
matchers.

| Step text | Corpus member and meaning |
| --- | --- |
| `the module "<name>" assembled from "<wat>" as "<wasm>" with SHA-256 "<sha256>"` | `module`, with its row of `modules`: the paths are relative to the corpus file, and the digest is the one the runner checks before the case runs. Exactly one, first. |
| `the worker is given the ABI "<profile>"` | `declaredAbi`: the worker is started with `--abi <profile>`. Absent when the case gives no ABI. |
| `the worker is started without the argument "<argument>"` | `worker.omit`, one step for each argument, in order. |
| `the worker limits requests to <n> bytes` | `worker.requestBytes`: `--request-bytes <n>`. `1 byte` for one. |
| `the worker limits responses to <n> bytes` | `worker.responseBytes`: `--response-bytes <n>`. |
| `the worker is given another build identity` | `worker.buildIdentity: "other"`: the host's identity with its last hexadecimal digit changed. |
| `a new worker is started` | Starts a run (`runs[i]`). |
| `the worker is sent the frame "<name>":` | One frame of `runs[i].frames`, in order, with a `json` docstring that holds the frame's body exactly: the compact JSON of the frame's value with its members in the order written. |
| `the worker exits with status <n>` | `exitCode`. |
| `stdout has <n> bytes` | `stdoutBytes`: the byte count of all of stdout. |
| `stdout has exactly <n> frames` | `stdoutFrames`: stdout has these frames and no other. `1 frame` for one, `0 frames` for none. Followed by the matchers of frames 1 to n, in order. |
| `stdout frame <k> equals <json>` | A frame matcher with `json`: the body parses to a JSON value equal to this one. |
| `stdout frame <k> equals sent frame <j>` | A frame matcher with `sameAsFrame`: equal to the body of the run's frame j (the corpus counts from 0, the step from 1). |
| `stdout frame <k> has "<pointer>" equal to <json>` | One `pointers` entry with `equals`. Several steps for one frame are its entries, in order. |
| `stdout frame <k> has "<pointer>" of type "<type>"` | One `pointers` entry with `type`: `null`, `boolean`, `number`, `string`, `array` or `object`. |
| `stderr has an event "started"` [` with ABI "<profile>"`] | An `events` matcher for `started`, with its `abi`. |
| `stderr has an event "refused"` [` with code "<code>"`] [` whose message includes <list>`] | An `events` matcher for `refused`, with its `code` and `messageIncludes`. |
| `stderr has an event "fault"` [` of kind "<kind>"`] | An `events` matcher for `fault`, with its `kind`: `failure`, `trap`, `memory-limit`, `budget-exhausted` or `call-deadline`. |
| `stderr has an event "output"` | An `events` matcher for `output`. |
| `stderr has none of the events <list>` | `noEvents`. |
| `the guest output includes in order <list>` | `guestOutput`: the strings occur in this order in the text of the output events. |
| `the guest output includes <list>` | `guestOutputIncludes`: each string occurs, in any order. |
| `the guest output includes none of <list>` | `noGuestOutput`. |
| `the time to the first fault is between <s> and <s> seconds` | `withinSeconds` with `until: fault`. |
| `the time to exit is between <s> and <s> seconds` | `withinSeconds` with `until: exit`. |

The event steps of a run are its `events` list, in order: the events must appear
in that order, possibly among others. The corpus's `conventions` give the
meaning of each matcher; the reader of the pinned JSON refuses a corpus with a
convention, member or matcher it does not know, naming it.

## Generated features

While finos/morphir publishes the corpus as JSON, the pinned JSON is the
hand-reviewed source and the features are generated from it. Three guards keep
them the same:

- `FeatureReader.parse` refuses a feature that is not exactly what the
  generator writes for the cases it holds (`mck.not_generated`, with the first
  line that differs).
- `FeatureReader.read` and the stale check (`Generation.check`,
  `dotnet fsi scripts/generate-wasm-host-cases.fsx --check`) generate the suite
  again from the pin and the committed id map, and refuse every file that
  differs (`mck.stale_suite`), naming the file, the first line that differs and
  each case whose scenarios differ. An expectation edited by hand is therefore
  refused until the upstream corpus holds it.
- `Morphir.Conformance.Tests` reads the pinned JSON and the features into the
  case model and requires them equal for every case.

When the kit itself moves to Gherkin, the features become the source and the
generator is retired.
